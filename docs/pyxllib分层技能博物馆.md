## 核心目标

用本技能帮助 Codex 在写代码前先判断代码归属，在写代码后检查分层边界。重点不是泛泛优化代码，而是避免 AI 把机制、工具、功能、业务编排混在一起，导致项目后期难维护。

四层模型：

```text
pyxllib
├─ 编程层：语言增强、运行时补丁、底层抽象、兼容封装
└─ 工具层：跨项目通用工具，如文件、日志、路径、序列化、缓存

业务项目
├─ 功能层：项目内通用能力，封装业务相关的底层能力和执行机制
└─ 业务层：面向用户维护的接口、脚本、页面、CLI、工作流、任务清单、行为编排
```

依赖方向必须保持：

```text
业务层 -> 功能层 -> pyxllib 工具层 -> pyxllib 编程层
```

低层不得反向依赖高层。`pyxllib` 不得知道具体业务项目。

## 工作流程

1. 先读现有目录、模块命名、导入关系和用户给出的业务语境。
2. 判断本次需求主要触及哪一层：编程层、工具层、功能层、业务层。
3. 如果涉及新的框架思路、核心 API、扩展机制、行为树/流程编排、目录边界，先给用户方案和取舍，不要直接闷头实现。
4. 实现时保持代码放在最高合适层；只有证明可跨场景复用时才下沉到更底层。
5. 写完后检查是否有混层、倒依赖、业务参数泄漏、配置化滥用、万能工具类、过早抽象。

## 层级判断

### 编程层

放在 `pyxllib`。用于补足 Python 语言、运行时、兼容性或底层表达能力。

适合放入编程层：

- monkey patch、inject、运行时增强
- 语言兼容封装
- 通用装饰器、上下文机制、反射/动态调用底层能力
- 类似“把 Python 难表达但 JS 等语言容易表达的能力封装成自然接口”的代码

不适合放入编程层：

- 具体业务名词
- 项目路径、账号、任务名、页面名
- 为单个业务需求定制的底层机制

### 工具层

放在 `pyxllib`。用于跨项目通用的 utils 能力，不能绑定具体业务。

适合放入工具层：

- 文件、路径、日志、时间、缓存、序列化、配置、重试
- 通用数据结构和小型辅助函数
- 多个业务项目都可能复用的稳定工具

不适合放入工具层：

- 只在当前业务项目出现的领域概念
- 需要理解业务流程才能正确使用的函数
- “看起来通用”但其实只有一个场景会用的抽象

### 功能层

放在业务项目中，常见位置是 `infra`、`core`、`common`、`services` 等项目内通用模块。它可以接触业务领域，但不应是最终用户频繁编辑的入口。

适合放入功能层：

- 项目内复用的执行机制
- 行为树构建、调度节点、状态同步、账号切换、OCR/点击封装
- 业务能力的可组合封装
- 用户不应该反复理解的底层流程和失败恢复机制

不适合放入功能层：

- 用户经常要启停、排序、调参的任务清单
- 一次运行的账号选择、时间窗口、工作流组合
- 最终使用场景的“剧本”

### 业务层

放在业务项目中，通常是 `tools`、脚本、CLI、页面、用户入口或可编辑工作流。业务层不是只能剩一个 `run()`；它应该暴露用户需要维护的业务表达。

业务层要薄的是机制复杂度，不是业务表达量。它可以保留几十行甚至上百行，只要这些代码在表达用户关心的编排，而不是堆底层实现。

适合放入业务层：

- 本次运行账号
- 任务清单、启停策略、排序
- 时间窗口、运行参数、debug 开关
- 行为树装配、业务剧本、工作流组合
- 用户经常需要查看、调整、注释、增删的业务规则

不适合放入业务层：

- OCR 细节、点击重试、等待机制
- 行为树 runner 内部
- 状态文件读写和同步细节
- 通用调度器、窗口识别算法、异常恢复机制

业务层判断原则：

> 业务层应该像可编辑剧本，不是只有播放按钮，也不是把底层引擎源码摊给用户。

## 正例参考

`C:\home\chenkunze\slns\xlproject\src\xlsln\ckz2025\fx\tools\凡修手游.py` 是一个业务层正例：它不仅是启动入口，还开放了用户需要维护的行为编排。

在这个例子中：

- `pyxllib` 提供行为树基础设施，如 `Root`、`Action`、`Daily`、`Every`、`Window`、`BTreeRunner`。
- 业务项目功能层提供 `凡修助手`、任务配置对象、`build_tree`、账号任务节点、任务执行上下文、状态同步。
- 业务层 `凡修手游.py` 声明账号、运行期守护、动态时间任务、每日世界任务，并启动默认行为树。

维护原则：

- 用户调整任务、时间、账号、启停策略时，应主要改业务层。
- 用户不应为了改任务清单而钻进功能层的调度和状态同步实现。
- 如果业务层只剩一个启动入口，导致用户每次都要改功能层，那是把可维护面藏错了。

## 框架设计协商

当需求会影响长期分层或扩展方式时，先和用户确认方案。尤其是：

- 新建框架、引擎、pipeline、插件系统、规则系统
- 设计核心业务 API 或长期使用的入口
- 决定扩展机制：配置、函数、回调、策略对象、继承、注册器
- 引入新的目录结构、模块边界、跨项目沉淀规则
- 把一次性逻辑抽象成通用框架
- 用户反馈“不优雅”“不好维护”“屎山”“业务层不好改”

输出方案时至少说明：

- 推荐方案
- 不推荐方案
- 未来加需求时分别要改哪里
- 哪些点需要用户拍板

核心问题：

> 未来变化发生在哪里？当前设计会让变化更容易，还是把变化锁死在框架里？

## 配置化判断

配置适合表达稳定、有限、可枚举的数据；函数、回调、策略对象适合表达开放、不可穷举的行为。

当新增需求总是要求修改配置 schema、增加字符串枚举、解释嵌套 dict、发明表达式语法时，说明系统可能把开放行为错误建模成了配置数据。

优先考虑：

- callable 参数
- hook / callback
- strategy object
- protocol / interface
- pipeline step
- dependency injection

如果用户明明会写 Python，却被迫学习一套自制配置语法，通常是设计失败。需要配置文件、UI、可序列化、可复现时，可以额外提供配置入口，但不要让配置成为唯一扩展机制。

## 下沉与上移

按变化频率和复用范围决定代码迁移：

- 业务层逻辑开始重复：下沉到功能层。
- 功能层代码脱离当前业务项目，多个项目都能复用：考虑上移到 `pyxllib` 工具层。
- 工具层为了表达某类能力写出大量绕路代码：考虑是否需要沉到编程层，提供更基础的表达能力。
- 代码只服务一个具体用户场景：不要过早上移。

不要为了“看起来通用”把代码提前塞进 `pyxllib`。`pyxllib` 应该沉淀稳定、跨项目、低业务耦合的能力。

## 审查清单

实现或审查后检查：

- 新代码放在正确仓库和正确层了吗？
- 依赖方向是否仍是业务层到功能层到 `pyxllib`？
- `pyxllib` 是否引入了业务项目名、账号、路径、页面、任务？
- 业务层是否保留了用户需要编辑的任务清单、时间窗口、账号、编排？
- 业务层是否混入了 OCR、点击、等待、状态同步等机制细节？
- 功能层是否暴露太多底层参数，导致业务层用户必须理解内部实现？
- 是否把开放行为做成僵硬配置，而不是 callable、hook、strategy？
- 是否出现了万能 `utils.py`、万能 manager、过早基类、过度注册器？
- 新增需求下一次变化时，预计改业务层、功能层还是 `pyxllib`？这个位置合理吗？

## 原输出要求

回答用户时优先给出明确归属判断：

```text
归属：业务项目 / 功能层
理由：该代码包含项目内通用执行机制，但不是跨项目工具，也不是用户直接维护的编排。
边界：业务层只保留任务清单和运行参数；调度、状态同步、失败恢复放在功能层。
```

如果是实现任务，先按分层完成代码，再简要说明改动落在哪些层。若涉及框架级选择，先给方案并等待用户确认，除非用户已经明确要求直接实现。
