# 凡修统一榜单生命周期系统设计

## 1. 背景与目标

当前玩法榜、资源榜的采集、活动执行和结束收尾分散在活动专属 Job、页面 GET 物化、手动 collect 接口及少量生命周期代码中。相同的 occurrence 隔离、每日更新、奖励档次、榜单快照和最终封账被重复实现；魔道又单独存在一个“探查”Job，无法表达 00:30 对账、19:00 邮件/任务/探查和未来挑战属于同一期活动。

目标是建立一个标准作业 `日程_榜单系统更新`：

- 每天 00:30 枚举并处理全部相关玩法榜、资源榜 occurrence；同一时刻可以同时存在上一期结算、当期持续和下一期开启。
- 统一完成活动身份、奖励档次、榜单事实、商店/资源、策略和最终封账的状态投影。
- 允许活动 adapter 声明额外业务检查点；首期魔道声明 19:00。
- 魔道 19:00 在同一 occurrence 事务中依次处理邮件、任务奖励、天眼符补给和 `3×500` 探查。
- Scheduler 只保留一个 Job 和一个绝对 `next_time`；挑战功能以后只新增魔道 adapter 阶段，不新增平行 Job。

非目标：本期不自动执行魔道挑战事件；不把未开放时刻的保留数据宣称为实时榜单；不要求所有活动使用相同 GUI。

## 2. 设计审查

“一个 Job 调用所有活动函数”的直接实现存在严重耦合：采集失败会中断其它 occurrence，页面差异会污染调度器，魔道补符会让资源榜代码依赖储物袋，最终形成不可测试的巨型流程。

本设计只统一稳定的生命周期协议和运行权，保留以下正交维度：

| 维度 | 权威落点 | 生命周期 |
| --- | --- | --- |
| 规则定义 | `RankingLifecycleAdapterSpec` | 随代码版本 |
| occurrence 事实 | Runtime 日程全量快照 | 每次只读刷新 |
| 检查点状态 | 数据库 checkpoint 记录 | 跨 Job Cell |
| 执行命令 | 当前 Job Cell 内 adapter 调用 | 单次运行 |
| 业务快照 | Exchange activity/observation/ranking/shop 表 | 时间序列 |
| 展示投影 | 玩法榜/资源榜统一 API | 请求时只读 |
| 调度状态 | Scheduler `next_time` | 最近一个未完成检查点 |

因此，修改魔道储物袋补符不会影响资源榜采集；新增一种榜单只需注册 spec/adapter；修改 Scheduler 不需要理解任何活动文案。

## 3. 基础模型

### 3.1 Occurrence

一次活动由权威 Runtime occurrence 身份隔离：

```text
instance_key = runtime_id + activity_id + start_at + end_at
```

服内、跨服、多日活动和相邻期次不得共享 checkpoint 或进度。数据库已有 Exchange activity 行继续作为页面快照主体；`instance_key` 是生命周期层的精确运行身份，不用日期或名称猜测。

### 3.2 Checkpoint

所有表象需求归约成同一基础概念：

```text
Checkpoint(instance_key, checkpoint_kind, business_date, due_at)
```

- `daily_reconcile`：每天 00:30，一天一个键；适用于玩法榜和资源榜。
- `exchange_tail_0030`：正式结束后的首个 00:30，且兑换页仍在 `closePanelTime` 前；首期由魔道、云梦的已验收 adapter 执行动态锁定资源收尾。
- `magic_active_1900`：魔道活动日 19:00；是否每日重复由 adapter 规则声明，首期按 occurrence 的正式执行日生成。
- 未来挑战：新增 `magic_challenge_*` 规则即可，不改变 Scheduler 或数据库模型。

检查点结果记录 `completed / retained / unavailable / blocked`、证据时间和可选 `retry_at`。这些是业务执行结果，不是 Scheduler 状态；Scheduler 始终只消费所有待办检查点中最早的绝对时间。

### 3.3 一个 `next_time`

```text
全量 Runtime occurrence
  -> 各 adapter 生成候选 checkpoint
  -> 排除已完成 checkpoint
  -> 取最早 due_at / retry_at
  -> 原子写入唯一 Job.next_time
```

到期时一次 Job Cell 处理所有 `due_at <= now` 的检查点，按 occurrence 和 adapter 串行执行游戏动作。成功项立即独立提交；单项业务 unavailable 不空覆盖旧数据。全部项目处理后再计算新的最早时间。

## 4. 模块与接口

### 4.1 注册表与 Runtime 身份适配

```python
@dataclass(frozen=True)
class RankingActivityIdentity:
    activity_type: str
    family: Literal["gameplay_rank", "resource_rank"]
    vo_types: tuple[str, ...]
    runtime_activity_types: tuple[int, ...]
    activity_ids: tuple[int, ...]
    base_ids: tuple[int, ...]
```

现有 `ExchangeActivitySpec` 继续负责页面、榜单 scope、商店、币种和业务 adapter；生命周期层只投影家族与 Runtime 身份选择器，不复制页面能力。标准化 Runtime 日程以 `activityType / activityId / baseId` 为稳定识别事实；原始 AS3/Lua VO 类名仅作旧快照兼容提示，不能成为唯一识别依据。多个 identity 同时命中时失败关闭，不按名称或顺序猜测。

```python
class ExchangeActivityAdapter(Protocol):
    def collect_activity(self, session, *, activity_id: str): ...
```

公共 `reconcile_ranking_occurrence` 负责 00:30 对账，并调用现有 Exchange adapter 做只读动态采集；`ranking_lifecycle` Job 对 `exchange_tail_0030` 与魔道 19:00 专属 checkpoint 做显式分派。任何 adapter 都不写统一 Job 的 Scheduler 时间。

### 4.2 00:30 对账器

共同控制流固定为：

1. 读取完整 Runtime 日程，不按“当前活动”裁剪。
2. 将昨日结算、今日开始、跨日持续、页面关闭前尾期分别保留为 occurrence。
3. 按 activity type 找到 spec；未注册类型记 `observed_unhandled`，不执行。
4. 更新静态活动声明和奖励档次。
5. 尝试通过活动 adapter 刷新榜单、兑换宝阁、钱包和购买进度；资源榜若声明资源采集能力，再刷新任务/资源库存。
6. 动态 manager 或页面未开放时记录采集原因并标记 `retained/unavailable`，不得生成空榜；静态奖励档次和 occurrence 入库不受影响。
7. 写入 observation 时间序列并重算策略。
8. 正式结束后的首个 00:30 写 `formal_end`；若 adapter 已证明可幂等兑换，额外生成 `exchange_tail_0030`：刷新精确 occurrence 的最终榜单、钱包、商店购买次数，按祈愿队列动态决定最多两个锁定资源，并执行兑换收尾。
9. 九档完成时，卡邮件资源不在现场购买，只精确保留其总成本；九档未完成时在兑换保留期现场买入。卡邮件候选按 `瑶池玉莲 > 洗灵奇石 > 淬体精魄 > 珍品饲灵丸 > 炼丹灵草匣` 选择首个未使用资源，禁止按活动名硬编码。
10. 页面关闭前最后一次写 `final`。重复运行按 checkpoint 键和商店绝对 `purchased_count` 幂等；失败重试不得重复购买已完成项目。

### 4.3 魔道 19:00 adapter

魔道内部仍拆成可独立测试的原子：

```text
同步/选择性领取邮件
  -> 读取魔道任务 Runtime，逐项领取并复验
  -> 读取本 occurrence 已确认基础探查数
  -> 计算剩余天眼符需求
  -> 不足时退出到世界，经储物袋按 Runtime 物品身份打开授权补给箱
  -> 回到魔道并重新读取绝对天眼符数量
  -> 分三批补到500、探查、结果确认
  -> 写 occurrence 完成态
```

邮件没有新条目是合法幂等结果，不阻塞任务和探查。任务奖励必须由魔道专属 Runtime task adapter 确认可领/已领状态，不能复用普通日常任务 ID。储物袋只允许打开已静态证明会产出天眼符且 Runtime 唯一绑定的箱子；按缺口计算最少箱数，动作后以天眼符绝对数量增长复验。资源仍不足时记录 `blocked` 并安排有界复查，不允许用当前不足次数启动探查。

探查沿用现有 `armed -> result confirmed` 防重复事务。三批全部确认后，19:00 checkpoint 才完成；结果页额外次数不计入基础1500。

### 4.4 失败与恢复

- 业务上“页面未开放、没有邮件、没有可领奖励”由 adapter 正常分类，不产生 `run_status=error`。
- Runtime 身份冲突、资产契约断裂、不可逆动作无法复验才抛程序异常。
- 单个 occurrence 异常不阻止其它到期项被观察和安全提交；该 checkpoint 写 `error + retry_at`，整轮 Job 正常回写最早重试时间。
- 已完成 checkpoint 重跑只重新观察，不重复不可逆动作。
- `armed` 标记存在时保留现场并禁止重复500；恢复逻辑必须先证明服务端结果或当前绝对进度，不能直接清标记。
- 漏掉的 `daily_reconcile` 可以逐日追补；有游戏副作用的 19:00 checkpoint 只允许在精确 occurrence 尚未结束时补跑，结束后永不追执行。

## 5. 页面投影

玩法榜和资源榜页面继续共享 Exchange activity shell。新增统一生命周期字段：

- `instance_key`
- `lifecycle_phase`
- `last_reconcile_at`
- `facts`: rankings/shop/tasks/resources 各自的 `updated/retained/unavailable/not_applicable`
- `finalized_at`
- `next_checkpoint_at`
- `blocked_reason`

前端不根据当前时间自行猜活动状态，也不把 retained 显示成刚更新。魔道已经注册在玩法榜 `magic-invasion` spec 中，不新增独立页面；00:30 和19:00结果都投影到该实例。

## 6. 迁移

1. 新增统一 task type/id：`ranking_lifecycle` / `ranking-lifecycle`。
2. 注册标准 Job“日程_榜单系统更新”，初始 `next_time` 为下一个00:30。
3. 先让统一 Job 在活动结束后的安全时窗运行，验证 occurrence、历史 00:30 追补和过期动作禁补跑。
4. checkpoint store、魔道 adapter 和 Scheduler 契约测试全部就绪后，原子退休 `magic-invasion-explore`；迁移其当前 occurrence 的 confirmed/armed 证据，禁止清零。
5. 当前机器只保留统一 Job；旧 task type 可暂留兼容读取，但不得再进入标准清单或拥有 `next_time`。
6. 明日跨服先由统一 Job 00:30 建基线、19:00完成正式阶段；真实结果通过玩法榜 API与Runtime日志复验。

## 7. 实施与验收

### 阶段一：内核

- checkpoint 纯规划器、多 occurrence 分类、00:30/19:00时间计算。
- checkpoint 持久化与幂等键。
- Exchange registry 到生命周期 registry 的无重复投影。

### 阶段二：00:30 家族对账

- 玩法榜与资源榜共同 orchestration。
- 静态奖励档次与 retained/unavailable 语义。
- 同时存在“上一期结束 + 今日开始”的回归样例。

### 阶段三：魔道

- 邮件原子复用。
- 魔道任务 Runtime reader 与领取动作。
- 天眼符补给箱静态产出解析、储物袋执行和绝对数量复验。
- 3×500探查接入统一 checkpoint。

### 阶段四：迁移与真实验收

- 默认清单恰好一个统一 Job。
- 当前 Scheduler 成员迁移和 `next_time` 对账。
- 00:30真实对账页面验收。
- 19:00合法活动窗口真实执行；挑战仍显示“未启用/未来阶段”。

验收不以 pytest 替代真实 Runtime。未到合法窗口前只能报告静态、离线和 Scheduler 验收完成到哪一层。

## 8. 权衡

- 单一 Job 减少运行权竞争，但一次运行可能处理多个活动；通过 occurrence 独立提交和 adapter 串行执行控制影响面。
- 新 checkpoint 表增加一层状态，但避免把多 occurrence 进度塞入 Scheduler payload，也避免一个字段同时承担规则、状态和展示。
- 00:30 能获得奖励配置与既有事实，不保证获得未开放榜单的实时玩家记录；明确事实新鲜度比伪造完整性更重要。
- 首期只让魔道成为完整专属 adapter。其它活动先接共同00:30对账，再逐个迁移专属执行阶段，降低一次性切换风险。

## 9. 本次反思

- 第一版发现器直接依赖原始 VO `class`。真实 Runtime 标准化日程已经有意抹平实现类，只保留 `activityType / activityId / baseId`，结果测试样例能识别、生产 36 行日程却得到 0 个 occurrence。修复原则不是把 `class` 补回标准层，而是把稳定身份选择器抽成版本适配边界。
- “Job 执行成功”不等于业务成功。第一次真实运行显示 0 checkpoint，如果只看 Runtime 状态会形成假验收；继续核对 occurrence 数和 checkpoint 表才定位到识别层缺陷。
- 合并调度时不仅要保存旧进度，还要重算新体系更早的生命周期触发。若机械保留旧魔道 10:01，迁移后的首个 00:30 会被跳过。
- 补跑必须按副作用分类：数据库事实可以追补，游戏动作不能在活动结束后追补。把二者都简单解释成 `due_at <= now` 会在恢复服务时制造不可逆误操作。
- 00:30 的正确语义不是强行得到实时榜单，而是“静态事实必达、动态事实尽力刷新、失败保留旧值并留下原因”。这比用空数据伪造一次成功更新更可靠。
- 同一玩法可能连续出现服内、跨服等多个 occurrence，采集器不能把“当前玩法类型”误当成唯一实例。稳定绑定应以 Runtime 的 `activity_id` 为主，再由 adapter 映射该实例自己的 rank scope；丹道预赛与跨服因此分别读取各自榜单，不再被默认预赛入口串线。
- 复用旧活动内核时，必须把“由谁计算下一次调度”和“不可逆动作如何持久化”拆成两个开关。统一 Job 可以关闭旧内核的 `next_time` 管理，但绝不能关闭点击前 `armed`、结果确认后 `confirmed` 的事务证据；否则所谓单一调度所有权会以丢失防重复能力为代价。
- 资源榜不能依赖标准化层已经删除的原始 VO `class`。版本化 `activity_id` 集合集中留在身份 adapter，并按“精确 activity/base id > 唯一 activity type > VO class 兼容兜底”分级选择；真实日程因此补识别出此前漏掉的未来灵装化道 `1044311`。
- 服龄是全服事实，不属于某个玩法家族；但历史库中的 `9999` 也可能只是协议哨兵。奖励档次只能继承带明确来源说明的全局服龄下界，并保持“至少 31 天”这种下界语义，不能伪造精确开服天数。服内魔道据此恢复出 12 个真实奖励档次。
- 活动正式结束不等于页面关闭。服内魔道的 `endTime=22:00` 与 `closePanelTime=次日23:58:59` 必须分开存储；把 close 字段写成旧键会让仍可兑换的历史页被误判为关闭。
- 历史兑换页与全局“当前活动”可以同时属于不同 occurrence。采集器必须用 `runtime_id/activity_id/cross_count/start/end` 五项一致性绑定历史榜单与商店，不能让今天跨服 Runtime 覆盖昨天服内实例。
- 视觉场景分数不是业务终态。#519 因旧标注写着“位面魔晶”只能得82分，但标题、当前魔晶、累计魔晶和唯一竖排页签可共同证明兑换宝阁；竖排 OCR 必须先按 `parent_line_id` 重组，不能逐字符查完整词。
- 重试链必须从自身留下的安全现场继续：购买框先关闭、商店先走活动内返回，再进入全局导航；数据库事务也不得跨越真实游戏等待，否则外层读事务会自锁内部快照写入。
