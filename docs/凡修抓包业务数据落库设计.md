# 凡修抓包业务数据落库设计

本文约束凡修抓包服务解析出的业务明文如何进入数据库。它补充 `docs/凡修抓包服务架构约定.md`，用于判断“抓到了、解析到了，但页面没更新”这类问题应该修哪一层。

## 设计原则

抓包服务是运行态业务数据的生产者。只要协议字段已经探明，并且属于排行榜、玩家面板、储物袋、钱包、装备、玩法状态、拜谒等已开发业务范畴，就必须由抓包同步链路增量写入数据库。

前端页面是只读消费者。打开图鉴、面板、储物袋、活动页时，只能查询数据库或数据库派生的只读接口，绝对不能触发抓包、解码、同步、历史补扫或全量重建。

这条规则没有例外：即使用户是在图鉴页发现“数据没更新”“解析漏了”“面板没出来”，AI 实际要优先处理的也是抓包服务和业务写入链路，而不是让图鉴页主动同步。只有数据库中已有正确业务事实但页面展示错误时，才修改图鉴页。

JSON 快照只允许用于三类场景：

- 未探明协议的探索观察。
- 调试和兼容旧接口。
- 离线排查时的中间产物。

JSON 快照不能作为已探明业务域的权威持久化层。

## 职责边界

| 层级 | 职责 | 禁止 |
| --- | --- | --- |
| 抓包监控器 | 持续保存原始 pcap 段 | 解析业务字段、写业务表 |
| 解码层 | 生成协议帧和 packet 证据 | 按页面需求过滤业务数据 |
| 业务写入器 | 校验有效性、生成业务 key、幂等 upsert 数据库 | 把无效包覆盖有效记录 |
| 数据库事实层 | 保存业务明文、证据和更新时间 | 混入静态逆向 catalog |
| 展示接口 | 查询数据库并按 UI 需求裁剪字段 | 触发抓包同步、抓包补扫或历史重建 |

## AI 排查口径

用户经常会用图鉴页作为观察窗口描述问题，但观察窗口不是数据生产者。接手时按下面顺序判断：

1. 数据库没有对应事实：查抓包服务是否运行、是否捕获到 pcap、是否进入解码队列、业务写入器是否识别并入库。
2. 数据库有事实但字段缺失：查协议解析和业务有效性规则。
3. 数据库有正确事实但页面没显示：才查展示接口和前端字段裁剪。

禁止为了让页面“看起来能更新”，在图鉴页加同步按钮、自动同步、接口副作用或打开页面触发补扫。

## 当前落库映射

| 业务域 | 来源协议 | 数据库落库 | 说明 |
| --- | --- | --- | --- |
| 玩家面板 | Runtime 及历史 `SM_ShowOther`、`SM_SyncPlayer` | `fanxiuplayerprofilerecord` | 本体战力为主指标，攻击可空；仙侣队最大观测战力使用独立指标和时间，不覆盖本体战力。 |
| 世界线活动 | `SM_WorldLineActivitySync` | `fanxiupacketbusinessrecord(domain=worldline_activity)` | 原 JSON 记录保留为兼容快照。 |
| 活动排行 | `SM_ActivityRankSync` | `fanxiupacketbusinessrecord(domain=activity_rank)` | 包含个人排行 `selfRankVO`。 |
| 储物袋 | `SM_AllBagSyncInfo` | `fanxiupacketbusinessrecord(domain=storage_bag_item)` | 按物品实例/基础 id 写入最新明文事实。 |
| 钱包资源 | `SM_Wallet` | `fanxiupacketbusinessrecord(domain=wallet_resource)` | 按资源类型和 code 写入。 |
| 装备 | `SM_SyncAllEquipment` | `fanxiupacketbusinessrecord(domain=equipment_item)` | 按装备槽位/物品 id 写入。 |
| 玩法状态 | `SM_BlueStarSeaEnergyChange`、`SM_TakeMedicineSync` | `fanxiupacketbusinessrecord(domain=gameplay_state / medicine_state)` | 保存状态快照和来源证据。 |
| 拜谒 | `SM_Worship*` | `fanxiupacketbusinessrecord(domain=worship_record)` | 按已解析记录 key 去重。 |
| 属性变动 | `SM_RoleChangedAttrs`、`SM_ChangedPlayerAttribute` | `fanxiupacketbusinessrecord(domain=player_attribute_change)` | 保存最近属性变动事实。 |

## 有效性规则

业务写入器负责判定数据是否有效。典型规则：

- 玩家战力观察必须有稳定 `role_id`、正数战力、观测时间、来源和幂等 observation id；攻击字段是可选增强，不再是有效性门槛。
- 本体 `battle_score` 与 `xianlv_team_fight_score_max` 是两条独立时间轴。同一人同一天分别选择最高值，仙侣同分取较新记录。
- 仙侣队号不是图鉴维度，不进入公开字段或合并规则；来源若能严格证明队号，只能留在内部证据中。
- 同一业务实体的新快照可以更新摘要，但必须保留 packet 证据。
- 同一 packet 或同一业务 key 重复解析必须幂等。
- 玩家身份判断优先使用 role id；昵称只作为展示字段，因为昵称可能变化。

## 重构要求

新增抓包解析功能时，必须同时交付：

1. 协议和字段来源。
2. 业务有效性规则。
3. 数据库写入器或统一事实表 domain。
4. 幂等 key。
5. 历史补扫入口。
6. 展示接口只读查询。
7. 测试或验证记录。

如果只新增 JSON 快照或前端读取逻辑，不算完成业务解析功能。
