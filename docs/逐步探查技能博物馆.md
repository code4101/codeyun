## 原技能元信息

```yaml
name: "逐步探查"
description: >
  用于信息不完整、目标结构未知的探索性任务，尤其适合 GUI 自动化、手游脚本、爬虫、
  API 逆向、陌生数据解析和调试。每次只做一个最小实验，先观察真实输出或界面状态，
  再决定下一步。
```

## 核心定位

逐步探查用于处理无法预先设计完整方案的探索性任务。它的基本判断是：

> 不靠猜测写完整代码，而是靠真实观察驱动每一步。

典型适用场景：

- GUI 自动化、桌面软件控件操作、手游脚本
- 爬虫开发、网页自动化、登录态页面摸底
- API 逆向、陌生响应结构解析
- 调试复杂运行现场、缩小问题范围

这类任务经常依赖当前窗口、浏览器 tab、登录态、cookie、session、中间变量、下载目录和临时文件。最佳工作环境是 Jupyter、marimo、持久 Python REPL 或其他能保留运行时状态的 notebook 式环境。

## 方法论

### 最小实验

每个 cell 只验证一个最小假设：

- 当前页面是不是目标页
- 当前窗口是否处于预期界面
- 某个按钮、控件、选择器是否真的存在
- 某个动作后是否进入新状态
- 某段响应数据到底是什么格式

能用 5 行验证的，不写 20 行。探查阶段不急着写完整自动化流程，而是先确认现场。

### 输出即上下文

每一步执行后必须先读输出，再写下一步。输出、截图、DOM、URL、title、日志、报错、元素树和下载文件，都是下一步的依据。

常见观察点：

- GUI：窗口、焦点控件、弹窗、提示词、截图差异、OCR 文本、按钮状态
- 网页：title、url、首屏 HTML、DOM 结构、元素文本、链接
- 请求：状态码、响应头、响应体结构、反爬或验证特征
- 数据：字段形状、缺失值、嵌套层级、编码和清洗规则
- 报错：异常类型、堆栈位置、真实失败输入

### 显式记录观察

每个 cell 前写清楚：

- 当前假设是什么
- 这一步想验证什么

每个 cell 跑完后，用一句话总结观察结论，作为下一步输入。

## Notebook 式联调

逐步探查天然适合 notebook 语义：

- 上一个 cell 的输出、变量和对象直接成为下一个 cell 的上下文
- 已打开的浏览器、页面、登录态、tab、session 可以复用
- 人工观察、人工介入、继续执行是流程的一部分
- 不必每次从头完整复现上游流程

当底层正式实现已经复杂，而现场问题集中在一条真实链路时，可以把底层流程临时展开到 notebook：

1. 定位当前真实 tab、窗口或页面。
2. 验证关键元素、关键文本或关键状态。
3. 只执行一个动作。
4. 观察页面、变量、网络包或本地文件变化。
5. 和用户基于真实现场一起判断下一步。
6. 在 notebook 中找到最小正确路径后，再回填到底层共享库。

notebook 的目标是先找对，不是先写优雅。稳定路径被验证后，正式行为应回到共享库、正式类或正式函数中；notebook 最终应收缩成 smoke test 或调试档案。

## GUI 自动化节奏

### 先确认当前界面

```python
# 假设：当前已经来到主界面
# 验证：先截屏 / 读标题 / 读几个关键文本，不急着点击
img = capture_screen()
print(read_text(img))
print(find_all_buttons(img))
```

观察是否真的在主界面，是否存在活动弹窗、奖励页、网络错误或引导遮罩。

### 只执行一个动作

```python
# 观察结论：界面上确实有“开始”按钮
# 下一步假设：点击后会进入关卡选择，而不是弹出二次确认
click_text("开始")
img = capture_screen()
print(read_text(img))
```

观察点击后是否进入新页面、弹出确认框、按钮变灰，或根本没有点中。

### 根据新状态再决定

```python
# 观察结论：出现了“体力不足”弹窗
# 下一步假设：后续流程必须先处理这个分支
print(find_all_buttons(img))
```

不要假设原流程还能继续直走。GUI 自动化的关键是每一步都重新识别当前状态，再推进。

## 爬虫与网页自动化节奏

默认优先用 DrissionPage 做探查：先确认页面能否正常打开、拿到的是否是真实 DOM、定位器是否稳定，再决定是否继续深挖或切换采集方式。

### 摸底

```python
# 假设：页面在真实浏览器里能正常打开
# 验证：先看 title、url、html 前几百个字符
from DrissionPage import Chromium

tab = Chromium().latest_tab
tab.get(url)
print(tab.title)
print(tab.url)
print(tab.html[:500])
```

观察页面是否打开成功，是否跳转到登录墙、验证码页、空壳 HTML 或中间页。

### 人工介入

```python
# 观察结论：这里确实需要人工登录 / 过验证码
# 下一步假设：人工完成后，页面会进入真正的结果页
input("请在当前浏览器里手动完成登录或验证码，然后按回车继续...")
print(tab.title)
print(tab.url)
print(tab.html[:500])
```

人工完成后不能默认已经通过，要重新观察并等待下游确认信号。

### 验证提取

```python
# 观察结论：现在已经进入真正的目标页
# 下一步假设：目标链接或卡片已经在页面里
nav = tab.ele("#s-top-left")
links = nav.eles("t:a")
print(links.get.texts()[:10])
print(links.get.links()[:10])
```

先验证定位器稳定、字段可用，再决定是否写正式采集逻辑。

## 整合成正式脚本

探查阶段可以慢，因为它换来现场保留和分支试探能力。真正容易失败的是把 cell 串成脚本之后：

- 动作已经发出，但界面或页面还没稳定
- 上一步表面成功，但下游状态已经分叉
- 只靠固定 sleep，导致快时浪费、慢时误判

整合时重点不是把 cell 顺序拼起来，而是为每一步定义可靠的下游确认信号：

- 等待新页面独有的文本、按钮、标题、URL、卡片或列表项出现
- 等待旧页面元素消失，确认状态真的切换完成
- 优先选择差异明显、误判率低的元素作为等待目标
- 如果后续可能分叉，就分别等待多个候选信号，再按实际分支处理

推荐写法：

```python
click_text("开始")

if wait_text("关卡选择", timeout=8):
    enter_level_select_flow()
elif wait_text("体力不足", timeout=1.5):
    handle_no_energy_popup()
elif wait_text("网络错误", timeout=1.5):
    handle_network_error()
else:
    raise RuntimeError("点击开始后没有进入任何已知状态")
```

避免写成“点击 A，然后 sleep 2 秒继续”。如果确实需要 sleep，也只把它当成很短的缓冲，而不是完成判据。

## 人工关卡处理

登录、扫码、验证码、短信、授权、人工确认并不代表自动化失败，而是说明当前流程存在人工关卡。

处理原则：

- 先确认卡在什么界面：登录页、验证码页、扫码页、二次验证页、授权弹窗
- 保持当前 tab、窗口、session、cookie 现场，不要立刻全部重开
- 输出当前 URL、title、关键文本、截图或元素特征
- 明确把控制权交给人工处理
- 人工完成后重新观察并等待下游确认信号

走通之后，再决定后续策略：

- 保留人工关卡，脚本运行时停下来等待人工处理
- 复用登录态、cookie、用户数据目录，减少重复登录
- 只对稳定、合规、值得做的部分继续自动化

## 何时跳出逐步探查

满足以下条件后，可以切换到完整代码编写：

- 已摸清 GUI 关键界面、状态转移和主要异常分支
- 已知目标页面的完整结构
- 已验证关键选择器或解析逻辑
- 已确认无特殊反爬机制，或已明确人工边界
- 数据格式已完全明确
- 已为关键步骤找到可靠的下游确认信号
- 已确认哪些步骤可以自动推进，哪些步骤必须保留人工介入

如果前面是在 notebook 或持久 REPL 中探查，整合时要把“当前内核里已经存在的状态”显式化为正式代码里的初始化、等待条件和分支处理。

## 禁止行为

- 不在不知道 DOM 结构时就写选择器。
- 不在未确认渲染方式时就选择技术栈。
- 不在未确认当前 GUI 状态时就连续点击很多步。
- 不把“上一步应该成功了”当成事实，必须重新观察当前界面。
- 不在整合脚本时只靠固定 sleep 判断下一步能否开始。
- 不一遇到登录、验证码、授权关卡，就立刻假设必须完全自动绕过。
- 不一次性写超过当前信息量能支撑的代码。
- 不跳过输出观察直接写下一步。

## 历史价值

该技能沉淀的是一种探索型工作流：面对未知系统时，用最小实验和真实观察逐步建立事实层，再把稳定路径回填到正式代码中。

虽然它不再作为活跃技能使用，但在 `codeyun` 后续涉及凡修自动化、页面抓取、运行态逆向、桌面控制、远端现场调试时，仍可作为排障和方法论参考。
