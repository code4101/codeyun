# 筛选与排序实现说明

这份文档记录的是项目当前已经落地的实现，不是抽象愿景。

项目里有两套很“程序化”的机制：

- 笔记筛选不是传统的 `where` 条件拼接，而是受 `walker.py` 启发的“有序规则链”。
- 图库排序也不是单个 `sort_mode` 开关，而是“多关键字排序程序 + 稳定兜底顺序”。

它们看起来都像“筛选/排序”，但真正特殊的地方在于：

- 规则是按顺序执行的，后面的规则可以覆写前面的决定。
- 同一套规则模型会在不同层执行，前后端分工很明确。
- UI 只暴露了模型的一部分能力，底层 API 能力比界面更大。

## 1. 笔记筛选：本质是规则程序，不是布尔表达式

### 1.1 关键代码位置

- 数据模型：`backend/schemas.py`
- 后端执行器：`backend/core/note_walker.py`
- 后端 API：`backend/api/notes.py`
- 前端类型、构造器、本地执行：`frontend/src/api/notes.ts`
- 前端规则编辑器：`frontend/src/components/NoteProgramBar.vue`
- 列表视图：`frontend/src/views/notes/ListNotes.vue`
- 全局星系视图：`frontend/src/views/notes/StarNotes.vue`
- 日历视图：`frontend/src/views/notes/CalendarNotes.vue`

### 1.2 核心心智

`NoteWalker` 有两个决策通道：

- `select`：节点最后要不要进入结果集
- `expand`：遍历图时，当前节点要不要继续向邻居扩展

每个通道都有：

- 一个 `default` 默认决策
- 一串按顺序保存的规则 `(predicate, target_action)`

真正的执行逻辑在 `NoteWalker._check`：

1. 先从 `default` 开始。
2. 依次看每条规则。
3. 如果当前决策已经等于这条规则想要的目标值，直接跳过。
4. 只有“当前决策和目标值不同”时，才会去执行 predicate。
5. predicate 命中后，把决策翻到目标值。

所以它不是：

- “命中任意 include 就算通过”
- “先把所有 include 并起来，再减去所有 exclude”
- “一个静态 where 表达式”

而是：

- “从默认值出发，按顺序反复改写决策”

这也是为什么“先排除、后救回”是被明确支持的。

### 1.3 规则链为什么能覆写前面的结果

一个典型例子：

1. `include all`
2. `exclude node_status == done`
3. `include id == note-rescue`

最终 `note-rescue` 会重新被放回结果集里。

对应测试：

- `tests/backend/test_note_walker.py`
- `tests/backend/test_note_program_api.py`

### 1.4 `select` 和 `expand` 是两条独立通道

这是整套实现最容易被误解的点。

`select` 只回答“这个节点要不要出现在最终结果里”。

`expand` 只回答“遍历走到这个节点时，还要不要继续往外搜”。

它们是独立的，所以允许出现这种情况：

- 某个节点自己不进入最终结果
- 但仍然作为“桥”被穿过
- 最后把更远处的节点带进结果

测试里已经覆盖了这个行为：可以“穿过未选中的桥接节点”继续扩展。

一个直接后果是：如果桥接节点没被 `select` 到，最终结果边集也不会保留这段桥。
因为 `_build_result` 取的是“最终选中节点的诱导子图（induced edges）”，不是“遍历过程中走过的所有边”。

### 1.5 两类执行器：`scan` 和 `component`

`/api/notes/query-program` 当前支持两类 executor。

#### `scan`

- 面向完整候选集
- 本质上是“把每个节点当一次 `depth=0` 的 visit 去跑 `select` 通道”
- 不走图扩展

列表、全局星系、日历的“后端筛选”现在都走这个模式。

#### `component`

- 面向“从种子节点出发的连通图遍历”
- 会同时使用 `select` 和 `expand`
- 支持 `planetary` / `satellite`

`planetary`：

- 从中心节点出发，按弱连通分量扩开
- 既能往出边走，也能往入边走

`satellite`：

- 会忽略“指向中心种子节点的入边”
- 等价地说，不会因为“别人指向我”而继续向上游扩展
- 仍然允许沿着中心节点的出边继续往外走

老接口 `/api/notes/query` 的 `planetary / satellite` 也是同一语义，只是实现方式更旧。

### 1.6 当前支持的 matcher 能力

后端 schema 当前支持这些 matcher：

- `all`
- `none`
- `id`
- `field`
- `title_contains`
- `seed`
- `depth`
- `relative_month_window`

其中时间字段支持两种时间点表达式：

- `absolute`
- `relative`，单位支持 `day / week / month`，并支持 `start / end` 边界

后端 `field` matcher 还能直接匹配：

- 普通字段，如 `title / start_at / updated_at / weight / private_level`
- 自定义字段，写法是 `custom_fields.<key>`

### 1.7 当前 UI 暴露的是能力子集

`NoteProgramBar.vue` 现在主要暴露了这些模板：

- 标题
- 分类
- 形态
- 阶段
- 私密值
- 起始时间
- 更新时间
- 权重
- 指定 ID
- 全部节点

也就是说，底层虽然支持：

- `seed`
- `depth`
- `relative_month_window`
- `custom_fields.<key>`

但当前通用筛选栏并没有直接暴露这些能力。

还有两个实现细节值得记住：

- `NoteProgramBar` 当前会把 `channel.default` 强制写成 `false`
- 所以“默认包含全部”不是靠 `default=true`，而是靠第一条 `include all`

这也是为什么默认前端筛选会长成 `createIncludeAllProgram()`。

### 1.8 前端本地执行器并不是后端 100% 镜像

前端本地实时筛选走的是 `applyNoteProgramChannelLocally`。

它当前直接处理的 matcher 主要是：

- `all`
- `none`
- `id`
- `field`

其中：

- `title_contains` 会先被规范化成 `field(title, contains)`
- `relative_month_window` 会先被规范化成时间字段 `between`

但 `seed` / `depth` 这类图遍历语义并不会在前端本地视图层执行。

这和现在的产品接法是匹配的：

- 前端视图层只拿“已加载节点集合”做即时可见性过滤
- 不负责重新跑图遍历

### 1.9 当前三个主视图的接法

#### 列表视图

代码位置：`frontend/src/views/notes/ListNotes.vue`

- `dataProgram` 是后端筛选，点击“执行”后才请求 `/api/notes/query-program`
- `viewProgram` 是前端筛选，修改后立即在已加载结果上生效
- 默认后端程序是“`start_at` 落在最近前后 1 个月”
- 最终列表展示还会再按 `updated_at` 降序排一次

也就是说，列表页当前的“排序”不是用户可配置程序，而是视图内固定策略。

#### 全局星系视图

代码位置：`frontend/src/views/notes/StarNotes.vue`

- 全局星系同样有 `dataProgram + viewProgram`
- 后端筛选用 `/api/notes/query-program`
- 前端筛选只作用于当前已经加载的节点/边
- 视图层会在 `viewProgram` 改变后重新过滤节点，并把边裁到“双方都可见”的子集

注意：

- 全局星系接入了 program 体系
- 行星图 / 卫星图当前没有直接套这套通用筛选栏

#### 日历视图

代码位置：`frontend/src/views/notes/CalendarNotes.vue`

- 日历没有让用户直接编辑“后端筛选规则链”
- 后端程序由当前月视图可见网格自动生成
- 这个范围不是自然月，而是“整块日历网格”的起止日期，包含月头月尾补齐的邻月日期
- 前端仍然保留一套通用 `viewProgram`

日历里每天内部的展示顺序也不是通用 sort program，而是固定为：

1. `start_at || created_at` 升序
2. 时间相同再按 `weight` 降序

### 1.10 还有一套旧接口：`/api/notes/query`

这套接口仍在使用，尤其是：

- 行星图 / 卫星图当前还是走它

它和 `query-program` 的差异是：

- 它的 `rules` 是传统“全部条件同时满足”
- 后端会尽量把简单规则下推到 SQL
- 推不下去的规则再回退到 Python 过滤

当前可下推的主要是：

- `eq / neq / in / not_in / gte / lte / between`
- `title contains`
- `title not_contains`

像这些会回退到 Python：

- `custom_fields.*`
- `regex_search`
- 其他没法直接映射 SQL 的情况

所以：

- `/api/notes/query` 适合“普通筛选”
- `/api/notes/query-program` 适合“顺序规则链 + 图遍历”

### 1.11 当前排序能力的边界

笔记 program API 虽然有 `result.order_by / order_desc`，但当前前端通用筛选栏没有暴露出来。

现在主视图实际使用的是这些固定排序：

- `buildScanNoteProgramRequest()` 默认 `updated_at desc`
- 列表页前端视图层再次按 `updated_at desc`
- 日历页按“时间升序，权重降序”

后端允许的 `order_by` 目前仅限：

- `updated_at`
- `created_at`
- `start_at`
- `weight`
- `title`
- `private_level`

还有一个当前实现细节：

- `_sort_notes()` 用的是 `(value is None, value)` 作为 key
- 升序时 `None` 会排在后面
- 降序时 `None` 会排在前面

如果以后要开放笔记排序程序，这个行为要么显式接受，要么单独改。

## 2. 图库排序：本质是多关键字排序程序

### 2.1 关键代码位置

- 后端排序模型与执行：`backend/api/filesystem.py`
- 前端通用排序工具：`frontend/src/utils/imageGallery.ts`
- 前端规则编辑器：`frontend/src/components/GallerySortProgramBar.vue`
- 通用图库工作区：`frontend/src/components/ImageGalleryWorkspace.vue`
- 设备文件浏览：`frontend/src/views/cluster/DeviceFileBrowser.vue`
- 设备文件 API：`frontend/src/api/deviceFiles.ts`

### 2.2 排序程序的心智模型

`GallerySortProgram` 是一串有序规则：

- 每条规则包含 `field / direction / nulls`
- 比较时从前往后依次比较
- 只有前面结果相同，后面的规则才继续参与

这不是：

- “当前选一个排序模式”

而是：

- “把若干排序关键字串成一个比较器”

`GallerySortProgramBar.vue` 的提示文案也是按这个心智写的。

### 2.3 当前支持的排序字段

前后端当前共同支持这些字段：

- `random`
- `weight`
- `modified_at`
- `size`
- `duration`
- `relative_path`
- `name`
- `folder_path`
- `kind`
- `width`
- `height`
- `resolution_area`

`nulls` 虽然模型里有 `first / last`，但当前前端规范化后基本固定为 `last`，UI 也没有单独暴露空值顺序编辑。

### 2.4 排序一定会补稳定兜底规则

无论前端本地排序还是后端设备排序，最终都会补上稳定兜底：

- `relative_path asc`
- `name asc`

再不行，还会再用 `id` 做最终平局裁决。

这保证了：

- 多关键字相同的项不会在渲染时来回跳
- 分页、瀑布流和预览切换都更稳定

### 2.5 通用图库：本地即时排序

代码位置：`frontend/src/utils/imageGallery.ts`

通用图库工作流是：

1. 先按文件夹和关键字筛一遍
2. 如果 `preserveOrder=false`，再用 `sortProgram` 本地排序
3. `sortProgram`、缩放比例、视图模式等都存到 `localStorage`

默认排序程序是：

1. `weight desc`
2. `modified_at desc`

所以通用图库是“前端本地排序优先”的思路。

### 2.6 `random` 在前后端不是同一种随机

这是一个非常容易忽视的细节。

前端通用图库的 `random`：

- 用条目身份信息算稳定伪随机值
- 同一批数据反复进入页面，顺序通常保持稳定

后端设备图库的 `random`：

- 每次构造新列表时会生成新的随机种子
- 同一次列表会话内顺序稳定
- 重新发起新查询后，随机顺序可能变化

所以：

- 前端 `random` 更像“稳定洗牌”
- 后端 `random` 更像“本次会话随机”

### 2.7 设备文件浏览：排序程序跑在后端

代码位置：`frontend/src/views/cluster/DeviceFileBrowser.vue`

设备文件浏览没有复用通用图库的本地排序，而是故意做了分层：

- `ImageGalleryWorkspace` 上把 `show-sort-program` 关掉
- 同时把 `preserve-order` 设为 `true`
- 额外在 sidebar 的 `extra` 槽里挂了一个独立的 `GallerySortProgramBar`
- 改动后直接触发后端重新加载媒体列表

这样做的目的很明确：

- 前端不要再二次改顺序
- 服务器返回什么顺序，界面就按什么顺序渲染
- 排序、分页、快照三者保持同一个来源

### 2.8 设备图库排序为什么能和分页兼容

后端 `/api/fs/media/list` / `/api/device-entries/{id}/files/media/list` 做了一个内存快照层。

关键点：

- 查询签名 `query_signature` 会把这些因素一起算进去：
  - 设备
  - 根目录 / 路径 / 绝对路径
  - 是否递归
  - 扫描上限
  - 媒体类型集合
  - 规范化后的排序规则
- 命中相同签名且 `snapshot_id` 有效时，直接复用之前已经准备好的整份快照
- 大多数排序规则依然是“整份排序后再 `offset / limit` 切片”
- 但 `duplicate_cluster` 现在是例外：
  - 快照阶段只按去掉 `duplicate_cluster` 后的基础规则排好整份列表
  - 响应当前页时，再只对这一页条目补视觉哈希并做页内聚簇

所以设备图库当前不是“翻一页就重新扫目录并重排”。

它更像：

1. 先得到一个稳定的有序快照
2. 再围绕这个快照做分页和瀑布流布局
3. 如果启用了 `duplicate_cluster`，只在当前页内部再做一次局部重排

当前快照实现细节：

- 存在进程内存里
- 最多保留 32 份
- 空闲 30 分钟后过期

这也是为什么后端 `random` 即使是“每次新查询重新随机”，在同一个 `snapshot_id` 生命周期内依然能跨分页保持稳定。
而 `duplicate_cluster` 改成页内执行后，也不会再为了首屏排序去全量补视觉哈希。

### 2.9 兼容层：`sort_mode` 还在，但主路线已经是 `sort_program`

后端仍然保留了 `sort_mode`：

- `path`
- `modified-desc`
- `size-desc`
- `weight-desc`

但规范化逻辑已经是：

- 优先用非空的 `sort_program`
- 没有 `sort_program` 时才从 `sort_mode` 生成程序

当前前端设备文件浏览实际发送的是 `sort_program`。

`sort_mode` 更像兼容旧调用或远端代理时的兜底。

### 2.10 当前实现的分层建议

如果以后继续扩展，建议按下面这条线判断：

- 会影响扫描范围、分页边界、快照命中、服务端负载的，放后端
- 只影响当前已加载结果可见性或展示顺序的，放前端

套到现有代码上就是：

- 笔记“后端筛选”决定加载哪些节点
- 笔记“前端筛选”决定已加载节点现在怎么显示
- 设备图库排序放后端，前端不二次排序
- 通用图库排序放前端，因为它操作的是已经完整拿到的集合

## 3. 当前最值得记住的几个结论

- 笔记筛选最特殊的地方不是字段多，而是“顺序可覆写”。
- `select` 和 `expand` 是两条独立通道，不要混成一个布尔条件。
- 日历的后端筛选范围是“当前月网格”，不是自然月。
- 当前笔记 UI 暂时还没有把排序参数程序化开放给用户。
- 图库排序已经是规则链，不是单个排序开关。
- 设备图库必须保持“后端排序 + 快照分页 + 前端保序”这一整套联动，不要在前端再偷偷重排。
