# 凡修洞天行动力作业

## 业务目标

` 洞天_行动力 ` 在 21:30-22:00 的限时窗口内完成闭环：进入洞天，从已加载的
`XianLvMinesMgr.Model.Data` 读取行动力和 39 个地点，从
`ClubMgr.Model.data` 读取己方联盟，快速筛出敌对地点并反复挑战，直到行动力
小于 100。场景 #279/#341 只负责交互，不应用 OCR 重建阵容清单。

## 2026-08-07 失败复盘

当天没有在 22:00 前消耗行动力，结果为失败。持久化 Runtime 日志保留了主失败：

```text
RuntimeError: 洞天_行动力：Runtime 行动力不可用，拒绝降级 OCR：
洞天 Runtime 快速根解析失败；正式作业拒绝退化为全堆扫描；
global:XianLvMinesMgr: Runtime 管理器方法签名校验失败
```

后续仅读验证读取到了同一进程中的真实数据：

- `action_power=100`
- `decoded_mine_count=39`
- `own_union_id=24077380502945993`
- `enemy_count=22`
- `mines_root=0x7502948ae628`
- `club_root=0x750297167510`
- 冷路径总耗时 `108.020s`

因此不是游戏没有下发阵容清单，也不是 #341 场景问题，而是实现同时存在两个
独立缺陷：

1. 正确性缺陷：用会随客户端版本漂移的 Lua 方法名集合校验 Manager，导致
   真实 `XianLvMinesMgr` 被误拒绝。
2. 性能缺陷：冷路径在巨大 Lua 全局表中逐键、逐页读取字符串，ADB 往返
   累积到 108 秒。“最终能读到”不等于“可用于限时作业”。

## 已固化的规则

- 全局名只用于定位 Manager；真实性必须用稳定的 `Model.Data` 字段和业务完整性
  校验，不得依赖非业务 Lua 方法名。
- 正式作业不得退化为多分钟全堆扫描。诊断扫描必须显式使用
  `allow_legacy_scan=True`。
- Runtime 快照必须记录 `process_discovery / lua_state / mines_root / club_root /
  decode` 分阶段耗时和缓存命中情况，失败时同时记录失败阶段。
- 行业务时限是正确性的一部分。下次真实验收不能只看是否读出 39 个地点，
  必须同时证明快照耗时满足作业窗口要求。

## 明日验收顺序

1. 不点击游戏，先用已保存的进程绑定根跑一次快照，验证缓存路径耗时。
2. 若游戏进程已重启，先优化 `LuaJitReader.string_fields` 的批量内存读取，不得
   在限时作业中边跑边试 90 秒扫描。
3. 快照必须一次返回行动力、39 个地点、己方联盟和敌方地点列表。
4. 先做只读快照验收，再在用户授权的时间窗口提交正式 Cell；两者耗时分开
   报告。
