# 凡修逆向资源安全边界

## 固定外部目录

凡修逆向原始资源、解包产物、解析导出和相关文档统一放在仓库外：

```text
D:\home\chenkunze\data\m2606凡修逆向
```

CodeYun 仓库只保存源码、测试、轻量文档和必要配置，不保存 APK 解包后的大体积资源包、图片资源原件、临时抓包片段或一次性探针产物。

## 默认路径

后端默认使用以下目录：

```text
FANXIU_RESOURCE_ROOT        = D:\home\chenkunze\data\m2606凡修逆向\frxx_game_files
FANXIU_RESOURCE_EXPORT_ROOT = D:\home\chenkunze\data\m2606凡修逆向\frxx_analysis_exports
```

对应实现见 `backend/core/fanxiu_resources.py`。如需临时切换，使用环境变量 `FANXIU_RESOURCE_ROOT` / `FANXIU_RESOURCE_EXPORT_ROOT`，不要把路径写进前端或业务页面。

## 仓库内允许保存什么

允许保存：

- 解析、展示、校验这些资源的源码。
- 小型测试样本和单元测试数据。
- 文档化结论、流程、字段语义和验收脚本。
- 从资源二次加工后写入 CodeYun 数据库的轻量结构化结果。

不允许保存：

- APK 原包、Unity bundle 原件、大批量图片、音频、模型等逆向原始资产。
- 临时截图、OCR 裁剪、抓包片段、探针 JSON、一次性 stdout/stderr。
- 为了前端显示而复制一份图片到仓库。

## 前端图鉴的资源使用原则

凡修图鉴前端通过后端接口读取本地逆向资源，例如：

```text
/api/fanxiu/resources/icon?name=...
```

图片资源不需要复制进 CodeYun 数据库。数据库只保存邮件、附件、道具 ID、图标名、名称、类型、品质等结构化字段；实际图片仍由后端从 `m2606凡修逆向` 目录解析并返回。

## 验收口径

资源链路不能只看“数据库有字段”。至少要同时验证：

- 当前资源根和导出根必须先通过 `verify_fanxiu_reverse_boundary.py`。它检查后端默认根、环境变量覆盖、关键资源/导出产物、文件数量，以及 `frxx_game_f` 这类疑似误名同级目录；虚拟机 `D:\TapTap\Support\android_emulator\engine\vms\...` 路径不能作为当前默认根。
- 关键逆向输入和导出产物必须有机器可读 manifest。`verify_fanxiu_reverse_manifest.py` 会记录 `raw_inputs`、`filelist.csv/filelistVersion`、关键 rows/catalog、icon/by_source/apk_static_index 等条目的大小、mtime、SHA256 或目录摘要，并写入 `frxx_analysis_exports/parsed_configs/reverse_manifest_audit/`。
- 数据库邮件附件存在 `item_id`、可读名称和 `icon/small_icon`。
- 道具配置里的图标必须先通过底层资源导出检查。`verify_fanxiu_item_icons.py` 会遍历完整本地 `item_catalog`，确认每个唯一 icon 都能从逆向资源导出；这是资源恢复层检查，不能用页面首屏或 HTTP 抽样替代。
- 图标接口能返回真实图片。`verify_fanxiu_wiki_icons.py --full-items` 必须全量扫描道具目录，并分页扫描功法、灵界、数字门角色、斗破角色等必需图标目录；活动目录允许空 icon，默认只做页面级抽样。
- 图鉴接口不能只验证状态码和数量。`verify_fanxiu_wiki_endpoints.py` 必须检查核心列表行的关键字段，例如图鉴链接索引的 `tab/id/title/kind`，功法/道具的 `id/name/icon`，活动的 `id/name/source_table/presence_status`，以及视觉、音频、协议等资源的定位字段。
- 功法、道具、活动、灵界、数字门角色、斗破角色这些主图鉴卡片目录必须保持可加载；列表要非空，关键 ID/标题字段完整，默认每类按首段/中段/尾段抽 8 条代表性样本。除活动这类本身常见空图标的目录外，当前展示用的小图标字段必须能通过 `/api/fanxiu/resources/icon` 返回真实图片；有详情接口的目录还必须能打开对应详情。
- 前端邮件图鉴能渲染附件图片。
- 附件链接能进入道具详情页。
- 独立资源详情页 `/fanxiu-resource/:resourceType/:resourceId` 必须保持可用；当前已支持并验收 `gongfa/item/activity/digitdoor/doupotd/lingjie` 六类，默认每类打开 5 条真实资源详情页，必须能渲染标题、ID、返回图鉴链接和正文。除活动这类本身常见空图标的资源外，必须加载真实图标，且页面图片 URL 要和后端列表返回的 `icon/small_icon` 名称一致。
- 独立资源详情页不能为了富文本链接无条件拉完整 `/api/fanxiu/resources/wiki/link-index`。详情页应按当前资源正文、效果、附件等文本请求轻量 `/api/fanxiu/resources/wiki/link-targets`，只取当前文本实际出现的可跳转目标；全量 link-index 只保留给完整图鉴页或索引构建场景。
- 典型正文 fallback 可读，例如“灵脉收益”“修炼值自动领取通知”。
- 道具图鉴分类筛选后，列表行必须渲染真实游戏图标，不能只露出单字 fallback。
- 道具图鉴分类筛选后的浏览器验收必须随滚动多批采样。只验证筛选后的首屏不够，因为用户反馈的风险来自“随便一翻”后仍可能出现缺图或错图。
- 道具图鉴分类筛选必须能由 URL 直接复现。`/fanxiu/wiki?tab=item&type_key=...&sub_type_key=...` 进入页面时，地址栏、激活筛选、首屏行、后端请求和图标都必须落在同一分类下；不能依赖 localStorage 里的旧筛选或用户手点。
- 道具图鉴无筛选 URL 必须能清空旧筛选。先打开带分类筛选的 URL，再打开 `/fanxiu/wiki?tab=item` 时，地址栏和请求中不能残留非空 `type_key/sub_type_key`，页面应回到全量道具列表。这是防止“分享链接/刷新/验证入口被本地缓存污染”的硬约束。
- 道具列表图标 URL 必须和 `/api/fanxiu/resources/items/cards` 返回的 `icon/small_icon` 对齐，不能用 OCR、抓包字段或前端猜测替代。
- 道具列表图标验收必须优先按 `item_id` 对齐 API 期望图标；标题和序号只能作为降级兜底。同名道具、滚动采样和分类切换都不能靠标题猜图标。
- 道具图标浏览器验收要先等待当前可见行图片加载稳定，再采样 DOM。可见行缺 `data-item-id`、图片等待超时、真实 `src` 和期望 `icon` 不一致都必须失败。
- 道具图标加载成功后必须隐藏单字 fallback 层。透明 PNG 不能露出背后的“云/玄”等占位字，否则用户会误判为图标缺失或默认图。
- 邮件正文不能静默为空。真实抓包没有正文时，也要展示可解释摘要，例如“附件：...”或“抓包未携带正文或附件；邮件类型：...”。
- 邮件附件图片加载失败时，前端必须隐藏坏图并做有限退避重试；不能把浏览器破图状态留在用户可见界面里。
- 浏览器验收必须打开真实 `/fanxiu/wiki` 页面并检查 DOM、图片自然尺寸、正文弹窗和附件跳转，不能用单纯 API 成功代替页面成功。
- 除邮件和道具专项验收外，还必须用真实浏览器打开功法、活动、灵界、数字门、斗破等主图鉴 tab，确认页面有观测结果、无请求失败、无可见坏图。
- 核心图鉴 tab 浏览器验收不能只看 `observation_count > 0`。功法、活动、灵界、数字门、斗破 5 个 tab 必须都有资源列表行；其中功法、灵界、数字门、斗破 4 个 icon 资源 tab 必须至少有一个可见真实图片。
- 邮件浏览器验收必须覆盖分页后的全部可见邮件页，不只看第一页。当前 `verify_fanxiu_wiki_browser.py --tab mail` 默认最多检查 20 页，足够覆盖当前 116 条邮件记录。
- 总质量闸门会做跨层一致性检查：邮件浏览器验收后会立即再跑一次 `verify_fanxiu_mail_records.py` 作为 `mail_records_final`。浏览器渲染邮件数/附件图标数/附件链接数/正文按钮数必须落在浏览器前快照和浏览器后快照之间。抓包服务常开时邮件可能在长质量门运行期间新增，不能把“后置快照新增”误判成浏览器漏渲染；但浏览器数量低于前置快照或高于后置快照仍必须失败。
- 总质量闸门不能只相信子脚本退出码。每个子脚本最后输出的 JSON 摘要也要被读取并做硬断言；例如邮件正文覆盖、附件字段完整、图标接口失败数、浏览器坏图数、道具 `item_id` 对齐、fallback 可见数都必须满足验收条件。
- 总质量闸门默认还会运行前端 `typecheck` 和 `build`。图鉴页面是前端页面，不能只用 API/浏览器局部脚本通过来替代完整前端构建通过。
- 总质量闸门允许对明确的服务层瞬断做一次整步重试，例如后端重载时的连接拒绝或读超时；但真实图标缺失、稳定接口 4xx/5xx、页面渲染失败和跨层计数不一致不能被重试吞掉。全量 icon 检查中单个 icon 首轮失败时会冷却后复查一次，复查仍失败才计入 `icon_endpoint_failures`。
