# 凡修新作业研究与上线指南

本文是凡修新作业研发的统一入口。它不替代各专题文档，而是规定从未知业务研究、资产生产、Cell 调试到 Scheduler 上线的完整顺序。

## 0. 先判断是不是小型作业

已有入口、只有一个核心点击、后续由游戏自动执行、终态可直接观察的任务，按小型作业走快速通道。底层可能同时涉及 OCR、资产树、只读数据和 Scheduler，不代表研究流程必须重型化。

小型作业先在 30～90 分钟内跑通一条纵向链：复用入口 -> 到核心页面 -> 最小 Cell 执行一次核心动作 -> 捕捉真实终态 -> 再补资产、必要的防重复执行标记、测试和标准 Job。20 分钟仍未执行核心动作时，暂停增加静态逆向、通用抽象和未见分支，重新检查当前场景与下一安全动作。

开发反馈不等待自然调度时间。需要真实探索时切 AI 并执行最小 Cell；正式逻辑闭环后交还工程，再用 Scheduler 的统一“置为到期”入口验证派发。未真实遇到但业务上可能存在的正常分支，最多落在关键代码注释或本作业专题文档，不阻塞主线交付，也不进入一级 skill。

短暂出现且会自动推进的机会式软场景不作为必经 scene。可在当前帧的限定 ROI 内轻量识别并点击加速；没有看到、已经消失或来不及点击都按 no-op 继续，不能等待它、因它失败，或让业务终态依赖它。只有决定分支、需要等待或承担完成判定的硬场景才进入正式场景地图和作业幂等分支。

## 1. 先定义业务，不先猜点击

新增作业前先写清：入口、成功终态、正常失败终态、限次规则、跨日边界、重复执行风险、异常重试边界和 `job_status -> next_time`。游戏里的“已完成”、按钮消失或列表进度，只有在业务语义已确认后才能当终态；相邻功能的同名文案不能直接复用。

限次或自动连续执行的作业必须在第一次不可逆点击前持久化防重复执行标记。这个标记只用于证明“本周期已经授权过不可逆点击，重跑时必须先读当前事实再决定是否收口”，不能变成跨 Cell 的步骤记录。正常业务失败应返回成功并写下一次业务时间；链路损坏、终态不确定或防重复标记未收口应抛异常，由 Scheduler 重触发完整 Job Cell，但不得再次执行有重复风险的点击。

## 2. 研究只占 Scheduler 空档

1. 先读取 Scheduler 运行权、Kernel 状态、当前 Cell 和近期 `next_time`。
2. 工程作业正在执行或即将到期时只做静态研究，不切换 AI。
3. 空档中通过唯一“工程 / AI”开关切到 AI，再向长期 Kernel 提交普通 Python Cell。
4. Cell 结束后立即确认 Kernel idle，并恢复工程运行权；不要把未知弹窗、详情页或战斗现场留给下一项工程作业。
5. `interrupt` 只停止当前 Cell；只有代码或资产需要完整重载时才 `restart`。不得建立第二执行协议、临时作业或 Kernel 内队列。

推荐先做 5～30 秒的最小 Cell：识别当前场景、验证一个 shape、完成一步跳转并采帧。探索时逐步扩大动作范围，不把整条未知流程一次性提交。

## 3. 静态代码与动态证据并行

静态研究优先回答“游戏本来如何工作”：原始 Lua、消息定义、配置表、Unity/UE 资源和旧任务代码可以证明入口调用、自动续层、字段更新和面板切换。静态结论必须记录来源文件和关键函数，不能只保留口头推断。

动态插桩固定为外部只读：只读进程身份、`/proc` 映射、进程内存、已保存数据包和数据库快照。不得附加或 Hook Frida、执行游戏 Lua、初始化 Manager、主动刷新、替换方法或发送 `CM_*`。数据没有由游戏正常加载时应安全失败，不用写动作制造“可读状态”。

动态字段必须先确定语义再参与控制流。例如配置主键变化可以证明状态推进，却未必能按差值换算层数；本轮计数、每日计数和历史最高值也不能混用。

## 4. frame / shape 资产生产

每个新状态先采真实 frame，再决定是扩展旧 scene、建立新 scene，还是只新增 shape。动态列表项优先使用稳定 ROI、OCR 关系和相对位置，不因一次截图写死左右、塔名、层数或动画帧。

OCR 标注和运行时定位应使用“能在限定 scene / frame / ROI 内保持唯一的最小稳定片段”，不要把底层 OCR 当成完整 UI 文案数据库。比如按钮可能显示“每日签到”或“签到”，优先使用 `签到`，需要兼容可选前缀时使用有界正则 `(?:每日)?签到`；不要硬匹配一整句可能随活动、数字、空格或本地化变化的文字。这里的“精确定位”是指片段在当前证据边界内唯一且落入正确 shape，不等于必须对整行做字符串全等。只有文本本身已经是最小稳定 token（例如限定在按钮 ROI 内唯一的“挑战”）时，运行时 `exact` 才是合适约束。

正则也不能用于无边界放宽：必须绑定已确认的 scene / frame 和尽量小的 shape ROI，并对当前正样本、相邻负样本和同屏重复文本做唯一性检查。模糊 OCR 只负责吸收已证明的字形、空格或可选前缀变化，不能靠 `.*`、全屏搜索或低阈值绕过资产身份。

修改资产前必须保存：

- 当前真实 frame；
- 资产树 SHA-256；
- 原节点或父目录摘要；
- 可回滚的完整资产树副本。

修改只走资产存储的加锁、原子入口。图片文件名由存储层分配，不手填可能冲突的编号。修改后必须回读唯一节点，并验证：

- 当前正样本；
- 相邻负样本；
- scene 互斥分数；
- 重复节点 ID、shape ID 和图片文件名；
- 旧样本没有被无关破坏。

执行 shape 在真实点击成功前只能标成候选或身份依据；真实动作验证后再记录 `sceneJumpTarget` 和 `observedLanding`。如果两个页面布局相同但业务状态不同，应使用明确的 OCR 身份、局部图像或 discriminator 分开，不把它们合并成一个 scene。

## 5. 用 AI Cell 精确调试

Cell 应直接复用正式 Runtime 原语：`goto_view`、`wait_view`、`wait_click_then_view`、ROI OCR、只读事实探针和正式业务 helper。不得新增调试 API，也不得复制一套 ADB 点击器。

每一步输出最少但充分的证据：来源 scene/score、OCR 行及其真实 box、点击点、落地 scene/score、frame 临时路径和只读字段快照。点击点必须来自已验证 shape、OCR box 或静态资源布局；“大概在这里”不能进入正式作业。

探索失败也是有效结论。保留现场和证据，区分：入口状态不符、OCR 未加载、点击层不接收事件、场景图缺路径、业务已完成但仍可进入、以及真正的作业异常。

## 6. 实现标准 Job

用户说“加作业”默认同时完成两层：

1. 注册完整业务 Job：任务类型、标签、payload、admission、运行边界、必要的防重复执行标记和绝对 `next_time` 算法。
2. 通过 `runtime_control` 的统一原子存储把当前机器唯一实例加入 Scheduler。

`scheduler_supported=True` 的业务 Job 必须在默认清单中恰好出现一次。固定首次时间显式写入默认实例；后续调度只消费作业写回的绝对 `next_time`，不解析描述文案。不要直接读写 `scheduler_tasks.json`，也不要让旧快照省略掉磁盘上的其他 Job。

## 7. 验收与交接

单测、静态代码或“曾进入入口页”都不是完成。至少需要：

- admission 和 `next_time` 边界测试；
- 业务 helper 与防重复执行标记回归测试；
- 默认清单唯一实例契约测试；
- 新 scene 的正负样本和图模型互斥验证；
- 动态探针未加载时安全失败、正常加载时字段可信；
- 真实 Runtime 至少走通一次关键动作和一个真实终态；
- 正常失败不会被记成 Scheduler error；
- 不确定中断不会重复执行不可逆点击；
- 最终画面回到安全场景，Kernel idle，运行权交还工程。
