# 凡修 data-annotation 闭环与浮动模板案例

本文沉淀 `#204 小助手清单` 的真实调试经验：固定坐标只能解决首屏局部按钮，滚动列表和动态条目必须使用“场景身份 + 滚动容器 + 父标题锚点 + 子控件模板”的组合；每次点击都必须形成可重复执行的闭环。

术语遵守 [凡修 data-annotation 命名约定](../architecture/凡修data-annotation命名约定.md)：业务场景用 `scene`，截图和资产树底层帧结构才用 `frame`，`view` 只作旧兼容。

同类思想也适用于 `#69 日常` 的任务块模板：日常列表项应作为滚动容器中的浮动条目处理，而不是按固定屏幕位置写业务逻辑。

## 1. 闭环幂等

GUI 自动化里的“点击成功”不能只等于“发出了 click”。一个动作至少要落到以下闭环结果之一：

- 命中明确结果帧，例如 `#205 小助手详情`，再点击“点击屏幕继续”并确认回到 `#204`。
- 命中明确失败/无事项帧，例如 `#208 当前没有可执行的事项`。
- 等待完整保底窗口后仍停留在原场景，例如 `#204`，记录为 `no_popup`。对 `日常_助手` 来说，这不是失败，而是已处理过/无弹窗的正常成功态。
- 进入未声明场景、场景识别失败或控件消失时，中断并报告缺失诊断，不用猜测成功。

对 `#204` 前三个执行项的经验是：

- `道义秘库助手` 的第一个执行按钮和遮挡文字可能重叠，首屏可用固定 shape 点击，但点击后不能立刻继续。
- 点击后等待一个短窗口，优先捕获瞬时 `#208`；它出现很快，错过后不能反推没有出现。
- 同时等待 `#205` 详情帧；如果出现，就点继续并确认回到 `#204`。
- 等待结束还在 `#204`，才把结果标为 `no_popup`，作为幂等闭环的一种成功状态。

这个模式让同一个执行项可以反复调用：已执行过时通常得到 `#208` 或 `no_popup`，未执行过时可能进入 `#205`，二者都能回到稳定清单页继续下一项。

这里的等待窗口非常关键：`no_popup` 不是“立刻没弹窗就算成功”，而是“给游戏足够反应时间后仍没有弹窗”。游戏可能卡顿几秒才出现结果页或提示页，所以 `日常_助手` 的默认等待窗口应保持 10 秒量级。维护时不要恢复 1 秒快速收口，也不要把 `no_popup` 当成未确认失败；否则已处理过的助手项会被错误重试或阻塞整组闭环。

完整小助手的正常路径应该连续留在 `#204` 内执行：领完仙府资源后继续在清单里向下滚动查找弟子相关功能，执行完所有助手项后再统一返回 `#69 日常`。代码里的分组只是实现组织，不代表运行时要退出再进入。`returned_daily` 只作为兜底收口：如果某个条目确实把游戏带回 `#69`，才重新打开小助手清单继续，不能把“每组执行后退出再进”当成标准流程。

## 2. 浮动模板

滚动列表里的业务项不能用绝对坐标表达。正确建模方式是：

1. 标注滚动容器，例如 `滚动窗口`，只用于拖拽和限制 OCR 搜索范围，不参与场景身份。
2. 为一类条目标注父 shape，例如 `神物园助手`、`仙府资源小助手`。
3. 在父 shape 下标注子 shape，例如 `标题`、`执行`、`领取`。
4. 运行时在当前截图 OCR 中定位父标题中心点。
5. 用模板里的相对偏移计算目标按钮：

```text
actual_button_center =
  actual_title_center + (template_button_center - template_title_center)
```

这样 `仙府资源小助手/领取` 不需要额外保存一张已经滚动到该项的专用帧。它和 `神物园助手/执行` 属于同一种条目布局，只要模板里父标题和子按钮的相对关系稳定，就能在任意滚动位置复用。

## 3. 场景身份与列表内容分离

`#204 小助手清单` 的场景身份应该来自稳定页头或固定外框，不能把滚动窗口内容纳入场景身份：

- 滚动窗口内的条目随滚动和业务状态变化，不适合作为页面锚点。
- 业务项标题适合作为“当前列表里是否看见目标”的搜索条件，不适合作为 `#204` 是否成立的判断条件。
- 如果当前根本不在 `#204`，不能按 `#204` 的固定坐标点击；必须先通过 `go_scene` 回到目标场景。
- shape 匹配和场景匹配要同时成立。shape 是“在当前场景里的控件”，不是跨场景绝对坐标。

## 5. 基础设施启发

pyxllib 的旧 `anlib.py` 和新 `pyxllib.autogui.behavior_tree` 已经具备这套抽象的基础。

旧 `anlib.py` 中：

- `AnShape / AnView / AnRegion` 已表达父子 shape、截图、OCR、点击、拖拽等能力。
- `AnView.create_sub_view(sub_view_loc, anchor_shape_loc, det_shape)` 已经是“静态模板 + 动态锚点”的早期实现；注释里明确说明它用于滚动窗口中元素的动态定位。
- `ActivityWatchParams.activity_ignore_regions` 已有“画面变化比较时忽略局部区域”的思想，和遮挡不参与滚动哈希属于同类需求。

新 `pyxllib.autogui.behavior_tree` 中：

- `View` 表示静态帧。
- `Shape` 支持 `children()` 和 `descendants()`，适合表达父条目和子控件。
- `ActionPlanner.shape_center()` 可把标注归一化坐标转成帧内像素中心。
- `ShapeMatchPlanner` 处理图像/OCR 匹配角色。
- `Runtime.load_shape()` 和 `ActionPlanner.drag_shape_content_*()` 已有滚动容器抽象。

缺的不是概念，而是把旧 `create_sub_view` 的经验迁移到新版轻量模型中，形成一个业务无关的“浮动模板定位”示例或工具函数。推荐后续沉淀为类似接口：

```python
resolve_child_by_floating_anchor(
    view,
    parent_title="仙府资源小助手",
    anchor_child_title="标题",
    target_child_title="领取",
    observed_anchor_center=(x, y),
)
```

它只负责几何变换，不负责 OCR、截图或点击。业务 Runtime 负责在滚动窗口内找 `observed_anchor_center`，再交给该工具计算目标子控件中心。

## 6. 实现准则

- 能用父子 shape 表达的，不在业务代码里散落固定偏移。
- 能用标题 OCR 锚定的，不用整条条目图像强匹配动态内容。
- 首屏固定按钮可以直接点，但点击后也要走同一套结果闭环。
- 对浮动按钮，子 shape 命名应保持通用，例如父级 `神物园助手` 下叫 `执行`，父级 `仙府资源小助手` 下叫 `领取`，避免 `执行-神物园助手` 这类难复用命名继续扩散。
- `no_popup` 是 `日常_助手` 的正常成功态：它表示等待完整窗口后没有弹窗且仍在 `#204`，通常说明该小助手项今天已处理过。不要把它当失败，也不要省略等待窗口。
- 完整助手应优先保持在 `#204` 连续执行。跨分组开始前可以做“仍在 #204”的确认；只有实机已经回到 `#69` 时才恢复重进，不能主动割裂成“仙府资源一组退出、弟子功能一组再进入”。
- 新版 `#204 小助手总览` 的 `一键执行` 已作为统一入口覆盖 `日常_游历`、`日常_妖王来袭`、`日常_妖族袭城`、`日常_灵祖`、`日常_灵塔`、`日常_双修`，这些旧独立作业不再单独调度。未明确纳入新版小助手的能力，例如 `日常_每日副本`，仍需独立业务完成证明。
- 真实验收必须走 Runtime/行为树公开入口，并用当前 MuMu/ADB 画面验证，不能用单元测试或构造截图冒充。
