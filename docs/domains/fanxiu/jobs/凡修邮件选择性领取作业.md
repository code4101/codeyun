# 邮件选择性领取作业

## 业务目的

`邮件_选择性领取` 以当前 Runtime 邮件列表和附件事实为准，领取明确应领的资源，保留法则与当前祈愿策略要求保护的资源，并清理已经完成且允许删除的邮件。

幂等终态不是“本进程曾经领取过”，而是当前邮件列表中已没有应领附件、没有可删除垃圾，所有剩余附件都能由现行业务策略解释。用户、其他进程或上次中断前完成的动作都通过同一个当前终态自然对齐。

## 奖励身份与策略

1. 优先使用版本化静态 Item 图鉴解析奖励名称、类型和业务价值。
2. 服务端热更新可能先于静态导出出现。静态图鉴缺行时，只读客户端已经加载的 `DBMgr.ConfigDic[Item.Item]`，补充道具类型、子类型、活动条件、图标和分解产物等权威结构。
3. Runtime 配置存在不等于可以领取。只有显示名称已知，或结构命中明确的安全策略类，才视为完成策略分类；法则仍拥有最高保护优先级。
4. 当前支持的无名称结构兜底仅限带 `ActivitybaseId` 条件的临时活动材料。其他无名称奖励继续失败关闭，不能按邮件标题或相似 ID 猜测。
5. 同封邮件已经明确含有“潜修心得”等必领资源时，未知陪同附件不能阻断整封邮件；同封明确含法则时仍必须锁定。

## 真正未知的升级闭环

当静态图鉴、当前 Runtime 配置和现有策略类都无法唯一解释附件时：

- Task 不领取、不推进次日 `next_time`，保留到期状态供幂等重试；
- 错误携带邮件 ID、奖励 type/code、Runtime 名称 ID、类型、子类型、图标和活动条件等最小证据；
- 按证据指纹去重后，将一次 Codex CLI 工程协助放入后台队列；相同未知在冷却窗口内不会重复拉起 Agent；
- Agent 只能调查并把可靠结论收敛回正式解析代码、测试和契约，不能点击游戏或替代领取策略；证据不足时继续失败关闭。

因此“未知”是显式、可恢复的工程状态，不是永久静默留存，也不会把 AI 变成正常邮件决策器。

## 调度边界

Scheduler 只负责按 `next_time` 提交作业。邮件完成判据、失败关闭、未知升级和下一次时间均由 Task 业务层负责；只有完整终态才写入下一日时间。
