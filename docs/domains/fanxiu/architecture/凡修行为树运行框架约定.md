# 凡修行为树运行框架约定

> Last Updated: 2026-08-28
> 本文只定义 Kernel、Cell、运行权与 Scheduler 边界。
> Job 状态与时间语义见 [凡修 Job 运行与调度语义](./fanxiu-job-scheduling-semantics.md)；GUI 与场景图见 [凡修 GUI 场景地图与图模型约定](./凡修GUI场景地图与图模型约定.md)。

## 唯一模型

```text
工程 / AI / 用户
  -> Kernel 外 Scheduler / Dispatch Arbiter
  -> 一个长期存活的 Jupyter Kernel
  -> 普通 Python Cell
  -> Kernel 内 runtime / ctx / task / guard / generator
```

- Kernel 是唯一执行实体，底层必须是真实 `ipykernel + jupyter_client`。
- Cell 是唯一外部执行原语；调试代码和正式 Job 使用同一提交协议。
- Scheduler 在 Kernel 外，只决定运行权、到期选择、优先级和 Cell 提交。
- OCR、ADB、shape、scene、行为树和业务状态都在 Kernel 内，不形成第二协议。

`kernel.task(task_type, payload)` 只构造包含 `run_task_cell(...)` 的普通 Cell。禁止 Kernel 内队列、JSON 控制文件、resident runner 或第二执行器。

## Kernel API

Kernel 对外只有四个原语：

| 原语 | 语义 |
| --- | --- |
| `execute` | 串行执行一个 Cell |
| `interrupt` | 中断当前 Cell，保留 namespace |
| `restart` | 替换 Kernel、清空 namespace、重新 bootstrap |
| `shutdown` | 终止 Kernel |

连续 Cell 共享原生 IPython namespace、execution count、stdout、result 和 traceback。`restart` 后旧 connection 与旧客户端立即失效，不得重连或重放旧 Cell。

`wait_for_ready` 只用于 Kernel 启动验收。Kernel busy 时不能回答 readiness 请求是正常状态，不得据此 restart。

### 精确中断契约

中断必须绑定当前 `execute_request.msg_id`：

```text
读取 active_cell_msg_id
  -> 发送原生 Jupyter interrupt
  -> 等待同一 msg_id 的 terminal idle
  -> 返回 interrupt_confirmed=true
```

- 控制通道自己的 busy/idle、其它 Cell 的 idle、Runtime JSON 投影都不能证明目标 Cell 已停止。
- `interrupt_request` ACK 只表示请求被接收，不能直接作为成功终态。
- ACK 后目标仍活跃时，可通过 `KernelManager.interrupt_kernel()` 有限补发同一种原生中断；两条路径共享一个默认 15 秒确认预算。
- `KeyboardInterrupt` 由当前 Cell 所有者写成 `run_status=interrupted` 后继续向 Jupyter 传播。
- 超时必须明确失败；禁止把 interrupt 降级成 restart。
- Kernel `idle / busy / dead` 与 Job `run_status` 是两套正交状态。

内部优先级抢占可以直接调用这个原语。面向用户的“停止自动化”必须使用下节的运行权交接，不能只发裸 interrupt。

## 运行权

`job_group_enabled` 是唯一运行权开关：

| 模式 | 值 | Scheduler | AI / 用户 |
| --- | ---: | --- | --- |
| 工程 | `true` | 自动提交到期 Job Cell | 不提交 GUI Cell |
| AI | `false` | 保持心跳，不提交工程 Cell | 可提交普通 Cell |

禁止增加 observe、巡检模式、自动派发开关或其它平行状态。

### 交出 GUI 的统一操作

从工程切到 AI，或用户明确要求停止自动化时，只走一个入口：

```text
原子写 job_group_enabled=false
  -> 读取当前 attempt
  -> 若为工程 Cell，精确 interrupt
  -> Cell 内写 interrupted 终态
  -> CAS 结束同一 Scheduler attempt
  -> 返回 Kernel idle + interrupt_confirmed
```

先撤销派发权，再中断。顺序不可颠倒，否则恢复后的 `next_time` 可能让同一 Job 立即重派。

- 普通“切到 AI”只中断带 Scheduler task id 的工程 Cell，不误杀已有 AI/人工 Cell。
- 显式 CLI `interrupt` 表示用户取得 GUI，允许中断任意当前 Cell，并保持 AI 模式。
- Runtime 与 Scheduler attempt 的终态只允许对同一 `attempt_id` 做 CAS 写回；迟到调用方不得覆盖新 attempt。
- 恢复工程模式前必须确认 Kernel idle；AI 调试结果不能替代正式 Scheduler attempt 验收。

## Scheduler 边界

常驻链路只有：

```text
CodeYun lifespan
  -> watch-doctor
  -> 读取 Scheduler plan
  -> 选择一个到期 Job
  -> 提交一个普通 Cell并同步等待
  -> 写回 attempt 终态
```

Scheduler 负责 `next_time` 到期比较、优先级、attempt CAS、Kernel 代码代际检查和模拟器资源仲裁。它不负责 OCR、点击、导航、generator 推进、业务周期或业务消息解释。

共享调度文件必须在文件锁内合并；调用方只能写自己持有的 attempt 字段，不能用旧整表覆盖新状态。严格更高级 Job 到期时可中断当前低级工程 Cell；相同级别不互相打断。旧 Cell 确认终止后才允许提交下一 Cell。

## Cell 与 Job 边界

- 一个 Job Cell 是一次完整 attempt。
- generator 栈、`job_status`、scene cursor 和选择意图只活在当前 Cell。
- interrupt、restart、Kernel dead 或执行进程丢失都会使 attempt 整体作废。
- 新 attempt 从稳定入口重新观察并整单运行，不恢复旧步骤或中间页面意图。
- 登录、遮挡处理、`goto_view(34)`、成功离场和失败恢复都属于具体 Job；通用包装层不得加入固定业务前后置动作。

## 只读巡检

游戏状态巡检在 Kernel 外只读游戏 Runtime，不截图、不 OCR、不点击、不提交 Cell。命中业务事实时只原子写目标 Job 的 `next_time=now`。

- 工程模式自动巡检。
- AI 模式暂停自动巡检；按需单次只读查询不改变运行权。
- 缓存失效后的重建必须服从资源仲裁，不能退化成 GUI 操作。

具体实现和页面契约见 [凡修 data-annotation 自动化 Runtime 与 Scheduler](./凡修data-annotation自动化Runtime与Scheduler.md)。

## 禁止模式

- `exec + dict` 假 Jupyter namespace。
- 为每个调试步骤新增 API。
- Kernel 内 Scheduler、来源锁、manual queue、claim/requeue 或业务 JSON 队列。
- 用 JSON 文件模拟 interrupt/restart/shutdown。
- 把 interrupt 实现成 restart。
- restart 后跨代重连或重放旧 Cell。
- 跨 Cell 保存 generator、业务步骤或 scene 游标。
- 从遗留确认页、进度页、结果页恢复旧动作意图。
- 新旧两条 Cell 提交路径并存。

## 验收

1. Cell A 写变量；Cell C 可读取。
2. Cell B 持续运行；interrupt 后只认 B 自己的 terminal idle，A 的变量仍在。
3. 控制通道 idle 和其它 Cell idle 不会误清 B。
4. 用户取得 GUI 时，工程派发权先关闭，旧 attempt 终止后无自动重派。
5. restart 后旧变量和旧连接失效，runtime / ctx 已重新加载。
6. `kernel.task(...)` 只产生普通 Cell 源码。
7. Scheduler、Runtime 与 Kernel 状态可以分别观察，不互相冒充权威事实。
