# 凡修天地弈局功能逻辑

> 最后更新：2026-08-28。本文按当前代码描述天地弈局的活动识别、结构化数据、奖励领取与兑换目标对弈能力；运行现场状态不属于本文的长期契约。

## 1. 功能边界

天地弈局属于统一玩法榜家族 `gameplay_rank`，当前能力状态为 `implemented_exchange_target_loop_pending_asset_contract`。这表示生产目标循环已经装配，但 #680 配置/次数控件与新版结果浮层的正式资产契约尚未完整，不能视为真实业务闭环。系统负责：

- 从完整 Runtime 日程识别精确 occurrence，并生成每日对账与 10:05 活跃检查点。
- 在数据库中建立可被统一 Exchange API 查询的活动实例。
- 独立采集兑换宝阁、棋符钱包和棋局榜单；单项失败不空覆盖其它有效事实。
- 遍历“修炼、夺分”两个任务页签，领取 Runtime 明确授权的奖励。
- 用 Runtime 选择精确棋点，按跨数配置五个自动对弈选项，并围绕统一兑换计划的“收尾道具”货币缺口执行有界反馈批次。
- 每批复用公共安全计数与公共反馈规划器，回读绝对钱包、重新采集商店并重新规划普通棋点；天元一经 Runtime 选定则在本次循环内保持锁定。
- 通过玩法榜公共页面展示个人榜、宗门/位面榜、棋符和兑换宝阁。

当前仍不负责自动购买兑换宝阁商品或活动结束后的兑换购买收尾，也不把分组/赛程面当成可操作棋盘。跨服目标循环会按既定配置使用仙弈盒、妙手技和四倍棋符来生产足够的兑换货币；这与“自动购买商品”是两个不同事务。

## 2. 活动身份与版本契约

| 阶段 | Runtime `activityId` | `activityType` | 是否可操作 | 榜单 ID | 商店 / 币种 |
| --- | ---: | ---: | --- | --- | --- |
| 本服预赛 | `8090001` | `9` | 是 | 个人 `90101`；宗门 `90102` | `90000` / `11` |
| 跨服分组/赛程 | `8090002` | `13` | 否 | 无独立物化 | `90001`，不采集 |
| 8 跨棋局 | `8090004` | `17` | 是 | 个人 `90808`；宗门 `90813` | `90002` / `13` |

`8090002` 与真实 8 跨棋盘时间重叠，只表示分组/赛程面。生命周期层不为它生成 `daily_reconcile` 或动作检查点，避免同一账号弈力被两个身份重复消费。

识别以标准化日程中的 `activityType + activityId` 为主，`AlliancePlayChessActivityVO` 仅用于旧快照兼容。活动实例仍使用通用 occurrence 身份：

```text
instance_key = runtime_id + activity_id + start_at + end_at
```

## 3. 结构化数据生成链路

```text
Runtime 完整日程
  -> ranking_lifecycle 识别 tiandi-yiju occurrence
  -> ranking_reconcile 解析该 occurrence 的精确榜单、商店与币种契约
  -> upsert Exchange activity 静态实例
  -> 显式 collect 时分别读取商店、钱包、棋局 manager
  -> 写 activity / shop / ranking 表
  -> 通用 Exchange API
  -> 玩法榜公共前端
```

### 3.1 存储封装原则

玩法榜、资源榜会高频轮换，数据库应采用“一个精确 occurrence 一行根记录 + 通用明细表 + JSON 扩展字段”的复合模型，而不是每种活动新建一组表，也不是把整页数据全部塞进一个 JSON：

- `FanxiuExchangeActivity`：每个精确活动实例一行，保存稳定、需要索引的公共字段，例如 family/type、Runtime 身份、四个绝对时间、跨数、币种、当前/累计资源和事实新鲜度。
- `FanxiuExchangeShopItem`：每个 occurrence 下每件商品一行，支持商品唯一约束、购买进度更新、排序和查询。
- `FanxiuExchangeRanking`：每个 occurrence、scope、名次主体一行，支持完整榜单、分页、本人/末位检索和不空覆盖。
- `FanxiuExchangeActivityObservation`：保存同一 occurrence 的不可变时间序列快照；根记录表示最新投影，observation 表示首次、运行中、正式结束和最终封账等历史事实。
- `FanxiuRankingLifecycleCheckpoint`：独立保存 occurrence 的每日对账和动作检查点，不把调度过程塞进活动 JSON。
- JSON 字段只承载低频、可扩展、活动专属且不需要跨行查询的内容，例如 `resource_strategy`、原始 evidence、adapter 专属 payload 和明细行 `raw_data`。

“一次活动一行”中的活动必须指精确 occurrence，不是一个活动类型永久一行，也不是 Runtime 中每个依附 VO 各占一行。根活动、子赛程和榜单/商店依附模块要先还原层级；只有拥有独立生命周期和业务事实的 occurrence 才建立根记录。

当前根模型已经以 `instance_key` 作为唯一身份，并将 `family / runtime_id / game_activity_id / prepare_at / start_at / end_at / close_at` 提升为正式字段；日期只保留为展示投影。V108 数据库迁移会回填旧实例、移除旧的日期组合唯一约束，并在保持根记录 `id` 不变的前提下保留商品、榜单和 observation 外键。活动专属复杂数据写入 `instance_data`，不再挤入身份字段或另建专属根表。

Scheduler 仍只暴露“玩法榜、资源榜”两个顶层复合 Task。父 Task 每次从日程发现具体 occurrence，并把它作为一个完整活动实例处理；云梦、魔道、天地弈局、丹道等 adapter 是该实例的行为差异，不是额外 Scheduler Task 或额外数据库主模型。

### 3.2 为什么过去前端没有“天地弈局”数据

旧逻辑只在生命周期额外身份中发现天地弈局，并将其标记为 `observed_unhandled`；`EXCHANGE_ACTIVITY_SPECS` 没有公开 spec、精确榜单绑定和采集 adapter。因此 `daily_reconcile` 只能留下 retained 检查点，不能生成 `FanxiuExchangeActivity` 结构化实例。前端只是数据库投影，缺行是后端物化链缺失的结果。

当前注册表已经把 `tiandi-yiju` 纳入公共玩法榜类型，并由 occurrence adapter 解析本服/8 跨各自的榜单、商店和币种。前端下拉项只消费这条公共数据链，不自行保存活动事实。

### 3.3 静态播种与动态刷新

00:30 `daily_reconcile` 首先根据日程和注册表写入活动身份、日期、跨数、榜单 ID、商店 ID、币种等静态事实。即使棋局 manager 尚未初始化，这一步也应保留实例，不能因动态读取失败而让前端完全看不到活动。

显式采集由 `collect_and_store_tiandi_yiju_activity` 完成：

1. 要求数据库中已有精确的 `tiandi-yiju` 实例。
2. 按 `game_activity_id` 选择商店和币种，不按页面文案猜测。
3. 读取商店条目和购买进度；商店快照不完整则拒绝写入。
4. 独立读取钱包中的当前棋符与累计棋符。
5. 尝试读取 `AllianceplaychessMgr` 榜单；该 manager 不可用或内部缓存不一致时只保留旧榜单。
6. 通过通用 Exchange 持久化函数更新活动和商店；仅在榜单快照完整时替换榜单行。

### 3.4 新鲜度与失败语义

| 事实层 | 成功时 | 失败时 |
| --- | --- | --- |
| occurrence / 静态契约 | 写入或更新活动实例 | 身份不唯一时失败关闭，不猜测 |
| 商店 | 更新 19 类商品、限购与已购进度 | 不完整则本次采集失败，不写半份商店 |
| 钱包 | 更新当前棋符、累计棋符 | 不把旧值伪装成新值 |
| 榜单 | 替换个人榜与宗门榜 | 标记 `retained`，保留旧榜，不写空榜 |

`refresh_status.currency/shop/rankings` 是三个独立状态。静态播种且尚未动态采集的实例不得默认显示为 fresh；页面必须按状态展示“已更新、保留或不可用”。

## 4. 棋局 Runtime 读模型

`instrumentation/tiandi_yiju.py` 只读已加载的 `AllianceplaychessMgr`，不发游戏指令。主要输出：

- 当前弈力、最大弈力、单局消耗和自然可玩局数。
- 入口层与棋盘层的个人积分缓存、个人排名、宗门积分和宗门排名。
- 棋点列表、己方宗门 ID、己方棋点 ID。
- 个人榜和宗门榜行。
- 三个持久化选择：四倍棋符、妙手珠、自动使用仙弈盒。

本服棋局没有直接暴露“本宗 ID”，读模型以入口宗门积分在宗门榜中唯一匹配来反推。候选不是恰好一个时抛错；这能发现入口缓存与榜单缓存不同步，而不是误标 `is_self`。

动作后验证要求：前后事实完整、三个资源开关均关闭、单局消耗不变、体力迁移符合自然消耗（允许跨越一次自然恢复边界）、个人积分增加或已有明确成功终态、宗门积分不倒退。

## 5. 任务奖励通用事务

天地弈局任务由 `QuestMgr.Model.QuestData.taskInfoMap[3]` 提供状态，静态 `ActiveTask` 只负责说明任务版本、页签和顺序：

- `subType=6`：修炼页签，场景 `684`。
- `subType=7`：夺分页签，场景 `683`。
- 本服 Runtime `8090001` 对应任务活动 `8090001`。
- 8 跨 Runtime `8090004` 对应任务活动 `8090002`。

任务 reader 会对每个逻辑档位选择唯一的在线任务版本；缺档或同时出现多个版本均失败关闭。首次完整读取会缓存当前进程的 live spec，单次领取后可走精确 fast reader，但进程身份变化或快速结果不完整时自动退回完整读取。

领取动作复用玩法榜通用多页签事务：

1. 从活动主页进入任务页。
2. 依次访问“修炼、夺分”全部顶部页签，不能只处理当前页。
3. 只点击任务行/标题/进度区域，不点击奖励道具图标。
4. 每次只领取一个 Runtime 授权的 task ID。
5. 点击后必须验证该 ID 进入已领集合，且待领列表只减少这一项。
6. 全部页签处理完后返回活动主页。

若误点奖励图标打开道具详情，通用退出方式是快速点击左下角背景面关闭弹窗，再继续任务行操作。这是 GUI 操作约定，不改变 Runtime 的授权与复验规则。

## 6. 10:05 下棋检查点

生命周期每天在可玩 occurrence 的活动窗口内生成 `tiandi_yiju_active_1005`。执行流程是：

```text
读取完整日程并精确对齐 occurrence
  -> 进入天地弈局主页 #677
  -> 领取修炼、夺分两个页签奖励
  -> 进入棋盘 #678
  -> #678[弈局] 打开 #686 精确棋点列表
  -> Runtime 选择离天元最近、己方占比分最高的可攻棋点
  -> 按 Runtime piece_id 唯一对齐 #686「棋点NNN-*」Shape
  -> [跳转] 并等待异步镜头过渡到 #679
  -> 打开 #680 自动对弈设置
  -> Runtime 读取五个配置状态，只点击差异项并复验
  -> 从统一 exchange_plan 读取「收尾道具」required_new_currency
  -> 复用通用试探/半量/稳定收尾批次算法，天地弈局每批上限 100
  -> 每批后回读绝对钱包、重新采集商店、重算缺口和棋点
  -> 收尾道具目标满足后退出并返回世界 #34
```

棋点策略只消费 `read_tiandi_yiju_recommended_target()` 的结果，不再从棋盘 GUI 猜“哪个点可点”。若目标四方积分全为 0，先只挑战 1 次完成占点；非天元棋点在批后变为己方时，返回棋盘重新规划。天元仍可作为持续挑战目标。任何页面终态、钱包、商店、资源开关或棋点事实不明确时均失败关闭，不用固定坐标或“看起来成功”替代验证。

参数配置复用 `tiandi_yiju_config.py`：公共三项“自动使用仙弈盒、失败不中断、跳过动画”始终开启；妙手技与四倍棋符只在跨服局开启，本服局关闭。2026-08-28 的 Runtime-GUI 对齐已真实证明 `chooseStateDic[4]=自动使用仙弈盒`、`[3]=妙手珠`、`[2]=四倍棋符`；连续配置项 `[5]/[6]` 当前投影为“失败不中断/跳过动画”，仍需在真实配置页逐项复验后才能晋升为完整运行验收。

分批次数不在本模块重写滑杆算法，只调用 `set_tiandi_yiju_round_count()`；兑换缺口不在本模块重算，只读取统一 `exchange_plan.target_budgets["收尾道具"].required_new_currency`；批次大小不另写算法，只复用活动无关的 `plan_feedback_batch()` 并叠加天地弈局 100 次硬上限。云梦保留的同名规划入口只是兼容包装，不再是天地弈局的依赖层。

2026-08-28 的 8 跨实例真实验证补充了四条运行约束：

- #66 已由 Runtime 精确对齐当前活动卡片时，卡片入口不再依赖表头 OCR 必须出现“今天”或当天日期；表头只服务日历格定位。
- 跨服本宗动态 ID 由入口宗门积分精确榜单行与“当前棋路排除显式盟友后的占领者”共同证明；`allianceRank` 会独立刷新，不能参与动作授权。真实实例最终对齐本宗 `22077`、配置槽位 `1004`，显式盟友为 `22028`。
- 新版结果页标题为“对弈”，按钮为“确认”，不再包含旧版身份词“数据统计”。旧 #681 与新版结果浮层必须各自完成“识别终态、点击各自确认按钮、等待返回设置页”的完整事务，不能在识别新版浮层后仍固定点击 `#681[点击屏幕继续]`。
- 离开棋盘后可能出现只有“前往讨伐”业务按钮的推荐遮罩；正式流程只点击已验证的左上遮罩空白关闭，不得点击“前往讨伐”。

本次研发单局从个人棋符 `19590` 增至 `58709`，结果页明确给出个人棋符 `+39119`、阵营棋符 `+38835`、体力消耗 `1`。弈力观测为 `22→22`，对应单局消耗 `1` 与等待期间自然恢复 `1`，符合允许一次自然恢复边界的迁移模型；该证据只证明一次手工研发事务，不能替代当前生产 target loop 的多批真实验收。生产 checkpoint 在 #680 五个缺失 Shape 与新版结果 scene/“确认”Shape 接入前，会在任何游戏导航、领奖和资源消耗动作之前失败关闭。

## 7. 页面投影

前端 `top-activity/page.vue` 将 `tiandi-yiju` 放入玩法榜下拉框，并复用 Exchange ranking 公共页面：

- 主榜为个人榜。
- 对比榜 scope 为 `alliance`，标题显示“宗门/位面排名”。
- 页面从通用 Exchange API 获取活动列表、选中实例、棋符、商店和榜单。
- collector 只保存当前 occurrence 的真实玩家行；奖励边界、本人、榜尾与独立奖励档位由公共 ranking key-point 投影统一生成，天地弈局不得维护第二套 guard/self/last 算法。
- 页面不维护独立的天地弈局数据库，也不从直播画面推导持久事实。

因此排查顺序应是：先查 occurrence 是否识别，再查 Exchange activity 是否播种，再查各事实层的 `refresh_status`，最后才看前端选择和渲染。

## 8. 当前证据与限制

2026-08-27 的真实采集已证明本服实例可持久化：当前棋符 `66`、累计棋符 `66`、商店商品 `19` 条，商店与钱包状态为 updated。同期棋局 manager 的入口宗门积分/排名与榜单缓存无法唯一对齐，因此榜单按契约保留为 retained；这不是前端丢数据，也不影响商店和钱包落库。

当前仍有以下限制：

- registry 是天地 occurrence 的 shop/rank 唯一映射权威，并同时校验 `activity_id + cross_count`；登记的 rank activity 缓存未加载或与棋局 manager 不一致时只能 retained，不能按相邻 ID、跨数或棋盘积分强行拼榜。
- 天地弈局专用代码已离线接入统一收尾道具目标、公共五开关规划、公共安全计数与公共批次规划，相关专用测试通过；尚未在真实多局托管中验收，不能把离线装配当成业务完成。
- 旧的固定“己方中心棋点候选”自然单局任务旁路已经删除；生产入口只能通过 Runtime 推荐棋点与统一目标循环。
- 新版“对弈 / 确认”结果浮层目前没有独立正式 scene/shape 契约。真实验收前必须补齐或找到已有可复用资产，并把确认动作与返回 #680 作为同一事务；禁止用 OCR 文本坐标临时点击。
- `chooseStateDic[5]/[6]` 的“失败不中断/跳过动画”语义仍需一次逐项 Runtime-GUI 差分复验。
- 兑换宝阁已能通过现有导航打开，但尚未把该页面补成独立、正式的资产树 scene 契约。

### 9.2 新版结果浮层

旧 #681 `天地弈局单次对弈结果` 是全屏“数据统计 / 点击屏幕继续”，应保持原样作为旧结果分支和负样本；不能把新版浮层硬塞进 #681。

新版结果目前只适合提出一个新增 scene 候选：暂定标题 `天地弈局自动对弈结果`，并新增本 scene 内的 `确认` Shape。scene 编号、文件名、坐标和身份锚点均没有现存静态帧支持，全部标记为“需唯一操作槽采样”，不得预填。采样后允许的字段范围是：新 scene 的 `id/title/filename/source/verificationStatus`，稳定身份 Shape 的 `title/x/y/w/h/ocrText/ocrMatchMode/isSceneIdentity/sceneIdentityRole`，以及 `确认` 的 `title/x/y/w/h/description/sceneJumpTarget`。其中：

- “对弈”和“确认”文本过于通用，不能单独充当 scene 身份；必须从新鲜帧选择至少一个结果层专属稳定锚点，并以 #680、#681 和相邻弹窗作负样本。
- 只有真实点击 `确认` 后稳定回到 #680，才允许把 `sceneJumpTarget` 记为 #680；采样前保持空值。
- 同帧验收必须证明新版 scene 命中新帧、旧 #681 不命中新帧、新版 scene 不命中 `0681.png`，且 `确认` 框只覆盖按钮本体。

### 9.3 `chooseStateDic[5]/[6]` 差分方案

现有可追溯证据只真实证明 `[4]=自动使用仙弈盒`、`[3]=妙手珠`、`[2]=四倍棋符`。源码把 `[5]/[6]` 投影为“失败不中断/跳过动画”，依据只是配置项连续顺序；现有 entry 的诊断 JSON/日志中没有找到逐项差分记录，因此二者仍是待证假设。

待上述两个开关 Shape 获得明确授权并完成原帧叠框复核后，由唯一操作槽执行可逆、零挑战的最小实验：

1. 在同一 Runtime 进程代际、同一 #680 scene 记录初始 `chooseStateDic` 与同帧截图；要求键 5、6 都可读。
2. 只点击 `对弈失败时不中断自动对弈开关` 一次；等待界面稳定后回读。通过判据是只有键 5 翻转，键 6 和其余键完全不变，且同帧只有目标开关视觉状态变化。
3. 再点同一 Shape 一次恢复；字典与 GUI 都必须精确回到初值。
4. 对 `跳过动画开关` 重复同样过程；通过判据是只有键 6 翻转并可精确恢复。
5. 全程禁止点击 `对弈`、改次数、领取或兑换。任一步出现多键变化、键缺失、scene 变化或 GUI/Runtime 不一致，立即保留现场并停止，不晋升语义。

一次合格证据必须同时保存进程 `pid/process_start_ticks`、操作前后字典、操作前后同帧、目标 Shape 标题和唯一 delta；不能用“两项同时为关闭”或控件上下顺序替代逐项差分。

## 10. 真实验收晋升清单

只有以下项目全部留下同一 occurrence、同一进程代际的真实证据后，能力状态才可从 `implemented_exchange_target_loop_pending_asset_contract` 晋升：

1. 资产预检：#680 的五个配置开关及次数区域、减少、滑块、增加 Shape 全部存在；新版结果浮层有独立正式 scene 与“确认”Shape，并与旧 #681 互为负样本。生产 checkpoint 在预检失败时必须保持零导航、零领奖、零挑战。
2. Runtime-GUI 配置差分：逐项证明 `chooseStateDic[5]/[6]` 的语义；跨服实例最终五项均符合策略，本服实例的妙手技与四倍棋符关闭。只点击差异项，回读后无剩余 action。
3. 精确棋点：生产入口消费 `read_tiandi_yiju_recommended_target()`；#686 点击的 Shape 前缀与 `piece_id` 唯一一致，整条动作轨迹不出现固定“己方中心棋点候选”。
4. 特殊棋点规则：四方总积分为 0 的目标只设置 1 次；普通棋点每批后重新规划；天元一旦被 Runtime 选中，后续批次复用同一 recommendation。
5. 次数事务：公共整数计数器设置值与 Runtime/OCR 回读一致，天地单批不超过 100；无法唯一读数或校准时不点击“对弈”。
6. 结果局部事务：旧 #681 只消费“点击屏幕继续”；新版结果 scene 只消费自己的“确认”，两者都必须等待回到 #680。裸 OCR 只能触发保留现场，不能授权点击。
7. 钱包对账：每批前后 `currency_type/source/pid/process_start_ticks` 不变；当前棋符与累计棋符增量均为正且完全相等。
8. 兑换反馈：每批后重新采集同一 `occurrence.instance_key` 的 shop/wallet，统一 `required_new_currency` 单调重算；planner 收到本批与上一批的精确产率样本，不复用其它活动或旧进程 measurement。
9. 业务终态：`required_new_currency == 0` 后不再制造挑战，正式导航回世界 #34；checkpoint 记录真实 completed，活动实例 refresh 状态、榜单投影和未来 `next_time` 均可回读。
10. 运行方式：真实验收只由唯一游戏操作者使用最小研发 Cell 逐段完成，最后再跑一次正式 checkpoint；不得用离线测试通过、Cell 正常退出或一次手工单局代替多批业务闭环。
