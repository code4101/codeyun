# 凡修统一榜单生命周期系统设计

> 最后更新：2026-08-27。天地弈局专项逻辑见[《凡修天地弈局功能逻辑》](./凡修天地弈局功能逻辑.md)。

## 1. 背景与目标

改造前，玩法榜、资源榜的采集、活动执行和结束收尾分散在活动专属 Job、页面 GET 物化、手动 collect 接口及少量生命周期代码中。相同的 occurrence 隔离、每日更新、奖励档次、榜单快照和最终封账被重复实现；魔道又单独存在一个“探查”Job，无法表达 00:30 对账、19:00 邮件/任务/探查和未来挑战属于同一期活动。

目标是建立两个按家族隔离、对外边界一致的标准作业：

- `ranking-lifecycle` / `ranking_lifecycle` / `玩法榜`：只处理 `gameplay_rank`。
- `resource-ranking` / `resource_ranking` / `资源榜`：只处理 `resource_rank`。

- 每天 00:30 枚举并处理全部相关玩法榜、资源榜 occurrence；同一时刻可以同时存在上一期结算、当期持续和下一期开启。
- 统一完成活动身份、奖励档次、榜单事实、商店/资源、策略和最终封账的状态投影。
- 允许活动 adapter 声明额外业务检查点；当前包括魔道 19:00、仙盟 10:00 与天地弈局 10:05。
- 魔道 19:00 在同一 occurrence 事务中依次处理邮件、任务奖励、天眼符补给和 `3×500` 探查。
- Scheduler 的榜单公共面只保留上述两个父 Job，每个家族各有且仅有一个绝对 `next_time` owner；活动专用能力只新增 adapter/checkpoint，不新增平行 Scheduler Job。

非目标：本期不自动执行魔道挑战事件；不把未开放时刻的保留数据宣称为实时榜单；不要求所有活动使用相同 GUI。

## 2. 设计审查

“一个 Job 调用所有活动函数”的直接实现存在严重耦合：采集失败会中断其它 occurrence，页面差异会污染调度器，魔道补符会让资源榜代码依赖储物袋，最终形成不可测试的巨型流程。

本设计只统一稳定的生命周期协议和运行权，保留以下正交维度：

| 维度 | 权威落点 | 生命周期 |
| --- | --- | --- |
| 规则定义 | `RankingLifecycleAdapterSpec` | 随代码版本 |
| occurrence 事实 | Runtime 日程全量快照 | 每次只读刷新 |
| 检查点状态 | 数据库 checkpoint 记录 | 跨 Job Cell |
| 执行命令 | 当前 Job Cell 内 adapter 调用 | 单次运行 |
| 业务快照 | Exchange activity/observation/ranking/shop 表 | 时间序列 |
| 展示投影 | 玩法榜/资源榜统一 API | 请求时只读 |
| 调度状态 | 两个父 Job 各自的 Scheduler `next_time` | 对应 family 最近一个未完成检查点 |

因此，修改魔道储物袋补符不会影响资源榜采集；一个 family 的异常和触发时间也不会污染另一个 family；新增一种榜单只需注册 spec/adapter，Scheduler 不需要理解任何活动文案。

## 3. 基础模型

### 3.1 Occurrence

一次活动由权威 Runtime occurrence 身份隔离：

```text
instance_key = runtime_id + activity_id + start_at + end_at
```

服内、跨服、多日活动和相邻期次不得共享 checkpoint 或进度。数据库已有 Exchange activity 行继续作为页面快照主体；`instance_key` 是生命周期层的精确运行身份，不用日期或名称猜测。

持久化采用复合模型：一个精确 occurrence 对应一行 Exchange activity 根记录，公共可索引事实使用正式列；商品、榜单和生命周期 checkpoint 使用通用明细表；活动专属策略、证据和低频扩展使用 JSON；同一 occurrence 的首次、运行中、正式结束和最终快照使用 observation 时间序列表。禁止为每个新活动复制专属表，也禁止把完整榜单、商品清单和调度过程全部压进根行 JSON。

Exchange activity 已以 `instance_key` 作为唯一身份，并正式保存 `family / runtime_id / game_activity_id` 与四个绝对时间；日期字段仅作页面派生投影。V108 迁移回填旧记录并移除 `activity_type + cross_count + start_date + end_date` 日期组合唯一约束，同日多轮或重叠子赛程可以各自拥有实例；旧根记录 `id` 保持不变，因此商品、榜单和 observation 子记录不需要改写业务外键。

玩法榜、资源榜仍各只有一个顶层 Scheduler Task；父 Task 内发现的每个具体 occurrence 是一个复杂活动实例。实例聚合生命周期、榜单、任务、商店、资源与策略，spec 声明 family 和公共契约，adapter 只实现活动差异。不得把每个活动 adapter 再注册成一级 Scheduler Task，也不得为每种活动复制专属根表。

### 3.2 Checkpoint

所有表象需求归约成同一基础概念：

```text
Checkpoint(instance_key, checkpoint_kind, business_date, due_at)
```

- `daily_reconcile`：每天 00:30，一天一个键；适用于玩法榜和资源榜。
- `exchange_tail_0030`：正式结束后的首个 00:30，且兑换页仍在 `closePanelTime` 前；首期由魔道、云梦的已验收 adapter 执行动态锁定资源收尾。
- `magic_active_1900`：魔道活动日 19:00；是否每日重复由 adapter 规则声明，首期按 occurrence 的正式执行日生成。
- `tiandi_yiju_active_1005`：天地弈局可玩 occurrence 活动日 10:05；领取全部任务页签奖励，并按统一兑换计划的“收尾道具”棋符缺口执行有界反馈批次。当前在 #680 与新版结果浮层正式资产契约完整前，于任何游戏导航和资源消耗动作之前失败关闭。
- 未来挑战：新增 `magic_challenge_*` 规则即可，不改变 Scheduler 或数据库模型。

检查点结果记录 `completed / retained / unavailable / blocked`、证据时间和可选 `retry_at`。这些是业务执行结果，不是 Scheduler 状态；每个父 Job 只消费自己 family 待办检查点中最早的绝对时间。

### 3.3 每个 family 一个 `next_time`

```text
全量 Runtime occurrence
  -> 各 adapter 生成候选 checkpoint
  -> 排除已完成 checkpoint
  -> 取最早 due_at / retry_at
  -> 按 family 分组
  -> 原子写入该 family 唯一父 Job.next_time
```

到期时父 Job Cell 只处理自己 family 中所有 `due_at <= now` 的检查点，按 occurrence 和 adapter 串行执行游戏动作。成功项立即独立提交；单项业务 unavailable 不空覆盖旧数据。全部项目处理后，玩法榜只写 `ranking-lifecycle.next_time`，资源榜只写 `resource-ranking.next_time`。子 adapter、daily sync 和专用 Runtime Cell 均无权写入或清除任何父/子 Scheduler 时间。

## 4. 模块与接口

### 4.1 注册表与 Runtime 身份适配

```python
@dataclass(frozen=True)
class RankingActivityIdentity:
    activity_type: str
    family: Literal["gameplay_rank", "resource_rank"]
    vo_types: tuple[str, ...]
    runtime_activity_types: tuple[int, ...]
    activity_ids: tuple[int, ...]
    base_ids: tuple[int, ...]
```

现有 `ExchangeActivitySpec` 继续负责页面、榜单 scope、商店、币种和业务 adapter；生命周期层只投影家族与 Runtime 身份选择器，不复制页面能力。标准化 Runtime 日程以 `activityType / activityId / baseId` 为稳定识别事实；原始 AS3/Lua VO 类名仅作旧快照兼容提示，不能成为唯一识别依据。多个 identity 同时命中时失败关闭，不按名称或顺序猜测。

```python
class ExchangeActivityAdapter(Protocol):
    def collect_activity(self, session, *, activity_id: str): ...
```

公共 `reconcile_ranking_occurrence` 负责 00:30 对账，并调用现有 Exchange adapter 做只读动态采集；两个父 Job 复用 occurrence/checkpoint 底座，但分别发现、执行和计算自己 family 的下一次时间。`ranking_lifecycle` 对玩法榜的 `exchange_tail_0030`、魔道 19:00、仙盟等 checkpoint 显式分派；`resource_ranking` 对资源榜免费礼包、丹道任务和缘定三生等 checkpoint 显式分派。任何 adapter 都不写 Scheduler 时间。

具体 task type 仍可通过普通 `/runtime/cells/task` Cell 做原地、轻量调试，但全部为 `standard_job=False`、`scheduler_supported=False`，不得生成 Scheduler 实例。当前包括魔道、虚天榜单/自动执行、云梦试剑/收尾、仙盟挑战、资源榜免费礼包、丹道任务奖励和缘定三生礼包等专用入口。`daily_activity_list_sync` 只同步事实，不创建、改写或清除这些子任务的 `next_time`。资源免费礼包父 adapter 必须绑定精确 `activity_type + activity_id` occurrence，候选不是恰好一个时失败关闭，不能用“领取 0 个”的 success 假完成父 checkpoint。

能力状态必须显式而保守：天地弈局为 `implemented_exchange_target_loop_pending_asset_contract`，生产 checkpoint 已装配按统一兑换缺口反馈分批的 target loop，但 #680 计数/配置 Shape 与新版结果浮层 scene/shape 契约尚未补齐，不能冒充真实运行闭环；其中 `8090002` 只表示跨服分组/赛程，不生成对账或动作检查点。兽渊为 `observed_reconcile_only`，当前只做 occurrence/对账投影，尚无稳定执行 adapter 时不伪装成可自动执行能力。

### 4.2 00:30 对账器

共同控制流固定为：

1. 读取完整 Runtime 日程，不按“当前活动”裁剪。
2. 将昨日结算、今日开始、跨日持续、页面关闭前尾期分别保留为 occurrence。
3. 按 activity type 找到 spec；未注册类型记 `observed_unhandled`，不执行。
4. 更新静态活动声明和奖励档次。
5. 尝试通过活动 adapter 刷新榜单、兑换宝阁、钱包和购买进度；资源榜若声明资源采集能力，再刷新任务/资源库存。
6. 动态 manager 或页面未开放时记录采集原因并标记 `retained/unavailable`，不得生成空榜；静态奖励档次和 occurrence 入库不受影响。
7. 写入 observation 时间序列并重算策略。
8. 正式结束后的首个 00:30 写 `formal_end`；若 adapter 已证明可幂等兑换，额外生成 `exchange_tail_0030`：刷新精确 occurrence 的最终榜单、钱包、商店购买次数，按祈愿队列动态决定最多两个锁定资源，并执行兑换收尾。
9. 九档完成时，卡邮件资源不在现场购买，只精确保留其总成本；九档未完成时在兑换保留期现场买入。卡邮件候选按 `瑶池玉莲 > 洗灵奇石 > 淬体精魄 > 珍品饲灵丸 > 炼丹灵草匣` 选择首个未使用资源，禁止按活动名硬编码。
10. 页面关闭前最后一次写 `final`。重复运行按 checkpoint 键和商店绝对 `purchased_count` 幂等；失败重试不得重复购买已完成项目。

天地弈局的动态事实进一步按 `shop / currency / rankings` 独立标记新鲜度：商店与钱包可正常更新而榜单 retained；榜单读取失败不得阻止已验证的商店、棋符入库，也不得用空榜覆盖历史榜单。

### 4.3 魔道 19:00 adapter

魔道内部仍拆成可独立测试的原子：

```text
同步/选择性领取邮件
  -> 读取魔道任务 Runtime，逐项领取并复验
  -> 在当前 Cell 内初始化本 occurrence 的三批执行计划
  -> 计算本 attempt 所需天眼符
  -> 不足时退出到世界，经储物袋按 Runtime 物品身份打开授权补给箱
  -> 回到魔道并重新读取绝对天眼符数量
  -> 分三批补到500、探查、结果确认
  -> 写 occurrence 完成态
```

邮件没有新条目是合法幂等结果，不阻塞任务和探查。任务奖励必须由魔道专属 Runtime task adapter 确认可领/已领状态，不能复用普通日常任务 ID。储物袋只允许打开已静态证明会产出天眼符且 Runtime 唯一绑定的箱子；按缺口计算最少箱数，动作后以天眼符绝对数量增长复验。资源仍不足时记录 `blocked` 并安排有界复查，不允许用当前不足次数启动探查。

点击前后产生的不可逆事实写入 occurrence checkpoint evidence，而不是 Scheduler payload。三批全部在同一 attempt 中确认后，19:00 checkpoint 才完成；结果页额外次数不计入基础1500。若 Cell 中断后只留下非终态 evidence，新 attempt 必须失败关闭并等待人工对账，禁止从 `armed`、页码、批次或任一 GUI 步骤继续。

### 4.4 失败与恢复

- 业务上“页面未开放、没有邮件、没有可领奖励”由 adapter 正常分类，不产生 `run_status=error`。
- Runtime 身份冲突、资产契约断裂、不可逆动作无法复验才抛程序异常。
- 单个 occurrence 异常不阻止其它到期项被观察和安全提交；该 checkpoint 写 `error + retry_at`，父 Job 正常回写自己 family 的最早重试时间。
- 已完成 checkpoint 重跑只重新观察，不重复不可逆动作。
- 框架严格禁止恢复业务中间态。Job Cell、Kernel 或进程中断后，下次从稳定入口整单重跑并重新读取游戏事实；payload 不保存 GUI 步骤、页码、批次或游标。只有能够独立证明已完成/已领取/已购买的服务端或 occurrence 证据可用于幂等跳过；不完整的不可逆 evidence 必须失败关闭，不能转换成续跑指令。
- 漏掉的 `daily_reconcile` 可以逐日追补；有游戏副作用的 19:00 checkpoint 只允许在精确 occurrence 尚未结束时补跑，结束后永不追执行。

## 5. 页面投影

玩法榜和资源榜页面继续共享 Exchange activity shell。天地弈局已进入玩法榜下拉框，复用个人榜 + 宗门/位面榜 + 兑换宝阁的公共页面，不在前端另存一份业务数据。新增统一生命周期字段：

- `instance_key`
- `lifecycle_phase`
- `last_reconcile_at`
- `facts`: rankings/shop/tasks/resources 各自的 `updated/retained/unavailable/not_applicable`
- `finalized_at`
- `next_checkpoint_at`
- `blocked_reason`

前端不根据当前时间自行猜活动状态，也不把 retained 显示成刚更新。魔道已经注册在玩法榜 `magic-invasion` spec 中，不新增独立页面；00:30 和19:00结果都投影到该实例。

## 6. 迁移

1. 保留玩法榜持久身份 `ranking_lifecycle` / `ranking-lifecycle`，展示名规范化为“玩法榜”；新增资源榜持久身份 `resource_ranking` / `resource-ranking`，展示名“资源榜”。
2. 玩法专用旧 rows（`magic-invasion-explore`、`xutian-palace-rankings`、`xutian-palace-native-auto`、`yunmeng-trial-auto-challenge`、`yunmeng-tail`、`legacy-daily-xianmeng`）只把最早合法绝对 `next_time` 迁到 `ranking-lifecycle`；资源专用旧 rows（`resource-rank-daily-free-gift`、`dandao-task-rewards`、`yuanding-sansheng-daily-gift`）迁到 `resource-ranking`。不迁 payload、run 状态或 GUI 中间态，已知 `magic_invasion_progress` 定向清除。
3. 若 canonical row 已存在，也幂等规范化 `task_type/label/template_id/template_label`；重复迁移不得改变已经合法的结果。
4. 旧 task type 保留为 internal Runtime Cell 兼容入口，但 `standard_job=False`、`scheduler_supported=False`，不得重新生成子 Scheduler row；daily sync 同样不得回写退休 row。
5. 两个父 Job 分别重新发现 occurrence、执行自己 family 的 checkpoint 并写回自己的最早合法 `next_time`，禁止双轨执行。
6. 不迁移魔道 `confirmed/armed` 等 GUI 过程；不可逆进度只允许作为 occurrence 对账 evidence，非终态 evidence 在新 attempt 中失败关闭。

## 7. 实施与验收

### 阶段一：内核

- checkpoint 纯规划器、多 occurrence 分类、00:30/19:00时间计算。
- checkpoint 持久化与幂等键。
- Exchange registry 到生命周期 registry 的无重复投影。

### 阶段二：00:30 家族对账

- 玩法榜与资源榜各自 orchestration，共享 occurrence/checkpoint 底座但不共享执行或 `next_time`。
- 静态奖励档次与 retained/unavailable 语义。
- 同时存在“上一期结束 + 今日开始”的回归样例。

### 阶段三：魔道

- 邮件原子复用。
- 魔道任务 Runtime reader 与领取动作。
- 天眼符补给箱静态产出解析、储物袋执行和绝对数量复验。
- 3×500探查接入统一 checkpoint。

### 阶段四：迁移与真实验收

- 默认清单恰好两个榜单父 Job，且分别只处理一个 family。
- 当前 Scheduler 成员迁移和 `next_time` 对账。
- 00:30真实对账页面验收。
- 19:00合法活动窗口真实执行；挑战仍显示“未启用/未来阶段”。

验收不以 pytest 替代真实 Runtime。未到合法窗口前只能报告静态、离线和 Scheduler 验收完成到哪一层。

## 8. 权衡

- 两个 family 父 Job 比单一巨型 Job 多一个 Scheduler 成员，但换来玩法榜与资源榜的触发时间、失败域和执行适配隔离；每个 family 内仍通过 occurrence 独立提交和 adapter 串行执行控制影响面。
- 新 checkpoint 表增加一层状态，但避免把多 occurrence 进度塞入 Scheduler payload，也避免一个字段同时承担规则、状态和展示。
- 00:30 能获得奖励配置与既有事实，不保证获得未开放榜单的实时玩家记录；明确事实新鲜度比伪造完整性更重要。
- 魔道保留完整专属 adapter；天地弈局已增加“结构化数据 + 多页签奖励 + 一局自然弈力”的受限 adapter。其它活动先接共同 00:30 对账，再逐个迁移专属执行阶段，降低一次性切换风险。

## 9. 本次反思

- 第一版发现器直接依赖原始 VO `class`。真实 Runtime 标准化日程已经有意抹平实现类，只保留 `activityType / activityId / baseId`，结果测试样例能识别、生产 36 行日程却得到 0 个 occurrence。修复原则不是把 `class` 补回标准层，而是把稳定身份选择器抽成版本适配边界。
- “Job 执行成功”不等于业务成功。第一次真实运行显示 0 checkpoint，如果只看 Runtime 状态会形成假验收；继续核对 occurrence 数和 checkpoint 表才定位到识别层缺陷。
- 合并调度时不仅要保存旧进度，还要重算新体系更早的生命周期触发。若机械保留旧魔道 10:01，迁移后的首个 00:30 会被跳过。
- 补跑必须按副作用分类：数据库事实可以追补，游戏动作不能在活动结束后追补。把二者都简单解释成 `due_at <= now` 会在恢复服务时制造不可逆误操作。
- 00:30 的正确语义不是强行得到实时榜单，而是“静态事实必达、动态事实尽力刷新、失败保留旧值并留下原因”。这比用空数据伪造一次成功更新更可靠。
- 同一玩法可能连续出现服内、跨服等多个 occurrence，采集器不能把“当前玩法类型”误当成唯一实例。稳定绑定应以 Runtime 的 `activity_id` 为主，再由 adapter 映射该实例自己的 rank scope；丹道预赛与跨服因此分别读取各自榜单，不再被默认预赛入口串线。
- 复用旧活动内核时，调度所有权和不可逆证据必须落在不同领域：具体 adapter 永远没有 Scheduler 写权限，occurrence evidence 也永远不能塞回 Scheduler payload。非终态 evidence 的意义是阻止不确定重做，而不是授予下一 attempt 恢复 GUI 步骤的能力。
- 资源榜不能依赖标准化层已经删除的原始 VO `class`。版本化 `activity_id` 集合集中留在身份 adapter，并按“精确 activity/base id > 唯一 activity type > VO class 兼容兜底”分级选择；真实日程因此补识别出此前漏掉的未来灵装化道 `1044311`。
- 服龄是全服事实，不属于某个玩法家族；但历史库中的 `9999` 也可能只是协议哨兵。奖励档次只能继承带明确来源说明的全局服龄下界，并保持“至少 31 天”这种下界语义，不能伪造精确开服天数。服内魔道据此恢复出 12 个真实奖励档次。
- 活动正式结束不等于页面关闭。服内魔道的 `endTime=22:00` 与 `closePanelTime=次日23:58:59` 必须分开存储；把 close 字段写成旧键会让仍可兑换的历史页被误判为关闭。
- 历史兑换页与全局“当前活动”可以同时属于不同 occurrence。采集器必须用 `runtime_id/activity_id/cross_count/start/end` 五项一致性绑定历史榜单与商店，不能让今天跨服 Runtime 覆盖昨天服内实例。
- 视觉场景分数不是业务终态。#519 因旧标注写着“位面魔晶”只能得82分，但标题、当前魔晶、累计魔晶和唯一竖排页签可共同证明兑换宝阁；竖排 OCR 必须先按 `parent_line_id` 重组，不能逐字符查完整词。
- 重试链必须从自身留下的安全现场继续：购买框先关闭、商店先走活动内返回，再进入全局导航；数据库事务也不得跨越真实游戏等待，否则外层读事务会自锁内部快照写入。
