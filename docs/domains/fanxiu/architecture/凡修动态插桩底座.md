# 凡修动态插桩底座

## 定位

动态插桩 Runtime 是凡修的独立能力接口层。它只定义和实现游戏运行态查询与
命令，不负责决定何时调用、由哪个业务调用或调用后继续什么流程。

## 严格只读锁（2026-08-03）

当前动态插桩全局固定为 `strict-read-only`，且采用源码级、失败关闭的保护，
不提供环境变量或 API 临时解锁。允许范围只有：读取设备/进程身份、读取
`/proc` 映射和进程内存、解析已经保存的数据包、读取 CodeYun 数据库快照。

以下操作即使业务名称叫“查询”也一律拒绝：

- Frida 附加、脚本注入和 Hook；
- 启动、部署 Frida Server，或向设备推送桥接库/脚本；
- 在游戏主 Lua 状态执行代码、调用 `require` / `Inst_get` 初始化 Manager；
- 替换 Lua 方法或其它运行时代码；
- 通过插桩调用 `CM_*` 等游戏网络命令。

历史实现可以留作离线研究材料，但任何公开 API 和底层直调入口都必须先经过
`instrumentation.policy` 拒绝，且测试要证明拒绝发生在设备发现、ADB、Frida
和 Lua 执行之前。若未来确需恢复写能力，必须由用户另行明确授权并重新设计，
不能把本锁改成默认可绕过的开关。

```text
任意调用方 -> 动态插桩业务接口 -> 探针实现 -> 游戏进程
```

Scheduler、Kernel、Cell 和行为树均可能成为调用方所在的上下文，但不进入动态
插桩 Runtime 的接口语义，也不能成为接口能否执行的前置判断。

当前查询只允许从游戏进程外部读取已经存在的数据。业务接口层不提交 Cell、
不注册作业，也不读取 Scheduler、Kernel 或行为树状态。权威业务模型尚未加载
时必须安全失败或返回不完整状态，不得通过初始化 Runtime Manager 补齐数据。

这条限制只约束动态插桩接口本身，不禁止上层业务编排使用已经验证的 ADB、
Runtime 与资产树图路径正常访问对应玩法，使游戏自然创建 Manager、Model 或同步
榜单数据。此类流程必须明确区分“未加载”与“读取失败/版本不支持”，并采用
“只读观测 -> 有界 GUI 预热 -> 重新只读观测”的闭环；打开页面之外的领奖、购买、
刷新、挑战等动作仍需各自业务授权。

## 用户触发更新的新鲜度边界

玩法榜页面加载、切换活动和刷新浏览器时只读取 CodeYun 数据库快照，不自动访问
游戏、不轮询运行态，也不因快照时间较旧而隐式采集。游戏侧采集只允许由用户点击
“从游戏更新”或等价的显式操作触发，采集成功后写入数据库，页面再读取新快照。

页面上的“从游戏更新”表示读取按钮触发时的当前游戏状态，不等于“读取数据库中
最近一条历史运行态事实”。抓包事实只有在能够证明采集水位已经覆盖本次触发时间
时，才能作为本次更新结果；否则只能作为历史证据，禁止写回并显示“更新成功”。

用户触发的普通更新只允许读取已预热的运行态缓存，禁止同步执行 LuaJIT 全堆发现
或其它可能长时间拖慢模拟器的扫描。缓存缺失时必须快速失败且保留原数据库值；根
发现只能作为显式诊断操作单独执行。兑换商店等活动期内不变且已经完整入库的数据，
余额更新时直接保留，不重复扫描。

## 已有能力

- 自动发现正在运行凡修进程的唯一 Android 设备。
- 分别报告设备 ABI、内核机器架构和目标进程模块，适配模拟器 ARM 转译场景。
- 检查 Frida Python 绑定、设备端 Frida Server、版本和进程状态。
- 历史上曾支持启动 Frida Server 和短暂附加；严格只读锁启用后这些入口均已禁用。
- 暴露能力目录，为以后增加业务查询和命令保留稳定边界。

### 资源榜：灵装化道

`ActivityrankMgr` 已收敛为按 `activity_id` 参数化的公共运行态适配器：

```text
GET /api/fanxiu/dynamic-instrumentation/activity-ranks/{activity_id}
```

适配器统一解析 `V_RankDataDic`、`selfRankVO`、`rankVOS` 与
`rankListSize`，并统一补全区服身份。新增玩法榜只需声明活动 ID、榜单角色、
奖励和完整性语义，不得复制 LuaJIT Manager/Model 解析代码。

资源榜首个业务适配“灵装化道”继续保留兼容接口：

```text
GET /api/fanxiu/dynamic-instrumentation/activity-ranks/lingzhuang-huadao
```

两个接口的数据都来自游戏已经加载的常驻榜单模型：

```text
ActivityrankMgr.Model.ActivityrankData.V_RankDataDic[44307]
  -> selfRankVO / rankVOS / rankListSize
```

普通请求只使用已验证的进程缓存和统一 `activity-rank` 逻辑根缓存，不调用榜单
同步命令、不主动打开活动页面，也不在请求内启动全内存扫描。缓存缺失返回
`process_cache_miss` / `root_cache_miss`，活动数据尚未加载返回
`data_not_loaded`，并统一标记 `recovery_required=true`；不得用空榜或旧活动数据
冒充实时结果。慢速根发现只允许通过显式恢复/诊断入口执行，成功后回写同一缓存。

探针默认读取：

```text
libil2cpp.so
libunity.so
libtolua.so
libc.so
```

## 储物袋业务研究

储物袋的权威运行态数据已经定位到游戏 Lua 模型：

```text
SM_AllBagSyncInfo(30110).bagInfoVOs
  -> BackpackMgr.Inst_get().Model.BackpackData:AllPackDataInfo(...)
  -> BackpackData.BagInfoVOs
  -> itemVOs / ItemVoDic
```

`BagInfoVOs` 是登录全量同步后常驻内存的原始分包数据；`itemVOs`
是汇总物品列表，`ItemVoDic` 按 `baseId` 和实例 `id` 建索引。模型更新范围包含：

- 普通储物袋
- 功法
- 法宝
- 核心装备
- 玉

客户端还提供 `CM_AllBagSyncInfoFun()`，可显式请求服务器重新发送全量数据。
它会产生网络副作用，必须设计成单独的 `inventory.refresh` 命令；普通
`inventory.snapshot` 只读当前常驻模型，不应自动刷新。

现有抓包快照可作为迁移验收基线：`2026-07-24 18:09:26` 的
`SM_AllBagSyncInfo` 完整解码出 5938 个实例、`is_truncated=false`。它只用于
对比动态读取是否完整，不作为新接口的数据源。

### 当前库存归并器（2026-07-31）

储物袋当前状态已不再依赖一次性的全量 JSON 快照。抓包事实层按客户端
`BackpackData` 的同一语义归并：

- `SM_AllBagSyncInfo` 建立完整基线。
- `SM_BagSyncInfo` 替换单个分包。
- `SM_RewardResult` / `SM_CostResult` 中 `type=0` 的 `ItemVO.content`
  以实例 `id` 和服务端返回的变更后 `num` 更新；`num=0` 删除实例。
- 每个事件带有抓包时间和 packet 顺序水位，历史补扫不能倒灌覆盖新状态。
- 旧版被截断的奖励/消耗列表直接跳过，不能用半份清单污染库存；解码 schema
  5 起完整保留 `RewardResult` / `CostResult` 列表。

数据库当前投影使用 `storage_bag_current_item` 与 `storage_bag_state`，
`storage_bag_state.complete=true` 只在完整全量基线后成立。动态插桩完成后应把
`BackpackData` 快照/变更转换成同一事件模型，不另写一套库存算法。

### 当前运行态结论

当前 MuMu 进程是 x86_64 宿主承载 ARM64 Unity/IL2CPP/Lua：

- `/proc/<pid>/maps` 能确认 ARM64 `libil2cpp.so`、`libtolua.so` 已加载。
- 普通 Frida attach 进入 x86_64 宿主，`Java.available=false`。
- `realm=emulated` 不可用。
- Android NativeBridge 已初始化，但游戏 ARM 库不在标准
  ClassLoader linker namespace，后附加探针无法取得已有 ARM 库句柄。

以上是历史逆向环境事实，不构成当前实现建议。严格只读锁启用后，储物袋只能
通过进程外内存读取或已保存协议事实获取；禁止再建设 ARM/Lua 早期注入入口。
若现有只读链无法证明快照完整，应明确返回不完整并进入诊断，不能借初始化或注入
补齐。

### GUI 与数据源迁移边界

- 读取已登录账号的常驻储物袋：设计上不需要打开储物袋页面，也不需要点击。
- 当前模型尚未完成首次全量同步时：需要登录完成；可等待游戏自然同步。
- 主动刷新网络命令在当前严格只读策略下禁用；数据未加载时只能等待自然同步，
  或由上层业务使用已验证 GUI 图路径访问对应页面后重新只读观测。
- Wiki 数据源保持不变。只有动态快照与抓包基线完成总数、实例 ID、数量和分类
  对账，并经过连续增量更新验证后，才另行切换。

## 聊天红包业务研究

红包入口显示在聊天系统，但“是否仍可领取”的权威运行态不应通过聊天文字或
界面图标推断。游戏已经提供了完整的业务判定链：

```text
ChatMgr.Inst_get().Model:CheckHasRedBagShow()
  = RedbagMgr.Inst_get().Model:ChatHasRedPacket()
  + NpcMgr.Inst_get().Model.NpcData:GetNpcRedBagCount()
```

普通/系统红包保存在 `RedbagData._RedBagList`。游戏的
`ChatHasRedPacket()` 会逐个排除：

- 已被当前账号领取：`CheckHasRewardRedBag(uid)`
- 已过期：`CheckHasOverdue(uid)`
- 被领取限制拦截：`IsBeLimit(uid)`
- 不满足配置条件或当日次数：`HasReward(id)`
- 年会、全民抽奖、巅峰赛等活动专用状态不允许领取
- 已加载详情且奖励已经领完：`detail.isReward` 或
  `detail.receiveNum >= detail.num`

因此动态接口应复用同一判定语义，而不是只检查
`ChatContentType.RedPacket/SystemRedPacket`。建议业务接口：

```text
chat.red_packet.pending  只读返回 total、普通红包、NPC 红包和可领取明细
chat.red_packet.claim    对指定 uid/id 发起领取，单独声明奖励和网络副作用
```

红包状态会由 `SM_NewRedBag`、`SM_OfflineRedBag`、`SM_UpdateRedBag`、
`SM_UpdateRedBagList` 和 `SM_GrabRedBag` 更新，并通过
`RED_BE_REFRESH` 通知聊天 UI。因此只读查询不需要打开聊天页；长期监听也可以
订阅模型更新事件，而不需要轮询或识别 GUI。

当前“没有待领取红包”只能作为负样本。动态桥接完成后，应先验证返回
`total=0`；随后还必须等待一个真实新红包正样本，验证
`0 -> pending -> claimed/expired -> 0` 的状态迁移，才能替换现有 GUI 快速门卫。

### RedbagMgr 未加载处理

`NpcMgr` 可用而 `RedbagMgr` 不可用时，只能说明红包 Runtime 数据不完整，
不能把 NPC 红包数量 `0` 合并成“当前无红包”。当前查询遵循以下顺序：

1. 先从 LuaJIT 内存解析 `RedbagMgr` 与 `NpcMgr`。
2. 若只有 `RedbagMgr` 实例根缺失，返回 `data_not_loaded`，不得把 NPC 数量
   合并成完整结论。
3. 上层业务如有已验证聊天页 GUI 图路径，可先正常访问页面促成自然加载，再重新
   只读观测；探针本身不得执行 `require`、`Inst_get` 或 NativeBridge 初始化。
4. 重新观测仍失败时返回 `complete=false / ok=false`，保留加载状态和失败分类供
   工程巡检或 Agent 诊断。

历史 NativeBridge/Lua 初始化适配器仅可作为离线研究材料，当前策略必须在设备
发现和执行前失败关闭。

## 2026-08-11 系统审计与首批收敛

静态审计覆盖 `backend/core/fanxiu/instrumentation` 的 50 个 Python 模块：27 个
模块使用 Manager 根解析器，19 个模块仍存在允许隐式发现的缓存读取，5 个模块
已有严格缓存快路径。首批选择活动榜作为代表性纵切面：

- 原灵装化道与云梦各自复制 `ActivityrankMgr` 解析，且错误语义混入活动名称；
- 原灵装化道普通请求在根缓存缺失时同步进入大范围内存发现，真实基线 59 秒仍未
  返回；
- 现已抽出 `activity_rank_runtime.py`，以活动 ID 参数化读取任意已加载玩法榜，
  灵装化道与云梦共用同一个 `activity-rank` 根缓存；
- Manager 身份验证与具体活动是否加载已经拆开，换活动不会再把正确 Manager 根
  误判失效；
- 普通玩法榜请求改为严格快路径，实测缓存未预热时约 0.13–0.15 秒明确失败并
  请求恢复，不再阻塞一分钟。

后续迁移不能机械把全部探针改成缓存模式。应逐个 Manager 补足结构验证、类型化
错误、显式恢复函数和真实冷热基线，再把用户请求中的隐式扫描关掉；直接定位、
缓存读取、对象重绑定、版本适配和冷发现必须是可观测的不同阶梯。

## 洞天与灵脉现场验证（2026-07-29）

真实窗口验证确认，原根定位器失败不是业务 Manager 未加载，而是 LuaJIT
内存布局假设错误：

- GC 字符串对象、引用它的 hash node、全局管理器表头可能分属不同匿名 RW
  region，不能只在 marker 所在 region 内查找。
- Lua hash 冲突会把目标键搬到 `hash & hmask` 之外的空闲 node，不能只反解
  原始桶。
- 当前 Android 进程的宽候选集合达到约 `995` 个 region、`3.57GB`；全量读取
  不仅慢，也会影响游戏稳定性。正式定位只在 GC 字符串周围 `128MB` 的无路径
  匿名 RW LuaJIT 堆邻域内跨区解析。

现场中 `LuaUnionVenisMgr` 字符串与其 tagged key 相距约 `74.1MB`。修复后已在
真实 #285 联盟灵脉页读出：

- `leftListenTime`、`maxVenisTime`
- `strength`
- `UnionVeinsGroup`
- `myRoomId`、`seatId`、`battleId`、`localServer`
- `roomList` 及每个房间的剩余空位
- `roleInfo`

对应只读能力为 `lingmai.snapshot`。概览、剩余时间、体力、联盟分组和房间空位
已可不依赖抓包；具体座位 roster 仍需进入房间后验证 `roomInfoDic/seatList`
的动态填充，未验证前不得宣称完全替代座位抓包。

同一修复在真实 #279 洞天页读出 `XianLvMinesMgr.Model.Data` 与
`ClubMgr.Model.data`：行动力、自联盟身份、矿位及占领联盟均完整，
`dongtian.snapshot` 因此从 `pending-live-window` 更新为 `live-validated`。

### 洞天管理器别名漂移（2026-07-31）

当前真实游戏进程已不再暴露旧探针使用的全局字符串
`LuaXianLvMinesMgr`，但仍完整存在 `XianLvMinesMgr`、
`V_AttackFatigueValue`、`_MaxAtkMaxTried` 与 `V_MinesVoDic`。因此洞天快照
不再把管理器的展示别名作为权威入口，改为按稳定的 `Model.Data` 字段组合直接
定位活跃数据表；`ClubMgr` 仍沿用已验证的管理器根读取。

本次已用真实进程证明字段字符串存在，并完成离线回归；由于发现时已过
21:30–22:00 行动力窗口，新的数据表根定位仍需在下一次真实 #279 页面完成
运行验收。窗口外不得用抓包旧事实或 GUI OCR 冒充动态快照成功。

2026-08-03 的真实 #279 验收补齐了这项窗口验证。直接字段表发现先因一块
约 1.02 MiB 的匿名映射短读而中止；跳过单块不可读候选后又证明当前 LuaJIT
布局并不保证三个业务字段出现在同一张原始表。修复后按
`XianLvMinesMgr -> LuaXianLvMinesMgr -> 字段表兜底` 解析 Manager，再从
`Model.Data` 严格校验行动力和 39 个矿位。真实作业连续读出
`300 -> 200 -> 100`，完成三轮战斗后复验为 `0/300`，两个根均命中当前
`PID + process_start_ticks` 缓存。模拟器重启后旧根仍必须失效并重新发现；
不得缓存跨进程地址，也不得因单个候选映射短读放弃后续有效堆区域。

## 邮件业务研究

邮件同样具备完整的客户端常驻业务模型，不需要打开邮件界面。全量邮件到达后，
客户端按以下链路保存：

```text
SM_MailBox
  -> MailMgr.Inst_get().Model:SetMailBox(msg)
  -> MailData.mailList = msg.mailVos

MailMgr.Inst_get().Model:GetMailList()
  -> MailData:GetMailList()
  -> 当前本地结构化邮件清单
```

新邮件还会通过 `SM_NewMail -> Model:NewMail(msg)` 增量插入。因此动态接口可直接
读取当前客户端已经同步到的邮件，而不需要 GUI 点击、OCR 或抓包。每封邮件的
`MailVo` 已确认包含：

- `id`、`type`
- `title`、`content`、`senderName`
- `createTime`、`expireTime`
- `rewards`
- `read`
- `rewardGetted`

“未读”和“附件未领取”不是同一概念。客户端自己的附件红点判定是：

```lua
rewards and rewards:Count() > 0 and not mail.rewardGetted
```

所以 `mail.unclaimed` 必须按“存在附件且 `rewardGetted=false`”筛选，不能使用
`read=false` 代替。建议基础接口分为：

```text
mail.snapshot    只读返回本地完整邮件清单及汇总
mail.unclaimed   只读返回本地尚未领取附件的邮件
mail.claim       对指定邮件 ID 发起领取，单独声明网络和奖励副作用
```

只读结果至少应返回 `total`、`unread_count`、`unclaimed_count` 和邮件明细。
邮件 ID 属于 64 位整数，跨 Lua、JavaScript、JSON 时应序列化为字符串，避免
精度丢失。

这里的“本地未领取”表示当前客户端模型中尚未标记领取。若调用方需要保证邮件
在服务器此刻仍然可领取，还要显式执行过期校验：客户端已有
`CM_IsMailExpired(ids)`，服务端返回后会从本地删除过期邮件。这个网络动作不能
偷偷塞进 `mail.unclaimed`；应作为独立的刷新/校验命令，由调用方决定是否使用。

领取成功后，客户端会在 `OnGetRewardSucceed` 中同时设置
`read=true` 和 `rewardGetted=true`。领取命令还需要显式返回背包已满、邮件过期、
部分成功以及实际奖励，不能只以请求发送成功作为业务成功。

2026-08-04 已通过严格只读外部内存读取打通主 `lua_State`：从线程环境表中的
`MailMgr` 沿 `inst -> Model -> data -> mailList/lockList` 读取当前模型，未调用
Lua 方法、未初始化 Manager、未发网络请求。真实 #121 邮件页同一时刻读出
`120` 封邮件、`6` 封锁定邮件，并逐封解出附件数量及 `type/code/amount`；因此
`mail.snapshot` 与 `mail.unclaimed` 标记为 `live-validated`。邮件标题/正文可能
为空，因为客户端会按 `type + i18nParams` 从静态配置生成显示文本；附件存在性
仍直接以 `rewards:Count() > 0` 为准。`mail.claim` 继续未实现且受只读策略禁用。

## 后续业务扩展

新增业务功能时，先设计面向业务的接口，例如：

```python
bridge.player.get_profile()
bridge.inventory.list_items()
bridge.activity.get_attempts("xianyuan_duel")
```

业务接口内部再选择 IL2CPP、Lua、Java 或其它探针实现。调用方不接触内存地址、类偏移、Frida 脚本名或 RPC 细节。

所有写操作必须单独声明副作用、前置状态、幂等语义和验证方式；不能把任意脚本执行暴露成公共业务 API。
