# 凡修活动商店动态采集

## 目标

活动商店采用“游戏运行态采集 → 完整性校验 → 后端数据库快照 → 前端只读展示”的固定链路。AI 只负责首次登记活动类型的稳定身份，不再逐项探索商品、抄价格或维护商品编号清单。

## 通用采集模型

每类活动商店只登记两个稳定参数：

- `shop_base_id`：游戏商店的业务身份；
- `expected_currency_type`：可选的代币类型断言。

采集器 `backend/core/fanxiu/instrumentation/activity_shop.py` 在运行时自动完成：

1. 从 `V_ShopCfg` 提取该商店的全部候选配置；
2. 从商店 Manager 的临时索引中读取已经过游戏完整条件引擎筛选的商品集合；
3. 自动识别 `EqualCrossGroup` 对应的跨服数；
4. 按 `shopItemId` 聚合同一商品的多条配置及限购；
5. 复现 Lua 5.1 `table.sort`，还原游戏原始顺序及相同排序值的非稳定次序；
6. 用物品图鉴补名称，并校验币种、数量、价格、限购和完整项数；
7. 输出标准快照，由活动适配器写入数据库。

商店 Manager 的索引是页面初始化产生的短生命周期运行态对象。正式作业应在完成活动页面导航后立即采集；索引不存在或候选不唯一时直接失败并保留数据库中的上一份有效快照，禁止退化为“把同跨服的所有配置都写入数据库”。

## 标准快照

```text
complete
shop_base_id
cross_count
currency_types
active_shop_item_count
resolved_shop_item_count
items[]
  goods_id / item_id / name / goods_num
  token_cost / currency_type / purchase_limit
  source_order / show_limit / disappear_limit
evidence
  pid / process_start_ticks / config counts / source
```

运行态证据保留配置行 ID、聚合行数、游戏排序值和原始索引位置；业务表只保存稳定字段，不保存易失内存地址。

## 活动适配器

云梦试剑适配器位于 `backend/core/fanxiu/activity/yunmeng_trial_instrumentation.py`：

- 固定身份：`shop_base_id=210001`、`currency_type=19`；
- 跨服数、商品 ID、商品顺序、价格和限购全部由通用采集器获得；
- `collect_and_store_yunmeng_trial_shop(...)` 是 Agent/作业使用的一次调用入口；
- 写入前使用 `expected_shop_item_count` 完整性门禁；
- 前端 API 始终读取数据库，不直接访问游戏。

后续活动实例（例如另一日期的 8 跨云梦试剑）只需再次运行同一适配器并提供活动日期。新的活动类型只需登记商店稳定身份和自己的日期/资源策略适配，不复制内存扫描、排序、聚合或持久化逻辑。
