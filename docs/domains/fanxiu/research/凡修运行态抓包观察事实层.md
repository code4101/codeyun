# 凡修运行态抓包观察事实层

简称：运行态观察。

本文记录抓包解析与图鉴系统的协作边界。运行中才能观察到的数据，例如用户当前物资、货币余额、榜单排名、战力、灵石等，不应直接写回静态图鉴 catalog，而应先进入一层可追溯的观察事实层，再由图鉴按需叠加展示。

这项工作适合作为 Runtime 自动化之外的并行子任务：Runtime 继续负责截图、标注、场景跳转和动作执行；抓包子任务负责持续解析运行中才能得到的事实，并把结果汇总到图鉴 overlay。两条线可以同步推进，但不要互相阻塞。

## 分层边界

1. `fanxiu_tcp_flow` 继续负责 pcap 解码、业务帧索引和 packet 证据保留。
2. 运行态观察层负责把已解码业务帧归一化成事实记录，例如 `item_balance`、`wallet_balance`、`activity_rank`、`player_profile`。
3. 已探明业务域必须通过业务写入器增量落到数据库事实层；JSON 只作为探索、调试或兼容快照。
4. 图鉴层只读取观察事实作为 overlay，例如道具卡展示最近观察数量、活动卡展示最近榜单或个人排名。

这样可以避免把一次抓包里的临时状态误写成静态配置，也保留 packet 来源、时间和置信边界。

## 最小记录模型

观察记录至少保留：

- `entity_type`：例如 `item`、`wallet`、`activity`、`player`。
- `entity_id`：可关联静态图鉴的 id；无法关联时保留原始 code/name。
- `observe_kind`：例如 `delta`、`snapshot`、`rank`、`profile`。
- `value`：数量、排名、战力等结构化值。
- `packet_name` / `pro_id`：来源协议。
- `record_id` / `frame_index`：来源抓包记录定位。
- `observed_at`：观察时间。
- `confidence`：`snapshot`、`delta`、`inferred` 等可信语义。

第一阶段只做观察事实，不声明“当前库存”。只有识别到明确全量快照包后，才把语义升级为当前状态。

## 第一阶段

优先从已解码历史中扫描 `_build_fanxiu_tcp_entries(...)` 的奖励、消耗、道具分类，识别明确字段：

- 道具：`baseId`、`itemId`、`item`、`code`。
- 数量：`num`、`amount`、`count`、`total`。
- 钱包：`wallet`、`currency`、`value`。

未知协议或字段语义未闭合时，可以先输出到 `get_settings().data_dir / fanxiu/runtime-observations/` 作为探索快照。只要字段语义和业务范畴已经探明，就必须迁入 SQLite 业务事实层，并让抓包同步服务自动增量写入。

## 子任务拆分

抓包子 agent 可以按以下顺序推进：

1. 扫描现有 decoded packet，未知语义先产出观察事实 JSON；已探明语义直接走数据库业务事实层。
2. 按协议族归类可确认的事实来源，例如奖励/消耗、钱包余额、活动榜单、角色概况。
3. 给每条事实保留 packet 证据、时间和置信语义，尤其区分 `snapshot`、`delta`、`inferred`。
4. 先接一个最小图鉴 overlay，例如道具卡的最近观察数量或活动卡的最近排名，再扩展到战力、灵石、榜单门槛等。

运行中才能解析到的数据要允许抓包服务自动增量更新；同一实体的新观察覆盖摘要，但历史证据仍保留，方便回溯和纠错。这个同步动作属于抓包服务，不属于图鉴页面。图鉴页面只能读取数据库事实层，不能以 `auto_sync`、刷新按钮、打开页面副作用等方式驱动抓包同步。

## 图鉴叠加

图鉴接口保持静态 catalog 为主：

- `get_fanxiu_item_card` 可以增加 `runtime_summary`，展示最近观察数量、来源协议和时间。
- `get_fanxiu_activity_card` 可以叠加最近榜单、个人排名、门槛线。
- 区服角色页可以选择读取 `player_profile` 观察，形成战力快照。

玩家观察以本体战力为主、攻击为可选附属。仙侣队最大观测战力单独保存自己的数值、时间和可空队号；图鉴可以按角色合并展示，但不能用仙侣战力覆盖本体战力，也不能把未知队号显示成固定“1队”。两条时间轴的每日摘要都按同一角色当日最高值生成。

图鉴叠加必须展示来源和时间，避免用户把抓包观察误解成静态配置或永久事实。
