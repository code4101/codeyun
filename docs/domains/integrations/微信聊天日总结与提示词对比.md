# 微信聊天日总结与提示词对比

本文用于新会话接力：继续把本机微信逆向数据生成到星图笔记，并重点优化“聊天数据”日总结的摘要、笔记结构和提示词对比。

## 背景

CodeYun 已经接入本机微信只读逆向数据，目标不是发送消息，而是把微信底层数据库、图片/文件等资源解析为可查看、可总结、可复用的个人知识数据。

当前重点页面在“笔记工具 / 星图笔记 / 聊天数据”。它复用星图笔记日历视图，但数据来源是微信聊天记录自动生成的文档节点。后续也可以扩展 TIM/QQ 数据。

- 微信逆向数据目录：`D:\home\chenkunze\data\d2605微信逆向`
- 已解密数据库目录：`D:\home\chenkunze\data\d2605微信逆向\decrypted\db_storage`
- 测试日期：`2026-05-29`
- 测试聊天对象：`紫丹`
- 匹配账号：`wxid_nifgbwprjgan22`
- 当日数据量：379 条消息，其中文本 337 条，资源证据约 60 条。

## 产品目标

星图笔记“聊天数据”不是原始聊天浏览器，而是把一天内每个聊天对象/群聊沉淀为一个文档节点：

- 节点标题用聊天对象或群名，不要机械加“微信”前缀。
- 节点开始时间用当天与该聊天对象第一条消息时间。
- 节点权重默认应为 `0`，避免日历过挤。
- 节点进度按内容量计算，不是按条目数；我发出的消息权重可高一些，对方消息可低一些。
- 星图笔记原本的数据和聊天数据应分隔展示，不要在普通星图日历里混入微信聊天总结。

文档内容分为两块：

- `摘要`：解释当天这段聊天“发生了什么事”，短而顺，不要流水账。
- `笔记`：沉淀事实、知识、流程、资源、链接、后续待办，可以用 HTML 富文本和嵌套列表。

## 当前对总结风格的要求

用户反复反馈后形成的核心要求：

1. 摘要第一句要先说清楚事件背景，而不是按聊天顺序复述。
   - 好例子：`紫丹那边 Clash 突然连不上，于是找我帮忙判断是本机、节点还是网络问题。`
   - 坏例子：`你说开始突然连不上，我这边一开始还能连上，后来也出不稳定...`
2. 摘要不要像第三人称报告，应从“我”的视角总结我的判断、处理和后续安排。
3. 摘要不能只写判断，要包含：背景触发、尝试排查、我的判断、后续安排。
4. 笔记不能只是纯知识，也不能只是流水账；要“事实 + 沉淀”结合。
   - 好例子：`我先买 1GB 小流量包做连通性测试，可用；再视稳定性之后可以买 20/30 元等更高流量套餐。`
   - 坏例子：`初期可先买小包做连通性测试，再视稳定性决定高流量套餐。`
5. 笔记的重点不是人物关系，而是可复用的知识、素材、备忘和流程。
6. 需要支持嵌套多层级列表；例如“排查流程”应该能展开成有序步骤，而不是一段长句。
7. 不要把辅助工具误判成核心故障对象。`向日葵`只是远程协助工具，本例主线是 `Clash/Clash Verge/DirectACCESS/mojie/节点/订阅/网络环境`。
8. 图片/OCR 资源可以作为素材辅助判断，但不能编造 OCR 没有体现的内容。

## 2026-05-29 紫丹案例的事实理解

这个案例的核心不是“向日葵连不上”，而是紫丹那边代理/梯子突然连不上，找我帮忙判断原因。

更准确的事实主线：

- 紫丹那边 Clash/梯子突然不稳定或连不上。
- 对方反馈曾经“只有一次有”“还不行”，并提到重启、刷新后仍失败。
- 我这边一开始能连上，所以初步判断不是单纯服务全局故障。
- 后续按网络和客户端两条线排查：
  - 网络侧：宽带、Wi-Fi、手机热点、不同运营商、学校/实训室网络、路由器自动切换。
  - 客户端侧：Clash Verge、DirectACCESS、mojie、订阅、节点、安装包/重装。
- 向日葵只用于远程协助看图和辅助操作，不是主线故障对象。
- 我后来买了/测试了 mojie 1 元 1GB 小包，验证可用，并提供购买入口。
- 后续可视稳定性再决定是否买 20/30 元等更高流量套餐，同时保留 DirectACCESS 或其他服务作为备选。

## 已实现文件

主要脚本：

- `scripts/import_wechat_daily_notes.py`
  - 从微信解密后的 `db_storage` 读取指定日期聊天。
  - 关联资源证据和图片 OCR。
  - 生成或更新星图笔记节点。
  - 当前已经把内容改为 `摘要 + 笔记` 两块。
  - 当前正常节点示例：`2026-05-29 紫丹`，数据库里曾见到节点 id `54656`。

- `scripts/wechat_daily_summary_variants.py`
  - 定义 20 套微信聊天总结提示词模板，用于横向比较风格。

- `scripts/import_wechat_daily_note_variants.py`
  - 新增的对比脚本。
  - 用同一天同一聊天对象，按 20 套模板生成多个星图笔记节点。
  - 节点标题形如：`紫丹 · 01 话题精华`。
  - 增加自定义字段：
    - `wechat_daily_variant_key`
    - `wechat_daily_variant_name`
    - `wechat_daily_variant_index`
    - `wechat_daily_variant_set`
    - `wechat_daily_variant_source_hint`

10. `personal_diary`：个人日记
11. `resource_index`：资源索引
12. `followup_checklist`：跟进清单
13. `signal_vs_noise`：主线去噪

## 下一步建议

1. 先跑少量模板，确认 AI 调用和写库稳定：

```powershell
$env:UV_CACHE_DIR = "$PWD\.uv-cache"
uv run python scripts/import_wechat_daily_note_variants.py --date 2026-05-29 --chat 紫丹 --limit-variants 3 --ai-limit-chars 9000 --variant-set summary_prompt_compare_20260601
```

2. 在星图笔记“聊天数据”里查看 `2026-05-29`，确认出现 `紫丹 · 01 ...` 等对比节点。

3. 如果前三个效果没问题，再跑完整 20 个：

```powershell
$env:UV_CACHE_DIR = "$PWD\.uv-cache"
uv run python scripts/import_wechat_daily_note_variants.py --date 2026-05-29 --chat 紫丹 --ai-limit-chars 9000 --variant-set summary_prompt_compare_20260601
```

4. 打开浏览器可视化检查：
   - 日历格子是否过挤。
   - 节点高度是否与星图笔记原机制一致。
   - 文档详情里的 HTML 列表、嵌套列表是否正常显示。
   - 摘要是否先说“发生了什么事”，而不是流水账。
   - 笔记是否既有事实又有可复用沉淀。

5. 根据用户实际偏好，从 20 个模板中挑 1-3 个融合成默认生产提示词。

## 需要避免的问题

- 不要让 AI 失败后用规则 fallback 覆盖已有较好的 AI 总结。
- 不要把对比实验节点混成正式日总结；建议保留 `wechat_daily_variant_*` 字段区分。
- 不要只生成知识卡片，忽略当天实际发生的事实。
- 不要只写聊天过程，变成流水账。
- 不要把“向日葵”误判为主线故障。
- 不要在普通星图笔记页面混入微信聊天数据。
