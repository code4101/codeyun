# 步进器-任务设计与调度规范

简称：任务调度。

本文描述在已有场景帧、shape、OCR 规则和滚动容器数据基础上，步进器如何选择任务、识别当前场景、规划跳转、执行动作和避免卡死。它关注“如何使用已有数据调度任务”，不是“如何自动探索补标注数据”。

## 两层任务选择

底层任务应函数化，UI 做两层：

1. 第一层选择函数名，例如 `到场景`、`日常定位`、`隐藏浮动窗`。
2. 第二层选择该函数的预设参数，例如日常定位里的 `双修`、`灵塔`、`剑灵`。

第二层应优先使用预设值，而不是让用户直接输入任意文本。参数未来不一定只是字符串，也可能是枚举、shape 引用、函数或更复杂的结构。

`隐藏浮动窗` 这类任务本身就是第一级任务，第二层参数可以为空。

## 候选场景优先级

步进器每个 tick 会把可匹配场景分成三组：

1. 上一步动作已有跳转经验的目标场景。
2. 独立场景或弹窗场景，例如存在 `-1` 跳转 shape 的截图。
3. 其他普通场景。

这三组只是候选排序优先级，不是阻塞边界。识别阶段必须收集所有组的候选，再统一选择可执行候选；不能因为第一组里有截图匹配成功，就跳过第二组或第三组。

决策规则是：

- 候选分数必须达到当前场景阈值。
- 如果前组候选存在通向目标任务的可执行路径，优先尝试前组。
- 如果前组候选的可执行动作已经尝试过且没有推进，后续 tick 应允许选择后组候选继续探索。
- 只有“优先尝试”，没有“前组命中后完全屏蔽后组”的语义。

这个规则保证了弹窗、遮挡层、误识别场景同时存在时，步进器不会被某个高优先级但走不通的候选长期卡住。

## 场景跳转哨兵

`场景跳转=-1` 表示独立/返回型未知跳转。它通常用于退出、空白、返回原场景这类动作：点击后会离开当前画面，但具体回到哪里取决于进入来源，所以不记录固定目标。

某张图片只要存在 `-1` shape，就会被步进器视为独立场景候选。步进器可以把 `-1` shape 当作可尝试动作，但不会把它解析成普通目标场景，也不会在自动记录经验时覆盖 `-1`。

`场景跳转=0` 表示明确无场景跳转。它可以用于会触发局部状态变化、开关、展开、隐藏等动作，但这些动作不应该被记录成“进入了某个场景”。

步进器构图时会保留 `0` shape 作为可执行动作候选，但不会把它解析成目标场景，也不会被自动跳转经验覆盖。

## Shape 匹配语义

一个 shape 可以同时带有图像匹配、OCR 文本匹配、抠图、容差、区分等配置。图像和 OCR 不必极端互斥，但默认应把它们理解为同一个 shape 的综合检测逻辑。

三态匹配强度：

- `关`：不参与匹配。
- `必`：必须命中，所有必检条件都通过才能认为 shape 通过。
- `定`：命中即可强判定，适合能直接确认场景或目标的强特征。

场景标识本身也遵循三态。勾选场景标识时，如果图像和 OCR 都关，默认应开启图像的 `定` 或当前约定的强判定模式，避免场景标识没有任何实际检测条件。

综合检测结果应同时展示图像相似度和 OCR 识别文本。使用 OCR 时显示识别文本；使用图像时显示相似度；两项都启用时都显示。

## 日常定位任务

日常定位应使用自动标注阶段产出的稳定数据：

- 用日常页顶部稳定锚点识别当前场景。
- 用滚动容器 shape 限定 OCR 搜索和拖拽范围。
- 用预设任务参数决定目标标题文本和匹配方式，例如包含、通配符、正则。
- 找到标题后，用任务块模板对齐标题锚点，生成当前目标任务块的浮动视图。任务块模板本身是普通 shape，只是拥有字段子 shape；浮动发生在父模板这一层，子字段只按父模板相对位置读取，不单独做浮动匹配。
- 在浮动任务块中读取状态、次数/进度和活跃度，再决定是否点击或返回已完成状态。

日常定位必须先通过日常页稳定锚点确认当前场景。确认失败时，只能停止并提示先进入日常页，不能继续滚动任务清单。因为滚动容器的坐标只在日常页内有意义；如果当前还在世界页、弹窗页或其他活动页，继续拖拽会污染现场，也会把“找不到任务”误判成任务完成。

滚动容器的拖拽策略、惯性处理和重叠扫描规则属于自动标注文档；任务调度只依赖它提供的容器边界和默认拖拽行为。

旧版凡修的 `日常_查找` 返回 `(status, task_view)`，其中 `task_view` 不是固定截图区域，而是由标题 OCR 命中结果动态构造的任务块子视图。新版任务调度也应保留这个模型：标题负责定位，任务块模板负责把标题附近的状态、次数和进度读出来。

任务状态建议保持旧版语义：

- `0`：正常找到任务，且未判定完成。
- `1`：特殊进行中状态，例如 `闻道中`。
- `2`：任务已经完成，例如状态命中 `已结束`、`已完成`、`可购买`，或进度确认完成。

如果状态和进度冲突，进度未满应优先按待执行处理；如果能看到任务块但读不到进度，不要直接排到次日，应安排短时间后重试，避免误判完成。

新版 `日常定位` 的一次结果应至少包含：

- `statusCode`：兼容旧版 `0/1/2` 状态。
- `summary`：任务块文本、状态文本、进度、活跃度、来源是模板还是启发式。
- `blockBox`：浮动后的任务块范围，相当于旧版 `task_view` 的空间边界。
- `clickPoint`：后续任务要进入该日常时的推荐点击点，优先来自 `任务状态` 或操作字段。
- `decision`：调度层可直接理解的判断，例如 `ready`、`ongoing`、`completed`、`retry`、`not_found`。
- `reason`：为什么这样判断，尤其要解释状态和进度冲突、未读到进度、找不到任务等情况。

这里的 `decision` 不取代具体任务逻辑。它只是把旧版 `日常_任务需要执行` 的通用部分提前结构化：进度未满优先按可执行，进度已满按完成，状态完成但没有进度时谨慎复核，特殊进行中状态交给任务自身决定下一次调度。

状态判断应尽量放在独立纯函数里，而不是散落在页面 tick 流程中。页面层负责截图、OCR、滚动、模板浮动和点击；纯函数负责把 `notFoundStatus / requireProgress / statusCode / progress` 转成 `decision / reason`。这样后续新增状态词、任务预设或单元测试时，不需要重新理解整个页面组件。

状态词也应集中维护，并明确拆分三类：完成态、进行态、状态文本候选。旧版通用完成态主要包括 `已结束`、`已完成`、`可购买`，特殊进行中态包括 `闻道中`；`未占领`、`前往`、`挑战`、`领取`、`参与`、`进行`、`扫荡` 等词只能作为任务块状态文本抽取候选，不应直接等同完成。页面层只负责把 OCR 文本交给状态识别函数，不应另写一套状态正则。

状态解析还要先从字段文本中抽状态词，再进入判断。任务状态字段附近可能混入次数、活跃度或 OCR 杂字，例如 `活10/次0/3未占领`，不能把整段文本当作状态。正确顺序是：先抽取状态候选词，再抽取进度对，最后把状态词和进度一起交给纯函数判断。进度未满的优先级高于完成态状态词，因为任务块可能显示 `可购买` 但日常进度并未达成，旧版在每日副本、首领、妖族等任务里都保留了这种复核空间。

`日常定位` 本身只负责查找和返回结构化结果，默认不直接点击进入任务。旧版调用者拿到 `task_view` 后会自行决定是否 `task_view.click()`；新版也应保持这个边界：定位层返回 `clickPoint`，执行层只有在确认 `decision=ready` 且该任务策略允许进入时，才点击这个点。这样可以避免“只是想查找状态”时误进入任务，也方便首领、每日副本、妖族这类任务先读取购买/次数状态再决定下一步。

为了让步进器 UI 可以直接验证入口，新版可以提供两个第一层函数：

- `日常定位`：只查找，返回 `statusCode / decision / summary / clickPoint`。
- `日常进入`：复用同一套预设参数，先执行日常定位；只有 `decision=ready` 时才点击 `clickPoint`，其他状态只报告结果，不盲目进入。

这两个函数共享第二层预设，区别只在是否消费 `clickPoint`。不要为了方便把所有日常定位都改成自动点击；查询状态和进入任务是两个不同动作。

### 特殊任务策略备注

`日常定位` 的结果不要被误解成最终任务完成判定。一些任务有自己的二级状态：

- 妖族、每日副本、首领：日常任务块只提供入口和粗进度，进入后还要读取购买次数、挑战次数、剩余奖励次数或刷新 CD。
- 挑战仙缘：标题 OCR 容易拆字；找不到入口时旧版还有“同一任务块上下文确认已完成”的兜底扫描。
- 奇袭：即使日常任务块显示已完成，也可能仍要进入报名次日活动，所以它的业务层不能只看 `completed`。
- 论道：`闻道中` 是进行中状态，不应按普通待执行进入。

因此任务调度层要区分“日常任务块定位结果”和“具体业务任务是否完成”。前者负责提供结构化证据，后者负责决定下一次调度时间、是否购买、是否继续挑战、是否进入次日流程。
