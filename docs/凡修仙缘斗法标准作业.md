# 凡修仙缘斗法标准作业

> Last Updated: 2026-07-25

## 完成判据

- 仙缘斗法只有一个 Job；游戏每天 `10:00` 后开放，周一至周六在 `23:59:59`
  后关闭，周日以 `22:00` 为结算关闭边界。一般调度策略是周一至周六
  `23:00`、周日 `19:00`；触发策略不是开放窗口。失败后 1 分钟重试。
- 手动运行与自动调度使用同一真实开放窗口；在开放窗口内即使尚未到一般触发点，
  也允许执行。只有游戏尚未开放或已到结算关闭边界时才跳过游戏操作。
- 进入 `#308` 后尝试打开 `#311`，只在 `[价格] <= 300` 时购买次数；
  价格超过 300 时返回。若便宜档位已经买完，导致购买入口不再打开或购买后
  自动回到 `#308`，按幂等完成继续挑战，不把整单判失败。
- 每轮重新读取当前三名对手；只在抓包服务确认本轮事实已追平后决策。
- 每轮回到 `#308` 后重新 OCR `[次数]`；只有该 UI 数值为 `0` 才算本周期完成，
  并写入次日业务周期的日程时间，不能因为完成时尚未到当天一般触发点而再次安排
  到当天。抓包次数只作诊断，不参与完成判定。

## 抓包事实

仙缘斗法属于短期现场事实，不建立长期专表。统一入口位于
`backend/core/fanxiu/packet/current_facts.py`：

- `SM_PartnerArenaPlayInfo(90102)`：首屏、自身仙侣队伍战力、次数、刷新次数和三名候选。
- `SM_PartnerArenaChallenge(90108)`：战斗结果及战后新候选。
- `SM_PartnerArenaRefresh(90116)`：刷新次数及刷新后的新候选。

业务只调用 `catch_up_and_get_fanxiu_xianyuan_duel_facts`，不直接遍历抓包服务命令信封，也不在任务里扫描 pcap。追平失败时不得回读旧 `90108` 冒充当前名单。

`90102` 的 `joinerVO.teams` 是稀疏 CList：逻辑槽位数与实际序列化队伍数不同。解码器必须先处理第二个实际数量，再继续解析记录和候选；解码版本变化后由维护体系重解码历史证据。

战力口径固定为：

- 我方：`joinerVO.teams[*].power`，战后可由 `recordVO.attacker.power` 延续。
- 对手：`target.teamVO.power`。

禁止用玩家主角色战力或界面其它战力代替仙侣队伍战力。

## UI 映射

抓包数组顺序不等于 UI 顺序。`#308` 使用已有标注：

- `姓名1/姓名2/姓名3`
- `挑战1/挑战2/挑战3`
- `刷新`

映射顺序：

1. 分别 OCR 三个姓名区域。
2. 对 OCR 姓名和三个抓包姓名构造 `3×3` 相似度矩阵。
3. 枚举三人的全排列，选择总相似度最高的一一映射。
4. 不使用绝对相等或简单包含作为匹配条件。
5. OCR 置信不足时，只允许按已验证的 UI 积分降序兜底；积分并列则停止，不能按抓包顺序或战力猜位置。

## 选人规则

1. 只比较仙侣队伍战力，筛出低于我方的可挑战目标。
2. 可挑战的非友军存在时，选择其中积分最高者。
3. 没有可挑战的非友军，但存在可挑战的友军时，软保护降级，选择可挑战友军中积分最高者。
4. 三人全部高于我方时，若今日仍有刷新次数，点击一次 `刷新`，等待新的 `90116` 事实后重新决策。
5. 刷新后仍无人可挑战，选择三人中仙侣战力最低者强制挑战。
6. 后续每轮继续按同一规则选人，必须把今日剩余挑战次数全部用完；不得提前推进到次日。

友军关系统一调用共享区服关系树 `classify_fanxiu_target_relation`，不在仙缘任务里维护第二份名单。

## 单轮闭环

```text
#308 读取最新事实和姓名 OCR
  -> 动态选择挑战1/2/3
  -> #309 阵容优化
  -> 开始挑战
  -> 若进入 #345 战斗动画则点击跳过
  -> #310 点击继续
  -> 返回 #308
  -> 重新追平抓包并读取剩余次数和新候选
```

购买、阵容优化和战斗仍复用原有正式实现。Scheduler 只提交完整任务 Cell；任务内部不保存跨 Cell 进度。
