# 云梦试剑运行态测量

云梦试剑的积分、排名和兑币采用“运行态只负责采集，数据库保存业务事实，前端只读数据库”的分层。

## 标准字段

- 个人积分与排名：`ActivityrankMgr.Model.ActivityrankData.V_RankDataDic[rank_activity_id].selfRankVO`
- 奖励档位榜单：先由活动 `Activity.rewardGroup` 关联 `ActivityListReward`，按活动日期筛选 `ActivityIdOpenBefore/After` 生效版本，再读取全部 `rankingRange`；每个区间的末名才是该奖励档位的守门员。只有区间末名确实存在于当前榜单时才采集该档。最后从同一活动对象的 `rankVOS` 提取这些名次，并保存档位上下限、角色、区服、宗门和积分。即使某次结果恰好是 `1、2、4、8……`，也必须由配置区间推导，不能硬编码猜测。
- 兑币余额：`WalletMgr.Model.WalletData._WalletInfo[currency_type].amount - borrow`
- 当前 8 跨活动配置：`rank_activity_id=210801`、`currency_type=19`（论剑玉）

当前静态配置中，`210801 -> rewardGroup 8210001`。2026-08-02 生效的档位是 `1、2、3–4、5–8、9–16、17–32、33–64、65–128、129–256、257–512、513–1000、1001–2000`。不同跨次、日期或配置版本必须重新走同一关联链，不能复用这组具体数字。

页面手动更新不再调用云梦专用的钱包根、榜单根或 PID 缓存，而是调用通用活动观测器。云梦活动只声明 `rank_activity_id` 和 `currency_type`；观测器从数据库的 `activity_rank` 与 `resource_state` 标准事实组合一次测量。详细通用边界见《凡修活动标准事实与兑换评估》。

资源事实由 `SM_Wallet` 全量快照以及 `SM_RewardResult/SM_CostResult` 中变化后的绝对 `ResourceVo` 持续更新。运行实例动态选择真正运行凡修进程的设备与 PID，默认设备地址不参与业务身份。HTTP 请求仍禁止进程发现后的 Lua 根扫描或整段内存遍历。

钱包项未驻留、且刚完成一轮自动挑战时，允许使用经过次数校验的精确增量路径：

`上一条数据库测量余额 + YunmengpkData._QuickAutoInfo.rewardList[code=currency_type,type=1].amount`

该路径必须同时满足 `_AutoFightCount == challenge_count_delta`；否则采集失败，不写入半套或推测数据。禁止以截图、OCR、界面文本或另一个同名资源代替以上字段。

## 后端接口

- `POST /api/fanxiu/activity-list/yunmeng-trial/{activity_id}/measurements/collect`
  - 请求：`challenge_count_delta`（可选校验值）、`note`
  - 行为：读取数据库标准事实，追加历史测量，刷新活动当前值、个人榜当前值和当前已有的奖励档位守门员
  - 同一组标准事实不会重复追加测量
  - 返回：本次/上次测量、积分与兑币增量、单次挑战均值
- `GET /api/fanxiu/activity-list/yunmeng-trial/{activity_id}/measurements`
  - 返回该活动按采集时间排列的测量历史

测量历史表 `fanxiuyunmengtrialmeasurement` 为追加式事实记录；刷新页面和读取活动详情不会访问游戏进程。

活动详情中的 `yield_rate` 使用最近一个有效挑战批次，将积分增量和兑币增量统一折算为每百次平均收益，同时返回原始样本挑战数。兑换宝阁的“还需挑战”与该展示采用同一最近批次口径。
