# 步进器-自动探索标注数据

简称：自动标注。

本文描述步进器或 AI 在缺少完整标注数据时，如何通过截图、OCR、拖拽探索和人工/AI 辅助判断，逐步补齐场景、shape、滚动容器和任务块标注。它关注“如何获得可靠数据”，不是“已有数据如何调度任务”。

## 探查前置条件

自动探索只能发生在已有标注不足以支撑当前任务时。执行任何探查前，必须先检索当前帧树中相关场景、shape、子 shape、`sceneJumpTarget`、场景标识、OCR/图像匹配配置、内容方向和备注说明。

如果已有标注已经能表达要做的事，就直接使用标注，不要重新猜坐标、重新 OCR 猜按钮、或把明显已标注的元素当成未知界面。例如要点击某个按钮，应先找该场景下对应 shape；标题不稳定时，再看它的跳转目标、父子结构和标注框，而不是直接写固定点击比例。

主动探索的合法触发条件包括：

- 目标场景或目标元素在帧树里不存在。
- 已有 shape 无法匹配当前画面，并且截图证据显示可能是新状态、遮挡、缩放变化或标注过期。
- 已有标注存在冲突，例如标题、跳转目标、OCR 规则互相矛盾。
- 任务需要新增状态分支，例如同一弹窗出现新的成功、失败、重复领取或冷却提示。

探查完成后，结论不能只留在代码里。稳定结论应回填到帧树标注或本文档相关规则中；临时坐标只能作为一次性验证手段，不能成为长期任务逻辑的首选路径。

## 数据边界

自动标注的产物包括：

- 场景帧：保存当前画面为帧树图片节点。
- 稳定场景锚点：例如日常页顶部“日常”标题，用作场景标识。
- 可操作 shape：按钮、页签、入口、确认/取消、可点击任务块。
- 滚动容器 shape：只表示搜索/操作边界和内容方向，不表示稳定画面元素。
- 浮动结构模板：例如滚动列表里的单个任务块，以及任务块内部的标题、状态、次数、活跃度等相对区域。
- OCR 规则：目标文本、通配符、正则、状态文本、进度文本等。

新增或补充 shape 时必须同时保存对应的原始帧图片。即使当前业务逻辑只使用 OCR、坐标或子 shape，不使用整帧图像匹配，也要让帧树节点有可加载的截图证据；不能只在 JSON 中创建空图节点或只把截图留在临时目录。

自动标注不直接决定任务策略。它只给后续任务调度提供可复用的结构化数据。

## 已有标注作为地图先验

自动标注不是从零开始识图，而是在已有标注地图上继续探索。已有标注数据相当于游戏里的已探查区域，未知界面和未知列表项相当于战争迷雾。自动标注应充分利用已探查区域里的经验，再按当前任务需要扩展未知区域。

已有标注可以提供：

- 命名习惯：场景、shape、滚动容器、按钮和任务块应该如何命名。
- 角色语义：哪些 shape 是场景标识，哪些是动作入口，哪些只是滚动/搜索边界。
- 备注说明：shape 的 `description`、历史备注和人工解释可以帮助 AI 理解它为什么这样框、为什么这样配置。
- 匹配策略：图像/OCR/抠图/容差/区分等配置如何组合，哪些位置适合必检，哪些位置只适合操作范围。
- 地图结构：已知场景之间的跳转关系、返回关系、独立弹窗、遮挡层和特殊 `0/-1` 跳转语义。
- 坐标经验：同类按钮、同类页签、同类任务块在相似界面中的布局规律。

自动探索新区域前，应先检索和阅读相关已有帧、shape 和备注，优先模仿同类场景的标注风格。不要把新界面当作完全孤立的图片处理；它通常是已有地图的邻接区域、变体页面、弹窗覆盖或滚动列表的后续内容。

当新探索结果和已有地图冲突时，不要直接覆盖旧标注。应保留新截图、OCR 候选和推断理由，再判断是旧标注过期、当前状态不同、遮挡导致误判，还是出现了新的场景分支。

## OCR 辅助定位与语义理解

自动标注阶段可以充分引入 OCR。OCR 不只是文本匹配条件，更是探索界面结构和理解元素语义的工具。

OCR 可以用于：

- 元素定位：通过文字 bbox 初步定位按钮、页签、标题、任务名、状态按钮和进度区域。
- 语义命名：根据识别文本给 shape 生成更可读的标题，例如 `日常`、`参与灵脉争夺`、`未占领`、`活动报名`。
- 功能理解：识别“前往”“领取”“挑战”“已完成”“闻道中”等词，推断元素是入口、动作按钮、状态标签还是已完成提示。
- 任务块归并：把同一行或同一卡片内的标题、状态、进度 `0/3`、图标附近文字合成一个任务块候选，而不是只保存孤立文字框。
- 区域校验：确认滚动容器内出现的是任务列表内容，避免把固定标题、底部页签或弹窗文字误归入列表。
- 规则生成：从稳定文本片段生成 OCR 匹配规则，例如包含、通配符或正则。

自动标注时应优先做全量 OCR 观察，再决定 shape 边界。不要只查目标关键词；先识别当前屏幕上“有哪些文字、分别在哪里、它们组成什么控件或任务块”。OCR 结果可以和视觉框、图像匹配、抠图、滚动容器边界结合使用，由 AI 或人工进一步修正为正式 shape。

OCR 不是最终真相。艺术字、遮挡、低清晰度、小字、数字和图标附近文字都可能识别错误，因此自动标注要保留截图、OCR 框和候选解释，必要时用视觉判断和后续点击验证修正。

## 场景锚点与滚动容器

滚动窗口 shape 只表示搜索/操作边界，不表示稳定画面元素。比如日常页中间的任务清单，内部内容会随着滚动不断变化，所以它不能作为场景标识，也不应该开启图像或 OCR 匹配。

稳定场景锚点应放在不会随列表内容变化的元素上，例如日常页顶部的“日常”标题：

- `日常`：场景标识，图像必检，可以作为进入日常页后的稳定识别点。
- `滚动窗口`：滚动容器，图像关、OCR 关、场景标识关，只提供边界和 `contentDirection=down`。

## 滚动窗口内部结构

GUI 自动化里经常会遇到局部结构：一个较大的容器内部重复出现多个结构相似的条目，每个条目又有自己的标题、状态、按钮、数字和说明。滚动列表、背包格子、任务卡片、好友列表、弹窗表单、战斗结算条目都属于这类问题。

滚动窗口内部通常不是无结构文本，而是重复出现的局部结构。日常页中间的任务清单就是典型例子：它由多个任务块组成，每个任务块里有标题、活跃度、次数/进度和状态。

这套思路不是日常页专用，而是 GUI 自动化面对局部结构时的通用建模方式。不要把一个滚动窗口理解成“找到了文本就点一下”的扁平区域；它通常应该拆成三层：

1. `容器`：限定搜索、滚动、点击、截图和 OCR 的边界，例如任务清单、背包区域、好友列表。
2. `条目模板`：描述容器中单个重复项的整体范围，例如一条任务、一件物品、一名好友、一条奖励。它本身仍是普通 shape，只是下面挂字段子 shape，不需要另立特殊组类型。
3. `字段 shape`：描述条目内部的相对字段，例如标题、按钮、状态、次数、价格、图标、说明。

运行时不要让业务代码到处写“标题下面 40 像素是状态”这类临时像素规则。正确做法是：先识别一个字段作为动态锚点，再把条目模板整体平移/缩放到当前条目位置，最后按模板字段读取局部信息。

这里的浮动语义属于条目模板整体，而不是模板内部每个字段各自独立浮动。字段 shape 是父模板坐标系里的相对区域；父模板被锚点移动到当前条目后，字段跟随父模板一起得到当前实际位置。不要把 `标题`、`次数`、`任务状态` 这类字段配置成独立浮动目标，否则运行时会重复扫描、互相错位，甚至把字段匹配到相邻任务块。

自动标注应把这种结构显式标出来：

- `任务块模板`：表示单个任务块的整体范围；它是可被匹配、可被检测、可被标注调优的普通 shape，同时作为字段子树的父节点。
- `标题`：动态锚点，用 OCR 命中目标任务名；它是父模板定位依据，不是独立浮动 shape。
- `次数`：读取 `0/3`、`10/次` 等进度或次数信息。
- `任务状态`：读取 `未占领`、`已完成`、`闻道中`、`可购买` 等状态文本。
- `活跃度`：辅助识别任务块内部奖励/活跃度结构，避免把别的数字误当进度。

这些子 shape 不是固定屏幕位置上的唯一元素，而是任务块模板里的相对结构。运行时先在滚动窗口所在页面中识别 `标题`，再把 `任务块模板` 对齐到这个标题锚点，随后按模板内部相对位置读取 `次数`、`任务状态` 和 `活跃度`。

旧版凡修的关键技巧是：OCR 查标题时保留在 `日常/日常` 外层视图里查，返回的标题锚点坐标才能直接用于 `create_sub_view("任务块", "标题", anchor)`。如果先把 OCR 裁到任务清单子区域，再把局部坐标拿去构造任务块，容易错位到下一条任务。

通用原则：

- 先标容器，再标条目模板，再标条目内部字段。
- 条目模板应包含一个稳定锚点，例如标题、头像、图标、序号或按钮文本。
- 自动探索时先在统一坐标系里找锚点，再用锚点把模板浮动到当前条目。
- 条目内部字段按模板相对位置读取，不单独开启浮动，不要在业务代码里临时猜“标题下方多少像素是状态”。
- 如果同一容器里存在多种条目类型，应增加区分 shape 或模板变体，而不是把所有条目硬套一个模板。
- 模板字段的备注要写清楚作用，例如“状态文本用于判断是否完成”“次数用于提取进度”“图标列用于区分奖励结构”。

### 通用局部结构模型

局部结构不是日常页的特例，而是 GUI 自动化的通用抽象。遇到任何“一个区域里有很多重复块，每块内部又有字段”的界面，都优先按下面的模型建模：

- `scope`：外层范围，负责限定 OCR、图像搜索、拖拽和截图边界。
- `template`：单个重复项的模板，负责描述这个条目整体有多大。
- `anchor`：模板里的定位字段，负责把模板对齐到当前真实条目。
- `fields`：模板里的相对字段，负责读取标题、状态、次数、价格、按钮、奖励等局部信息。
- `actionPoint`：由字段或模板推导出的推荐操作点，负责让任务层点击正确的局部位置。
- `evidence`：运行时收集到的文本、图像相似度、bbox 和来源，用于解释为什么认为这是目标条目。

这个模型要求所有字段共享同一个父级坐标系。锚点可以来自 OCR，也可以来自图像或图标；但一旦锚点命中，模板和字段都应通过同一个平移/变换得到当前条目的实际范围。不要混用“容器裁剪后的局部坐标”和“整屏坐标”，否则字段会错位到相邻条目。

自动标注时，AI 可以先用 OCR 做候选归并：把同一水平带或同一卡片内的标题、状态、进度、按钮文字合并为一个条目候选，再反推模板边界和字段边界。确认后要把这种结构保存为 shape，而不是只把推断逻辑留在一次性的分析里。

运行时也应保留证据链：命中了哪个锚点、模板浮动到哪里、字段读到了什么、最终点击点来自哪个字段。这样后续出现误点、漏扫或 OCR 错字时，可以从日志和 overlay 直接复盘，而不是重新猜坐标。

### 字段读取与动作点

条目模板除了用于识别，还应该能提供后续动作所需的数据：

- `标题锚点`：用于把模板浮动到当前条目。
- `状态字段`：用于判断可执行、已完成、进行中、可购买、未占领等状态。
- `进度字段`：用于提取 `m/n`，并在状态和进度冲突时优先进度。
- `操作字段`：如果条目右侧有按钮或状态区，点击点应优先来自这个字段；没有字段时才退回条目中心或启发式点击点。
- `辅助字段`：活跃度、奖励图标、价格、等级、时间等，用于区分相似条目或解释为什么命中。

自动标注保存模板时，应尽量把“后续要读什么”和“后续要点哪里”都显式标出来。这样任务调度层拿到的是一个可执行的局部结构，而不是一堆彼此孤立的框。

## 滚动拖拽惯性

滚动搜索不能把拖拽比例理解成内容实际滚动比例。触摸列表有惯性：同样是从 A 拖到 B，实际内容滚过多少取决于持续时间、速度曲线、加速度、释放瞬间速度、列表自身阻尼和设备实现。`duration` 越短，释放速度通常越大，刹车惯性越强，内容可能继续滑出很远。

因此“拖拽 50%”并不等于“内容只移动半屏”，它可能实际滚过 80% 或 90%。滚动 OCR 搜索的核心目标是避免漏扫。假设当前可见列表是 `1 2 3 4`，如果一次手势导致内容实际滚过超过 100% 可视窗口，下一屏可能直接变成 `6 7 8 9`，中间的 `5` 就被跳过了。

为了避免漏扫，自动探索必须保留重叠区：每次拖拽后，新旧画面至少有一部分共同内容，再对新画面重新 OCR。

## 拖拽默认参数

窗口拖拽框架的默认手势比例就是约 50%。普通滚动搜索应使用框架默认值，不要在每个调用点重复显式配置。

50% 是框架默认安全余量，不是对内容位移的线性承诺，也不是某个日常任务的临时经验值。不要把默认拖拽比例随手改成 100%。如果调用方没有特殊原因，应信任框架默认参数。

如果设备或页面惯性更强，应继续降低手势比例或增加拖拽持续时间，而不是追求“一次翻一屏”。对已经命中但靠近底部的任务块，使用更小的复核拖拽，例如 18%，让任务块完整露出后再判断状态和进度。

旧版 AnLib 的 `drag_to()` 默认 `drag_percent=50`，实现是以当前 shape 中心为基准，起点和终点分别偏移半个手势距离。这个默认值的意义不是“温和一点”，而是给不可控惯性留重叠扫描余量。

## 探索流程

自动探索滚动列表时：

1. 先确认当前场景锚点，而不是直接拖动。
2. 在滚动容器范围内做 OCR，记录全量文本和 bbox。
3. 找不到目标时，在滚动容器内部执行默认拖拽。
4. 拖拽后等待画面稳定，重新截图/OCR。
5. 保留每屏 OCR 结果和候选框，不能用拖拽前坐标推断拖拽后内容。
6. 命中目标但靠近容器底部时，小幅复核拖拽，让任务块完整露出。
7. 将稳定的场景锚点、滚动容器和目标任务块回填到帧树标注数据。

拖拽必须发生在滚动容器 shape 内；不要按整页高度拖，否则固定标题、底部页签和列表惯性会共同放大实际滚动距离。
