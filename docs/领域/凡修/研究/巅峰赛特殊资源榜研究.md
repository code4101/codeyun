# 巅峰赛特殊资源榜研究

## 状态与结论

巅峰赛不能作为普通资源榜的一条 occurrence 接入。它是一个跨一周的复合赛事：外层活动负责总生命周期，六个阶段榜按星期与轮次展开，另有总榜、赛后领奖和独立膜拜阶段。普通资源榜的单榜、商店、礼包和一次性完成模型无法表达这些状态。

当前工程已完成只读身份解析、日程投影和业务状态投影；尚未注册自动作业，也未授权竞猜、领奖或膜拜动作。实现事实以以下代码为准：

- `backend/core/fanxiu/activity/peakrace_schedule.py`：从静态 Activity 关系和 Runtime 出现事实投影完整赛事族。
- `backend/core/fanxiu/instrumentation/peakrace.py`：只读 PeakraceMgr 运行态。
- `backend/core/fanxiu/activity/peakrace_state.py`：纯业务状态机与安全门卫。
- `backend/core/fanxiu/activity/peakrace_business_snapshot.py`：校验进程身份后组合公共日程与赛事运行态。
- `GET /api/fanxiu/dynamic-instrumentation/peakrace/business-state`：带凡修标准授权的公共只读业务快照；调用方不再自行拼接日程和 Runtime。
- `backend/core/fanxiu/activity/peakrace_lifecycle.py`：纯观察 checkpoint 时间规划；未注册 Scheduler、未写状态、未授权动作。
- `backend/core/fanxiu/activity/peakrace_checkpoint.py`：逐 checkpoint 的 `observed/blocked/error` 判据；不得用顶层状态替代历史事实。

## 与普通资源榜的差异

| 维度 | 普通资源榜 | 巅峰赛 |
| --- | --- | --- |
| 生命周期 | 单一 occurrence | 外层赛事、六阶段、总榜、膜拜组成复合生命周期 |
| 参赛条件 | 通常按活动是否开放 | 还要判断当前轮次、分组和本人资格 |
| 完成判据 | 单榜 checkpoint 可闭环 | 每阶段观察、竞猜策略、赛后领奖、膜拜均需独立留痕 |
| 动作风险 | 可按榜类型挂接安全适配器 | 竞猜确认不可撤销；领奖与膜拜也需要独立完成事实 |
| 调度 | 一个活动时间点 | 周二至周日阶段边界，加外层 reward/close 与膜拜窗口 |

因此不得把巅峰赛塞入 `resource-ranking`，也不得复用其商店、免费礼包或资源消耗适配器。

## UI 与业务状态机

已知资产只覆盖三个业务表面：

- `#368`：排名页，只能作为榜单可见性的 UI 证据。
- `#369`：竞猜页，只能作为候选与已选状态的观察入口。
- `#370`：竞猜最终确认页；确认后不可修改，自动化必须停止并等待显式策略。

业务状态按 `prepare → open → reward → closed` 投影；当外层结束而膜拜活动开放时进入独立 `worship` 状态。`open` 阶段还要同时解析：

1. 当前阶段与预期星期是否一致；
2. Runtime 当前轮次是否与阶段轮次一致；
3. 本人是否进入当前阶段分组；
4. 当前阶段榜和总榜是否完整加载；
5. 竞猜策略、次数上限与截止时间是否具有权威来源。

任一来源缺失、多个活动冲突、进程身份不一致或轮次不一致时，状态投影失败关闭。页面出现 `#370` 时额外产生不可逆确认阻断，不允许自动点击。

## 推荐作业边界

后续正式入口应是独立顶层 Job，例如 `peakrace-lifecycle`，并拥有自己的 checkpoint 存储。第一阶段只实现观察型 checkpoint：

- 外层 occurrence 对账；
- 六个阶段的 open/close 观察；
- 竞猜策略与窗口观察，不执行选择；
- 外层 reward 状态观察；
- 膜拜 open/close 观察；
- 生命周期关闭审计。

纯规划器已经能够从真实 outer Runtime 区间和六阶段 `TC` 配置解析稳定实例键及上述时间边界。实例键使用 outer activity id + 起止时间，不依赖可能刷新的 Runtime 行 id；同秒 checkpoint 显式保证先观察阶段开放，再观察竞猜策略。当前仍缺独立持久化表与 Scheduler Job，因此不得把规划器存在误报成正式 Job 已完成。

checkpoint-specific 完成谓词现已实现为纯函数：只有 `observed` 是终态，`blocked/error` 均需重试；阶段开放必须有 child Runtime、同轮次、明确资格及完整阶段榜/总榜，竞猜策略未知不会结算，最终 close audit 必须看到全部前置 checkpoint 键。独立持久化表和 Scheduler Job 仍未实现，因此生产调度边界保持不变。

只有在公共只读入口能权威给出竞猜限额与截止、用户提供明确竞猜策略、领奖状态和膜拜日次数完成判据后，才能分别讨论动作解锁。不得通过截图猜策略、直接调用 Lua、拼协议请求或用普通资源榜动作补偿。

## 2026-09-01 首次实证

当日 05:00 开放前的同进程只读快照确认：外层赛事为 `32620001`，当前预期为第一轮炼体阶段，本人处于第 1 组、自排名第 2。阶段子活动在开放前尚未被 Runtime 实际加载，因此日程投影明确标记为 configured，而不是伪装成 runtime observed。

06:17 开放后的同进程公共业务快照进一步确认：外层已进入 `open`，阶段为第一轮“炼体巅峰”，资格为 `qualified`，本人仍在第 1 组、自排名第 2；但阶段榜与总榜都尚未由 Runtime 加载，竞猜策略也没有权威来源。因此顶层 `complete=false`、`observation_complete=false`、`safe_to_act=false`，阻断项精确为 `current_stage_rank_incomplete`、`total_rank_incomplete` 与 `guess_policy_unknown`。这次复验没有为了补数据强行导航 UI，也没有触发竞猜、领奖或膜拜动作，证明开放期的失败关闭边界按设计生效。

08:35 再次通过长期存活 Kernel 读取同进程组合快照，`pid=2628`、`process_start_ticks=5812` 仍一致，outer/阶段/资格/分组/自排名均未变化；阶段榜与总榜依旧未自然加载，竞猜策略依旧 unknown，三个 blocker 与 06:17 完全一致。这说明“未加载”不是开放瞬间的短暂竞态；在没有正式 UI 观察 Job 和竞猜策略前，系统必须持续保持 `safe_to_act=false`，不能靠等待数小时后自行放宽。

10:02 第三次通过同一长期存活 Kernel 只读复验，`pid=2628`、`process_start_ticks=5812` 继续一致，outer=`open`、第一轮“炼体巅峰”、qualified、第 1 组、自排名第 2；阶段榜和总榜仍未自然加载，竞猜策略仍为 `policy_unknown`，`complete=false`、`observation_complete=false`、`safe_to_act=false`。连续近四小时的开放期证据进一步排除短暂初始化竞态，也证明单靠后台 Runtime 读取无法替代一次受控 UI 观察；在独立 observe-only Job 落地前仍不得执行竞猜、领奖或膜拜。

这条运行数字只作为本次研究证据，不是长期配置；后续运行必须重新读取公共日程与 PeakraceMgr，不得复用本段数值。

## 验收边界

当前完成的是只读研究与工程化状态投影，不代表赛事全生命周期自动化完成。正式验收至少需要：

1. 05:00 后真实 Runtime 复验 outer/stage/round/group/qualification；开放期 child 未实际加载、轮次不一致或阶段榜/总榜不完整时，`observation_complete` 必须为 false；
2. 若 UI 自然进入相关页面，记录 `#368/#369/#370` 的可见状态，但不为了研究强行导航；
3. 每个 checkpoint 都能独立重试且不会触发不可逆动作；
4. 生命周期历史完成事实可持久化，而不是用“页面已关闭”倒推完成。
