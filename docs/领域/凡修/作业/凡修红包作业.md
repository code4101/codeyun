# 凡修红包作业

本文记录红包作业的当前业务真值与可追溯演进。当前实现以代码、Runtime 终态和回归测试为准；历史段落只用于解释稳定性问题为什么反复出现，不得把旧路径恢复为当前实现。

## 当前业务真值

红包只有两类处理路径：

1. 普通红包：Runtime 给出待处理群和红包候选，进入对应群后直接领取。
2. 鸿运福签：Runtime 给出活动频道、唯一待领 UID 和唯一话术；进入“鸿运福签”，清空输入框，写入 Runtime 话术，发送，等待红包弹层，点击领取。

鸿运福签的稳定路径固定为：

`Runtime 唯一 UID/频道/话术 → 活动 Tab → “鸿运福签”标题行 → 清空并输入 Runtime 话术 → 发送 → #397[开] → 同 UID rewarded 终态`

约束：

- Runtime 是话术的唯一真值。输入框存在遮挡与横向滚动，不再用局部 OCR 复验或否定 Runtime 话术。
- “鸿运福签”标题是会话行身份；祝贺话术会出现在多条活动预览中，不能兼任列表行定位锚点。
- 不点击会随卡片动画漂移的复制图标。
- 输入框可能保留中断前内容；每次发送前先 `MOVE_END + DEL` 幂等清空，再写入当前 Runtime 话术。
- 日常业务严禁 Esc、Android Back 和 `KEYCODE_BACK`。退出输入层、聊天层和弹窗只能点击当前真实画面的正式 `[返回]`、关闭或背景 Shape；没有可靠 Shape 时保留现场并停止。
- 成功判据不是“点过发送/开”，而是同一 Runtime UID 进入 `rewarded` 终态并安全返回世界页。

## 后续修改门槛

修改红包路径前，必须先证明当前两类业务模型不再成立。不得为了“多一层确认”重新加入复制图标定位、话术 OCR 真值、Esc/Back 兜底或另一套内部队列。任何稳定性修复都必须用正式 Scheduler 入口完成同 UID 终态验收，并把结果追加到本文时间线。
