# 可验证所有权租约与双向通信设计

> 本文沉淀 CodeYun 中“锁、资源占用、任务领取、运行态 owner”的通用设计原则。凡修行为树本体不是锁案例；它更像一个 Jupyter 内核，负责串行执行外部提交的 cell。本文只把凡修中的服务 owner、job group isolation 等会残留占用的部分作为相关案例。

## 一句话定义

传统锁只表达“资源被占用”。可验证所有权租约表达的是：

```text
某个资源的使用权，在一段时间内授予给一组可识别、可验证、可回收的持有人。
```

这不是单纯的锁文件设计，而是一种用于高风险协调关系的通信设计：把原本“调度方发出命令后失联”的单向关系，升级为“命令、持有人、执行代次、心跳、回收依据都可查询”的双向协调协议。

这里不是要求所有通信都做身份标记和双向确认。普通请求、普通通知、幂等查询、失败后可直接重试的轻量动作，不需要上这套模型。它专门解决“持有人失踪会阻塞后续参与者”的问题，尤其是锁、资源占用、任务领取、设备独占和并发配额。

## 核心洞察：锁是通信问题

单向命令模型在普通通信里通常没有问题；真正危险的是它被用来表达“占用关系”时。锁的失败后果不是少一次消息，而是后面的人都在等待一个可能已经消失的持有人。

典型问题是：

```text
调度方 -> 执行方：执行 command
调度方 -> ?：执行方还活着吗
调度方 -> ?：执行方还在执行原 command 吗
调度方 -> ?：异常中断后资源能不能回收
```

可验证所有权租约只在这种会造成阻塞的协调关系上增加身份标记：

```text
command_id：这次指令是谁
owner_id：谁接了这次指令
generation：第几代执行关系
lease_token：本次租约 token
heartbeat_at：最近一次证明仍活跃的时间
expires_at：最晚有效时间
```

一旦这些字段存在，通信关系就不再是“我喊了一声”，而是：

```text
调度方发出 command_id
执行方以 owner_id 接管 command_id
第三方可以围绕 owner_id + command_id + generation 验证执行关系是否仍有效
```

因此，身份标记是锁类双向通信的最小锚点；租约、心跳、代次和 token 是让这个锚点可靠的工程配套。它的目标不是让通信协议变复杂，而是避免“加锁者失踪后无人能证明它已经失效”的死锁。

## 概念分层

### 执行声明 Execution Claim

声明某个执行主体正在持有某项资源或任务。

典型字段：

```json
{
  "resource": "fanxiu-behavior-tree",
  "owner_id": "pid:53420",
  "owner_kind": "process",
  "command_id": "scheduler_poll",
  "generation": 17,
  "lease_token": "uuid",
  "acquired_at": 1781997198.0
}
```

### 执行租约 Execution Lease

声明这个持有关系的有效期和续约状态。

典型字段：

```json
{
  "heartbeat_at": 1781997220.0,
  "expires_at": 1781997520.0,
  "ttl_seconds": 300
}
```

### 执行见证 Execution Witness

第三方如何验证 owner 是否仍然有效。见证不一定是单一进程检查，也可以是运行态注册表、队列状态、远端 worker 状态、心跳文件或服务状态 API。

典型字段：

```json
{
  "witness": {
    "type": "process+command",
    "pid": 53420,
    "command_fingerprint": "fanxiu_bt.py service",
    "entry_id": "30b82d72-8a76-4a74-be4b-4fc1591c6ce2"
  }
}
```

### 防旧写入 Fencing Token

如果旧 owner 卡住后恢复，不能让它继续写入新状态。写入方必须携带当前代次或单调 token；存储层只接受最新 token。

```text
旧 owner 仍活着 != 旧 owner 仍有写入权
```

这点是“进程还在，但指令已经变了”时最重要的防线。

## 从互斥锁推广到并发锁

这个模型不局限于单例锁。

### 容量为 1：可验证租约互斥锁

```json
{
  "resource": "fanxiu-behavior-tree",
  "capacity": 1,
  "holders": [
    {
      "owner_id": "pid:53420",
      "command_id": "scheduler_poll",
      "generation": 17,
      "lease_token": "uuid",
      "heartbeat_at": 1781997220.0,
      "expires_at": 1781997520.0
    }
  ]
}
```

### 容量为 N：可验证租约信号量

```json
{
  "resource": "image-ocr-worker",
  "capacity": 3,
  "holders": [
    {"owner_id": "worker-a", "command_id": "cmd-1", "lease_token": "t1"},
    {"owner_id": "worker-b", "command_id": "cmd-2", "lease_token": "t2"}
  ]
}
```

获取条件不是“锁文件不存在”，而是：

```text
有效 holder 数量 < capacity
```

释放或回收条件是：

```text
holder 主动释放
或 holder 心跳过期
或 holder 对应进程/worker 不存在
或 holder 仍存在但 command_id/generation 已不匹配
或 holder 的 fencing token 已被新代次替代
```

因此，互斥锁、信号量、读写锁、任务领取、设备占用、配额门控都可以共用同一个基础模型。

## CodeYun 当前相关场景

### 凡修行为树本体不是锁案例

凡修行为树内核应按 Jupyter kernel 理解：

```text
多个下游调度渠道 -> 同一个行为树内核 -> 内核一次只运行一个 cell
```

这里的核心约束是“内核串行执行”，不是“外部加锁后直接运行”。Jupyter kernel 自身的执行协议就应该保证同一时间只推进一个 cell；下游渠道如果提交多个 cell，应该由下游调度器决定排队、跳过、合并、重试或等待。

因此，凡修行为树本体的简化模型是：

- 内核服务单例：只启动一个 Jupyter/Runtime 内核。
- 内核执行串行：一次只运行一个 cell。
- 下游渠道多源：工程 scheduler、AI、手动入口、本地脚本都只是 cell 提交者。
- 下游冲突归下游调度：哪个 cell 先提交、是否排队、是否去重，不应该塞进行为树内核本体。

这部分不要设计成复杂锁系统。只有当“占用状态可能残留，导致后续参与者等待”时，才进入本文的可验证租约模型。

### 凡修行为树常驻服务 owner

当前实现已经有明确雏形：

- `backend/core/fanxiu/runtime/behavior_tree.py`
  - `fanxiu_behavior_tree_service_owner_path()`
  - `read_fanxiu_behavior_tree_service_owner()`
  - `_fanxiu_process_exists()`
  - `_fanxiu_process_matches_service_owner()`
- `backend/core/fanxiu/data_annotation/runtime_runner.py`
  - `_acquire_service_owner()`
  - `_write_service_owner()`
  - `_mark_service_heartbeat()`
  - `_release_service_owner()`

现状优点：

- owner 文件记录 `pid/token/entry_id/generation/step/updated_at`。
- 读取 owner 时会验证 pid 是否存在。
- 读取 owner 时还会验证 pid 是否仍像凡修 service 进程。
- service 循环会持续写 owner，已经具备心跳性质。
- release 时按 token 删除，避免误删别人的 owner。

主要缺口：

- 字段仍偏实现态，缺少统一 `owner_id/command_id/lease_token/heartbeat_at/expires_at` 语义。
- stale 判断散落在读取函数和 runner 内部，尚未抽成通用 `ExecutionLease` 判断。
- `generation` 已存在，但语义应收窄为 owner 租约代次；它最多参与 owner 更新/释放校验，不应扩散成行为树 cell 执行状态的复杂锁协议。
- `step` 更像展示字段，不应承担 command 身份；建议新增 `command_id` 或 `session_id`。

### 凡修 job group isolation

当前实现：

- `fanxiu_job_group_isolation_path()`
- `read_fanxiu_job_group_isolation()`
- `acquire_fanxiu_job_group_isolation()`
- `release_fanxiu_job_group_isolation()`
- `fanxiu_job_group_isolated()`
- `clear_stale_fanxiu_job_group_isolation()`

现状优点：

- 已复用 `acquire_json_lease/release_json_lease`。
- 有 `ttl_seconds`、`token`、`pid`。
- stale lease 可以清理。
- owner pid 死亡时可以释放隔离。

主要缺口：

- 它更接近租约锁，但和行为树 owner 是两套字段口径。
- 缺少更明确的执行来源标记，只能知道“某进程拿了隔离”，不能精确知道这是本地脚本、AI 保底还是工程调度拿的隔离。
- 目前是容量 1；未来如果某些作业组允许并发，应升级为 `holders[] + capacity`。

### 后台任务 runner 文件锁

当前 `backend/core/runtime/background_task_runner.py` 使用 `FileLock` 限制后台任务行为树单例。

这类锁适合本进程内或单机轻量保护，但它缺少业务身份：

- 不知道 owner 是哪个任务。
- 不知道 owner 当前执行哪条 schedule。
- 不知道 owner 是否只是文件残留。
- 第三方只能看到锁存在，不能验证执行关系。

建议后续不要直接删除文件锁，而是在外层补一个 `ExecutionLease` 状态文件：文件锁负责原子互斥，租约文件负责身份、心跳和可观测性。

### 后台任务队列 resource_lock

当前 `backend/core/runtime/background_task_queue.py` 已有 `resource_lock` 元数据。

这说明系统已经在表达“任务需要某类资源”。但现在它主要是标签，不是可验证租约。后续可以把 `resource_lock` 作为 `resource`，在执行前进入统一租约门控：

```text
resource_lock -> resource
queue task id -> command_id
running snapshot id -> owner/session
```

## 凡修相关简化建议

凡修行为树本体应简化为“单例 Jupyter 内核 + 串行 cell 执行器”，不要把下游调度冲突都建模成内核锁。

建议边界：

- 行为树内核只负责：启动、停止、执行一个 cell、返回执行状态。
- 行为树内核保证：同一时间只运行一个 cell。
- 下游调度器负责：是否提交、何时提交、冲突时排队还是跳过。
- 工程 scheduler、AI、手动按钮、本地脚本都不直接并行执行行为树任务，只向内核提交 cell。
- 下游 cell 之间的业务互斥、去重、优先级和重试，是调度器策略，不是行为树内核的锁模型。

凡修中仍适合保留可验证租约的点只有两类：

- 服务 owner：防止启动多个内核服务实例，或识别旧 owner 残留。
- job group isolation：防止某些外部本地作业和工程常驻调度抢同一组资源。

如果当前实现把过多 `running/queued/owner/isolation` 逻辑塞进行为树内核，应优先做减法：

```text
内核：单例 + 一次一个 cell
调度器：提交策略 + 冲突处理
租约：只处理会残留占用的外部资源
```

## 设计边界

### 不要泛化到所有通信

身份标记双向通信不是通用默认项。只有当单向通信失败会留下“别人必须等待的占用状态”时，才值得引入。

不需要使用本模型的场景：

- 普通查询请求。
- 普通事件通知。
- 可以自然超时并由调用方重试的短请求。
- 不占用共享资源的幂等操作。
- 失败后不会阻塞后续参与者的后台统计或日志写入。

需要优先使用本模型的场景：

- 锁的持有人失踪后会导致死锁。
- 任务领取后不释放会导致后续任务无法运行。
- 设备、进程、截图流、OCR worker 等资源被独占。
- 并发配额被占满后，其他请求只能等待。
- 旧执行流恢复后可能覆盖新执行流结果。

判断标准很简单：

```text
如果持有人失踪，后面的人是否只能傻等？
```

如果答案是是，就需要身份标记、第三方验证和可回收租约；如果答案是否，就不要为了“协议完整”增加复杂度。

### 它不替代线程锁

`threading.Lock` 仍适合保护同一进程内的内存临界区，例如缓存、列表、状态字典。可验证所有权租约适合跨进程、跨线程、跨调度入口、跨 AI/工程主体的执行权管理。

### 它不要求所有场景都持久化

纯内存、单线程、短生命周期代码不需要上租约。只有当存在以下任一条件时才需要：

- 持有人可能异常退出。
- 调度方和执行方生命周期不同。
- 第三方需要判断资源是否可回收。
- 同一资源存在多个入口竞争。
- 状态会被旧执行流延迟写回。
- 用户需要在 UI 或日志里解释“谁占着”。

### 它不等于只检查 pid

`pid` 只是低级身份。可靠判断必须组合：

```text
owner_id + command_id + generation + lease_token + heartbeat/expires_at + witness
```

进程仍存在但指令已变化时，旧持有关系应视为失效。

## 推荐术语

- 通用中文名：可验证所有权租约
- 通用英文名：Verifiable Ownership Lease
- 互斥锁形态：可验证租约互斥锁 / Verifiable Lease Mutex
- 并发锁形态：可验证租约信号量 / Verifiable Lease Semaphore
- 执行会话形态：可验证执行会话 / Verifiable Execution Session
- 通信模式：身份标记双向通信 / Identity-Anchored Bidirectional Communication

## 实施顺序

1. 不急着改所有锁，先把凡修 owner 文件字段口径统一。
2. 在读取层兼容旧字段，增加新字段投影，不改变执行路径。
3. 给凡修 owner 增加 `command_id/session_id/heartbeat_at/expires_at`。
4. 抽出通用租约判断函数，先服务凡修 owner 和 job group isolation。
5. 给 Runtime 状态写入加 `generation/lease_token` 校验。
6. 再评估后台任务 runner、resource_lock、OCR/截图资源是否迁移到同一模型。

## 验收标准

- UI 能明确显示当前资源由谁持有、执行哪条指令、最后心跳时间。
- owner 异常退出后，第三方能在不依赖 owner 主动释放的情况下回收。
- owner 仍活着但 command/generation 不匹配时，旧执行权失效。
- 旧 owner 延迟写入不会覆盖新 generation 状态。
- 单例锁和 N 并发门控共用同一套 holder/lease 判断。
- 行为树内核常驻运行，调度入口只领取执行会话，不把“关闭调度”等同于“关闭内核”。
