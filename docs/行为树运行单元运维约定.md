# 行为树运行单元运维约定

> Last Updated: 2026-07-01

## 目的

统一 CodeYun 对“外部行为树运行时”的正式运维路径，避免后续 agent 被旧 `xlserver`、旧脚本路径或手工直跑单课的历史经验误导。

本文适用于两类运行单元：

- 考勤行为树：业务运行时在 `xlproject/xlsln/kq5034/kqmain.py`
- 凡修行为树：业务运行时在 CodeYun 自己的 Runtime/Scheduler 体系

共同原则：

- CodeYun 是控制层和状态聚合层，不一定是业务节点定义所在仓库。
- 行为树必须作为单实例常驻服务管理，不要并行拉起第二棵树。
- 日常诊断优先读状态文件、日志、运行单元状态接口；不要先凭 UI 直觉或历史口径猜。
- 不要绕过状态机直调单个业务 step，除非任务明确要求且该行为经过业务授权。

### 3. 正式控制 API

统一使用 `backend.core.attendance_behavior_tree_service` 暴露的 helper：

- `get_attendance_behavior_tree_status()`
- `start_attendance_behavior_tree_service(replace_existing=True)`
- `stop_attendance_behavior_tree_service(timeout=5.0)`
- `show_attendance_behavior_tree_schedule(limit=20)`
- `reset_attendance_behavior_tree_state()`
- `probe_attendance_subprocess_utf8(text="考勤中文探针")`
- `build_attendance_behavior_tree_log_lines(limit=500)`

运行管理层还提供统一 runtime action 协议：

- `POST /api/runtime/items/builtin/attendance-behavior-tree/actions/inspect`
- `POST /api/runtime/items/builtin/attendance-behavior-tree/actions/restart`
- `POST /api/runtime/items/builtin/attendance-behavior-tree/actions/reset`
- 设备入口代理：
  - `POST /api/device-entries/{entry_id}/runtime/items/builtin/attendance-behavior-tree/actions/inspect`
  - `POST /api/device-entries/{entry_id}/runtime/items/builtin/attendance-behavior-tree/actions/restart`
  - `POST /api/device-entries/{entry_id}/runtime/items/builtin/attendance-behavior-tree/actions/reset`
- 运行页：
  - `frontend/src/standard/cluster/tasks/page.vue` 的运行单元右键菜单已接入“查看调度”“重启调度器”“重置状态”
  - 这些动作只对声明了 `actions` 包含对应 action key 的 builtin service 显示，当前默认是考勤行为树

使用原则：

- 需要重启时，优先 `start_attendance_behavior_tree_service(replace_existing=True)`。
- 需要从统一 runtime 管理接口远程执行“停旧实例并拉起唯一实例”时，优先走 `actions/restart`。
- 需要确认下一次锚点和状态文件时，优先 `get_attendance_behavior_tree_status()`。
- 需要只读查看当前调度摘要时，优先 `show_attendance_behavior_tree_schedule()`。
- 需要从统一 runtime 管理接口远程触发“查看调度/重启/重置状态”时，优先走上述 `actions/{inspect|restart|reset}` 路由，而不是自定义临时管理脚本。
- 只有明确要“删除调度状态、让所有 start='next' 节点从下一锚点重新计算”时，才调用 `reset_attendance_behavior_tree_state()`。
- `reset_state` 不会补跑错过的任务；它只清空行为树状态。
- 如果怀疑课程入口子进程中文 stdout 再次乱码，先调用 `probe_attendance_subprocess_utf8()` 验证当前 Python/env/capture 链路，不要先怀疑业务课程脚本本身。
- 当前 Windows 链路下看到 `root python + descendant python + conhost` 三条进程记录不等于多 root 行为树；判断是否双树，优先看 `process_count/root_processes`，不要把 descendant 误报成第二棵树。
- 当前运行单元日志摘要也已按这个口径展示：`行为树根进程数 / 子孙进程数 / 总进程数`，并在进程清单里标注 `root` 或 `descendant-of:<pid>`。

## 二、凡修行为树正式路径

### 1. 先读的文档

- `docs/凡修行为树运行框架约定.md`
- `docs/凡修data-annotation运行设备约定.md`

### 2. 正式原则

- 凡修行为树是 CodeYun 内部 Runtime/Scheduler 体系，不应被当作“随手起一个脚本”的临时流程。
- 运行、停机、手动作业、守护开关都应走后端 Runtime 管理层。
- Canonical Python 实现路径优先认：
  - `backend.core.fanxiu.runtime.behavior_tree`
  - `backend.core.fanxiu.data_annotation.runtime_control`
  - `backend.core.fanxiu.data_annotation.runner`
- 默认不要直调私有 `_DataAnnotationRuntimeRunner`；优先使用运行页、公开 API、注册任务和 `debug_eval`。
- 运行页 builtin service 的 `stop` 当前语义是“请求停止当前任务”，不是“关闭 resident service 进程”；排障时不要误读成彻底停机。
- `backend.core.fanxiu_behavior_tree`、`backend.core.fanxiu_data_annotation_*` 旧扁平模块现在只是兼容别名；新代码和新文档不要再把它们当成主实现路径。

### 3. 当前可用运维动作

- 统一运行管理接口：
  - `POST /api/runtime/items/builtin/fanxiu-behavior-tree/actions/inspect`
  - `POST /api/runtime/items/builtin/fanxiu-behavior-tree/actions/restart`
  - `POST /api/runtime/items/builtin/fanxiu-behavior-tree/actions/wake`
  - `POST /api/device-entries/{entry_id}/runtime/items/builtin/fanxiu-behavior-tree/actions/inspect`
  - `POST /api/device-entries/{entry_id}/runtime/items/builtin/fanxiu-behavior-tree/actions/restart`
  - `POST /api/device-entries/{entry_id}/runtime/items/builtin/fanxiu-behavior-tree/actions/wake`
- `inspect` 返回：
  - 当前 runtime 状态
  - resident owner 摘要
  - 手动作业队列摘要
  - 普通作业隔离锁状态
  - doctor watch 最新巡检摘要
- `wake` 会写入本地控制请求 `wake_service`，用于唤醒 resident loop 立即重新轮询；它不是彻底重启进程。
- `restart` 会先写入 `shutdown_service` 控制请求，等待旧 owner 释放后，再重新 ensure 常驻服务；它是明确的“重启行为树”语义，不再要求操作者自己拼 `stop/wake/trigger`。
- 运行页右键菜单会把这些动作显示为“运行诊断”“重启行为树”“唤醒行为树”，避免把 `wake` 误读成 restart。

### 4. 对 agent 的操作要求

- 接到“凡修行为树没跑/要重启/要保底”这类任务时，先确认当前机器是否是规定运行主机。
- 先看 Runtime 状态、守护清单、手动作业、到期作业、owner/锁，再决定是否重启。
- 不要同时保留工程 Scheduler、AI 保底调度和第二个临时行为树执行流。

## 三、推荐排障顺序

### 考勤行为树

1. 看 `get_attendance_behavior_tree_status()`：
   - 是否单实例
   - `next_run_at`
   - `last_error`
   - `state_last_error`
   - `state_updated_at`
   - 日志更新时间
2. 看 `kqmain.<hostname>.state.json`：
   - 目标任务 `next_run_at` 是否推进
   - `last_error` 是否为空
3. 看 `kqmain.<hostname>.log`：
   - 是否有“收尾完成”或“任务已完成”
   - 是否有更新更晚的 `RuntimeError`/课程入口失败
4. 必要时：
   - 停旧实例
   - 重置状态
   - 拉起唯一实例

### 凡修行为树

1. 确认运行主机与运行页状态
2. 确认是否已有 resident loop / owner / manual job / due task
3. 优先用 `inspect` 看 owner / 队列 / 隔离 / doctor 摘要
4. 再决定是唤醒、重启还是只提交手动作业

## 四、给后续 agent 的结论

- 先认控制层，再认业务运行时，不要把两者混成一个仓库。
- 先认状态文件和正式 service helper，再认历史经验。
- 考勤：`CodeYun service helper -> xlproject kqmain.py -> scheduler 状态/日志`
- 凡修：`CodeYun runtime management -> resident loop / runtime 状态 -> 标注与任务定义`
