# 凡修行为树运行框架约定

> Last Updated: 2026-06-19

## 核心原则

- 通用术语和目标分层见 [通用可执行系统架构：内核、框架与调度](./通用可执行系统架构-内核框架调度.md)。凡修行为树后续重构应按“内核是运行容器、框架是执行语义、调度是触发来源”的边界收敛；本文保留当前 Runtime/Scheduler 实现细节与迁移期约束。
- 凡修行为树应被理解为独立于 CodeYun UI/Scheduler 的常驻内核服务。CodeYun 后端、前端页面、本地脚本和自动调度都只是提交任务或修改配置的入口；CodeYun 热重载、页面关闭、作业组关闭或暂停自动调度不应停止内核服务，也不应阻止手动作业继续使用内核。
- “暂停调度”只控制自动作业是否由工程 Scheduler 自主到期提交，不等同于关闭行为树内核，也不等同于禁止 AI 保底调度。守护组、作业组和单个作业开关只影响对应工程节点是否参与 tick；内核服务本身应继续存在。
- 行为树里的“守护”和“作业”本质上都是后端运行框架管理的分组节点；“守护/作业”只是当前默认分组，不是底层不可变分类。
- 行为树调度底座必须复用 `pyxllib.prog.behavior_tree`，不要在 CodeYun 里重复实现行为树、选择器、守护服务调度或生成器推进逻辑。
- CodeYun/Fanxiu 只实现业务层节点：识别当前场景、关闭弹窗、执行作业、场景跳转、点击 shape、等待到达等。
- `pyxllib.prog.behavior_tree` 外层需要有 CodeYun/Fanxiu 专用动态容器，负责读取后端配置、分析当前白名单、生成本轮 guard/job 节点。
- 当前核心仍是 `tick + yield / yield from`：作业内部用生成器保存进度，行为树每轮只推进一次；守护命中时不推进作业生成器。
- 前端不是守护/作业清单的事实来源，不应硬编码业务项、补本地假状态或自行决定哪些功能存在。
- 前端只负责展示后端清单、提交开关状态、传递“哪些节点被允许执行”这类白名单信息。
- 具体执行逻辑、默认清单、启用状态、日志归属、运行状态和调度行为都应由后端维护。

### 标注数据优先

- 行为树业务节点必须先使用当前 `entry_id` 的已有帧树标注数据：`CODEYUN_DATA_DIR/fanxiu/data-annotation/entries/<entry_id>/asset-tree.json`，并从同一 entry 目录下的 `images/` 读取参考图片和同名 sidecar JSON。
- 后端读取入口是 `_data_annotation_asset_tree_path(entry_id)`、`_load_asset_tree()`、`_index_images()`；业务节点拿到的 `ctx["images"]` 已按帧编号索引。
- 场景判断用 `isSceneIdentity / sceneIdentityRole`，点击用已命名 shape 的 `x/y/w/h` 和匹配配置，跳转用 `sceneJumpTarget`。不要从当前截图重新目测坐标、根据 OCR 文本偏移猜按钮，或在业务代码里写临时固定点。
- 如果现有标注与真实游戏画面不一致，任务必须失败并提示缺少/过期标注，由人工补标或修标后再重试；不能把“猜到一个能点的坐标”当作行为树基础设施的一部分。
- Runtime 和 agent 禁止自主补标：不要自动保存未知截图到资产树，不要创建“未知场景”占位 shape，不要根据当前画面猜测场景编号或 shape 区域，也不要把未标注的实际落点新增到 `sceneJumpTarget`。用户给到的凡修任务默认视为标注数据已经准备好；若运行中发现缺标注、标注过期或跳转落点未配置，应立即中断并把缺失项交给人工处理。
- 对已经在 `sceneJumpTarget` 中声明的目标，Runtime 命中后可以累加该目标的次数并写回资产树。这是确定性运行统计，不属于自主补标；它用于维护高频路径排序和后续调度特征。
- 帧树里的「遮挡标记」分组是固定排除区域，不是要匹配的固定内容。列表哈希、滚动签名、顶部内容签名等稳定性判断必须避开这些 shape 区域，因为其中可能不断出现不同通知或公告文字。
- 滚动列表和动态条目应使用“滚动容器 + 父标题锚点 + 子控件模板”的标注方式，动作执行必须有可重复的结果闭环；真实案例见 [凡修 data-annotation 闭环与浮动模板案例](./凡修data-annotation闭环与浮动模板案例.md)。

### 调度底座

- 后端 runtime 应使用 `Action` 包装普通函数或生成器函数。
- 作业子流程应优先写成生成器，使用 `yield` 让出本轮 tick，使用 `yield from` 组合子流程。
- 守护应作为 `WithServices` 的 service 节点挂在作业子树外层；嵌入 Runtime 的守护处理了遮挡事件后不能长期返回运行中状态抢占主作业，应记录事件并让主作业继续获得 tick。
- 当前 `backend/api/fanxiu.py` 的 `_DataAnnotationRuntimeContainer` 负责把后端配置转换成 `BehaviorTreeRunner + Action + WithServices`；后续补场景跳转时，应继续沿用这个入口，不要新增手写状态机循环。
- 现有礼包码等历史任务函数还没有全部改成生成器，这是迁移过程中的业务层遗留；框架层已经先对齐 pyxllib 行为树。

### 动态容器

- `_DataAnnotationRuntimeContainer` 是 CodeYun/Fanxiu 的高级容器，不是 pyxllib 的替代品。
- 容器按“分组”组织运行记忆。每个分组有独立记忆，同一分组同一时间最多保留一个正在运行的任务。
- 当前默认分组按调度优先级从高到低：
  - `guard`：守护，最高优先级；只处理已标注全局遮挡和弹窗，不承载业务任务。
  - `manual_job`：手动作业；用于人工调试、API 临时提交和受控一次性任务。
  - `job`：自动作业；来自 Scheduler 到期任务。
- 容器输入来自后端事实源：
  - 守护定义：`_DataAnnotationRuntimeRunner.guard_definitions`
  - 守护启用状态：后端 runtime 状态与持久化配置
  - 作业实例：后端 Scheduler tasks、本地配置、到期分析结果
- 前端白名单只能通过接口修改后端配置；行为树运行时不直接信任前端临时状态。
- 容器每次构建或 tick 时应从后端状态判断节点是否启用。未启用节点返回 `SKIP`，不应执行截图、点击或业务逻辑。
- 分组优先级是第一调度维度。每轮先按 `guard -> manual_job -> job` 选择最高可运行分组，然后才进入该组内部逻辑；不能先续跑任意旧 yield 再考虑分组。
- 组内运行记忆是第二调度维度。进入某个分组后，如果该组已有未完成的 yield / `RUNNING` 任务，必须先续跑它，直到 `SUCCESS / FAILURE / STOP`；同组新候选不得插队，也不得改写当前运行任务的 checkpoint。
- 组内后续逻辑由分组自己定义：`guard` 每次全量遍历已启用守护；`manual_job` 在组内无运行记忆时按提交/发送时间升序取一条；`job` 在组内无运行记忆时按调度触发时间升序取一条。`manual_job` 与 `job` 本质共享“候选池 + 组内运行记忆 + 时间顺序取下一个”的状态模型，差别只是时间字段语义。
- 跨组规则：高优先级组先运行；高优先级组命中并返回运行中时，低优先级组本轮暂停，但低优先级组的候选状态不应被改写成“已排队”。因此，正在跑一半的 `job` 可以被 `guard` 或 `manual_job` 暂停/插队，但不能被另一个 `job` 打断，即使另一个 `job` 的触发时间更早。
- 每轮调度只从一个分组启动一个新 task。即使同组同时有多个候选，也只启动排序后的第一个；该 task 完整结束并释放该组运行记忆后，resident loop 下一轮再读取最新 Scheduler/队列状态决定是否启动下一个。
- 当前 runner 已对齐的部分：空闲 tick 先跑守护，守护真实处理弹窗时本轮不再启动手动/普通作业；普通作业执行中通过 `WithServices` 允许守护暂停作业生成器。尚未完成的部分：`manual_job` 对运行中 `job` 的暂停/恢复式插队仍需要组级运行记忆改造；不得用“停止当前 job 后启动 manual_job”冒充该语义。
- `job_group_enabled=false` 的语义是关闭工程常驻 Scheduler 的自主启动入口，避免工程层和 AI/人工层同时抢行为树。它不是“这些作业今天不需要运行”。当 AI 保底调度接管时，应继续按 Scheduler `due_tasks` 顺序一次提交一个具体作业，并让 Runtime 正常回写该作业的 `last_result/next_time/retry_after`。
- AI 保底调度是另一个触发主体，不是第二个行为树执行器。它必须先确认 owner、Runtime、manual_jobs、隔离锁均未占用，再通过本地公开入口或 core 控制层提交任务；已有任务运行时只能等待或跳过本轮，不得并行创建第二个执行流。
- AI 保底调度的框架入口应优先使用 `uv run python scripts/fanxiu_bt.py watch-doctor --max-iterations 1 --auto-run-due`。该入口负责 doctor、安全判断、`job_group_enabled=false` 覆盖、逐个提交、提交后复查和批量清空到期项；提示词或人工操作不应绕过它去改 Scheduler 数据。
- AI 保底调度的汇报不能把“Runtime 任务返回 success”直接等同于“游戏业务已完成”。新版 `日常_助手` 是综合入口，细节见 [凡修data-annotation闭环与浮动模板案例](./凡修data-annotation闭环与浮动模板案例.md)；它覆盖的 `日常_游历`、`日常_妖王来袭`、`日常_妖族袭城`、`日常_灵祖`、`日常_灵塔`、`日常_双修` 不再作为独立 Scheduler 作业，未覆盖的其它日常仍需要各自的业务完成证据。
- `daily_audit` 是只读日常总账复核作业：它必须通过 Runtime 进入 `#69 日常`，遍历已标注 `滚动窗口`，读取任务块标题和最后一个 `当前/总次数`。该结果可以反证 Scheduler 的旧成功记录：若审计时间晚于 task 的 `last_run_at` 且次数未满，对应已启用 task 应重新进入到期候选；若审计时间早于最后运行时间，则不能再拿旧审计否定新运行。未映射的未完成条目只能报告为待补能力/映射，不得猜测归属。
- `日常_助手` 不是“全日常总控”，但新版小助手 `一键执行` 已覆盖 `日常_游历`、`日常_妖王来袭`、`日常_妖族袭城`、`日常_灵祖`、`日常_灵塔`、`日常_双修`。这些旧作业不再单独启用；其它未覆盖日常，例如 `日常_每日副本`，仍由独立 Scheduler task 表达。
- 如需限时抢占，优先新增更高优先级分组，例如 `urgent_job`，不要轻易开启同组抢占。
- 业务操作函数只能做“一步”并交还控制权，不能实现“循环直到完成”的同步兼容路径。连续操作必须通过 `yield`、`RUNNING` 或下一轮 tick 推进。
- 手动按钮不应直接调用业务逻辑。手动操作应写入后端 `manual_job` 队列，由行为树按分组优先级调度；有守护时先处理守护，有普通自动作业待运行时也先完成手动作业。
- `/data-annotation/runtime/task/start` 这类调试入口也应按手动作业理解：它提交一个临时任务并唤醒常驻行为树，不代表创建或关闭行为树服务本身。
- `scheduler/task/run-now` 同样只提交一次性手动作业并唤醒常驻行为树，不能为了“立即运行”先直接消费队列里的旧手动作业。所有手动作业必须由 resident loop 串行判断空闲后启动。
- 手动作业用于调试和人工干预，不能被全局守护候选扫描长期挡住。当前手动作业执行节点会跳过嵌入式守护 service；空转守护和自动作业仍走守护优先。
- 手动作业 API 和行为树执行器之间必须有提交中介：API 只把后端已注册的 `task_type + payload` 标准化为一条 `manual_job` 实例并落队列/唤醒 resident loop，不直接调用行为树节点，也不绕过已有运行状态。
- 新增手动作业能力优先通过 `register_fanxiu_data_annotation_manual_job()` 注册，注册项定义 label、payload 标准化、默认优先级、是否可中断、是否允许进入 Scheduler。调用方不应再散落维护 label 白名单、supported 白名单和 dispatch 分支。
- 手动作业注册表定义“后端支持哪些临时能力”，`manual_jobs.json` 只保存“本次提交的一条实例”。产品前端不要把任意 Python 代码当成普通作业能力开放；本机开发/AI 调试可使用受控的 `debug_eval` 手动作业执行临时代码。`debug_eval` 仍必须进入 `manual_job` 队列，受常驻行为树单例、timeout、stop、日志归属和 `readonly/act` 模式约束；复杂逻辑验证稳定后应沉淀为正式注册作业。
- 任务函数注册表和任务实例清单要分离：
  - 注册表定义“后端支持哪些能力”。
  - 实例清单定义“当前机器配置了哪些作业、是否启用、参数是什么、何时到期”。
- 未实现但已定义的守护/作业可以是 pass 节点；它们仍属于后端清单，前端不应隐藏或增加 disabled 第三态。

## 守护模型

- 守护定义在后端 `_DataAnnotationRuntimeRunner.guard_definitions`。
- 守护是常驻行为树的高优先级节点配置，不应拥有独立的生命周期线程。开启守护只是把该节点纳入后续 tick；关闭守护只是让该节点返回 `SKIP`。
- 空闲复原属于行为树 resident loop 的内建自维护调度，不属于业务 Scheduler，也不是 AI/本地临时调度。resident loop 在没有运行任务、没有手动作业、没有到期自动作业时，最多每 5 分钟自主运行一次 bounded idle recovery。
- 空闲复原必须复用现有守护项：先走 `device_health` 的既有健康检查/恢复策略，再用 `close_popups` 做多轮弹窗处理，直到守护跳过、达到上限或被新任务打断。它不得启动业务作业，也不得新增独立心跳线程或第二套设备恢复逻辑。
- Runtime 状态接口返回 `guard_items`，每个守护至少包含：
  - `id`
  - `label`
  - `message`
  - `enabled`
  - `running`
  - `entry_id`
- 前端页面 `/fanxiu/data-annotation/runtime` 必须遍历 `runtimeStatus.guard_items` 渲染守护列表，不要手写“关闭弹窗”“万灵切磋邀请”等业务行。
- 守护开关统一调用 `/data-annotation/runtime/guard/set`，提交 `entry_id`、`guard_id`、`enabled` 和 `interval_seconds`。
- `/data-annotation/runtime/guard/set` 只能修改后端配置并唤醒常驻服务，不能启动一个与主行为树并列的“守护线程”。
- 已实现守护和未实现守护走同一套接口。未实现守护应在后端以 pass/空实现登记状态和日志，不能在前端做 disabled 第三态。

### 当前守护

- `device_health`：环境健康守护。
  - 负责低频检查 TapTap 内置 MuMu/安卓容器状态，发现模拟器 runtime error、安卓容器未启动等环境异常时，按 `shutdown -> launch -> app launch` 恢复。
  - 默认每 60 秒最多执行一次真实 `MuMuManager info` 检查；普通 tick 只读缓存状态，避免每秒启动外部进程。
  - ADB 取帧失败只作为升级信号：连续多次失败后才触发真实健康检查，不能因为单次 ADB 抖动重启模拟器；若连续失败且错误属于连接拒绝、设备不存在或远端重置，即使 MuMuManager 显示 Android 已启动，也允许强制重建安卓容器。
  - 该守护只恢复运行介质，不处理游戏内公告、登录页、活动弹窗或业务流程；这些仍归 `close_popups` 和具体 Runtime 任务。
- `close_popups`：真实执行“关闭弹窗”守护。
  - 使用当前 tick 的同一帧进行弹窗识别。
  - 只扫描资产树顶层 `弹窗` 分组的第一层图片，嵌套子目录不参与。
  - 命中后点击对应关闭 shape，本轮向行为树返回 `RUNNING` 以暂停作业；下一轮重新取帧继续守护检测，直到守护跳过后作业才继续获得 tick。
  - #47/#84 这类需要连续操作的弹窗也按多轮 tick 处理：第一轮点击 `不再提示` 后立即让出，下一轮重新取帧确认状态，再点击 `确认`。不要在守护内部 `sleep` 后连续点击。
  - #84 如果是独立命中，且上一轮没有 `click:不再提示` 事件，则优先按父弹窗 `空白` 关闭；只有上一轮刚点击过 `不再提示` 时，下一 tick 才点击 #84 子弹窗 `确认`。
  - 关闭弹窗只保留单步 `step` 语义；不要再增加 `until_clear` 这类直接循环清空弹窗的同步入口。
  - 弹窗候选匹配可以做并行优化，但只能并行“打分”，不能并行“点击”。当前按本轮候选数量并行打分，全部分数返回后仍按候选顺序选择第一个命中项，保证行为语义不变。
  - 弹窗候选列表按资产树文件签名缓存，避免每轮 tick 反复读取和解析资产树；资产树修改后缓存自动失效。
  - 候选索引保留两类来源：`弹窗` 分组第一层图片无条件进入候选，用于 #47 这类父弹窗和子弹窗特殊处理；其它嵌套帧只有明确 `sceneJumpTarget=-1` 的独立退出 shape 才进入候选，避免把普通嵌套页面当全局弹窗反复扫描。
  - `弹窗` 分组第一层图片里的 `空白` 是背景关闭动作，很多弹窗点击遮罩/背景即可关闭；守护应把它当作合法关闭 shape，即使没有填写 `sceneJumpTarget`。同一弹窗同时存在 `空白`、`关闭`、`确定` 时，优先点击 `空白`：显式关闭按钮常常很小，实机点击容错差；`确定` 可能触发领取、前往、跳转等业务行为，带来额外状态复杂度；点击背景取消弹窗通常是最大、最稳、最少副作用的关闭方式。非弹窗嵌套页仍优先依赖 `sceneJumpTarget=-1` 判断是否可作为全局退出动作。
- `wanling_invite`：当前为空实现。
  - 可以开关。
  - 后端登记启用状态并写日志。
  - 未来补具体检测/处理逻辑时，应接在同一个 `guard_id` 下。

## 作业模型

- 作业清单来自后端 Scheduler tasks。
- 前端只展示后端返回的作业，并提交启用/禁用后的任务配置。
- 本地开发调试不再以“前端手动作业”为主路径。高频调试应优先直接写 Python 调 core 门面，例如 `from backend.core.fanxiu.runtime.behavior_tree import go_fanxiu_scene; go_fanxiu_scene("#121")`；也可以使用本地脚本入口，例如 `uv run python scripts/fanxiu_bt.py go-scene #121`。两者都提交到同一个 resident kernel 队列，由常驻行为树内核串行复用资产树、识别、点击、OCR 和等待能力。
- AI/本地自动化调用默认不走 CodeYun HTTP API，也不依赖前端登录态、cookie、token 或鉴权中间件。凡修行为树本质是本机 Runtime/行为树内核，AI 调度应优先使用 core 门面或 `scripts/fanxiu_bt.py` 这类本地公开入口；HTTP 只作为前端/服务适配层。
- 只有明确调试前端鉴权、路由、请求体兼容、API 权限、前端按钮行为或远程服务调用链时，才优先走 `/api/fanxiu/...` HTTP 路径。否则用 HTTP 会把“鉴权失败、登录态缺失、前端请求包装问题”和“行为树是否真实运行”混在一起，降低自检结论可信度。
- 本地公开入口仍必须走真实 Runtime/行为树语义，不能为了绕过 HTTP 鉴权而改成私有函数直调、构造帧、静态截图或只读状态改写。需要验证守护 tick 时，优先使用 `runtime_framework.execute_tick(...)`、`scripts/fanxiu_bt.py service/status/logs` 或已注册手动作业入口，让运行器真实取帧、匹配、点击并落 Runtime 日志。
- Python 通用入口为 `submit_fanxiu_task(task_type, payload, run_mode="auto")`：`auto` 和 `enqueue` 都只提交到 resident kernel 队列；`direct` 不再绕过 kernel，而是“提交并等待完成”的兼容语义。排队后需要像普通脚本一样等待结束时加 `wait=True`，结果会保留 `submitted_status` 和最终 `runtime_status`；`direct` 会把最终 Runtime 状态作为主返回值，并附带 `queued_job`/`wait_result`。`go_fanxiu_scene("#121")`、`run_fanxiu_mail_cleanup(...)` 这类快捷函数默认也走同一个队列入口，并支持同样的 `wait=True`。
- 本地多步 Python 调试可以用 `with isolate_fanxiu_job_group(reason="debug"):` 包住一段脚本，临时隔离普通作业组；上下文退出或异常时自动释放隔离锁。单个提交任务默认会把隔离 token 写入手动作业 payload，显式上下文主要用于“一段 py 里连续做多步”的场景。
- 本地 `go-scene`、`mail-check`、`task` 默认使用 `--run-mode auto`：命令只提交到 resident kernel 队列并返回 queued 状态；需要命令像脚本一样等到任务真实结束时，使用 `--wait` 或 `--run-mode direct`。`direct` 只是 submit-and-wait，不允许绕过 resident owner。
- 本地可用作业类型应通过 `uv run python scripts/fanxiu_bt.py tasks` 查看。该命令读取 core 注册表，显示 `task_type`、label、是否支持 Scheduler、是否可中断，避免开发者从前端或源码里记忆作业名。
- 本地脚本还应支持常用观测动作，例如 `uv run python scripts/fanxiu_bt.py status`、`uv run python scripts/fanxiu_bt.py logs --scope guard`、`uv run python scripts/fanxiu_bt.py clear-logs`。这些命令读取/修改 core Runtime 持久状态，不需要启动或重启 CodeYun。
- 需要在本地单独跑常驻行为树时，应使用 `uv run python scripts/fanxiu_bt.py service`。这是前台开发进程，Ctrl+C 即停止当前进程内的 resident service；它不依赖 CodeYun HTTP API，也不要求前端存在。
- 若单次 `runtime_framework.execute_tick(..., guard=True, manual_job=False, scheduled_job=False)` 返回 `waiting_context`，不要把它解释为“守护识别失败”或“弹窗不会点击”。这只说明当前进程没有可用 service context 或常驻服务尚未恢复；应先用 `scripts/fanxiu_bt.py status/owner` 确认 `service_running/owner`，必要时短时运行 `scripts/fanxiu_bt.py service --duration-seconds <N>`，再通过 `logs --scope guard` 和 `last_guard_event` 判断是否真实执行了守护点击。
- 因为行为树是全局单例，本地启动 resident service 前可先运行 `uv run python scripts/fanxiu_bt.py owner` 查看当前 owner。该命令只读取 `behavior_tree_service_owner.json` 做诊断，不跨进程强杀或抢占 CodeYun 后端持有的执行器。
- 当 CodeYun 后端或本地 service 已经持有 resident owner，开发者要添加手动作业时应优先使用 `uv run python scripts/fanxiu_bt.py enqueue go_scene --target-scene-id 121` 这类命令。它直接写入 core 手动作业队列，由 resident service 下一轮 tick 串行执行；不需要打开前端，也不需要重启 CodeYun。`enqueue` 默认会临时隔离普通作业组，并把隔离 token 写入手动作业 payload；该手动作业结束后由运行器释放隔离锁。确实要允许普通作业并行等待时，才显式加 `--no-isolate-jobs`。
- `enqueue` 和 API submit 返回的 Runtime status 应包含 `queued_job.id`，本地调试时后续 `cancel <job_id>`、查看队列或定位日志都以这个 id 为准。
- 本地排队后如果希望命令像普通脚本一样等待完成，可使用 `--wait`，例如 `uv run python scripts/fanxiu_bt.py go-scene 121 --wait` 或 `uv run python scripts/fanxiu_bt.py enqueue go_scene --target-scene-id 121 --wait`。等待逻辑只轮询 core 队列和 Runtime 状态，不经过前端接口。
- 本地误加入手动作业后，应使用 `uv run python scripts/fanxiu_bt.py cancel <job_id>` 或 `uv run python scripts/fanxiu_bt.py clear-queue` 清理队列。默认只删除未运行的 pending/queued 项；running 项应优先通过停止当前任务处理，只有确认只是残留记录时才使用 `--force`。
- 普通作业组隔离状态应可本地诊断：`uv run python scripts/fanxiu_bt.py isolation` 查看当前隔离锁，`isolate --ttl-seconds 300` 手动隔离普通作业组，`release-isolation <token>` 按 token 释放。隔离锁是 core runtime 文件，不依赖前端/API。
- 本地停止当前任务应使用 `uv run python scripts/fanxiu_bt.py stop`。该命令写入 core 控制请求文件，由当前 resident owner 进程的 control watcher 消费并设置运行中的 stop event；不要把“本地新起 Python 进程里的空 runner stop”当成跨进程停止。
- 本地脚本应依赖 `backend.core.fanxiu.runtime.behavior_tree` 这类 core 门面，不直接依赖 `backend.api.fanxiu`。API 层只是 CodeYun 的适配器；行为树本体应逐步迁移到 core 层，保证调试时新起 Python 进程即可加载最新代码，不需要重启 CodeYun。
- `backend.core.fanxiu.runtime.behavior_tree` 作为本地 py 入口，模块顶层不应硬导入 `backend.db`、`backend.models` 或 `sqlmodel`；需要从 CodeYun 数据库解析设备时，只能在 `resolve_fanxiu_entry()` 内懒加载，失败时退回轻量本地入口对象。
- `backend.core.fanxiu.data_annotation.runtime_control` 作为状态/队列/调度控制层，模块顶层也不应为了类型标注硬导入 `backend.models`、`backend.db` 或 `sqlmodel`；入口对象按 duck typing 使用即可。
- `backend.core.fanxiu.data_annotation.runtime_runner` 不应顶层导入 `backend.db.engine`、`backend.models`、`sqlmodel` 或 `fastapi`；导入 runner 本体不能加载 CodeYun ORM 或 HTTP 框架。数据库 engine 只能在 `_db_engine()` 内懒加载，`_default_engine = None` 只作为测试或外部注入点保留。
- 行为树 core 层不能抛 `HTTPException`；运行时请求非法、任务冲突等错误用 `backend.core.fanxiu.runtime.errors.FanxiuRuntimeError` 表达，API 层再翻译成对应 HTTP 状态码。
- 邮件清理需要读取/更新 `FanxiuMailRecord` 时，应通过 `backend.core.fanxiu.mail.runtime_store` 这类存储适配层完成；runner 只保留行为树流程、画面状态判断、相似度和策略组合，不直接写 SQLModel 查询。
- 行为树执行动作所需的截图、匹配、点击、拖拽、按键、文本输入和 OCR helper 可以保留在 core 驱动模块，但 runner 顶层应懒加载这些适配器，避免仅导入行为树本体就加载 API/用户/设备模型。
- data-annotation 资产树路径、行为树 runtime 状态文件路径和普通作业组隔离锁属于 `backend.core.fanxiu.runtime.behavior_tree` 门面基础设施；API 层可以保留同名兼容包装，但不应再复制实现。
- CodeYun 的运行单元管理也应通过 `backend.core.fanxiu.runtime.behavior_tree` 启停和读取状态，不应从 `backend.core.runtime_management` 反向导入 `backend.api.fanxiu`。
- Runtime runner 单例的常用操作应收敛到 `backend.core.fanxiu.runtime.behavior_tree` 门面，例如状态读取、唤醒、手动作业启动、守护开关、日志替换和任务 label 解析。HTTP API 不应继续扩散 `_DATA_ANNOTATION_RUNTIME_RUNNER.xxx` 直接调用；迁移时可以按端点逐步替换，保证旧测试和旧接口兼容。
- Runtime runner 本体归 `backend.core.fanxiu.data_annotation.runtime_runner.DataAnnotationRuntimeRunner`；API 层只保留 `_DataAnnotationRuntimeRunner` 懒兼容别名和 `_DATA_ANNOTATION_RUNTIME_RUNNER` 懒代理，不能在 `backend.api.fanxiu` 导入阶段直接导入或实例化 runner 本体。
- Runtime runner 全局实例应通过 core 工厂按需创建；API 可以在过渡期继续暴露兼容句柄给旧测试和旧端点，但不应直接负责“导入时实例化并注册全局单例”的语义。
- Runtime runner 类注册与独立实例创建归 `backend.core.fanxiu.data_annotation.runner` 管；`backend.core.fanxiu.runtime.behavior_tree` 只作为本地脚本和运行单元管理使用的门面继续导出这些函数。core 工厂默认直接创建 core runner，不应再通过导入 `backend.api.fanxiu` 获取 runner 类。
- 行为树执行动作所需的游戏窗口点击、拖拽、截图、匹配、按键和文本输入 helper 归 `backend.core.fanxiu.game.window_actions`；runner 不能再回调 `backend.api.fanxiu` 的同名 HTTP helper 执行动作，API 里的同名 helper 只能作为 core helper 的薄包装。
- `backend.core.fanxiu.data_annotation.runtime_runner` 不应导入 `backend.api.fanxiu`，也不应读取 API 侧 monkeypatch 过的路径、engine 或 datetime。测试和本地调试需要替换运行路径或 DB 时，应直接 patch core runner 模块或 core 门面。
- Runtime 状态文件、世界事实、手动作业队列、常驻服务确保、任务启动/停止、守护开关、单步 tick、日志查询/清理、Scheduler task 读写、到期计划、排队状态更新、`run-now` 和 `run-due` 执行编排归 `backend.core.fanxiu.data_annotation.runtime_control`；API 里的同名私有函数只作为端点和旧测试兼容包装，不应复制状态/队列实现。
- 新代码和测试需要构造独立 runner 时，应优先使用 `backend.core.fanxiu.runtime.behavior_tree.create_fanxiu_runtime_runner()`，不要继续直接调用 `backend.api.fanxiu._DataAnnotationRuntimeRunner()`；后者只是迁移期兼容名。
- 作业类型注册属于 core 能力：默认作业由 `backend.core.fanxiu.data_annotation.default_jobs` 显式注册，`debug_eval` 调试作业由 `backend.core.fanxiu.data_annotation.debug_eval` 显式注册；注册由 `backend.core.fanxiu.runtime.behavior_tree.ensure_fanxiu_runtime_jobs_registered()` 及 core runtime/control 入口按需触发，API import 阶段不能注册作业或依赖注册副作用。
- `backend.core.fanxiu.runtime.behavior_tree` 的本地运行和服务启动入口负责初始化默认作业注册；本地脚本不能依赖 `backend.api.fanxiu` 的导入副作用来获得 `go_scene`、`mail_cleanup` 等任务能力。
- 本地脚本运行期间默认隔离普通作业组：常驻行为树仍可执行守护，但 Scheduler 到期作业不会被拉起，避免调试动作被低优先级日常作业干扰。隔离是带作用域的 runtime 锁，脚本结束后自动释放，不修改普通作业的全局启用配置。
- “手动作业队列/API”只作为兼容和受控入口保留，不应成为开发者日常调试的最快路径；成熟、稳定、适合日常运行的能力再进入普通作业清单。
- 工程自动作业由常驻行为树在空闲 tick 中读取 Scheduler 到期结果后串行提交；`schedule_kind=manual` 的任务不能被空转 loop 当成到期任务反复运行，只能由用户手动提交。
- Scheduler 到期任务也应在 resident service 线程内串行执行，不再创建 `fanxiu-data-annotation-scheduler` 业务线程。工程 `run-due` 只是唤醒常驻 loop，实际启动仍由 loop 判断空闲后完成；AI 保底在工程作业组关闭时可以作为调度主体提交同一个 Scheduler task，但仍必须走 Runtime/行为树公开入口并保持单任务串行。
- 前端不应创造作业项，也不应用本地状态模拟作业是否存在。
- 新增作业类型时，优先在后端定义任务类型、执行逻辑、默认说明和支持状态；具体本机是否加入清单、是否启用、下次触发时间属于后端/本地数据配置。

## 日志模型

- 运行日志按分组归属记录，不是前端临时拼出来的日志。
- 每条日志应带：
  - `scope`：例如 `guard` 或 `job`
  - `item_id`：例如 `close_popups`、`wanling_invite` 或某个作业 id
- 守护日志使用 `scope=guard`。
- 守护组任务定义稳定，`item_id` 使用具体 `guard_id`，例如 `close_popups`。
- 手动作业是临时实例队列，统一写入组级日志：`scope=manual_job`、`item_id=manual_job`。单条日志消息中保留临时 job id，例如 `[manual-...] 手动作业已启动：单步识别`。
- 不允许在业务 worker 结束时再开一个额外 drain 线程去消费下一条手动作业；这会制造第二套调度入口。worker 只负责完成当前任务、落状态、持久化，下一条任务由常驻 loop 下一轮 tick 启动。
- 手动作业应在 resident service 线程内串行执行，不再创建 `fanxiu-data-annotation-manual-job` 业务线程。这样用户手动提交的调试/API 任务和空转 tick 使用同一个调度入口。
- 手动作业被 claim 后仍保留在 `manual_jobs.json`，状态改为 `running`；完成后再由运行器按 job id 删除。后端重载恢复时，只重排可安全重放的 running 手动作业，例如 `mail_claim_check`、`detect_scene`、`manual_tick`；礼包码等可能有副作用的 running 作业不自动重放。
- 自动作业组任务定义稳定，日志使用 `scope=job`，`item_id` 使用具体 task id。
- 前端右键“日志”只进入详情页并按 `scope + item_id` 查询，不自行筛选或重建业务含义。

## Tick 与帧复用

- 行为树一轮 tick 只应获取一次当前帧。
- 公开 tick 入口按分组参数理解：`guard` 控制本轮是否运行守护前置检查和空闲弹窗守护，`manual_job` 控制是否消费一条手动作业，`scheduled_job` 控制是否启动普通到期作业。对应 HTTP 入口为 `/data-annotation/runtime/cell/tick`，core 入口为 `runtime_framework.execute_tick(...)`。
- 执行单位由 `run_mode` 表达：`tick_once` 只执行一个最小 tick，`until_idle` 在 `max_ticks/timeout_seconds` 上限内连续推进到无可推进作业，`current_job` 用来表达运行当前或本次作业到结束。前端不得用一个“运行/停止”按钮混合表达重启内核、中断 cell、暂停调度和执行 tick。
- `重启内核` 对应 `/data-annotation/runtime/kernel/restart` 和 `runtime_framework.restart_kernel(...)`，语义是停止 resident Runtime service 后重新 ensure kernel；它不得通过关闭/开启调度来模拟。`暂停调度` 只改变调度服务是否自动提交 cell，不应清空内核运行上下文。
- 旧 `/data-annotation/runtime/task/tick` 保留为兼容入口，语义是提交一个“单步识别”手动作业，不再作为执行层分组 tick 的首选接口。
- 前端运行页加载、刷新、启用作业组或保存作业清单时，只能读取/保存调度配置，不能顺手调用 `run-due` 提交到期作业。需要推进任务时，必须由用户明确让调度器提交 cell，或由后端调度服务按策略提交 cell。
- 同一轮 tick 内，守护、识别和后续动作应复用这张帧，避免重复截图造成状态不一致。
- 列表滚动后应清掉旧帧缓存并固定等待 1 秒，再进入下一轮截图/OCR/签名。不要用“反复计算哈希直到稳定”的方式等待稳定，这会把完成条件和等待条件耦合成新的循环。
- 滚动列表到底的正常判据是“滚动并等待后签名不变”；空滚动次数只能作为兜底上限，不能作为主要逻辑。
- 当点击、等待、进入下一轮 tick 或需要重新观察画面时，才清理帧缓存并重新获取。
- 场景移动、等待到达、弹窗连续处理这类跨帧流程必须用生成器 `yield` 交还行为树；`30s / 60s` 等等待预算是跨 tick 累计真实时间，不是在业务函数里 `sleep`。

## 场景识别

- 普通场景识别只使用 frame 的 `layer`、frame/subframe `structure` 和显式标记了 `isSceneIdentity / sceneIdentityRole` 的 shape。`layer` 只决定 root frame 的全局识别队列，`structure` 决定命中 frame 后如何沿 children 细化，shape 承载“证明当前 frame 是谁”的证据；这三者不能混在一个字段里。
- `structure` 是 frame 嵌套 frame 的树形结构，不是业务目录结构。目录只方便人浏览和放入 Layer 队列；Runtime detect 应把 image.children 中的 image 视为粗场景到细场景的父子关系。命中父 frame 后只沿该父 frame 的 children 继续细化；子 frame 的 `layer` 不会触发全局 layer 扫描。
- frame 的 `layer=1/2/3` 分别表示 root frame 的第一、第二、第三全局识别队列；同一 layer 内按 `layerOrder` 从小到大表达识别优先级。Layer 视图拖拽排序只更新 `layerOrder`，不改变业务目录和 frame/subframe structure。无上下文 detect 按 `Layer 1 -> Layer 2 -> Layer 3` 阻断式尝试：前一层命中 root frame 后，不再检测后续 root layer。每个候选组可以并行打分，但返回按配置顺序第一个过阈值的显式场景，不按最高分抢结果。
- 有候选清单或路径上下文时，候选清单视为 `layer0`：先在候选所在 root 及其 structure 子树内识别；候选未命中，才回到默认 root layer 队列。父 frame 已命中后，subframe 命中则继续细化，subframe 不命中则返回最近命中的父 frame；不会因为 subframe 未命中而继续尝试更低全局 layer。
- subframe 的 identity chain 继承父 frame：命中父 frame 后再下钻匹配子 frame 自己的增量身份；不要在子 frame 分数里重复计算父 frame 的身份锚点。shape lookup 则向上继承：当前 frame 查不到指定 shape 时，可以使用父 frame/祖先 frame 的普通 shape、动作 shape、区域 shape 和滚动 shape；子 frame 同名 shape 覆盖父 shape。继承 shape 的匹配/点击参考来源是 shape 所属 frame，当前运行上下文仍是子 frame。
- 旧 frame 等级只作为一次性迁移输入：旧等级 2 -> `layer=1`，旧等级 1 -> `layer=2`，旧非场景帧 -> `layer=3`。迁移后代码、UI、文档和 Runtime 只使用 `layer` 与 `structure`。
- 没有场景标识证据的图片即使位于 Layer 1，也不是可靠场景；普通 shape 图像相似度不能替代 `_identify_scene` 的 frame 场景标识判定。
- unknown 诊断里的全图相似度只能作为聚类、归并或人工复核线索，不能替代场景身份链。若某帧全图相似很高但该帧身份证据分数很低，应输出“全图相似但身份不成立”类结论，而不是复用该帧的返回路径或断言已经识别到该场景。
- unknown 是慢路径，候选召回应先覆盖全部已标注 frame，再按场景分、全图相似度和预期目标排序截断报告。`max_candidates` 只能限制输出条数，不能限制打分范围；否则局部帧会被全局帧抢掉诊断机会。
- 普通 shape 只表示可点击区域、跳转入口、遮挡/弹窗模板或待人工分析的占位信息；它不自动升级为场景锚点。
- Runtime 点击或检测 shape 时必须复用标注页的匹配协议：`imageMatchRole / ocrMatchRole / floating / jitterEnabled` 共同决定 payload。特别是 `floating && OCR 开启` 时不做全屏 scan，只在标注框区域做 OCR；未真实命中时不得兜底点击原始框。
- 场景身份锚点必须是固定位置、全屏唯一、能代表当前页面的区域。入口按钮、菜单项、跨页面复用文字不适合作为唯一场景身份，例如世界页也会出现“日程”入口，不能用它单独判定已经进入日程页。
- 同一场景允许配置多个身份锚点，但它们表达的是该细场景成立的必要条件组合；Runtime 场景分数按这些身份锚点的最低分理解，任一 required 锚点不过阈值都不能判定为该场景。不要把“多个备选锚点满足一个即可”的 OR 关系混进同一场景身份；如果确实存在备选形态，应拆成不同帧/子帧，或通过更稳定的共同粗域标识加各自细分标识建模。
- 单个身份锚点内部必须尊重 `imageMatchRole / ocrMatchRole`：`required` 条件不过阈值时该锚点整体为 0；`optional` 只能在 required 已满足或没有 required 时贡献分数；`off` 不参与。不能把 required OCR 写在标注里，Runtime 却只看图像相似度。
- Runtime 默认场景阈值按 80 处理。低阈值会让类似 `#85[离开]` 这种小图标在已离开后的世界画面里产生 69% 左右的假阳性，导致已经到世界却被误判回子场景。确需放宽阈值时必须给具体场景单独配置。
- 对带 OCR 文本的场景身份，图像低分时可以用 OCR 回退；但不能因为一个弱图像分数刚过低阈值就跳过更稳定的文本校验。遇到子场景返回按钮、标题文字等场景身份时，优先补 OCR 锚点。
- 场景身份识别不能使用全屏 scan 兜底；scan 会把当前页上的入口按钮误匹配成目标页标题，造成假到达。scan 只适合浮动弹窗或漂移元素。
- 弹窗守护是独立模板匹配口径。弹窗候选可以在没有 `isSceneIdentity` 时兜底使用前几个普通 shape 打分，也可以保留 scan 处理浮动位置；这个兜底只属于 `_popup_score`，不能复用到 `_scene_score`。

## 场景移动

- 场景移动是作业内部可调用的基础子流程，入口任务类型为 `go_scene`。
- 它的核心循环是“识别当前在哪里 -> 从当前场景选择最应该尝试的下一步动作 -> 点击后重新取帧识别实际落点 -> 继续选择下一步”。资产树中 shape 的 `sceneJumpTarget` 构建出的场景图只提供可达性和候选动作证据，BFS 最短路径只能作为排序参考，不能被当成确定性事实路径。
- 业务任务需要“回到 #34 世界”或进入某个已标注场景时，优先调用通用 `go_scene` / `runtime.goto_view(...)`。不要在具体业务任务里手写 `#A -> #B -> #C` 的私有返回链；如果通用 `goto` 无法从已识别场景到达目标，应把问题归因到场景移动基础设施或资产树标注，而不是绕过它写硬编码。
- 调试 `go_scene`、场景识别、shape 匹配时，必须先使用现成 Runtime/行为树公开接口，例如 `scripts/fanxiu_bt.py task debug_eval` 中的 `ctx.scene(...)`、`ctx.shape(...)`、`runtime.current_scene(...)`、`runtime.goto_view(...)`，或正式 `go_scene` 任务。临时 Python 只能作为这些接口的调用包装，不得重新实现一套识别、点击或路径逻辑来替代结论；尤其不能只检测某一个 shape 后断言 frame 是否命中，因为场景树父子证据和同帧多个身份证据必须一起判定。
- 局部点击转场使用 `wait_click_then_view(source, shape, *targets)`：它先按 `wait_click` 的规则等待源场景并点击 shape，再等待显式目标场景；如果调用方没有传目标，则从该 shape 的 `sceneJumpTarget` 推断目标场景。缺少显式目标且 shape 也没有可用 `sceneJumpTarget` 时必须失败并提示补标或显式声明目标。
- `wait_click_then_view` 只适合“当前已在源页面、点一个 shape 后等待直接落点”的局部事务。跨多个场景的路径规划仍使用 `go_scene`；不要把所有 `wait_click` 都升级成转场点击，也不要用局部 helper 绕过 `go_scene` 的动态候选选择和未声明落点校验。
- 起点识别应优先限制在“可到达目标场景”的候选场景内；候选组可并行评分，但结果仍按候选顺序返回第一个过阈值的显式场景。不要用最高分抢结果，否则低优先级弱锚点或全图相似素材会压过真实起点。
- 选择下一步动作时，必须从当前场景枚举全部已标注跳转候选，按“是否直达目标、声明落点是否还能到达目标、历史真实落点次数、声明落点歧义度、动态确认边风险、路径长度参考”等因素排序；不要只拿 BFS 返回的第一条边直接点击。
- 每一步跳转都按事务处理：
  - 点击当前场景上的目标 shape。
  - 让出本轮 tick，下一轮重新取帧。
  - 每轮 tick 重新识别当前场景，并优先按该 shape 的 `sceneJumpTarget` 顺序匹配预设目标。
  - 命中任一预设目标即认为本步跳转完成。
  - 如果实际落点不是最终目标，从实际新场景重新规划到目标场景。
- 如果点击某个候选后保底等待仍稳定停在源场景，本次 `go_scene` 应把该候选暂时标记为失败，回到“当前在哪里 + 下一步最该试什么”的动态选择循环；只有当前场景没有其它可靠候选时，才中断并输出缺标/修标证据。
- 普通跳转保底时间为 `60s`。如果 60 秒内没有进入预设结果之一，就把最后稳定识别到的当前场景视为实际跳转结果。
- 如果 `sceneJumpTarget` 明确包含自身，则本步跳转允许回到自身，保底时间缩短为 `30s`；30 秒后仍稳定在自身，就认定结果为自身。
- 运行观测到已声明目标后，只累加当前 shape 的 `sceneJumpTarget` 次数；未声明落点记录到同一 shape 的 `observedLanding`，用于复盘高频意外路径，但不自动变成可规划边。两者都沿用 `目标(次数)` 协议，无括号表示 0 次，保存时按次数降序排序。
- `sceneJumpTarget=-1` 和 `sceneJumpTarget=0` 是哨兵值，不被自动跳转经验覆盖，也不作为普通图边参与 BFS。
- `返回/退出/关闭` 不能天然视为普通图边，必须先判断它是“结构性返回”还是“上下文关闭”：
  - 结构性返回：页面只能由唯一父页面进入，例如从固定父页进入的二级详情页，返回后确定回父页，才可以写具体 `sceneJumpTarget`。
  - 上下文关闭：同一页面可从世界、日常、仙府、背包、弹窗等多个场景打开，关闭后回到哪里取决于打开来源，通常应写 `sceneJumpTarget=-1`，不得参与 BFS 路径规划。
  - 对“绝大多数情况下稳定回世界”的特殊页面，可以保留具体返回目标，例如 `#69 日常` 的 `退出` 通常回 `#34 世界`，可以标为 `34(...)`；但业务任务不能把这类跨业务域恢复路径当作自己的入口链路。典型反例：`仙府_寻访仙侣` 不应从 `#69 日常` 经 `#34` 再进入仙府，它只能从世界或仙府自身相关场景开始。
- 嵌套在父场景文件夹下的子场景，如果有空 `sceneJumpTarget` 的 `离开/返回/关闭` shape，Runtime 可以把它隐式视为返回父场景标题对应的同名图片。例如 `#85 某区域内部` 在“世界”文件夹下，`离开` 没有显式目标时应可规划为 `#85 -> #34 世界`。
- `离开/返回/关闭` 点击后出现“是否离开当前场景”类确认弹窗时，确认弹窗是中间态，不是最终场景。Runtime 等待阶段可以在识别到 `离开场景` 且存在 `确认/确定` shape 时自动点确认，然后继续等待原目标。
- 自动学习真实落点时，不要把这类确认弹窗 `#86` 记录成原始 `离开` 按钮的最终 `sceneJumpTarget`。否则下一次规划会污染成 `#85 -> #86`，失去 `#85 -> #34` 的真实业务语义。
- 如果超时后仍识别不到任何场景，或点击后进入了 `sceneJumpTarget` 没有声明的落点，Runtime 必须中断并报告目标场景、起点场景、点击 shape、等待时间和最近识别日志。不要保存未知帧、不要创建占位 shape、不要自动新增实际落点；由人工补标/修标后再运行。命中已声明目标时，可以累加该目标次数。
- 如果 `go_scene` 候选识别把当前帧命中到一个“可规划但业务上下文不充分”的场景，必须继续用现成接口拆证据链：检查该帧全部 `isSceneIdentity` 是否同时满足、当前 OCR 是否符合该场景语义、点击 shape 是否属于结构性返回还是上下文关闭。真实案例：`#266 法则详情` 的三个场景标识通过 `ctx.scene(preferred_scene_ids=[266])` 可 AND 命中 100 分，调试时不能只 probe 单个 shape 后下结论；而 `#229 游历购买体力` 的弹窗 `空白` 在其它业务上下文中只会关闭弹窗回到打开来源，不能当作固定回 #34 的路线。此类问题应修通用候选识别、动态落点或标注语义，不应写具体任务特例。
- 弹窗不进入场景移动逻辑。弹窗由更高优先级守护组解耦处理；但嵌入 Runtime 的守护 service 不能长期返回 `RUNNING` 抢占主作业，否则一次误命中会让 `go_scene` 永远拿不到执行 tick。守护处理一次后应记录事件、清理当前帧，并让主作业继续在后续 tick 运行。

## 行为树真实验收

- 凡修里讨论“测试”“运行”“能否达成”“运行速度”时，默认验收对象是 Runtime/行为树在真实游戏画面上的实际操作，不是私有函数直调、构造帧、接口短路或静态识别。
- 如果启动任务时当前已经处于目标场景，例如已经在 `#34` 时执行 `go_scene #34`，这只证明短路路径可用；它没有验证点击、等待、跳转和重新识别链路。汇报时必须明确说这是“已在目标场景”的短路命中，不能说完成了真实操作测试。
- 需要验证真实操作时，应先用行为树/Runtime 自己复现非目标状态，再执行目标任务。例如验证回到世界场景，应跑 `#34 -> #66 -> #34` 这样的可回退路径；复现步骤本身也是对场景移动、点击和等待逻辑的测试。
- 验收记录必须包含 action 日志、场景跳转日志、最终状态、耗时和游戏画面结果。没有 action 日志或场景变化的运行，只能算短路识别，不算完整行为树操作验收。
- 游戏画面结果必须用当前 MuMu/ADB 帧或用户可见画面复核。截图观察链路如果出现桌面、旧帧或非游戏内容，不能作为验收证据；应重新用 ADB 当前帧确认。
- 不要为了制造起点而手工点游戏、直接改状态文件或只调用底层函数；除非用户明确要求只做底层探针。正式结论必须来自 Runtime/Scheduler/行为树公开入口。
- 对 Fanxiu 结论必须先自检到真实 Runtime 通过再汇报。最低自检顺序：相关单元测试通过；后端已重载；真实 ADB 截图上的场景分数符合预期；通过 `/data-annotation/runtime/task/start` 执行公开任务；轮询到 `success/done`；最后用真实截图复核画面。任何一步失败都应报告失败层级，不得包装成成功。
- `code4101` 本地账号可用于 CodeYun 接口登录执行真实自检，但不要在日志、回答或文档中泄露密码、token 或 cookie。

## 前端开发禁区

- 不要在前端硬编码守护/作业业务清单。
- 不要给守护或作业增加 disabled/runnable 这类额外第三态，除非后端模型明确返回该状态且业务语义成立。
- 不要用本地 `ref` 假装某个守护已启用；启用状态必须来自后端状态。
- 不要把未实现功能从清单移除。若后端定义了该节点，前端应展示它；当前空实现由后端处理。
- 不要把“显示一行”理解成“前端拥有该业务”。显示只是后端运行框架状态的投影。
