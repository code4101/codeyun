## 唯一心智模型

```text
工程 / AI / 人工触发来源
  -> Scheduler / Dispatch Arbiter
  -> Fanxiu Jupyter Kernel
  -> 普通 Python Cell
  -> Kernel 内已加载的凡修行为树框架
```

- Kernel 是长期存活的真实 `ipykernel` 进程，是运行实体。
- Cell 是提交给 Kernel 执行的代码，是唯一外部执行原语。
- Scheduler / Dispatch Arbiter 在 Kernel 外根据 `next_time` 决定何时提交哪个 Cell，并负责优先级和模拟器资源仲裁。
- runtime、ctx、task、guard、generator、OCR、ADB、shape、scene 都是 Kernel 内凡修框架能力，不是外部执行协议。

## Cell

临时调试、单步动作和正式任务没有不同的提交协议：

```python
kernel.cell("ctx.scene([34, 69])").run()
kernel.cell("run(runtime.go_scene(69))").run()
kernel.cell("run_task('daily_mozu', {})").run()
```

`kernel.task('daily_mozu', payload)` 只负责构造等价的普通 Python Cell。它不得写入队列、建立 task token、claim/requeue 或调用第二执行器。

用户或 AI 说“发一个 cell”时：

1. 从已有业务实现抽取当前最小相关代码。
2. 提交给当前 Kernel。
3. 等待 Cell 最终状态和用户指定锚点。
4. 停止，等待下一步。

不得为调试步骤新增 API、注册临时作业或写入中间队列。

## Kernel

Kernel 启动后 bootstrap 以下对象：

- `fanxiu`、`runner`
- `runtime`、`ctx`
- `run`、`run_task`
- OCR、ADB、shape、scene、标注导航
- 已注册 tasks、guards、generators

连续 Cell 使用 IPython 原生 namespace、execution count、stdout、display result 和 traceback。

Kernel 对外生命周期只有：

- `execute`：执行一个 Cell。
- `interrupt`：中断当前 Cell，保留 namespace。
- `restart`：替换 kernel 子进程，清空 namespace，重新 bootstrap runtime/ctx。
- `shutdown`：终止 Kernel。

KernelManager 进程持有 Jupyter 原生进程句柄；Windows interrupt 走 `KernelManager.interrupt_kernel()`。框架提供 `sleep(seconds)` 作为可被 Jupyter interrupt 及时打断的长等待，因为当前 Windows/Python 的单次 `time.sleep(30)` 不会在等待期间及时检查 SIGINT。

restart 会生成新的 Jupyter connection key；旧客户端和旧连接不得向新 Kernel 提交或重放 Cell。调用方必须重新读取当前 connection file 并建立新客户端。

Jupyter 的 `idle / busy / dead` 是 Kernel 状态，不能代替 Job Cell 的 `run_status`。
`run_status` 的终态为 `success / error / interrupted`；完整语义以
[凡修 Job 运行与调度语义](./fanxiu-job-scheduling-semantics.md) 为准。

## Scheduler / Dispatch Arbiter

Scheduler 负责：

- 唯一触发事实 `next_time`、派生调度时间、最终结果；
- 到期选择与优先级；
- 工程、AI、人工来源之间的仲裁；
- 模拟器独占资源仲裁；
- 构造 Cell 并提交 Kernel。

### 运行权唯一开关（强约束）

前端调度器的“工程 / AI”选择是系统唯一的运行权开关，不得再叠加“自动派发 / 只观察”“巡检模式”“保底派发”等第二套开关。

| 前端选择 | `job_group_enabled` | 外部 Scheduler | AI / 用户 |
| --- | ---: | --- | --- |
| 工程 | `true` | 自动选择到期作业并向 Kernel 提交 Cell | 不应抢占工程运行权 |
| AI | `false` | 保持进程和心跳存活，但不提交新的工程 Cell | 可以按用户意图提交普通 Cell |

这里的“保持心跳存活”只是证明 Scheduler 进程健康，不构成第三种调度模式。Scheduler 始终具备派发能力；是否允许它提交 Cell，只读取 `job_group_enabled`。因此：

- 工程模式下只要作业到期、Kernel 可用且没有业务阻断，就必须自动派发。
- AI 模式下即使存在到期作业，Scheduler 也只返回 `job_group_disabled`，不得提交工程 Cell。
- AI 提交任何研究、调试、探针或手动作业 Cell 之前，必须先切到 AI 模式，并依次确认 `job_group_enabled=false`、Scheduler 已停止新派发、Kernel 已 idle。工程模式下仅观察到一时 idle 不代表 AI 已取得运行权，仍禁止提交 Cell。
- 工程作业故障可以作为切换到 AI 模式的触发条件：先关闭工程提交权，必要时按下述协议中断故障 attempt，再做串行诊断和研发。所有 AI Cell 结束且 Kernel 重新 idle 后，才恢复工程模式；生产结论必须由恢复后的正式 Scheduler attempt 验收，不能用 AI 调试 Cell 的结果替代。
- AI 模式下由用户明确触发的手动 Cell（包括按标准 Scheduler task 身份运行的完整 Job Cell）拥有当前 attempt；工程到期事实不得通过等级仲裁、attempt 清理或其它 Scheduler 路径打断、作废或改写它。该 Cell 仍按自身运行结果正常收尾并写回自己的调度意图。工程优先级抢占只在 `job_group_enabled=true` 时成立。
- 从工程切换到 AI 时，先关闭后续工程提交权，再显式 `interrupt` 当前带 Scheduler task id 的工程 Cell；普通 AI/人工 Cell没有 Scheduler task id，不得被误停。中断成功后必须同时结束 Runtime/Scheduler 的当前 attempt 投影，但不得消费或改写原业务 `next_time`。该切换绝不使用 restart。
- `doctor` 是一次性只读诊断命令；它不是常驻 Scheduler，也不改变运行权。
- `watch-doctor` 是真实常驻 Scheduler，不提供“只观察”启动选项。
- `ensure-watch-doctor` 只负责确保唯一 Scheduler 存活和代码版本一致，不接受派发能力开关。

#### 游戏状态巡检的模式边界

“游戏状态巡检”属于工程自动化的一部分，其自动循环必须服从同一个
`job_group_enabled`：

Runtime 前端必须常驻显示“游戏状态巡检”面板，包括状态、周期、巡检项、最近检查和结果。它是用户依赖的一级业务能力，不得在 UI 精简或重构中删除；源码契约由 `backend/tests/test_fanxiu_runtime_page_contract.py` 锁定。

- 工程模式：自动巡检运行；探针只读取游戏本体的只读动态插桩 Runtime 状态，命中后的唯一动作是原子写入对应 Job 的 `next_time=now`，是否以及何时派发仍由 Scheduler 决定。以红包为例，只要每分钟巡检仍确认存在待领取红包，就再次写入当前时间；不建立触发请求队列、重复触发标记、刷新模式或上下文去重协议。红包事实留在红包业务自己的 Runtime 快照中，由 Job 启动后自行读取，禁止通过 `scheduler_meta` 或 Cell payload 运输。
- AI 模式：自动巡检暂停，不读取现场，也不更新作业触发时间；`watch-doctor` 只保持进程和心跳存活。
- AI 或用户按需发起一次只读 Runtime 查询，不等于开启自动巡检，也不得改变 `job_group_enabled`。
- 巡检数据源写死为只读动态插桩 Runtime/游戏内存。禁止接入抓包、截图、OCR、frame/scene/shape、GUI 状态或任何视觉兜底；需要视觉识别或操作时必须进入行为树，不能伪装成巡检探针。
- 高频巡检只能消费已预热的进程身份和最终业务数据表地址，禁止在巡检线程内退化为进程映射扫描、Manager 根发现或 Runtime 初始化。进程缓存不按分钟周期过期；只有实际读取失败（通常表示游戏进程已重启）才请求底层恢复。
- 动态插桩恢复是巡检框架的通用底层能力，不属于某个红包等业务探针。每个 Runtime 探针分别声明轻量 `read` 与重建 `recover`；框架统一负责单飞、失败退避、恢复状态和资源仲裁。缓存冷启动或失效时，本轮明确返回“尚未预热/不可判定”，仅在工程模式、Kernel 空闲且两分钟内没有到期作业时启动后台恢复；恢复可以重新发现游戏进程、Manager 根和最终数据地址，但不提交 Cell、不操作 GUI。恢复完成后的分钟巡检重新回到轻量读取。

这里有两条不能混淆的边界：

1. **数据与行为树执行解耦**：游戏本体动态 Runtime 探针在 Kernel 外只读，不创建行为树 runner，不截图替代 Runtime，不提交或占用 Cell。
2. **自动化生命周期服从产品模式**：解耦不等于绕过“工程 / AI”运行权；AI 模式必须暂停工程巡检，让现场控制权保持在 AI / 用户侧。

禁止以“巡检只改配置、没有立即派发”为理由让它在 AI 模式后台继续运行。这会造成用户以为工程自动化已暂停，调度配置却仍被静默修改。

禁止重新引入以下状态或参数：

- `dispatch_mode=observe`
- `auto_run_due_enabled=false`
- `ensure-watch-doctor --auto-run-due`
- `ensure-watch-doctor --no-auto-run-due`
- 任何可让前端显示“工程模式”，但后台只报告到期而不派发的隐含配置

排查“到期作业未触发”时，固定按以下顺序检查：

1. 前端当前选择是否为工程模式。
2. Scheduler plan 的 `job_group_enabled` 是否为 `true`。
3. Scheduler 心跳是否 `active=true` 且代码指纹一致。
4. 到期作业是否出现在 `due_tasks`，Kernel 是 idle、busy 还是 dead。
5. 若 Kernel busy，检查当前 `running` Cell；同一 Kernel 串行消费不是漏派发。
6. 若工程模式、心跳正常、Kernel idle 且仍有到期作业，则这是派发故障，不能用“巡检只观察”解释或绕过。

每个作业持久化 `dispatch_level`（0–5，默认 0）。Kernel 空闲时，Scheduler 在所有到期作业中先选择级别最高者，同级继续沿用原有顺序。工程作业 Cell 运行期间，外部 Scheduler 继续观察到期事实；若出现严格更高级的到期作业，则对当前低级 Cell 执行原生 `interrupt`，把低级 Job Cell 记为 `run_status=interrupted`，恢复运行前原始 `next_time` 后立即重新选单。相同级别不互相打断；被打断 Cell 的 `job_status`、generator 和业务栈全部丢弃，下次从稳定起点整单重跑。优先级判断、轮询和抢占状态都不得进入 Kernel。

同级到期作业再按“原触发时刻 -> `dispatch_order` -> id”选择。`dispatch_order=0` 表示未指定，排在同批显式正数顺序之后；正数越小越先。这是不打断当前 Cell 的软顺序，不产生作业组或 Kernel 队列。

作业只有统一结构，没有每日、每周、动态、手动等可执行触发类型。默认定义可在首次创建实例时给一个初始 `next_time`；此后的窗口、星期、完成周期和动态复查全部由作业自身根据业务上下文计算。`trigger_description` 只是给人看的说明文字，不参与调度。Scheduler 不保存、不解释 `window` 字段。作业没有独立启用字段：`next_time=None` 表示休眠，存在时间且派生调度时间到期才可运行；“手动触发”是一次操作，不是作业类型。

`run_status=success` 只表示 Job Cell 正常结束。Cell 内 `job_status` 不向 Scheduler 暴露；业务判断形成的未来意图只写入 `next_time`。`success` 收尾时 Scheduler 不修改 `next_time`。

`raise` 专门表示 Cell 没有正常完成运行契约，例如代码异常、识别/输入基础链无法继续、Kernel 丢失或进程故障；这些情况形成 `run_status=error`。外部明确 `interrupt` 单独形成 `run_status=interrupted`。禁止用 `raise` 表达“本轮没抢到座位”“目标暂不可用”等正常业务判断，也禁止让 Scheduler 根据业务文案决定下次时间。

每个带业务时间约束的任务必须声明同步、无副作用的“作业准入”。准入在通用 Cell 包装与业务 handler 之前执行；窗口外只能返回本次结果并更新 `next_time`，不得读取或操作 GUI。业务内部如需导航且可能跨过截止时刻，应在导航后自行复核准入。准入通过后，后续完成判据和下一次运行时间仍由业务结果负责。

### 故障域与恢复责任

- 一个 Cell 是一次完整的执行尝试。generator 的 `yield / yield from` 只在该 Cell 内保留内存栈和 tick 进度。
- Cell interrupt、Kernel restart/dead、后端或 Scheduler 进程退出，都会让本次 Job Cell 整体作废；禁止保存或恢复业务步骤。
- 时间由业务推进，状态由执行器维护。任务开始只登记 `running` 与 attempt，不消费或改写 `next_time`；业务可以给自己或另一个作业设置具体时间，也可以设置 `None` 令其休眠。
- 只有 `run_status=error` 时 Scheduler 有权限修改 `next_time`：0 级默认推迟 10 分钟，1 级及以上默认延迟 0 分钟；作业可用预设错误重试延迟覆盖等级默认值。Scheduler 只机械应用配置，不解释业务日志。
- `run_status=interrupted` 时不应用错误延迟，而是恢复本轮开始前的原始 `next_time`。被高等级任务打断的普通任务释放资源后整单重跑；从哪里开始由该作业自己的代码决定。
- `run_status=success` 时 Scheduler 不修改 `next_time`。凡是 Job 内部能够观察、分类并决定后续策略的结果都属于本次 `job_status`；Job 必须按该业务分支的真实语义主动写入延后时间、下一周期、`None`，或确有必要时的 `now`，然后正常返回。它与程序/基础设施异常触发的运行错误重试是两条不同路径。
- Scheduler 只持久化原始 `next_time`、显示说明、派发配置、最终结果和当前执行尝试标识。失败重试同样写入 `next_time`，不得另增 `retry_after`、冷却队列或第二套触发时间。
- 任务注册框架不包含场景生命周期，也没有 `start / success / scheduler_failure` 场景字段。`scheduler_supported` 只表示允许 Scheduler 提交该 task，标准作业只表示进入 Scheduler 标准清单。
- 登录、悬浮窗/遮挡处理、`goto_view(34)`、成功返回和失败恢复都属于具体作业的代码运行流程。需要世界起点的作业就在自己的函数开头显式写 `goto_view(34)`；需要收尾返回的作业就在函数结尾显式写，其他作业原地运行。Scheduler 和通用 `run_task` Cell 包装层不得执行任何固定业务前置/后置动作。
- 作业自己的稳定起点归一化不得继承旧动作意图。不得看到确认页、进度页、结果页后推断上次步骤并继续点击。
- 作业决定导航前，必须先消费“当前正式识别场景中属于本作业的可证明业务终态”。例如 `日常_玄荒` 启动时已在 `#418`，应先读取 `#418[次数]`；分子为 0 时直接判定今日完成，再由业务决定是否回 `#34`。不得先离开该场景、重新寻找入口后再重复证明同一终态。

Scheduler 不负责 OCR、点击、场景移动和生成器推进，不得进入 Kernel 轮询。若以后确需队列，它只能是 Scheduler 的待提交 Cell 队列，Kernel 不消费业务 JSON 队列。

当前 Jupyter shell 原生串行执行请求；正式 Scheduler 每次只选择一个到期任务，构造成普通 Cell并同步等待结果。没有 Kernel 内 manual queue，也没有 Kernel 内来源锁。

### 当前常驻唤醒实体

这不是抽象边界，当前真实启动链为：

```text
CodeYun 后端 lifespan / 开发热重载
  -> ensure_data_annotation_behavior_tree_service_on_startup()
  -> ensure_doctor_watch_background()
  -> scripts/fanxiu_bt.py watch-doctor
  -> 周期读取 Scheduler plan
  -> 选择一个到期任务并构造普通 run_task(...) Cell
  -> 当前 Fanxiu Kernel 执行并返回终态
  -> Scheduler 写回 last_result / last_run_at；业务按需写 next_time
```

`watch-doctor` 是 Kernel 外的常驻 Scheduler / Dispatch Arbiter。后端每次启动或热重载都会检查其 PID、心跳和代码指纹；心跳缺失、进程死亡或代码过期时会替换进程。它每轮最多向 Kernel 提交一个 Cell，Kernel busy 时等待，不重复提交。是否允许提交，只服从前端工程 / AI 对应的 `job_group_enabled`。

空闲时 Scheduler 按最近一个 `next_time` 计算下一次唤醒时刻，不用固定轮询周期
延迟已知作业；普通巡检间隔只是不漏触发的兜底。到期派发前先比较 Kernel
启动时记录的行为树代码指纹与当前磁盘代码指纹：一致则直接提交；不一致且
Kernel idle 时先原生 restart、完成 bootstrap 并确认新指纹，再提交同一个
到期作业。Kernel busy 时不得因代码更新打断当前 Cell，只在下一次提交前更新。
同一批作业只需更新一次 Kernel generation。

Scheduler 不保存跨轮次的“已尝试 task id”或固定派发冷却。普通失败、短窗口
立即重试和让路时间全部由唯一 `next_time` 表达；单次批处理只保留内存中的
有界防循环集合，进程退出后不形成第二调度事实。

心跳还必须携带启动时加载的凡修调度代码指纹。后端当前代码指纹与心跳不一致，或旧心跳没有指纹时，即使 PID 仍存活也必须视为旧版巡检：先确认进程命令确为 `fanxiu_bt.py watch-doctor`，再终止并拉起新版。PID 存活不能替代心跳新鲜度检查；进程仍在但心跳过期同样需要换代，避免旧调度逻辑静默漏掉新作业类型或动态 `next_time`。

外部 Scheduler 使用独立文件锁保证同一份调度状态只有一个派发者；这个锁只仲裁外部 Scheduler 与模拟器资源，不进入 Kernel，也不是 Cell 队列。心跳只表达进程健康、代码一致性和当前诊断摘要，不表达另一套派发模式。

## 行为树框架

凡修框架继续保留：

- task / guard / generator；
- `yield` / `yield from` 的业务推进；
- 截图、OCR、点击、等待、日志；
- shape 和 scene 标注语义；
- 守护作为任务运行前或每个框架 tick 的策略；
- 已注册正式业务任务。

业务代码只操作 scene 和 shape，不处理物理坐标。资产树、设备和真实运行规则分别见：

### 场景跳转历史

`sceneJumpTarget` 是一次 Shape 点击后真实落点的历史频次，例如 `282(6),20(1)`；规划器把频次归一化为动作后的条件概率先验，并结合目标图距离、失败边、连续自环和动作风险选边。它不是允许落点白名单或写死的业务规则。

真实落点可以等于源场景本身。`X[S] -> X` 同样要给 `S.sceneJumpTarget` 中的 `X` 累计一次：它可能来自点击未生效、卡顿、场景内状态切换，也可能说明该 shape 只是标识而非导航按钮。规划器应把自环频率作为连续的“不前进”证据参与排序，但不得用固定比例阈值直接定性或删除该 shape。

点击后若可靠识别到历史中没有的新落点 D，Runtime 应把 D 以一次观测写入同一个 `sceneJumpTarget`，随后从 D 重新规划到最终目标。D 没有现成路径时，再进入有界的低风险返回/关闭恢复；只有画面确实为 unknown、仍停在源场景或恢复耗尽时才停止。不得另设 `observedLanding` 把新落点隔离成“异常数据”，也不得仅因 D 未预先列出就中断。

实现时不得把 `_increment_scene_jump_target()` 简化成“只给已有目标加次数”。名字中的 `increment` 同时包含两种情况：已有落点次数 `+1`，新落点以 `(1)` 插入。底层若有只累计已有 label 的便利方法，Runtime 也不能直接委托给它，否则会悄悄丢掉 D。

绿瓶拜谒是本语义的固定回归案例：

```text
#282[境界排行] -> #283
#283[返回] -> #282
#282[返回] -> #20
#20[回到世界] -> #34
```

`#283[返回] -> #236`、`#282[境界排行] -> #197` 是历史 AI 误识别，与真实业务页面无关，禁止作为兼容分支恢复。业务任务完成拜谒后只调用 `runtime.goto_view(34)`；逐级返回由通用场景规划完成。

## 禁止模式

- 自制 `exec + dict` 的假 Jupyter namespace。
- 为每个调试步骤新增 API。
- Kernel 内 `manual_jobs.json` 或 task pending/claim/requeue/dedupe 队列。
- resident runner 轮询并消费 task-cell JSON。
- Kernel 内 Scheduler、job-group isolation 或人工/AI/工程来源锁。
- 用 JSON 控制文件模拟 Jupyter interrupt/restart/shutdown。
- 把 interrupt 实现成 restart。
- restart 后旧客户端跨代重连或重放旧 Cell。
- 把 generator、业务步骤、scene 游标或“上次执行到哪里”的进度写成跨 Cell 持久事实。
- 在业务 task 启动时枚举遗留确认页、进度页、结果页并承接上一轮动作。
- 新旧两条 submit 路径并存。

## 维护期资源仲裁

游戏维护属于 Kernel 外 Scheduler 的全局可用性门闩。Kernel 内业务/Guard 只负责报告 `#415` 事实并结束当前 Cell；外部 Scheduler 在门闩期间保留普通作业触发时间，但不提交它们，只按设备维护作业的 `next_time` 唤醒。

设备维护作业每次必须完整重启 MuMu，再关闭 `#14` 公告并在 `#18` 做 30 秒进入游戏行为探测。仍停在 `#18/#415` 才继续维护休眠；一旦进入游戏，模拟器资源即恢复可用，维护作业停止重启并把“登录”排到队首。回到 `#34` 由登录/场景导航链完成，unknown 走统一 `[返回]` 保底，不得把“尚未到 #34”重新解释为需要重启模拟器。该机制不得实现成 Kernel 内定时循环、手工队列或跨 restart 续跑协议。

## 标准验收

1. Cell A 设置变量；Cell C 能读取，证明 namespace 连续。
2. Cell B 执行 `sleep(30)`；原生 interrupt 后停止，Cell A 的变量仍存在。
3. restart 后旧变量消失，`runtime` / `ctx` 已重新加载。
4. restart 前的客户端不能提交；新客户端可立即执行。
5. `kernel.task(...)` 的产物是普通 Cell 源码。
6. 活跃 Kernel 路径不引用 manual queue、claim/requeue 或 Kernel 内锁。
7. Scheduler 信息与 Kernel idle/busy/dead 分开验证。
