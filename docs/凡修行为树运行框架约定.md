# 凡修行为树运行框架约定

> Last Updated: 2026-06-04

## 核心原则

- 凡修行为树应被理解为一个常驻后端服务，而不是一个由页面临时打开/关闭的任务。后端启动或 runtime 页面进入当前 `entry_id` 后，行为树 loop 应持续存在；页面只管理守护、手动作业和自动作业的配置与队列。
- 行为树没有单独的“开启/关闭”业务开关。允许存在“服务未初始化/后端重载/错误/空转”等技术状态，但产品语义上不是用户手动开关行为树。
- 行为树里的“守护”和“作业”本质上都是后端运行框架管理的分组节点；“守护/作业”只是当前默认分组，不是底层不可变分类。
- 行为树调度底座必须复用 `pyxllib.prog.behavior_tree`，不要在 CodeYun 里重复实现行为树、选择器、守护服务调度或生成器推进逻辑。
- CodeYun/Fanxiu 只实现业务层节点：识别当前场景、关闭弹窗、执行作业、场景跳转、点击 shape、等待到达等。
- `pyxllib.prog.behavior_tree` 外层需要有 CodeYun/Fanxiu 专用动态容器，负责读取后端配置、分析当前白名单、生成本轮 guard/job 节点。
- 当前核心仍是 `tick + yield / yield from`：作业内部用生成器保存进度，行为树每轮只推进一次；守护命中时不推进作业生成器。
- 前端不是守护/作业清单的事实来源，不应硬编码业务项、补本地假状态或自行决定哪些功能存在。
- 前端只负责展示后端清单、提交开关状态、传递“哪些节点被允许执行”这类白名单信息。
- 具体执行逻辑、默认清单、启用状态、日志归属、运行状态和调度行为都应由后端维护。

### 调度底座

- 后端 runtime 应使用 `Action` 包装普通函数或生成器函数。
- 作业子流程应优先写成生成器，使用 `yield` 让出本轮 tick，使用 `yield from` 组合子流程。
- 守护应作为 `WithServices` 的 service 节点挂在作业子树外层；嵌入 Runtime 的守护处理了遮挡事件后不能长期返回运行中状态抢占主作业，应记录事件并让主作业继续获得 tick。
- 当前 `backend/api/fanxiu.py` 的 `_GameWindow3RuntimeContainer` 负责把后端配置转换成 `BehaviorTreeRunner + Action + WithServices`；后续补场景跳转时，应继续沿用这个入口，不要新增手写状态机循环。
- 现有礼包码等历史任务函数还没有全部改成生成器，这是迁移过程中的业务层遗留；框架层已经先对齐 pyxllib 行为树。

### 动态容器

- `_GameWindow3RuntimeContainer` 是 CodeYun/Fanxiu 的高级容器，不是 pyxllib 的替代品。
- 容器按“分组”组织运行记忆。每个分组有独立记忆，同一分组同一时间最多保留一个正在运行的任务。
- 当前默认分组：
  - `guard`：守护，优先级 10。
  - `manual_job`：手动作业，优先级 50。
  - `job`：自动作业，优先级 100。
- 容器输入来自后端事实源：
  - 守护定义：`_GameWindow3RuntimeRunner.guard_definitions`
  - 守护启用状态：后端 runtime 状态与持久化配置
  - 作业实例：后端 Scheduler tasks、本地配置、到期分析结果
- 前端白名单只能通过接口修改后端配置；行为树运行时不直接信任前端临时状态。
- 容器每次构建或 tick 时应从后端状态判断节点是否启用。未启用节点返回 `SKIP`，不应执行截图、点击或业务逻辑。
- 跨组规则：高优先级组先运行；高优先级组命中并返回运行中时，低优先级组本轮暂停，但低优先级组的生成器记忆不清除。
- 同组规则：默认不抢占。一个任务一旦进入 `RUNNING`，该分组继续保留它的生成器记忆，直到它 `SUCCESS / FAILURE / STOP`；同组新到期任务进入候选池，等待当前任务结束后再参与选择。
- 如需限时抢占，优先新增更高优先级分组，例如 `urgent_job`，不要轻易开启同组抢占。
- 业务操作函数只能做“一步”并交还控制权，不能实现“循环直到完成”的同步兼容路径。连续操作必须通过 `yield`、`RUNNING` 或下一轮 tick 推进。
- 手动按钮不应直接调用业务逻辑。手动操作应写入后端 `manual_job` 队列，由行为树按分组优先级调度；有守护时先处理守护，有普通自动作业待运行时也先完成手动作业。
- `/game-window3/runtime/task/start` 这类调试入口也应按手动作业理解：它提交一个临时任务并唤醒常驻行为树，不代表创建或关闭行为树服务本身。
- `scheduler/task/run-now` 同样只提交一次性手动作业并唤醒常驻行为树，不能为了“立即运行”先直接消费队列里的旧手动作业。所有手动作业必须由 resident loop 串行判断空闲后启动。
- 手动作业用于调试和人工干预，不能被全局守护候选扫描长期挡住。当前手动作业执行节点会跳过嵌入式守护 service；空转守护和自动作业仍走守护优先。
- 任务函数注册表和任务实例清单要分离：
  - 注册表定义“后端支持哪些能力”。
  - 实例清单定义“当前机器配置了哪些作业、是否启用、参数是什么、何时到期”。
- 未实现但已定义的守护/作业可以是 pass 节点；它们仍属于后端清单，前端不应隐藏或增加 disabled 第三态。

## 守护模型

- 守护定义在后端 `_GameWindow3RuntimeRunner.guard_definitions`。
- 守护是常驻行为树的高优先级节点配置，不应拥有独立的生命周期线程。开启守护只是把该节点纳入后续 tick；关闭守护只是让该节点返回 `SKIP`。
- Runtime 状态接口返回 `guard_items`，每个守护至少包含：
  - `id`
  - `label`
  - `message`
  - `enabled`
  - `running`
  - `entry_id`
- 前端页面 `/fanxiu/data-annotation/runtime` 必须遍历 `runtimeStatus.guard_items` 渲染守护列表，不要手写“关闭弹窗”“万灵切磋邀请”等业务行。
- 守护开关统一调用 `/game-window3/runtime/guard/set`，提交 `entry_id`、`guard_id`、`enabled` 和 `interval_seconds`。
- `/game-window3/runtime/guard/set` 只能修改后端配置并唤醒常驻服务，不能启动一个与主行为树并列的“守护线程”。
- 已实现守护和未实现守护走同一套接口。未实现守护应在后端以 pass/空实现登记状态和日志，不能在前端做 disabled 第三态。

### 当前守护

- `close_popups`：真实执行“关闭弹窗”守护。
  - 使用当前 tick 的同一帧进行弹窗识别。
  - 只扫描资产树顶层 `弹窗` 分组的第一层图片，嵌套子目录不参与。
  - 命中后点击对应关闭 shape，本轮向行为树返回 `RUNNING` 以暂停作业；下一轮重新取帧继续守护检测，直到守护跳过后作业才继续获得 tick。
  - #47/#84 这类需要连续操作的弹窗也按多轮 tick 处理：第一轮点击 `不再提示` 后立即让出，下一轮重新取帧确认状态，再点击 `确认`。不要在守护内部 `sleep` 后连续点击。
  - 关闭弹窗只保留单步 `step` 语义；不要再增加 `until_clear` 这类直接循环清空弹窗的同步入口。
  - 弹窗候选匹配可以做并行优化，但只能并行“打分”，不能并行“点击”。当前按本轮候选数量并行打分，全部分数返回后仍按候选顺序选择第一个命中项，保证行为语义不变。
  - 弹窗候选列表按资产树文件签名缓存，避免每轮 tick 反复读取和解析资产树；资产树修改后缓存自动失效。
  - 候选索引保留两类来源：`弹窗` 分组第一层图片无条件进入候选，用于 #47 这类父弹窗和子弹窗特殊处理；其它嵌套帧只有明确 `sceneJumpTarget=-1` 的独立退出 shape 才进入候选，避免把普通嵌套页面当全局弹窗反复扫描。
- `wanling_invite`：当前为空实现。
  - 可以开关。
  - 后端登记启用状态并写日志。
  - 未来补具体检测/处理逻辑时，应接在同一个 `guard_id` 下。

## 作业模型

- 作业清单来自后端 Scheduler tasks。
- 前端只展示后端返回的作业，并提交启用/禁用后的任务配置。
- 自动作业由常驻行为树在空闲 tick 中读取 Scheduler 到期结果后串行提交；`schedule_kind=manual` 的任务不能被空转 loop 当成到期任务反复运行，只能由用户手动提交。
- Scheduler 到期任务也应在 resident service 线程内串行执行，不再创建 `fanxiu-game-window3-scheduler` 业务线程。`run-due` 只是唤醒常驻 loop，实际启动仍由 loop 判断空闲后完成。
- 前端不应创造作业项，也不应用本地状态模拟作业是否存在。
- 新增作业类型时，优先在后端定义任务类型、执行逻辑、默认说明和支持状态；具体本机是否加入清单、是否启用、下次触发时间属于后端/本地数据配置。

## 日志模型

- 运行日志按分组归属记录，不是前端临时拼出来的日志。
- 每条日志应带：
  - `scope`：例如 `guard` 或 `job`
  - `item_id`：例如 `close_popups`、`wanling_invite` 或某个作业 id
- 守护日志使用 `scope=guard`。
- 守护组任务定义稳定，`item_id` 使用具体 `guard_id`，例如 `close_popups`。
- 手动作业是临时实例队列，统一写入组级日志：`scope=manual_job`、`item_id=manual_job`。单条日志消息中保留临时 job id，例如 `[manual-...] 手动作业已启动：单步识别`。
- 不允许在业务 worker 结束时再开一个额外 drain 线程去消费下一条手动作业；这会制造第二套调度入口。worker 只负责完成当前任务、落状态、持久化，下一条任务由常驻 loop 下一轮 tick 启动。
- 手动作业应在 resident service 线程内串行执行，不再创建 `fanxiu-game-window3-manual-job` 业务线程。这样用户手动提交的调试/API 任务和空转 tick 使用同一个调度入口。
- 自动作业组任务定义稳定，日志使用 `scope=job`，`item_id` 使用具体 task id。
- 前端右键“日志”只进入详情页并按 `scope + item_id` 查询，不自行筛选或重建业务含义。

## Tick 与帧复用

- 行为树一轮 tick 只应获取一次当前帧。
- 同一轮 tick 内，守护、识别和后续动作应复用这张帧，避免重复截图造成状态不一致。
- 当点击、等待、进入下一轮 tick 或需要重新观察画面时，才清理帧缓存并重新获取。
- 场景移动、等待到达、弹窗连续处理这类跨帧流程必须用生成器 `yield` 交还行为树；`30s / 60s` 等等待预算是跨 tick 累计真实时间，不是在业务函数里 `sleep`。

## 场景识别

- 普通场景识别只能使用显式标记了 `isSceneIdentity` 的 shape。
- 没有 `isSceneIdentity` 的图片不是可定位场景，即使普通 shape 图像相似度很高，也不能被 `_identify_scene` 判定为当前场景。
- 普通 shape 只表示可点击区域、跳转入口、遮挡/弹窗模板或待人工分析的占位信息；它不自动升级为场景锚点。
- 场景身份锚点必须是固定位置、全屏唯一、能代表当前页面的区域。入口按钮、菜单项、跨页面复用文字不适合作为唯一场景身份，例如世界页也会出现“日程”入口，不能用它单独判定已经进入日程页。
- 同一场景允许配置多个身份锚点，判定分数取最高分，兼容“多个定满足一个即可”的行为树语义；调试检测页可以展示每个条件的独立结果，但 Runtime 不能把一个当前不可见的备选锚点平均进去拖垮整个场景识别。
- 单个身份锚点内部必须尊重 `imageMatchRole / ocrMatchRole`：`required` 条件不过阈值时该锚点整体为 0；`optional` 只能在 required 已满足或没有 required 时贡献分数；`off` 不参与。不能把 required OCR 写在标注里，Runtime 却只看图像相似度。
- Runtime 默认场景阈值按 80 处理。低阈值会让类似 `#85[离开]` 这种小图标在已离开后的世界画面里产生 69% 左右的假阳性，导致已经到世界却被误判回子场景。确需放宽阈值时必须给具体场景单独配置。
- 对带 OCR 文本的场景身份，图像低分时可以用 OCR 回退；但不能因为一个弱图像分数刚过低阈值就跳过更稳定的文本校验。遇到子场景返回按钮、标题文字等场景身份时，优先补 OCR 锚点。
- 场景身份识别不能使用全屏 scan 兜底；scan 会把当前页上的入口按钮误匹配成目标页标题，造成假到达。scan 只适合浮动弹窗或漂移元素。
- 弹窗守护是独立模板匹配口径。弹窗候选可以在没有 `isSceneIdentity` 时兜底使用前几个普通 shape 打分，也可以保留 scan 处理浮动位置；这个兜底只属于 `_popup_score`，不能复用到 `_scene_score`。

## 场景移动

- 场景移动是作业内部可调用的基础子流程，入口任务类型为 `go_scene`。
- 它从当前帧识别当前场景，再根据资产树中 shape 的 `sceneJumpTarget` 构建场景图，用 BFS 查找当前场景到目标场景的确定性最短路径。
- 起点识别应优先限制在“可到达目标场景”的候选场景内，并在候选中取最高分，而不是按候选顺序第一个过阈值就返回。否则目标场景或中间场景的弱锚点会压过真实起点。
- 每一步跳转都按事务处理：
  - 点击当前场景上的目标 shape。
  - 让出本轮 tick，下一轮重新取帧。
  - 每轮 tick 重新识别当前场景，并优先按该 shape 的 `sceneJumpTarget` 顺序匹配预设目标。
  - 命中任一预设目标即认为本步跳转完成。
  - 如果实际落点不是最终目标，从实际新场景重新规划到目标场景。
- 普通跳转保底时间为 `60s`。如果 60 秒内没有进入预设结果之一，就把最后稳定识别到的当前场景视为实际跳转结果。
- 如果 `sceneJumpTarget` 明确包含自身，则本步跳转允许回到自身，保底时间缩短为 `30s`；30 秒后仍稳定在自身，就认定结果为自身。
- 运行观测到真实结果后，直接更新当前 shape 的 `sceneJumpTarget` 字符串，沿用标注页既有协议：`目标(次数)`，无括号表示 0 次，保存时按次数降序排序。
- `sceneJumpTarget=-1` 和 `sceneJumpTarget=0` 是哨兵值，不被自动跳转经验覆盖，也不作为普通图边参与 BFS。
- 嵌套在父场景文件夹下的子场景，如果有空 `sceneJumpTarget` 的 `离开/返回/关闭` shape，Runtime 可以把它隐式视为返回父场景标题对应的同名图片。例如 `#85 某区域内部` 在“世界”文件夹下，`离开` 没有显式目标时应可规划为 `#85 -> #34 世界`。
- `离开/返回/关闭` 点击后出现“是否离开当前场景”类确认弹窗时，确认弹窗是中间态，不是最终场景。Runtime 等待阶段可以在识别到 `离开场景` 且存在 `确认/确定` shape 时自动点确认，然后继续等待原目标。
- 自动学习真实落点时，不要把这类确认弹窗 `#86` 记录成原始 `离开` 按钮的最终 `sceneJumpTarget`。否则下一次规划会污染成 `#85 -> #86`，失去 `#85 -> #34` 的真实业务语义。
- 如果超时后仍识别不到任何场景，Runtime 会保存当前帧到资产树 `未知场景` 分组，创建一个普通占位 shape，并把目标、起点、点击动作、等待时间和识别日志写入 `description`。占位 shape 不自动配置场景标识、跳转、OCR 或图像匹配语义，等待人工分析。
- 弹窗不进入场景移动逻辑。弹窗由更高优先级守护组解耦处理；但嵌入 Runtime 的守护 service 不能长期返回 `RUNNING` 抢占主作业，否则一次误命中会让 `go_scene` 永远拿不到执行 tick。守护处理一次后应记录事件、清理当前帧，并让主作业继续在后续 tick 运行。

## 行为树真实验收

- 凡修里讨论“测试”“运行”“能否达成”“运行速度”时，默认验收对象是 Runtime/行为树在真实游戏画面上的实际操作，不是私有函数直调、构造帧、接口短路或静态识别。
- 如果启动任务时当前已经处于目标场景，例如已经在 `#34` 时执行 `go_scene #34`，这只证明短路路径可用；它没有验证点击、等待、跳转和重新识别链路。汇报时必须明确说这是“已在目标场景”的短路命中，不能说完成了真实操作测试。
- 需要验证真实操作时，应先用行为树/Runtime 自己复现非目标状态，再执行目标任务。例如验证回到世界场景，应跑 `#34 -> #66 -> #34` 这样的可回退路径；复现步骤本身也是对场景移动、点击和等待逻辑的测试。
- 验收记录必须包含 action 日志、场景跳转日志、最终状态、耗时和游戏画面结果。没有 action 日志或场景变化的运行，只能算短路识别，不算完整行为树操作验收。
- 游戏画面结果必须用当前 MuMu/ADB 帧或用户可见画面复核。截图观察链路如果出现桌面、旧帧或非游戏内容，不能作为验收证据；应重新用 ADB 当前帧确认。
- 不要为了制造起点而手工点游戏、直接改状态文件或只调用底层函数；除非用户明确要求只做底层探针。正式结论必须来自 Runtime/Scheduler/行为树公开入口。
- 对 Fanxiu 结论必须先自检到真实 Runtime 通过再汇报。最低自检顺序：相关单元测试通过；后端已重载；真实 ADB 截图上的场景分数符合预期；通过 `/game-window3/runtime/task/start` 执行公开任务；轮询到 `success/done`；最后用真实截图复核画面。任何一步失败都应报告失败层级，不得包装成成功。
- `code4101` 本地账号可用于 CodeYun 接口登录执行真实自检，但不要在日志、回答或文档中泄露密码、token 或 cookie。

## 前端开发禁区

- 不要在前端硬编码守护/作业业务清单。
- 不要给守护或作业增加 disabled/runnable 这类额外第三态，除非后端模型明确返回该状态且业务语义成立。
- 不要用本地 `ref` 假装某个守护已启用；启用状态必须来自后端状态。
- 不要把未实现功能从清单移除。若后端定义了该节点，前端应展示它；当前空实现由后端处理。
- 不要把“显示一行”理解成“前端拥有该业务”。显示只是后端运行框架状态的投影。
