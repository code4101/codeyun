# 星云表格性能重构计划

更新时间：2026-07-06

## 结论

当前卡顿主要不是接口慢，也不是单纯 Handsontable 框架不可用，而是 CodeYun 表格页把 Handsontable 推入了多次重配置和重渲染路径。Handsontable 的 DOM 渲染模型会放大这个问题；WPS、金山文档、腾讯表格、Google Sheets 这类产品通常使用更底层的自研表格渲染引擎，长期上限确实不同。

短中期优先修 CodeYun 自身实现，目标是把 sheet 切换从“重建组件 + 重配插件 + 多轮 render”收敛为“稳定实例 + 单次数据加载 + 必要局部更新”。长期如果要接近 WPS 级丝滑，再评估自研 canvas/虚拟表格引擎。

## 已测事实

### 2026-07-06 真实部署入口复测

测试入口：`https://code4101.com/workbook/7?sheet=21&sheetPerf=0`

本轮必须区分两类指标：

- 内部表格打点：`sheet.load`、`handsontable.render` 这类指标已经能降到百毫秒级，但它们只能说明 Vue 组件内部某些阶段很快。
- Chrome 真实体感：从部署 URL 打开到标题、表格 DOM、非空单元格真正可读，仍然能达到 40-50s 级。这是用户实际感受到的卡顿，应优先服从真实入口。

最新事实：

- 后端 `GET /api/note-sheets/sheets/21?workbook_id=7&include_workbook_context=true` 曾经有明确瓶颈：
  - `header_links` 动态表头链接注入：约 1.35-1.62s。
  - 根因不是最终写链接，而是表头链接路径误加载了 `video_data`、`clockin_data` 等大型课程数据表。
  - 修复后 `header_links`：约 15ms。
  - 后端内部整条 sheet 组装：约 1.47-1.74s 降到约 132ms。
  - 公网 API 8 次采样：约 731ms，n=8。
- 公式裸显示问题已修：
  - 真实 Chrome 样本中 `rawFormulaCount = 0`。
  - 根因是公式引擎预加载后仍复用早期空公式显示缓存。
  - 修复点是空缓存遇到当前文档含公式时不再复用。
- `sheetPerf` 调试开关已改成 URL 级，不再用 localStorage 持久污染正常用户页面。
- 真实 Chrome 入口仍很慢：
  - 修复后一次样本：`goto` 返回约 22.2s，首个表格单元格可读约 43.3s，截图约 30.2s。
  - 外壳路由异步加载 `NoteSheetWorkspace` 后：首个表格单元格可读约 53.9s，未改善。
  - 非首屏子组件异步化后：首个表格单元格可读约 52.4s，未改善；颜色弹窗脚本未进入首屏脚本列表。

当前判断：

- 接口慢和公式渲染是已修复的问题，但不是 40-50s 级卡顿的主因。
- “小表也卡”不合理，说明不是 200x50 的数据量问题，也不能简单归咎于 Handsontable。
- 最大矛盾已转向 `NoteSheetWorkspace.vue` 本体：组件约 2.7 万行，首屏同步承载表格内核、考勤业务、Excel 导入导出、AI 检测、权限、反馈、富文本、颜色、公式、行详情等大量状态和 watcher。WPS/金山文档之所以切换快，本质上是编辑器内核和外围业务能力分层加载，首屏只让高性能表格内核运转。

下一阶段计划：

1. 抽出 `NoteSheetCoreGrid`：只保留 Handsontable、数据行列、公式显示、基本编辑、选择、复制粘贴、分页必要状态。
2. 抽出 `attendanceSheetActions`：考勤课程更新、报名匹配、打卡链接检测、问卷反馈、导出等全部作为按需插件加载。
3. 抽出 `sheetDialogs`：权限、列设置、单元格样式、富文本、Excel 导入、行详情等只在打开时加载。
4. 把首屏性能预算写成守卫：生产入口中 `NoteSheetWorkspace` 首屏不得静态依赖颜色工具、Excel/文件处理、考勤反馈历史、权限弹窗、AI/脚本状态等非首屏模块。
5. 每完成一刀都必须用同一部署 URL 复测：`goto`、首个表格 DOM、非空单元格、裸公式数、截图耗时。

依赖源码补充定位：

- 当前版本为 `handsontable 17.0.1` / `@handsontable/vue3 17.0.1`。
- `@handsontable/vue3` 的 `hotInit()` 会执行 `new Handsontable.Core(this.$el, newSettings)` 后立刻 `hotInstance.init()`。
- Handsontable core 的 `init()` 先 `dataSource.setData(tableMeta.data)`，再 `updateSettings(mergedUserSettings, true)`，初始化数据路径会进入 `populateFromArray -> setDataAtCell -> applyChanges -> instance.render()`，随后 `init()` 自身又调用一次 `this.render()`。
- 这解释了第三十二轮剩余两次 `unattributed` render：当前不是我方手动 render，而是 wrapper 带 data 初始化与 HOT core init 渲染叠加。
- 直接把 `:data` 改为空数组不可取：vue3 wrapper 的 prop watcher 依赖同一个 data 引用自动同步，维度变化时只调 mapper 并删除 `settings.data`，不会替我们把真实数组 `loadData()` 进去。下一步应做独立最小实验：不传 `data` prop / 自建轻量 wrapper / 挂载后命令式 `loadData()`，比较是否能把“满数据两次 render”降成“空表初始化 render + 满数据一次 render”。

- 要求公式引擎首屏预热预算保持 45ms 级别，防止为了等待 HyperFormula chunk 把 `sheet.load` 重新拉长。
- 要求 HotTable 首轮不再直接绑定真实 `sheetHotGridRows`，真实数据必须通过 `ensureHotInitialGridRowsLoaded()` 在挂载后手动注入，避免 wrapper/core 初始化阶段重新出现多次满数据 render。
- 要求横向虚拟化缓冲保持收缩后的配置，并显式关闭 `auto-column-size`，防止部署版重新渲染过多列或触发列宽自动测量。
- 要求 `restoreInitialDocument()` 不能等待 `requestAnimationFrame` 来强行提前注入初始数据，防止首屏 `sheet.load` 重新被 rAF 等待拉长到秒级。
- 要求 workbook/resource 页传入 `runtime-height-mode="fill"`，渲染高度使用运行态高度模式而不是直接使用旧文档保存的 `height_mode`。
- 要求 fill 模式的视口高度按浏览器可见剩余高度裁剪并记录 `containerHeight/windowHeight/viewportRemainingHeight/frameTop`，避免旧的 content-height 路径重新让 workbook 页按整表高度渲染。
- 要求 resource 页通过 `SHEET_RESOURCE_RUNTIME_MAX_GRID_HEIGHT` 限制首屏表格视口高度，并显式设置 `viewport-row-rendering-offset`，防止超高窗口下重新一次渲染整页行。
- 要求 `updateSheetViewportHeight()` 合并同一轮 pending 刷新，防止首屏多调用重复执行 `nextTick + getBoundingClientRect/clientHeight`。
