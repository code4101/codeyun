# 星云表格性能重构计划

更新时间：2026-07-06

## 结论

当前卡顿不能再用单一原因解释，需要分两条主线处理：

- 对 `sheet=21` 这类普通工作表，核心矛盾主要是 CodeYun 表格页把 Handsontable 推入了多次重配置和重渲染路径。Handsontable 的 DOM 渲染模型会放大这个问题；WPS、金山文档、腾讯表格、Google Sheets 这类产品通常使用更底层的自研表格渲染引擎，长期上限确实不同。
- 对 `sheet=54025` 这类“前端分页只看小片段、后端持久化 JSON 却很大”的工作表，核心矛盾是后端读请求仍会解析整份 `document_json`。本轮确认该表 `document_json` 约 81.9MB，而前端分页响应约 64KB；如果不做轻量加载和短期缓存，首次或缓存失效加载会被大 JSON 读取/解析主导。

短中期优先修 CodeYun 自身实现，目标是把 sheet 切换从“重建组件 + 重配插件 + 多轮 render + 大 JSON 重复解析”收敛为“稳定实例 + 单次数据加载 + 后端轻量读取/短期派生缓存 + 必要局部更新”。长期如果要接近 WPS 级丝滑，再评估自研 canvas/虚拟表格引擎和后端分块表格存储。

## 已测事实

### 2026-07-06 真实部署入口复测

测试入口：`https://code4101.com/workbook/7?sheet=21&sheetPerf=0`

本轮必须区分两类指标：

- 内部表格打点：`sheet.load`、`handsontable.render` 这类指标已经能降到百毫秒级，但它们只能说明 Vue 组件内部某些阶段很快。
- Chrome 真实体感：从部署 URL 打开到标题、表格 DOM、非空单元格真正可读，仍然能达到 40-50s 级。这是用户实际感受到的卡顿，应优先服从真实入口。

最新事实：

- 后端 `GET /api/note-sheets/sheets/21?workbook_id=7&include_workbook_context=true` 曾经有明确瓶颈：
  - `header_links` 动态表头链接注入：约 1.35-1.62s。
  - 根因不是最终写链接，而是表头链接路径误加载了 `video_data`、`clockin_data` 等大型课程数据表。
  - 修复后 `header_links`：约 15ms。
  - 后端内部整条 sheet 组装：约 1.47-1.74s 降到约 132ms。
  - 公网 API 8 次采样：约 731ms，n=8。
- 公式裸显示问题已修：
  - 真实 Chrome 样本中 `rawFormulaCount = 0`。
  - 根因是公式引擎预加载后仍复用早期空公式显示缓存。
  - 修复点是空缓存遇到当前文档含公式时不再复用。
- `sheetPerf` 调试开关已改成 URL 级，不再用 localStorage 持久污染正常用户页面。
- 真实 Chrome 入口仍很慢：
  - 修复后一次样本：`goto` 返回约 22.2s，首个表格单元格可读约 43.3s，截图约 30.2s。
  - 外壳路由异步加载 `NoteSheetWorkspace` 后：首个表格单元格可读约 53.9s，未改善。
  - 非首屏子组件异步化后：首个表格单元格可读约 52.4s，未改善；颜色弹窗脚本未进入首屏脚本列表。

当前判断：

- 接口慢和公式渲染是已修复的问题，但不是 40-50s 级卡顿的主因。
- “小表也卡”不合理，说明不是 200x50 的数据量问题，也不能简单归咎于 Handsontable。
- 最大矛盾已转向 `NoteSheetWorkspace.vue` 本体：组件约 2.7 万行，首屏同步承载表格内核、考勤业务、Excel 导入导出、AI 检测、权限、反馈、富文本、颜色、公式、行详情等大量状态和 watcher。WPS/金山文档之所以切换快，本质上是编辑器内核和外围业务能力分层加载，首屏只让高性能表格内核运转。

下一阶段计划：

1. 抽出 `NoteSheetCoreGrid`：只保留 Handsontable、数据行列、公式显示、基本编辑、选择、复制粘贴、分页必要状态。
2. 抽出 `attendanceSheetActions`：考勤课程更新、报名匹配、打卡链接检测、问卷反馈、导出等全部作为按需插件加载。
3. 抽出 `sheetDialogs`：权限、列设置、单元格样式、富文本、Excel 导入、行详情等只在打开时加载。
4. 把首屏性能预算写成守卫：生产入口中 `NoteSheetWorkspace` 首屏不得静态依赖颜色工具、Excel/文件处理、考勤反馈历史、权限弹窗、AI/脚本状态等非首屏模块。
5. 每完成一刀都必须用同一部署 URL 复测：`goto`、首个表格 DOM、非空单元格、裸公式数、截图耗时。

### 2026-07-06 `sheet=54025` 后端大 JSON 瓶颈复测

测试入口：

- 页面：`https://code4101.com/workbook/7?sheet=54025`
- API：`/api/note-sheets/sheets/54025?workbook_id=7&include_workbook_context=false`

关键事实：

- 该 sheet 数据库中的 `document_json` 长度约 81.9MB。
- 当前分页响应体约 64KB，说明用户首屏实际只需要一小片数据。
- 旧路径在权限 resolve 阶段就通过 ORM 加载并解析完整 `document_json`，导致 `resolve_sheet` 单阶段约 498-568ms。
- 直接 JSON parse 探针约 430-610ms，和接口中的 `resolve_sheet` 大头吻合。
- `include_workbook_context=false` 不是主要收益点；它减少重复上下文语义正确，但这张表真正的大头是大 JSON 读取/解析。

已完成修正：

- GET sheet 详情路径先用 `load_only` 只读取权限/元数据列，权限 resolve 不再加载 `document_json`。
- 权限通过后再按需读取 `document_json`。
- 新增 `(sheet_id, version, updated_at)` 维度的短期内存解析缓存，TTL 300s，最多保留 3 份大文档。
- `bootPerf=1` 时前端通过 `X-CodeYun-BootPerf` 请求后端返回 `Server-Timing`，避免把诊断和缓存细节污染到页面 URL。

复测结果：

| 场景 | 指标 | 优化前 | 优化后 | 说明 |
| --- | --- | ---: | ---: | --- |
| 本机 API | `resolve` | 540-713ms | 48-54ms | 缓存命中后，权限/元数据 resolve 不再解析 81.9MB JSON |
| 本机 API | `document_json` | 混在 `resolve_sheet` 中，约 500ms | 冷启动约 522ms，命中后 0ms | 冷启动仍需读一次完整 JSON |
| 本机 API | 总耗时 | 641-842ms | 81-102ms | 剔除首个冷启动样本 |
| 公网 API | 总耗时 | 1.1-2.0s | 416-527ms | 服务端实际约 80-120ms，其余主要是公网/FRP/HTTPS |

当前判断：

- “有些表首次慢、有些表快”的根因成立：缓存未命中时仍要读/解析大文档，缓存命中后同一 sheet 详情接口进入百毫秒内。
- 这不是 Handsontable 框架问题，也不是当前页 200x50 的前端数据量问题，而是持久化结构把全量历史表格压在一个 JSON 字段里。
- 当前短期缓存只能解决短时间重复访问/切回同表，不能从根上消除冷启动大 JSON 成本。长期应把大工作表拆成后端分块/页级快照，首屏只读当前页和必要元数据。

### 2026-07-06 `sheet=54025` 页级快照读路径

本轮落地第一版持久化 `sheetpagesnapshot`：

- 只覆盖非 `attendance` sheet 的 GET 详情分页响应，避免影响考勤主表的动态表头链接和课程配置语义。
- 快照键包含 `sheet_id/version/updated_at/workbook_id/page/page_size/paginate/include_workbook_context`，防止不同请求上下文混用。
- 快照只保存当前页 `document_json`、`pagination`、工作簿上下文和定义名称上下文；如果请求返回整表，不写快照，避免把大 JSON 复制一份。
- GET 详情在权限/元数据 resolve 后先查页级快照，命中时直接构造原有 `NoteSheetDetailResponse`，不读取完整 `SheetDocument.document_json`。

本机复测，清空 `sheet=54025` 快照后请求 4 次：

| 样本 | 总耗时 | 主要 Server-Timing | 说明 |
| ---: | ---: | --- | --- |
| 1 | 669.3ms | `document_json=485.1ms`，`snapshot_store=124.2ms` | 首次生成页级快照，仍需读一次全量 JSON |
| 2 | 54.9ms | `page_snapshot=0.7ms`，无 `document_json` 阶段 | 命中持久化页级快照 |
| 3 | 50.7ms | `page_snapshot=0.6ms`，无 `document_json` 阶段 | 命中持久化页级快照 |
| 4 | 55.9ms | `page_snapshot=0.6ms`，无 `document_json` 阶段 | 命中持久化页级快照 |

公网复测，已有快照：

| 样本 | 总耗时 | 主要 Server-Timing |
| ---: | ---: | --- |
| 1 | 252.1ms | `resolve=47.3ms`，`page_snapshot=0.6ms` |
| 2 | 223.1ms | `resolve=56.4ms`，`page_snapshot=0.7ms` |
| 3 | 159.4ms | `resolve=51.4ms`，`page_snapshot=0.8ms` |

当前判断：

- 这是真正朝 WPS/KDocs 式“切页不重新读全量数据”前进的一步：快照命中后，`sheet=54025` 的服务端读路径已经完全绕过 81.9MB `document_json`。
- 首次生成快照仍要支付一次全量 JSON 成本，后续应把快照生成前移到保存/导入/后台任务，而不是等用户首次打开。
- 还需要继续压缩 `resolve_sheet` 约 45-56ms 的固定成本；但它已经不是大 JSON 级主矛盾。

依赖源码补充定位：

- 当前版本为 `handsontable 17.0.1` / `@handsontable/vue3 17.0.1`。
- `@handsontable/vue3` 的 `hotInit()` 会执行 `new Handsontable.Core(this.$el, newSettings)` 后立刻 `hotInstance.init()`。
- Handsontable core 的 `init()` 先 `dataSource.setData(tableMeta.data)`，再 `updateSettings(mergedUserSettings, true)`，初始化数据路径会进入 `populateFromArray -> setDataAtCell -> applyChanges -> instance.render()`，随后 `init()` 自身又调用一次 `this.render()`。
- 这解释了第三十二轮剩余两次 `unattributed` render：当前不是我方手动 render，而是 wrapper 带 data 初始化与 HOT core init 渲染叠加。
- 直接把 `:data` 改为空数组不可取：vue3 wrapper 的 prop watcher 依赖同一个 data 引用自动同步，维度变化时只调 mapper 并删除 `settings.data`，不会替我们把真实数组 `loadData()` 进去。下一步应做独立最小实验：不传 `data` prop / 自建轻量 wrapper / 挂载后命令式 `loadData()`，比较是否能把“满数据两次 render”降成“空表初始化 render + 满数据一次 render”。

### P4：长期引擎路线

目标：判断 Handsontable 是否仍满足 CodeYun 星云表格的长期定位。

判断口径：

- 如果 P0-P3 后仍存在 500ms 以上的常态 render 长任务，开始调研 canvas/虚拟表格引擎。
- 若主要场景只是中小表格管理，继续保留 Handsontable，但限制重插件和复杂 renderer。
- 若目标是 WPS/KDocs 级连续滚动、切 sheet 和超大表体验，需要同时规划自研轻量表格渲染层和后端页级/块级存储。只换前端表格引擎而继续让首屏读 81MB JSON，无法达到 WPS 类首次打开体验。
