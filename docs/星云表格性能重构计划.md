# 星云表格性能重构计划

更新时间：2026-07-05

## 结论

当前卡顿主要不是接口慢，也不是单纯 Handsontable 框架不可用，而是 CodeYun 表格页把 Handsontable 推入了多次重配置和重渲染路径。Handsontable 的 DOM 渲染模型会放大这个问题；WPS、金山文档、腾讯表格、Google Sheets 这类产品通常使用更底层的自研表格渲染引擎，长期上限确实不同。

短中期优先修 CodeYun 自身实现，目标是把 sheet 切换从“重建组件 + 重配插件 + 多轮 render”收敛为“稳定实例 + 单次数据加载 + 必要局部更新”。长期如果要接近 WPS 级丝滑，再评估自研 canvas/虚拟表格引擎。

已定位的主要问题：

- sheet 切换曾通过 `HotTable` key 绑定 `sheetId`，导致切 sheet 重建 Handsontable。
- core/enhanced 两阶段渲染会让 `cells/contextMenu/manual*/mergeCells/readOnly/rowHeights/afterRenderer` 这些重配置经 Vue wrapper 再走一次 `updateSettings`。
- 旧版还在增强阶段手动调用了一次 `updateSettings`，形成重复大开销。
- 模板层 `:render-all-columns="rowMarkerColumnCount > 0"` 因为行号列常态存在，等价于强制渲染几乎全部列，导致首屏可见 14 列却实际渲染 67 列。

## 已完成改动

- `HotTable` key 从 `workbookId + sheetId` 收敛为 `workbookId`，减少切 sheet 时的组件重建。
- 给 Handsontable `render/updateSettings/loadData` 增加耗时打点，能区分数据加载、settings 更新和 render 耗时。
- 给 `sheet.loadDocument` 增加阶段打点，拆出 rows/header/merge/column-width/entities-formulas/Hot 应用阶段。
- 移除 `applySheetRenderEnhancement` 里的手动重复 `updateSettings`。
- 将 `beginSheetCoreRenderPhase()` 改为直接进入增强可用态，避免 core -> enhanced 的 props diff 触发全量 `updateSettings`。
- 将 data-only 的 `hot.updateSettings({ data })` 收敛为 `hot.loadData(...)`，避免普通数据刷新误走插件配置更新路径。
- 在结构性刷新里把 settings 更新和数据加载拆开：`updateSettings(结构配置)` 后再 `loadData(当前网格数据)`。
- `loadSheetDocument()` 不再在 HotTable 已挂载时手动推 `updateSettings/loadData`，改为让 Vue wrapper 在 nextTick 统一应用响应式 props，减少 sheet 文档加载的双通道更新。
- 关闭“有行号列就 renderAllColumns”的配置，改为 `render-all-columns=false`，并设置 `viewport-column-rendering-offset` 保留少量横向缓冲，让 Handsontable 恢复横向虚拟化。
- 将定义名称同步从 `restoreInitialDocument()` 的首屏阻塞链路移出，首屏完成后异步刷新公式显示、公式栏草稿和自适应列宽。
- 复用 `loadSheetDocument()` 中为列宽构建的公式显示状态，避免首屏路径里先为列宽算一次公式、随后 `refreshFormulaDisplayState()` 再算一次。

## 质量门禁

已新增源码级回归测试：`tests/test_note_sheet_workspace_performance_guards.py`

覆盖目标：

- 禁止重新引入 `hot.updateSettings({ data: sheetHotGridRows.value })` 这类 data-only 配置更新。
- 要求普通数据刷新继续通过 `loadCurrentHotGridRows()` / `hot.loadData(...)`。
- 要求 `loadSheetDocument()` 继续把 HotTable 更新延迟给 Vue wrapper，避免文档加载路径回到命令式更新和响应式 props 更新并存。
- 要求 `render-all-columns` 保持关闭，并通过 `viewport-column-rendering-offset` 保留横向缓冲，防止行号列再次禁用列虚拟化。
- 要求定义名称同步继续延后到 sheet 首屏加载之后，防止 `defined-names` 再次阻塞 `sheet.load`。
- 要求 `loadSheetDocument()` 复用已构建的公式显示状态，防止公式显示在首屏加载中重复计算。
- 要求 `loadSheetDocument()` 复用已标准化的 `cell_meta`，防止同一轮 `normalize -> load` 重复合并 inline link 和 action 元数据。
- 要求 `normalizeSheetDocument()` 保留 `sheet.normalizeDocument` 分阶段打点，继续拆分 `headers-config/grid-settings/source-rows/merge-grid/cell-meta/entities/formula-widths`，并保留 `cell-meta-source/inline-*/legacy-actions/registration-*` 子阶段以定位元数据处理热点。
- 要求 inline cell meta 合并继续批量归一化，防止 header/row/grid 三段合并各自重复全量 `normalizeCellMetaMap()`。
- 要求 legacy action label 识别继续使用预计算 Map，防止在每个格子里重建 label 列表并 `.find()`。
- 要求已标准化的 cell meta row-key 变换不要在变换后再次全量 `normalizeCellMetaMap()`。
- 要求 `sheet.load` 保留 Vue flush 相关细分阶段，防止把缓存、状态恢复和真实 `nextTick` 耗时重新混在一起。
- 要求 remote detail 缓存继续在首屏 sheet load 之后延后执行，防止本地缓存写入重新阻塞切 sheet 可见速度。

### P4：长期引擎路线

目标：判断 Handsontable 是否仍满足 CodeYun 星云表格的长期定位。

判断口径：

- 如果 P0-P3 后仍存在 500ms 以上的常态 render 长任务，开始调研 canvas/虚拟表格引擎。
- 若主要场景只是中小表格管理，继续保留 Handsontable，但限制重插件和复杂 renderer。
- 若目标是 WPS/KDocs 级连续滚动、切 sheet 和超大表体验，需要规划自研轻量表格渲染层。
