# 资源保存与并发更新约定

## 已确认的旧架构缺陷

旧实现把资源级 `version` 同时当作更新顺序、协作冲突和用户身份判断。只要后台任务、同一用户的另一个页面或自动保存先增加版本，随后到达的用户保存就会收到 409；前端又把所有 409 解释成“其他人更新”，并将编辑器锁死到刷新为止。

资源版本只能证明“资源发生过变化”，不能证明“本次编辑目标发生了冲突”，更不能证明更新来自另一个人。

## 统一写入协议

每次逻辑编辑应携带：

- `base_version`：编辑开始时看到的资源版本，用于判断是否需要重放。
- `expected_fields` 或操作级 `expected_value`：用户编辑目标的原值，用于检测真实的同目标冲突。
- `mutation_id`：单次逻辑变更的身份，后续用于重试幂等和确认回执。
- `client_instance_id`：当前页面实例身份，用于识别自身 WebSocket 回声。

服务端处理顺序：

1. 当前版本等于 `base_version` 时直接应用变更意图。
2. 当前版本较新，但所有目标仍等于其 expected 值时，在最新资源上重放变更。
3. 仅当同一字段、单元格或结构目标已经变化时返回 409，并返回具体冲突目标。
4. 广播必须明确携带 `source_kind`、真实 `updated_by_user_id`、`mutation_id` 和 `client_instance_id`；缺少用户身份的系统任务不得伪装成“其他用户”。

## 前端约束

- 同一资源的本地写入必须经过一个串行队列；整文档保存与局部补丁不能互相抢跑。
- WebSocket 新版本只负责通知和缓存失效，不直接判定冲突。
- 本页面 mutation 的广播属于回声，不触发冲突提示。
- 本地有未保存编辑时，不用远端快照覆盖；继续提交编辑意图，由服务端执行目标级重放。
- 409 只描述真实冲突目标，不使用“其他人更新”这类未经证实的归因。
- 页面隐藏时的 keepalive 保存必须复用同一 payload 语义，不能形成第二套保存协议。

## 资源策略

- 表格：以稳定的 `row_id + column_id` 定位单元格，并携带旧值或旧格式。结构操作仍采用严格版本保护。
- 普通文档与元数据：发送字段补丁及对应旧值；无关字段变更允许自动重放。
- 富文本多人实时协作：后续如确有同时编辑需求，再采用 Yjs/Automerge 一类操作历史或 CRDT；单用户加后台任务的场景不应先引入完整 CRDT。

## 后续演进

当前实现已统一目标级冲突判断和变更身份。下一阶段应增加服务端 mutation 幂等记录，并将剩余资源型 PUT 接口逐步迁移到公共 optimistic mutation helper；业务状态冲突、唯一性冲突等非保存型 409 不在此约定范围内。
