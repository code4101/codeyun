# 凡修邮件抓包协议研究

本文记录凡修邮件界面的抓包协议、客户端 Lua 处理链、现有样本解析状态，以及后续自动化的安全边界。

## 客户端处理链

`MailNetLogic.lua` 注册所有邮件协议。关键入口：

- `SM_MailBoxFun(msg)`：调用 `MailMgr.Inst_get().Model:SetMailBox(msg)`。
- `SM_NewMailFun(msg)`：调用 `MailMgr.Inst_get().Model:NewMail(msg)`。
- `CM_ReadMailFun(id)`：发送 `CM_ReadMail.id=id`。
- `CM_GetMailRewardFun(ids)`：发送 `CM_GetMailReward.ids=ids`。
- `SM_GetMailRewardFun(msg)`：检查错误码；如果 `bagFull` 则提示背包满；成功后调用 `OnGetRewardSucceed`。

`MailData.lua` 维护本地邮件模型：

- `SetMailBox(msg)`：把 `msg.mailVos` 和 `msg.locks` 写入模型，再按 `createTime` 倒序排序。
- `NewMail(msg)`：把新邮件插入列表开头，再刷新红点。
- `OnGetRewardSucceed(msg)`：把奖励结果交给奖励管理器，并将命中的邮件标记为 `read=true`、`rewardGetted=true`。

`MailPrefab.lua` 和 `MailContentView.lua` 展示标题、内容、发件人：

- 列表标题优先使用 `MailVo.title`，为空时使用 `Envelope_Envelope[type].title`。
- 详情内容优先使用 `MailVo.content`，为空时通过 `Envelope_Envelope[type].contentId` 和 `PostMgr.GetPostMessage(...)` 生成。
- 发件人优先使用 `MailVo.senderName`，为空时使用 `Envelope_Envelope[type].sender`。
- 因此 packet 同步器必须能读取静态 `Envelope.Envelope` 表。若出现 `未知邮件类型123`，优先检查 `lscripts/generate/cfg/envelope_*.bytes` 是否已经导出并解析成 `parsed_configs/Envelope/rows.json`；不能用 OCR 截图文字或临时硬编码当作 packet 标题事实。

## 领取安全边界

邮件界面存在两个全局按钮：`一键删除` 和 `一键领取`。自动化中必须把 `一键领取` 当成不存在，不能点击。

原因是 `WinMailBoxView.OnGetBtnClick` 会调用 `MailMgr:ClaimAllRewards()`，它会遍历所有未领取且未锁定的邮件，构造多个 id 后一次性发送 `CM_GetMailReward`。

单封详情里的按钮才是安全路径：`MailContentView.OnClickBtn` 会构造只包含当前邮件 id 的 `idList`，如果当前邮件可领取，则发送 `CM_GetMailRewardFun(idList)`；否则发送单封删除。

## 处理策略草案

当前邮件事实应以 packet 解析结果为准：邮件标题、附件、附件道具分类和状态来自 `SM_MailBox` / `SM_NewMail` / 领取删除回包以及静态 `Envelope`、`Item` 资源表，不再依赖 OCR 兜底结果。

新版 `邮件_领取检查` 策略按附件事实判断，旧的按邮件名白名单直接领取/删除规则已经废弃并从执行层移除，不再作为自动处理依据。当前阶段使用 packet 附件名称和类型做安全分流。

图鉴展示层不能把“抓包里没有正文模板”渲染成空白。当前固定规则：

- `MailVo.content` 或静态 `Envelope.contentId` 能解析出正文时，展示解析后的正文。
- 抓包没有正文但有附件时，展示附件摘要，例如 `附件：灵石 x128`、`自动领取：试炼手册 x360`。
- 抓包既没有正文也没有附件时，展示透明说明，例如 `抓包未携带正文或附件；邮件类型：秘境封魔杀报名提醒`。
- 不为了填空伪造游戏正文，不把 OCR 截图文字当成 packet 正文。
- 前端邮件图鉴的“正文”列可以压缩为“查看”按钮，但弹窗打开后必须能看到上述正文或摘要；验证脚本会把空正文视为失败。

当前自动领取/删除判断按以下优先级顺序执行：

1. 附件名称或类别带 `法则`：最高优先级保护，永远不能自动领取。后续应先锁定，避免手误或一键领取误触；锁定操作流程尚未固化。锁定上限为 10 封，若候选超过上限，应优先锁定更高价值法则，例如跨服法则优先于服内法则，具体等级规则后续再核对。
2. 附件带 `潜修心得·四刻`：可以自动领取。该规则优先于保护资源判断，但仍低于法则保护。
3. 附件含下列祈愿相关保护资源：暂缓，不自动领取。
   - 炼丹：`炼丹灵草匣`、`神品灵草匣`、`炼丹灵草宝匣`
   - 淬体：`淬体精魄`
   - 灵兽：`珍品饲灵丸`
   - 洗灵：`洗灵奇石`
   - 仙花：`瑶池玉莲`、`造化青莲`
4. 其余有附件邮件：packet 已明确解析附件名称，且不命中以上规则时，可单封自动领取。

无附件邮件默认直接删除。若界面按钮文案叫“领取”，也按“无附件可处理”理解。

安全边界：如果 packet 没解析出明确道具名，暂缓处理，不能靠 OCR 或截图猜测。

未决事项：

- 法则邮件的锁定入口、确认流程和失败恢复。
- 法则价值排序：跨服、服内、活动来源、等级或稀有度的具体优先级。
- 保护资源清单的继续扩展。当前只记录已在邮件样本中确认的名称，不假设完整图鉴分类已经准确。
- `祈愿` 活动如何消耗或影响这些资源，以及对应邮件何时可以领取。

## 解码器缺口

当前通用解码器对 `readMessageList2List` 的基本模型是对的：读取长度、共享类型标记、共享 proId 或逐项 proId，再按基础类型或消息 Bean 解析。

但邮件样本暴露了两个缺口：

- `SM_MailBox.locks` 在 Lua 读法上写成 `readMessageList2List(self.locks)`，但写法是 `writeLongList(self.locks)`。仅按读法当成消息 Bean 列表会误读，应该结合 writing 元信息或包字段特例把它按 LongList 解析。
- 部分 `MailVo.i18nParams` 的 `I18nParam2Num` 解析结果里，`key` 出现了 `\0...NUM` 这样的错位字符串，且另外两条 `SM_NewMail` 在同一区域失败。2026-06-05 用真实 `SM_MailBox` 样本校准后确认：当前运行包里的 `I18nParam2Num.value` 是 8 字节 `Double`，不是旧 Lua 导出的 `Int`。按 `Double` 读取后，样本中的 `SM_MailBox` 可以连续解出 78 封邮件和 5 个锁定 id。

后续修复顺序：

1. 为通用解码器补 `writeLongList` 字段提示，让 `SM_MailBox.locks`、`CM_GetMailReward.ids`、`SM_GetMailReward.ids` 等字段按 LongList 解析。
2. 针对 `I18nParam2Num.value` 按真实运行包补 `Double` 解码补丁，不能再按旧导出的 `Int` 或临时猜测的 `Long` 读取。
3. 重新解码历史 pcap，并回填 `FanxiuPacketDecodedRecord`，让当前 5 封邮件都能落到完整 type/title/read/rewardGetted 字段。

## 自动化原则

- 不使用 Android 返回键或 Esc；在凡修中它们是退出游戏用途。
- 不点击 `一键领取`。
- 邮件打开后优先通过场景 #121 和具体 shape/OCR 做 UI 验证。
- 抓包验证应关注 `SM_MailBox`、`SM_NewMail`、`CM_ReadMail`、`CM_GetMailReward`、`SM_GetMailReward`，不要只看点击打开邮件界面的瞬间是否出现新包。
- 邮件图鉴验收应同时跑数据层和页面层：
  - `uv run python scripts/verify_fanxiu_mail_records.py --api-timeout 15`
  - `uv run python scripts/verify_fanxiu_wiki_browser.py --tab mail --local-auth-user admin --scroll-steps 1 --wait-ms 10000 --screenshot`
- 数据层必须满足 `with_content == records`，页面层必须满足正文弹窗可打开且附件图标、附件链接都有效。
