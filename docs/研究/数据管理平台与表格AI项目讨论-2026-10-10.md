# 数据管理平台与表格 AI 项目：早间讨论整理

日期：2026-10-10。范围：本次早间讨论（微信消息 2192—2272）。

本文用于继续讨论，记录概念共识、项目回忆与待明确问题，不代表当前实现，也不作为新增开发任务清单。未经讨论确定的功能不自动进入规划。物理存储技术暂不讨论。

## 1. 当前讨论的核心结论

采用“素材—素材类型—素材库—数据集”的统一概念。表格、问题、JSA、答案、断言、文档都可以成为素材；组合后的对象也可以成为素材，并继续参与组合。

素材库统一存储素材实例，数据集通过引用组织素材。类型结构需要可扩展，不能提前预设死所有业务字段。目录用于分组管理数据集，不隐含合并或配对。

这些概念解决的是数据组织问题。它们如何支撑更高层次的专家工作平台，仍需进一步明确；底层抽象应让数据更好用，不能把复杂度转嫁给使用者。

## 2. 统一术语与逻辑关系

| 概念 | 含义 |
| --- | --- |
| 素材类型 | 定义字段、结构和约束，支持基础类型及复合类型 |
| 素材 | 某个类型的具体实例，可独立引用与复用 |
| 素材库 | 管理素材实例；不只是定义数据结构的目录 |
| 数据集 | 某一素材类型的若干实例引用，可由明确清单或规则选择形成 |
| 数据集目录 | 分组组织数据集，可以容纳不同素材类型的数据集 |
| Pipeline | 面向数据集的处理流程，产生新素材及新的数据集 |

编程类比：素材类型类似类，素材类似实例，复合素材类似对象组合，数据集类似同类型对象的集合。该类比用于理解数据结构，不意味着需要引入完整的面向对象编程机制。

### 2.1 类型与角色分开

类型描述素材是什么，角色描述它在某次组合中做什么。同一张表可以充当输入或参考输出；同一份文档可以充当背景材料、操作规范或校验依据。

组合需要保留角色及配对关系，不能只是把所有素材放进一个无区别的集合。例如：

```text
表格问题类型：{表格引用, 问题引用}
完整样本类型：{表格引用, 问题引用, 求解引用, 校验引用}
```

各角色是否允许为空、允许一个还是多个，由具体类型或处理任务决定，不要求所有数据都符合固定四件套。

多份表格、多道问题、多段求解放在一起，并不会自动确定配对关系。逐一配对、条件匹配、笛卡尔积是不同的构建规则。

### 2.2 复合素材可以嵌套

组合本身可以登记为新素材，再被其他组合引用。一个样本可以整体作为下游任务输入，组合中也可以同时包含自身字段和其他素材引用。

“样本”是某些复合素材的业务名称；“数据集”组织这类素材。不能把素材、样本、数据集理解为禁止复用或跨层引用的固定阶梯。

### 2.3 字段扩展

不同类型可以有不同结构；字段定义逐步完善，允许未预见的类型和业务字段。

讨论过的两种扩展方式可以统一：

```text
组合扩展：{表格: 引用 a, 问题: 引用 b}
字段扩展：{原问题: 引用 b, 难度: 3, 功能分类: "筛选"}
```

第二种方式只保存引用与新增属性，不必复制或修改原问题。若属性仅对某个数据集有意义，可以放在该数据集的成员关系上；若形成可复用的业务结构，可定义新的素材类型。

字段命名、约束和版本兼容的具体机制尚未制定，不应把这些示例当成已经实现的规格。

### 2.4 批次由业务决定

批次只是按需定义的业务字段。是否去重、是否跨批复用、如何标记来源，由业务处理；通用系统无需将批次提升为特殊核心实体。

此前提出独立批次、多重批次关联的建议已被收回，不作为通用设计要求。

## 3. 数据集与 Pipeline

### 3.1 数据集组织

数据集引用素材；一个素材可以被多个数据集使用。目录可以同时包含表格数据集、问题数据集、复合样本数据集。

目录分组不等于合并。即使类型相同，也由业务明确决定是否合并；不同类型的配对属于构建复合素材，而非简单合并。

数据集可以通过现成素材编号构建，也可以通过规则筛选和组合生成。规则最终需要确定具体素材引用及其组合关系，不只是选出一串编号。

素材版本固定、动态规则与执行时成员快照的处理方式曾被提出，但尚未详细确定。

### 3.2 上游导入

上游可以直接交付复合类型数据集。系统通过导入映射，将内容登记为素材，保留原来的角色与配对关系，再形成数据集。业务决定拆解粒度，不必把所有复合内容拆到最细。

### 3.3 组合与用途分离

“表格＋问题”本身就是有效组合，可以用于下游造数据、模型求解或专家标注，不需要补齐求解和断言。

组合描述有哪些素材及其关系；处理任务描述拿它们做什么。同一个组合可以服务多种任务。

```text
输入数据集 → 处理任务 → 新素材或复用已有素材 → 输出数据集
```

流程可以补充 JSA、答案、校验，也可以改写问题、生成表格或构建新的复合素材。

## 4. 求解、校验与评分

### 4.1 答案与断言

标准答案是期望结果数据；“实际结果与标准答案相等”是一条校验规则。单元格样式、位置等约束同样可以有明确标准，并非一定属于无标准答案。

可统一使用“校验规则”和“校验结果”。求解代码、校验脚本及其运行记录需要区分；一道题可以有多个求解尝试，也可以接受多个校验或评分。

### 4.2 操作题的对拍

用户描述的方式：同题求解 5 次，先确认沙盒代码可运行，再比较处理后文件 hash；至少 3 次结果一致时，将对应解答选为通过候选。

该方式属于多数一致性验证。一致性不能单独证明业务正确；原始文件 hash 还可能受非业务内容影响，具体比较方式需由业务确定。

历史顺序以用户更正为准：**2023 年 7 月先使用 return 返回的关联指标对比、对拍，后来才研究文件 hash 的可能性。**在本次抽象中，两者均属于对拍验证，仅比较对象不同。

另有一种方式：同一问题采用不同问法，分别求解，比较结果是否一致（用户指出 w231009 有参考图）。

### 4.3 数据分析题

用户明确：最终验证模型可以用 AI 结合专家知识自动打分。

**训练集如何筛选仍未知**：用户不记得明捷是否讲过，不能从最终评测方法反推训练集筛选方法，也不能据此断言历史上做过完整的无标准答案 Python 分析题验证流程。

## 7. 尚未收敛的上层架构

用户指出：当前梳理主要强调数据工作的组织形式，仍凸显不出与专家平台衔接的更高层架构；底层也必须设计好，避免数据更难使用。

后续讨论需要从专家实际工作案例理解任务、材料、判断及成果的衔接。素材库、数据集和 Pipeline 提供支撑，但不应要求专家先理解底层引用与类型机制才能工作。

尚未确定的重点包括：

- 专家平台的核心工作对象与任务组织方式。
- 专家标注、审核、评分的成果如何被下游采用。
- 数据分析训练集的筛选方法。
- 字段扩展、成员属性与复合素材的具体边界及交互。
- 类型演进、素材版本及数据集动态引用的详细规则。

这些是继续讨论的问题，不是已批准的开发清单。本次没有据此修改平台实现或新增正式规划。
