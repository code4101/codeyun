# Freebill 账单工具核心概念

Freebill 的目标不是手动记账，而是把支付宝、微信、银行卡等平台导出的真实流水导入系统，自动做分类、统计和查询。它不追求绝对精确，但要足够还原主要资金流向，让人能看清消费、借贷、理财和账户流转的真实规模。

## 核心定位

- 数据来自平台导出的账单明细，而不是用户逐条录入。
- 系统自动对齐字段、去重、解释分类，并生成趋势、分类树和明细表。
- 任意账单条目都允许人工修改，但人工修改不覆盖原始数据。
- 适合阶段性复盘，例如按年看整体开销和资金结构；实时同步不是当前第一目标。

## 特色优势

Freebill 的“Free”有三层含义：

- **解放双手**：机器已经记录了绝大多数交易，用户不应该再逐笔手动记账。
- **数据自由**：把分散在微信、支付宝、银行卡等平台的数据导回本地，打破支付平台的数据孤岛。
- **免费开放**：工具面向个人长期使用，不依赖订阅、广告或平台锁定。

Freebill 关注的不是“记录”，而是“洞察”。移动支付时代，交易事实已经天然存在，真正的问题是这些数据格式不统一、平台彼此隔离、官方统计过于粗粒度，用户很难按自己的口径复盘消费结构。

因此 Freebill 更像一条本地账单 ETL 流水线：

```text
原始账单 -> 字段标准化 -> SQLite 存储 -> 解释规则 -> 可视化分析
```

它的核心价值是：

- **零手动录入**：通过批量导入文件更新账目。
- **本地优先**：数据存储在本机 SQLite 中，不需要上传到云端。
- **统一视角**：微信、支付宝、银行卡等资金流可以在同一个视图里分析。
- **可编程性**：底层是结构化数据库，后续可以用 SQL、脚本或规则继续深挖。

## 数据层级

1. **外部原始层**：用户从支付宝、微信、银行等平台导出的压缩包、CSV、Excel、邮件附件和解压密码。
2. **文件整理层**：把原始文件解压、统一命名、转成更稳定的 xlsx/csv，形成可重复导入的文件集合。
3. **规范导入层**：程序把不同来源的字段对齐后写入数据库，保留交易时间、来源、收支、分类、交易对方、商品、金额、状态等结构化原始事实。
4. **解释规则层**：按当前用户口径，把原始字段解释成更适合分析的“类型、收支、分类、交易对方”等结果。
5. **人工覆盖层**：用户对单条或分组做的修改，以 JSON 字典保存，只记录被改过的字段。

## 导入与去重

账单导出是系统最大的现实门槛。不同平台导出流程差异很大，有的只能手机操作，有的要等邮件，有的有验证码和时效限制。Freebill 因此把“导入后可重复处理”作为优先设计：同一批数据重复导入也没关系，底层会基于交易号、来源、时间、金额、原始序号等信息做去重。

京东等平台缺少稳定批量导出能力，后续更适合单独通过爬虫或自动化补充。爬虫反而可能更接近实时，但它属于另一个采集链路。

## 五大类型

Freebill 不只按传统生活消费分类，而是先把账单拆成五种资金类型：

| 类型 | 含义 |
| --- | --- |
| 常规 | 日常消费支出、工资收入、普通经营性收支。 |
| 借贷 | 信用卡、借呗、花呗、京东白条、借款和还款。人情往来借还也可归入这一类。 |
| 理财 | 股票、基金、黄金、余额宝收益、余利宝等投资行为；买入是支出，赎回和收益是收入。 |
| 转账 | 自己不同 App、银行卡、支付平台之间的资金移动。理论上成对出现，整体应能对冲。 |
| 流水 | App 内部更细粒度的账户流转，例如支付宝余额和余额宝之间的内部转移，不直接当作收入或支出。 |

## 借贷口径

借给别人钱时，默认先算常规支出，因为这笔钱不一定能回来。如果未来确认对方还款，再把支出和收入两边一起调整到借贷类型，相当于把这段资金往来平账，减少原本常规开销的误差。

## 分类层级

当前主要分析层级是：

```text
类型 -> 收支 -> 分类 -> 交易对方
```

支付宝账单本身提供了较好的分类和交易对方信息，叠加 Freebill 的五大类型后，能比较清楚地看到资金结构。比如装修支出可以单独整理到一个分类；模糊的交易对方也可以改成更容易回忆的人名或事项名。

## 人工修改原则

人工修改不改原始数据，也不影响导入去重。系统会把用户修改保存到独立 JSON 字段中，例如只记录：

```json
{
  "type": "装修",
  "counterparty": "杨杨装修"
}
```

最终查询和统计时，解释规则层会用这些人工字段覆盖原始字段。这样既保留了原始账单，又能按用户自己的理解不断整理出更准确的分类。

## 当前边界

- 自动分类很难完全精确，尤其是平台内部转账、借贷、理财和退款混在一起时。
- 数据时效性受导出流程限制，现阶段更适合年度或阶段性复盘。
- 通用化还需要继续打磨导入流程、解释规则、手动批量调整和更多平台采集能力。
