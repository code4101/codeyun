# 作业与服务架构

## 不变量

- 作业不是进程。作业由 CodeYun 后端中的调度器触发，并由进程内执行器调用已注册的 Python callable。
- 服务是独立进程。服务拥有独立的启动、停止、健康检查、日志和重启策略。
- 作业执行器不得导入 `subprocess`、服务启动器或低层进程工具。
- 命令条目只表示服务；`runtime_kind=job` 的命令条目不再执行。
- 服务监控不进入作业队列；定时启动服务仍属于服务控制命令，不产生 JobRun。

## 目录边界

```text
backend/core/jobs/
  scheduler.py   规则求值与到期触发
  executor.py    串行执行进程内 callable，保存运行快照
  models.py      作业执行策略与投影

backend/core/services/
  monitor.py     常驻服务观察与恢复
  launcher.py    唯一的隐藏进程启动入口
  _subprocess.py Windows/POSIX 进程启动细节
  models.py      服务定义、策略与观测状态
  policy.py      命令服务策略与分组
```

共享只发生在 API/UI 投影层。作业和服务不共享执行器、队列或生命周期状态。

## Windows 控制台规则

- `codeyun-dev.cmd -> uv run dev.py` 是用户可见的主控制台。
- 后端使用普通 `python.exe -m uvicorn backend.app:app` 并继承主控制台，不再使用 `pythonw` 或 `uvicorn_hidden`。
- CodeYun 后端不得全局 monkey-patch `subprocess.Popen`。
- 只有独立服务入口可以安装服务进程树的无窗口策略。

## 作业注册规则

新增作业必须注册为进程内 callable。调度器只负责判断到期并入队，不接受命令字符串。

如果能力需要外部长期进程，应先注册为服务，再由作业调用该服务的客户端/API；作业不得负责拉起服务。如果现有流程只能通过临时命令实现，则在抽成应用能力或服务之前不得加入作业目录。

## 已删除的旧路径

- 两份并行的 `background_task_runner` 实现。
- `runtime.units` 中依靠名称和命令猜测 job/service 的混合模型。
- `TaskManager.enqueue_task_run` 命令作业执行链。
- 作业队列里的常驻服务自检。
- `pythonw + backend.core.runtime.uvicorn_hidden` 后端入口。
- 后端进程级 `subprocess.Popen` 全局补丁。
- 前端“自定义命令作业”入口。

旧源码只保存在仓库外归档，不参与导入、测试、构建或部署。
