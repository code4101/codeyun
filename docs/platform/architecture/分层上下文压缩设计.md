# 分层上下文压缩设计

## 1. 目标

当原始输入远超单次模型上下文时，不应继续尝试“截断后硬总结”。更稳的做法是把超大输入组织成一棵分层压缩树：

1. 先把原始输入切成很多小块。
2. 每个小块单独做一次“面向任务的结构化压缩”。
3. 再把这些压缩结果按同样方式继续分组、继续压缩。
4. 直到压到模型可以稳定处理的规模，再产出最终结果。

这不是 Git 专属技巧，而是一个通用能力。Git 提交、笔记归纳、日志整理、长文档问答都可以复用这套框架。

## 2. 核心思想

### 2.1 不是“多轮聊天”，而是“层级化 map-reduce”

- `map`：对每个子块独立执行任务定制的压缩。
- `reduce`：把上一层的结构化结果再分组、再压缩。
- 每一层的输出都不是泛泛摘要，而是该业务真正需要的结构化中间结果。

### 2.2 压缩率由分支因子控制

设每层最多合并 `m` 个节点：

- 原始输入规模为 `N`
- 第一层节点数约为 `ceil(N / m)`
- 第二层节点数约为 `ceil(N / m^2)`
- 最终层数约为 `O(log_m N)`

例如 `N = 1000, m = 10`：

- 第 1 层：100 个叶子摘要
- 第 2 层：10 个中间摘要
- 第 3 层：1 个顶层摘要

总节点数大约是 `100 + 10 + 1 = 111`。如果同层可以并行执行，整体轮次很少。

### 2.3 关键不在“摘要”，而在“任务定制”

同一套引擎可以服务不同业务，但每个业务必须自定义：

- 如何切块
- 每层提示词如何构造
- 输出结构长什么样
- 上层如何消费下层结果
- 什么时候可以提前停止

## 3. 通用抽象

这套能力已落地为通用后端组件：

- `backend/core/ai/hierarchical_reduction.py`

其中定义下面几个核心概念。

### 3.1 Source Unit

原始输入的最小业务单元。

例子：

- Git：一个文件 diff、一个文件预览、一个目录级变更块
- 笔记：一条笔记、一段笔记正文、一个节点子树
- 日志：一段时间窗口内的日志片段

### 3.2 Chunk

一轮模型调用实际消费的一组输入。

字段建议：

- `id`
- `level`
- `task_type`
- `items`
- `estimated_tokens`
- `metadata`

### 3.3 Reduction Profile

某个业务场景的“压缩配置”。

字段建议：

- `profile_id`
- `task_type`
- `branch_factor`
- `max_leaf_tokens`
- `max_reduce_tokens`
- `output_schema`
- `leaf_prompt_builder`
- `reduce_prompt_builder`
- `chunker`
- `merger`

说明：

- `chunker` 负责把输入切成块。
- `leaf_prompt_builder` 负责叶子层提示词。
- `reduce_prompt_builder` 负责中间层提示词。
- `merger` 负责把多轮结果组织回树结构和最终结果。

### 3.4 Summary Node

每次模型执行的结构化输出。

通用字段建议：

- `node_id`
- `level`
- `task_type`
- `summary`
- `key_points`
- `risks`
- `children`
- `source_refs`
- `raw_model_output`

这里的 `summary` 只是一个容器。真正业务字段由 `output_schema` 决定。

### 3.5 Reduction Run

一次完整的分层压缩任务。

字段建议：

- `run_id`
- `task_type`
- `profile_id`
- `root_input_meta`
- `status`
- `levels`
- `final_result`
- `error`

这样后续如果要做可视化、调试、重试、缓存，都有统一承载对象。

## 4. 执行流程

### 4.1 总流程

1. 业务方准备原始输入单元 `Source Unit`
2. 根据 `Reduction Profile` 切出叶子 `Chunk`
3. 对每个叶子块执行一次叶子压缩
4. 得到叶子层 `Summary Node`
5. 把这一层节点重新按 `branch_factor` 组块
6. 对每个中间块执行一次 reduce 压缩
7. 重复直到只剩一个根节点
8. 把根节点映射成业务最终结果

### 4.2 叶子层和中间层不是同一个 prompt

叶子层负责“忠实提炼原始材料”。

中间层负责“基于结构化摘要继续压缩，并保留跨块主题”。

二者应该使用不同模板。

### 4.3 强约束输出 JSON

每一层都应要求模型返回结构化 JSON，而不是自由文本。否则上层无法稳定消费下层结果。

最小要求：

- 输出 schema 固定
- 缺字段有默认值
- 失败时可重试
- 原始文本保留到 `raw_model_output`

### 4.4 需要保留来源引用

每个中间结果都应保留 `source_refs`，告诉上层它来自哪些子节点或原始材料。

这有两个价值：

- 调试时能回溯错误来源
- UI 上可以展示“这个总结是由哪些块归纳而来”

## 5. Prompt 设计原则

### 5.1 Prompt 是动态模板，不是写死一段话

每次调用都应该根据当前层级和任务目标动态生成 prompt。

建议拆成三部分：

- `system prompt`：角色、输出格式、禁止事项
- `task prompt`：本轮任务到底要提炼什么
- `context payload`：本轮输入块内容

### 5.2 叶子 prompt 关注“提炼”

以 Git 为例，叶子 prompt 不应让模型直接写最终 commit，而应先提炼：

- 这组文件在做什么
- 是否属于同一主题
- 主要改动类型
- 风险和噪音
- 推荐标题候选

### 5.3 reduce prompt 关注“归并”

reduce prompt 不再看原始 diff，而是看下层节点的结构化结果，然后要求：

- 找共同主题
- 合并重复描述
- 去掉低价值细节
- 判断是否需要再拆
- 形成更高层摘要

### 5.4 顶层 prompt 才产出最终业务结果

不要在叶子层就要求“最终 commit message”或“最终回答”。顶层才做最终输出。

## 6. Git 场景如何接入

## 6.1 当前问题

当前 AI 提交链路对超大改动的处理还是偏保守：

- 可以检测“大到不适合一轮总结”
- 可以给出“建议拆分”
- 但没有真正进行多层压缩

这会导致：

- 超大提交时只能阻断或降级
- 无法在非常大的改动集上继续得到稳定总结

## 6.2 Git 的输入单元建议

Git 的 `Source Unit` 不应直接等于“整仓 diff 文本”，建议分层：

### 原始单元候选

- 单文件 diff
- 未跟踪文件预览
- 目录级 diff 统计块

### 叶子切块策略

优先按业务邻近性切，不只按固定数量切：

- 先按目录/模块分组
- 同组内再按文件数或估算 token 切块
- 每块尽量保持主题一致

这样比简单“每 10 个文件一组”更稳定。

## 6.3 Git 的层级输出建议

叶子层输出 schema 可以是：

- `topic`
- `scope`
- `change_types`
- `key_points`
- `noise_points`
- `risk_points`
- `candidate_subjects`
- `should_split`

中间层输出 schema 可以是：

- `merged_topic`
- `merged_scope`
- `key_points`
- `conflicts`
- `candidate_subjects`
- `recommended_groups`
- `should_split`

顶层输出再映射为：

- 最终 commit 标题
- commit body
- 是否仍建议拆分
- 理由

## 6.4 Git 的产品形态建议

超大改动时不再直接调用“单轮 AI生成”，而是：

1. 用户点击 `开始拆分`
2. 后端发起一轮 `Reduction Run`
3. UI 显示：
   - 当前层级进度
   - 叶子组数量
   - 中间归并结果
   - 最终推荐主题
4. 最后才开放：
   - `生成该组草稿`
   - `生成最终草稿`

第一版不必展示完整树，只要先能拿到最终结果并在需要时展开中间层即可。

## 7. 笔记等其他场景如何复用

Git 只是第一个业务接入方。后续可以复用同一套引擎：

### 笔记场景

- 叶子单元：单条笔记或单段正文
- 叶子输出：主题、结论、待办、引用点
- reduce 输出：主题簇、共性、分歧、最终摘要

### 日志场景

- 叶子单元：时间窗口日志
- 叶子输出：异常、事件、频次、可能原因
- reduce 输出：根因趋势、异常聚类、最终报告

### 长文档场景

- 叶子单元：章节或段落块
- 叶子输出：章节摘要、结论、证据点
- reduce 输出：全局大纲、章节关系、最终结论

## 8. 实现建议

## 8.1 先做通用后端，不先做复杂前端

第一步先把后端执行模型跑通：

- 分块
- 多层调用
- 结构化中间结果
- 最终汇总

前端先只展示：

- 正在拆分
- 当前轮次
- 最终结果

等跑通后，再补树形可视化和中间结果调试。

## 8.2 先同步执行，后续再并行

第一版可先串行，先保证正确性。后续再优化为：

- 同层并行
- 单节点重试
- 失败节点局部恢复

## 8.3 先内存执行，后续再持久化

第一版可以只在请求周期内保存 `Reduction Run`。后续再把 run 记录落库，用于：

- 调试复现
- 可视化回放
- 缓存复用

## 8.4 输出 schema 要版本化

每个业务 profile 的中间输出 schema 应带版本号。否则 prompt 一改，历史结果就不兼容。

## 9. Git 第一版落地建议

建议按下面顺序推进。

### 第一步：抽象公共引擎

- 已落地为 `backend/core/ai/hierarchical_reduction.py`
- 先支持：
  - 固定分支因子
  - 叶子层 prompt builder
  - reduce 层 prompt builder
  - JSON 输出校验

### 第二步：接 Git profile

- 已落地为 `backend/core/ai/git_reduction.py`
- 定义 Git 的：
  - chunker
  - 叶子 schema
  - reduce schema
  - 最终 commit draft mapper

### 第三步：给 Git API 增加拆分入口

- 已落地同步入口 `/{entry_id}/git/reduce` 和后台任务入口 `/{entry_id}/git/reduce-runs`
- 超大改动时走这条链路，不再走单轮 `generate-message`

### 第四步：前端最小接入

- 超大改动时按钮改为 `开始拆分`
- 展示：
  - 进行中
  - 已完成
  - 最终建议标题/正文
  - 是否仍建议手动拆分

## 10. 当前边界

这套设计解决的是“上下文装不下”的问题，不自动解决：

- 敏感信息判断
- 提交是否合理拆分
- 业务语义是否完全正确
- 模型胡说八道

所以即使引入分层压缩，最终关键结果仍应保留人工确认。
