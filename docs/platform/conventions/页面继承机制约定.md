# 页面继承机制约定

本文档用于约定 `codeyun` 中一种可重复使用的前端开发模式：  
把一个已有标准页面抽象为**父页面**，再在其他功能树下挂接**子页面**，做到：

- 父页面新增通用功能后，子页面自动同步继承
- 子页面可以固定上下文，例如固定设备、固定根目录、固定筛选条件
- 子页面可以扩展自己的专属 UI 和逻辑，而不污染父页面
- 子页面不需要复制父页面源码，避免后续分叉

这套机制在概念上类似 Python 的“类继承”，但在 Vue 页面层的实际实现上，推荐采用：

> 父页实现 + 子页包装 + `props` 配置 + `slots` 扩展 + 必要时再抽 `composable`

而**不推荐**使用容易僵化的“复制页面再改”或框架层面的旧式 `extends`。

## 1. 背景

在业务中，经常会出现这样的需求：

- 先有一个通用页面，例如“集群管理 / 图片标注”
- 后来某个业务域也需要一个“同类页面”，例如“游戏工具 / 凡修手游 / 图片标注”
- 新页面与原页面的大部分能力相同，但有少量固定上下文和专属扩展

如果直接复制一份 `page.vue`：

- 父页后续修 bug、加通用功能，子页不会自动同步
- 子页慢慢会变成一份独立分叉
- 两边行为越来越不一致，维护成本会迅速上升

因此，这类需求不应采用“复制页面”，而应采用“页面继承”机制。

## 2. 核心定义

### 2.1 父页面

父页面是某类页面的**通用实现**，负责：

- 通用数据流
- 通用状态管理
- 通用交互流程
- 通用布局和默认 UI
- 对子页面暴露稳定扩展点

它在概念上等价于“基类”。

### 2.2 子页面

子页面是父页面的**业务特化包装层**，负责：

- 固定上下文参数
- 注册自己的路由、菜单、权限节点
- 在预留扩展位上补充业务专属能力

它在概念上等价于“派生类”。

### 2.3 页面继承

本文中的“页面继承”不是语言层继承，而是页面装配层继承。

实现核心是：

1. 父页面承担绝大多数实现
2. 子页面只做薄包装
3. 子页面通过 `props`、`slots`、局部组件、局部 `composable` 做特化

## 3. 设计目标

这套机制必须同时满足以下目标：

### 3.1 父页新增功能自动继承

只要新功能属于父页面的通用能力，并默认在父页面里启用，那么所有包装父页面的子页面都应自动获得该能力。

这意味着：

- 子页面不应复制父页面源码
- 父页面新增功能时不应要求所有子页面同步手改
- 父页面新增能力应尽量采用“默认开启”或“有默认值的可选参数”方式发布

### 3.2 子页可以固定业务上下文

子页面应能轻量固定一些上下文，例如：

- 固定设备 ID
- 固定根目录
- 固定视图模式
- 固定默认筛选或默认参数

这类差异应通过 `props` 或配置对象表达，而不是在父页面里写大量 `if feature === 'xxx'` 分支。

### 3.3 子页可以扩展专属能力

子页面应能添加自己的专属区块、按钮、提示、辅助面板或业务动作。

这类扩展应通过显式扩展点完成，而不是改父页面内部结构或用 DOM hack 覆盖。

### 3.4 父子页边界清晰、保持正交

应避免出现：

- 父页面知道凡修、戴森球、某插件等具体业务名字
- 子页面依赖父页面的内部局部变量命名或模板结构细节
- 父页面一改布局，所有子页面都碎掉

正确目标是：

> 父页面只表达“这一类页面的通用能力”，子页面只表达“本业务对这类页面的特化”。

## 4. 推荐实现模型

推荐按下面这套层级来做。

### 4.1 第一层：父页面通用实现

父页面负责：

- 通用模板
- 通用状态
- 通用 API 调用
- 通用行为
- 默认文案和默认交互

父页面对外暴露：

- `props`：用于固定上下文或调整行为
- 命名 `slots`：用于子页面插入或补充专属内容
- `slot props`：把子页面真正需要的运行时上下文传出去

### 4.2 第二层：子页面薄包装

子页面应尽量保持薄：

- 导入父页面
- 传入固定参数
- 在少量扩展位上插入专属内容

理想状态下，一个子页面甚至可以只有十几行。

### 4.3 第三层：子页面局部扩展

当子页面逻辑开始增多时，不要把逻辑继续堆进父页面，也不要把子页面写成第二个大单体文件，而应在子页面目录下继续拆分：

- `components/`
- `composables/` 或 `useXxx.ts`
- `utils/`

这样父页仍然稳定，子页扩展也能逐步长大。

父页面当前提供的通用能力包括：

  - `directory-after`
  - `stage-toolbar-after`
  - `inspector-after`

- 新的通用工具栏按钮

- 新的通用编辑能力
- 新的通用快捷键或默认行为

那么“凡修手游 / 图片标注”会自动同步继承，只要它继续包装父页面而不是复制父页面。

## 6. 父页面设计规范

父页面必须遵守以下规则。

### 6.1 父页面只放通用能力

凡修专属、某插件专属、某角色专属逻辑，不应直接进入父页面。

父页面里允许出现的是：

- 通用配置项
- 通用默认值
- 通用扩展位

不允许出现的是：

- `if (feature === 'fanxiu')`
- `if (route.path.startsWith('/fanxiu'))`
- 为某一个子页面硬编码专属逻辑

### 6.2 父页面新增参数必须尽量向后兼容

新增 `props` 时应遵循：

- 尽量提供默认值
- 不要求已有子页面立即补传
- 新增能力应能在“零配置”下安全工作

否则就会破坏“父页演进，子页自动继承”的目标。

### 6.3 父页面新增扩展位必须是可选的

新增 `slot` 时，父页面必须有自己的默认 UI，不能强制所有子页面都立刻实现该 `slot`。

正确方式是：

- 父页面默认渲染完整功能
- 子页面有需要时再覆写或补充

### 6.4 父页面对外暴露的是稳定接口，不是内部细节

父页面要把子页面需要的信息通过 `slot props` 明确暴露出来，例如：

- 当前设备
- 当前路径
- 当前图片项
- 当前文档
- 当前选中标注

而不是要求子页面去假设父页面内部 ref 名字、DOM 结构或 CSS 选择器。

### 6.5 父页面内部复杂度过高时，应继续下沉抽象

如果父页面越来越大，不要把“页面继承”变成“一个巨型父页面统治一切”。  
应及时把父页面内部再拆成：

- 更小的局部组件
- 通用 `composable`
- 纯工具函数

页面继承不是阻止拆分，而是让拆分之后仍有稳定的公共入口。

## 7. 子页面设计规范

子页面必须遵守以下规则。

### 7.1 子页面默认禁止复制父页面源码

只要目标仍然是“这是一类同源页面的业务特化版本”，就不应复制父页面。

只有在以下情况下，才考虑不再继承而独立分叉：

- 页面核心交互模型已经不同
- 页面主状态结构已经不同
- 通用部分已经少于专属部分
- 继续继承会导致父页面充满业务分支

也就是说：

> 继承适用于“同类页面的特化”，不适用于“名字相似但模型已不同”的页面。

### 7.2 子页面优先用配置固定上下文

子页面如果只是想固定：

- 某设备
- 某目录
- 某初始模式
- 某筛选范围

优先用 `props` 传进去，不要改父页面源码。

### 7.3 子页面专属功能优先放在扩展位

子页面新增专属功能时，优先级应为：

1. 用父页面现有 `props`
2. 用父页面现有 `slot`
3. 如扩展位不够，再给父页面补一个新的通用扩展位
4. 如果扩展开始复杂化，在子页面目录下继续拆局部组件和 `composable`

不要反过来把子页面需求硬塞成父页面内部专属分支。

### 7.4 子页面新增能力若已证明通用，应上移到父页面

如果某个 originally 子页专属能力后来发现多个子页面都需要，就应把它提升为父页面通用能力。

判断标准不是“它最早出现在哪”，而是“它现在是否已经成为这类页面的共性能力”。

## 8. 推荐扩展顺序

页面继承的扩展手段推荐按下面顺序使用：

### 8.0 先区分“自动继承 / 覆写 / 扩展”

为了让“页面继承”更接近大家对 Python 类继承的理解，建议统一按下面三种动作来描述：

- 自动继承：子页面只是包装父页面，没有关闭某项能力时，父页面后来新增的通用功能会自动进入子页面
- 覆写：子页面通过 `props` 改父页面的默认上下文或默认行为，例如固定设备、固定根目录、固定默认模式
- 扩展：子页面通过命名 `slot`、子页面局部组件、子页面 `composable` 增加自己的专属区块和逻辑

需要注意：

- 这里的“覆写”默认指**配置层覆写**，不是复制父页面源码后自己改一份
- 如果子页面想替换父页面某一整块 UI，也应优先通过父页面显式提供的扩展位或 replace 型插槽完成
- 如果子页面已经要改掉父页面的核心状态模型、核心交互流程、核心主视图区结构，那么这通常说明它已经不该继续作为“子页面继承”存在，而应独立成新页面

### 8.1 先用 `props`

适用于：

- 固定值
- 默认值
- 行为开关
- 上下文限制

这是成本最低、最稳定的扩展方式。

### 8.2 再用命名 `slot`

适用于：

- 在某块区域后面追加内容
- 在工具栏补一个业务按钮
- 在侧栏增加业务面板

这是最适合“子页扩展专属能力”的方式。

### 8.3 再考虑抽局部子组件

适用于：

- 子页面新增的区块已经不止一两行
- 需要自己的状态和交互
- 希望在子页面目录下形成模块化结构

### 8.4 最后再抽 `composable`

适用于：

- 业务逻辑可以脱离模板复用
- 多个子页面会共享同类扩展逻辑
- 某个扩展区块已有明显数据流和行为封装需求

## 9. 目录组织建议

当某个父页面出现业务子页时，建议目录形态如下：

```text
frontend/src/standard/
  cluster/
    labelme/
      page.vue                 # 父页面
      index.ts

  fanxiu/
    labelme/
      page.vue                 # 子页面包装层
      index.ts
      components/              # 子页面专属区块
      composables/             # 子页面专属逻辑
```

如果后续某个能力已经跨多个业务子页复用，可以再上移到父页面目录，或提到更高层公共目录。

## 10. 推荐文案与心智模型

为了让团队沟通统一，建议默认使用下面这套术语：

- 父页面
- 子页面
- 页面继承
- 固定上下文
- 扩展位
- 通用能力
- 专属能力

其中“页面继承”是允许使用的术语，因为它很符合开发直觉；但在实现说明里要补一句：

> 这里不是语言层继承，而是基于组合、配置和扩展位的页面装配继承。

## 11. 反模式

以下做法应明确禁止。

### 11.1 复制父页面再改

这是最常见、也最容易失控的反模式。  
一旦复制，就失去“父页新增功能自动同步”的能力。

### 11.2 父页面反向依赖子页面

父页面不应导入任何子页面组件或业务模块。  
依赖方向只能是：

- 子页面依赖父页面

不能反过来。

### 11.3 父页面写满业务名分支

例如：

```ts
if (scene === 'fanxiu') { ... }
if (scene === 'dsp') { ... }
if (scene === 'xxx') { ... }
```

这会把“父页面”退化成“所有子页面的分支调度器”，违反正交性。

### 11.4 扩展点只对一个子页面可用

如果某个扩展点本质上只服务一个具体业务，而且命名、上下文、语义都写死在该业务上，那么它不应进入父页面。

父页面扩展点必须是“抽象后仍成立”的通用扩展位。

### 11.5 新增父页面功能却要求所有子页面同步修改

只要新增的是通用能力，就应尽量做到：

- 父页面自己可用
- 老子页面不改也能工作

否则就破坏了页面继承机制的核心收益。

## 12. 采用这套机制时的检查清单

新增“同类页面变体”前，先按下面问题自检：

1. 这真的是同一类页面，只是业务上下文不同吗？
2. 哪些部分是通用能力，哪些部分是专属能力？
3. 专属差异能否用 `props` 固定？
4. 专属 UI 能否挂在扩展位上？
5. 父页面是否已经暴露了足够稳定的扩展接口？
6. 如果现在复制页面，半年后会不会形成两份分叉实现？

只要第 1 条成立，通常应优先选择页面继承，而不是复制页面。

## 13. 与 standard / plugins 的关系

页面继承解决的是：

- 页面之间如何共享实现
- 业务变体如何在不复制源码的前提下扩展

`standard / plugins` 解决的是：

- 功能代码来自哪里
- 扩展功能如何装配进宿主

两者是正交关系：

- 一个父页面可以在 `standard`
- 一个子页面也可以在 `standard`
- 未来也完全可以存在 `plugins` 中的子页面去继承 `standard` 的父页面

因此不要把“页面继承”和“插件机制”混为一谈。

## 14. 总结

这套机制的核心结论只有一句：

> 对于“同一类页面的业务特化版本”，默认方案应该是“父页面抽象通用实现，子页面做薄包装扩展”，而不是复制一份页面源码。

这样才能真正同时满足：

- 父页新增通用功能，子页自动同步
- 子页能固定业务上下文
- 子页能扩展自己的特殊能力
- 父子页不会逐步分叉成两套系统
