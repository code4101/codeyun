# 通用可执行系统架构：内核、框架与调度

> 本文描述一种通用的可执行系统架构抽象，并用于指导凡修行为树运行框架后续重构。本文不是某个具体实现的接口说明，而是用于统一术语、边界和设计方向。

## 一句话定义

可执行系统的核心，是把“运行容器、执行语义、触发来源”三件事解耦：

```text
内核 Kernel：代码跑在哪里
框架 Framework：代码怎么跑
调度 Scheduler：代码什么时候被触发
```

其中，框架是系统灵魂。内核和调度都可以替换；真正决定功能代码是否可运行、可调试、可观测、可恢复的是框架。

## 核心术语

### 内核 Kernel

内核是承载框架运行的长驻执行环境。

它负责：

- 保存运行上下文。
- 持有设备连接、缓存、当前任务状态等内存对象。
- 执行提交过来的 cell。
- 支持中断、重启、状态读取。

内核可以有多种形态：

- `JupyterKernel`：适合串行执行、交互调试、保留上下文。
- `FastApiKernel`：适合并发 API、服务化调用、直接函数调度。
- `WorkerKernel`：适合消息队列、后台任务、分布式运行。
- `LocalProcessKernel`：适合一次性隔离运行。
- `InProcessKernel`：适合测试和轻量开发。

同一个调度来源面对不同内核时，提交方式可以完全不同。例如 API 调度到 Jupyter 内核时，可能是提交一个 cell；API 调度到 FastAPI 内核时，可能是直接创建一个后端任务。

### 框架 Framework

框架定义执行语义，是系统核心。

它负责：

- 定义功能代码怎么写。
- 定义 `task / guard / step / tick / run` 协议。
- 提供运行上下文 API，例如截图、OCR、点击、等待、日志。
- 管理每一步的状态、耗时、错误、取消、超时。
- 管理本轮 view/OCR/cache 的生命周期。
- 决定守护如何介入主任务。
- 提供直接运行、单步调试、连续运行、运行到完成等入口。

功能代码隶属于框架，不是框架之外的独立层。邮件清理、日常助手、弹窗守护、设备健康检查，都是框架内部按协议编写的可执行功能。

执行不是一个实体层。执行是框架在内核里推进任务的过程：

```text
执行的本质是框架，容器载体是内核。
```

### 调度 Scheduler

调度只负责触发来源和运行策略。

它负责：

- 手动触发。
- API 触发。
- 定时触发。
- 队列、优先级、互斥。
- 失败重试、下次触发时间。
- 选择目标内核，并向框架提交 cell。

调度层不应该拥有业务执行语义。它不应该知道邮件如何翻页、日常如何点击、弹窗如何 OCR；这些都属于框架和功能代码。

编排不是独立必备层，而是调度的一种高级模式。只有当任务之间存在依赖、分支、补偿、多内核协同等需求时，才需要 `WorkflowScheduler / OrchestratedScheduler`。

## Cell 模型

统一称为 cell，不称为 block。

cell 是调度层提交给内核执行的最小外部提交单位。它可以是结构化命令，也可以是受控脚本，但不应默认开放成任意复杂业务逻辑。

推荐分三类 cell：

### 命令 cell

用于普通产品入口，安全、可记录、可重放。

```json
{
  "cmd": "run_task",
  "task_type": "mail_cleanup",
  "payload": {},
  "policy": {
    "guard": true,
    "timeout_seconds": 300
  }
}
```

提交到 Jupyter 内核时，可以包装成稳定的小段代码：

```python
result = framework.dispatch_cell({
    "cmd": "run_task",
    "task_type": "mail_cleanup",
    "payload": {},
    "policy": {"guard": True, "timeout_seconds": 300},
})
```

### 脚本 cell

用于开发、AI 调试、高级人工排查。

```python
task = framework.邮件_清理()
framework.run(task, max_steps=5, guard=False)
```

### 诊断 cell

用于只读探针、截图、OCR、场景识别、状态查询。

```python
framework.probe("scene", candidates=[34, 121])
framework.probe("ocr_shape", frame=35, shape="菜单")
```

原则是：cell 是提交单位，不是业务逻辑的主要承载地。业务逻辑应沉淀在框架功能代码里。

## Tick 与任务推进

tick 是框架最小推进单位。

一个典型 tick：

```text
1. 准备或复用本轮 view/cache。
2. 按策略运行守护检查。
3. 如果守护发现阻断项，本 tick 执行守护动作并结束。
4. 如果守护放行，推进当前任务一步。
5. 如果当前没有任务，根据调用参数决定是否启动一个可运行任务。
6. 写入结构化状态、日志、耗时和下一步建议。
```

框架可以暴露不同运行粒度：

```python
framework.tick(guard=True, manual=True, scheduled=True)
framework.run_ticks(10, guard=True)
framework.run_until_job_done(guard=True, start_if_idle=True)
framework.run_until_idle(guard=True, timeout_seconds=60)
```

这些入口都应该建立在同一个 tick 协议上，而不是各自实现一套运行循环。

## 功能代码的形态

功能代码应该可直接创建、直接运行、单步调试，不依赖调度器触发。

推荐心智：

```python
task = framework.邮件_清理()
framework.step(task)
framework.step(task)
framework.run(task, until="done", guard=True)
```

任务构造不应产生副作用：

```python
task = framework.邮件_清理()
```

这一步只创建任务实例，不截图、不点击、不 OCR。真正副作用发生在 `step / tick / run` 过程中。

这样同一个功能可以被多个入口复用：

```text
手动按钮 -> 调度层提交 run_task cell
API 请求 -> 调度层提交 run_task cell
定时任务 -> 调度层到点提交 run_task cell
AI 调试 -> 提交脚本 cell 单步运行
测试用例 -> 直接创建 task 并用框架推进
```

## 守护的定位

守护属于框架机制，不是普通定时任务。

守护不是“空闲时提交一个任务”，而是每个 tick 的高优先级前置策略：

```text
每个 tick 都允许 guard pipeline 参与判断；
但 guard pipeline 必须轻量，不能每轮无条件整帧 OCR；
命中阻断项时可以抢占本 tick；
没有阻断项时必须快速放行主任务。
```

守护抢占一次后应返回控制权，不能长期吞掉 tick。

## 调度层的边界

调度层可以有多种来源：

- 手动调度。
- API 调度。
- 定时调度。
- 队列调度。
- 编排调度。

它们最终都应该生成统一 cell，并调用框架入口。

调度层可以使用 APScheduler、队列、HTTP API、前端按钮等机制。调度本身通常不是难点，难点是调度调用的框架入口是否清晰。

调度层不应：

- 直接写业务点击逻辑。
- 直接操作 OCR/截图/shape。
- 为每种入口复制一套执行流程。
- 把触发时间和功能实现耦合。

任务触发时间、本地启用状态、重试策略属于持久配置数据。调度层读取这些数据，但它们不是调度层源码，也不是框架功能代码。

## 内核适配

同一个调度请求面对不同内核时，执行方式可以不同。

```text
API 调度 -> JupyterKernel
  -> 生成 cell
  -> 发送 execute_request
  -> 串行执行
  -> 收集 stdout/result/error

API 调度 -> FastApiKernel
  -> 直接创建后端任务
  -> 可能并发执行
  -> 状态写入任务表

API 调度 -> WorkerKernel
  -> 发送消息到队列
  -> worker 消费并执行
  -> result backend 返回状态
```

因此调度层应依赖内核适配器，而不是直接依赖某一种内核实现：

```python
kernel = kernel_registry.get(target_kernel)
kernel.submit(cell)
```

## 凡修行为树的落地指导

凡修当前问题，本质是把内核、框架、调度混在“行为树服务”一个概念里，导致：

- 前端按钮分不清重启内核、暂停调度、停止当前任务。
- 日志混入调度心跳、owner 锁、内部 phase。
- 守护和作业的边界不清。
- 手动作业、定时作业、调试入口容易各自绕路。
- 任务难以脱离调度器单步运行。

后续重构方向应是：

```text
内核：JupyterKernel 或后端服务进程，负责承载运行上下文。
框架：凡修行为树框架，定义 task / guard / step / tick / ctx / 日志状态。
调度：手动、API、定时、队列等来源，只负责提交 cell。
```

### 凡修框架应定义的核心能力

- `framework.tick(...)`
- `framework.run_until_job_done(...)`
- `framework.run_ticks(...)`
- `framework.create_task(task_type, payload)`
- `framework.step(task, guard=True)`
- `framework.probe(...)`
- `framework.snapshot()`

### 凡修功能代码应遵守的规则

1. 功能代码属于框架层，不属于调度层。
2. 功能代码必须可直接创建和调试。
3. 任务构造不产生副作用。
4. 点击、拖拽、等待、OCR、场景识别都通过框架 `ctx` API。
5. 任务每一步都应能产生结构化日志和耗时。
6. 守护只通过框架 pipeline 介入，不在调度层伪装成普通任务。
7. 真实 GUI 动作必须可被中断、超时和复盘。

### 凡修前端应区分的动作

- 重启内核：清空运行上下文并重新加载代码。
- 中断当前 cell：停止当前执行，但不必清空内核。
- 暂停调度：停止自动提交新 cell，不等于重启内核。
- 运行一次 tick：推进最小单位。
- 运行到当前作业完成：连续 tick 到完成边界。
- 提交手动作业：生成一个标准 cell，由调度层排队或直接提交。

前端不应使用一个“运行/停止”按钮混合表达这些不同动作。

### 凡修日志应展示什么

日志应优先展示任务执行流：

```text
进入 #34
打开邮件
识别邮件列表 4 行，耗时 0.5s
翻页，耗时 3.1s
处理「仙缘斗法排名奖励」，耗时 8.2s
回到 #34
```

不应把调度心跳、owner 锁、内部 phase 当成主要日志刷屏。

## 设计原则

1. 框架定义执行语义，调度不拥有业务语义。
2. 功能代码属于框架，不能绑定某一种调度来源。
3. 内核只是运行容器，不定义业务流程。
4. cell 是提交单位，不是业务复杂度的主要承载地。
5. tick 是最小推进单位，所有运行粒度都应建立在 tick 上。
6. 守护是框架前置策略，不是普通定时任务。
7. 前端展示的是框架状态和调度配置，不是内部实现细节。
8. 持久配置保存触发策略，不保存执行语义。

## 推荐迁移顺序

1. 先统一术语：内核、框架、调度、cell、tick、task、guard。
2. 清理前端文案：区分重启内核、中断 cell、暂停调度。
3. 把现有手动作业、定时作业、调试入口收敛为提交 cell。
4. 设计框架层 `tick / run / step / probe` 返回协议。
5. 让邮件清理这类任务能脱离调度器直接创建并单步运行。
6. 再评估是否引入 JupyterKernel 作为凡修串行运行内核。
7. 最后再考虑复杂编排调度，不要提前引入 DAG 系统。

## 最终目标

凡修行为树最终应收敛为：

```text
调度层决定什么时候提交 cell；
框架层决定 cell 如何变成可观测、可中断、可复盘的任务执行；
内核层负责承载框架运行上下文。
```

这套抽象不仅适用于凡修，也适用于 CodeYun 中其他可执行系统：数据导入、文档处理、AI 工作流、运维脚本、量化任务、后台巡检等。
