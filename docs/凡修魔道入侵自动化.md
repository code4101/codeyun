# 凡修魔道入侵自动化

## 生产目标

`ranking_lifecycle` 是玩法榜与资源榜唯一生产作业；`magic_invasion_explore` 只保留为手动兼容原子，不再拥有 Scheduler 实例。服内预赛与跨服魔道由统一作业内的魔道 adapter 共用流程，但不共享进度；每个 Runtime occurrence 都必须独立完成 `3 × 500 = 1500` 次基础探查。

排行榜邮件是 19:00 compound 的可选前置步骤，但不属于探查提交事务。邮件已领取、尚未生成或本轮没有新邮件，都不能阻塞任务奖励、补给与探查；底层继续复用幂等邮件原子。

## 稳定抽象与版本适配

稳定业务不变量：

- Runtime `activityType=7` 定义魔道活动族；这是标准化日程的稳定字段，不依赖某版 VO 类名。
- `Runtime id + activityId + startTime + endTime` 定义一次不可混账的 occurrence。
- 服内与跨服各欠 1500 次，结果页的 636、724、828、855 等增益值不改变基础次数。
- 单批先把地图次数精确补到 500，再执行快速探索。
- 每次不可逆点击前先写 `armed`，结果页出现后才写入已确认的 500。

版本相关适配：

- `activityId`、`serverCount`、服内/跨服副标题会随活动配置变化；前者参与精确 occurrence 隔离，后两者用于模式说明、商店选择和页面对齐，均不能代替活动族识别。
- 页面布局、滑轨端点、复选框像素与 OCR ROI 都属于资产适配层，统一由 509–518 场景维护。
- 奖励增益、剩余天眼符数量、地图初始残留次数和邮件存在性都是运行时数据，禁止写死。

静态 Lua 证据进一步确认了这条边界：`MapActInfoClass.PlayEffect` 读取当前探查次数并传给 `CM_MagicInvadeExploreFun(exploreCount)`，网络层发送的是精确次数；快速探索开关则由 `LuaGameSettingType.MagicInvadeExplodeTen` 持久化。工程因此只负责核对运行时次数与开关状态，不依赖某一版按钮文案或固定坐标。

因此，升级后先验收 Runtime occurrence 投影和 509–518 资产，不修改上层 3×500 业务算法；只有业务规则本身变化时才改作业核心。

## 事务顺序

1. 从只读 Runtime 日程选出当前唯一 `activityType=7` occurrence。
2. 通过 #66 的 Runtime-GUI 对齐进入当前活动，再进入 #512 大地图。
3. 读取当前探查次数；使用天眼符把它精确补到 500。
4. 校验快速探索开启态。
5. 持久化 `armed` 防重复标记，再点击探查。
6. 如遇 2000 事件上限，确认覆盖；只在 #515 结果页形成后记录本批基础 500。
7. 重复三批，持久化 occurrence 完成态；返回世界是提交后的清理步骤，不反向否定业务完成。
8. 每日 00:30 由统一榜单作业对齐全部 occurrence；精确魔道 occurrence 在 19:00 追加 compound checkpoint。若服务晚恢复，只能在该 occurrence 结束前补跑；结束后禁止追执行游戏动作。

## 00:30 兑换收尾

正式 `endTime` 后、`closePanelTime` 前的首个 00:30 生成 `exchange_tail_0030`，它与 19:00 探查是两个独立 checkpoint：探查结束后禁止补做，兑换保留期内则允许按商店绝对购买次数幂等补跑。

收尾固定先绑定精确历史 occurrence，再读取当前页的榜单 Runtime、币种15钱包和服内商店70000。九档完成时，动态卡邮件资源保持未购并保留精确成本；九档未完成时现场买入。卡邮件资源来自祈愿候选队列的首个未使用项，并不恒等于瑶池玉莲。

2026-08-22 真实服内收尾结果：`1070011400004` 排名2、功勋520950，九档完成；动态锁定瑶池玉莲40个，保留4000魔晶，最终余额4006。珍品饲灵丸、淬体精魄、洗灵奇石、炼丹灵草匣等规划项目均由最终 `purchased_count` 复验，checkpoint 完成后返回世界 #34，统一 Job 下一次唤醒为当日19:00跨服魔道。

## 本次复盘

- 原思路把 `magic-invasion` 当活动族累计，导致服内和跨服可以拼成 1500；根因是把“代码复用边界”误当成“业务账本边界”。
- 旧资产安装器只新增缺失场景，不升级同文件名场景，造成源码已有计数 ROI、现场仍是旧资产。现在按 filename 原位升级、保留稳定 id，并保证二次运行幂等。
- 第一次地图计数 ROI 偏高，真实 `35/120` 读不到；快速开关框又混入大量换色背景，只有 47% 相似。用服内真实帧回放后，计数稳定读出，开关相似度提升到 83%。
- 数量滑块最初沿用了外框，实际外框包含加减按钮。利用真实 `持有 2368 / 选择 500` 的旋钮位置反推滑轨端点后，数量比例才属于正确控件。
- 最短路径不是现场临时连续点击，而是先取得当前服内与明日跨服的 Runtime 身份、用即将结束的服内场景验证入口/地图，再把同一事务固化给明日跨服。
- 逆向结果必须分层保存：业务不变量来自数据流和协议语义，版本细节留在资产与适配层；任何一次客户端升级只允许局部适配失败，不能悄悄改变 3×500、occurrence 隔离和先记账后点击等安全语义。
- 第一版统一生命周期曾依赖原始 `MagicInvadeActivityVO`；真实标准化 Runtime 日程不再携带 `class`，导致生产识别为零。现在稳定层消费 `activityType/activityId/baseId`，VO 类名降为兼容提示，并对多重命中失败关闭。
- 漏跑恢复不能一刀切：00:30 数据 checkpoint 可按天追补，19:00 游戏 checkpoint 只能在活动有效窗内补跑。服内活动 22:00 后的真实验收确认只补了数据库，没有误触发探查。
- 复合 Job 不能只检查子流程返回的 `result=success`：活动可能恰在任务奖励与探查之间结束，底层“当前无活动、零动作”也是一种正常返回。生产完成门必须同时验证预期 occurrence、`state=complete`、3 个已确认批次与 `base_explore_count=1500`，否则保留 checkpoint 失败并等待有效窗内重试。
- 任务奖励的“完整”不能用当前看到的任务行反过来定义期望集合。应按 ActiveTask 的 `(subType, sort)` 逻辑档位建立完整性约束，每档必须由 QuestMgr 当前行或 `finishTasks` 精确代表一个版本；这样既拒绝部分加载，也能在全部任务行移除后证明已经全领。
- 兑换收尾不能把“当前全局魔道”当成屏幕中的历史魔道。昨天服内与今天跨服并存时，历史页榜单事实必须携带 occurrence runtime id；商店采集也必须复用同一绑定，否则应失败关闭。
- 商品行不能按截图猜等距坐标。服内宝阁真实行高与云梦不同；现在按可见商品名唯一行点击，再以购买框标题和单价复验，错误点到瑶池玉莲时会在确认前安全中断。

## 验收与回放

- 定向回归覆盖 occurrence 隔离、1500 规划、Runtime 周期选择、OCR 解析、滑块比例、Scheduler 注册和资产升级幂等。
- 真实服内回放确认 `1070011400004 / 预赛`；明日跨服为 `8070001400004 / 跨服[8]`，活动时间 10:00–22:00。
- 生产只保留 `ranking-lifecycle`：00:30 公共对账，魔道活动日 19:00 专属阶段；运行前仍由 Scheduler 做唯一运行权和 Kernel idle 门禁。
