# 凡修逆向增量更新约定

> Last Updated: 2026-05-30

## 触发口径

以后用户提到“增量更新凡修逆向”、“更新凡修图鉴”、“同步凡修逆向最新数据”、“凡修资源/图鉴最新情况”等相近表达时，默认目标是：基于最新游戏导出或逆向结果，增量更新 CodeYun 里的图鉴、资源、协议、静态表等数据。

除非用户明确要求全量重建，否则不要把这类任务理解为暴力重算全部数据。应优先走“快照留存、差异比较、低风险自动合并、高风险审查”的增量机制。

## 核心原则

1. 原始导出不直接覆盖业务数据。
2. 每次更新都保留可追溯快照。
3. 先比较新旧版本，再决定更新范围。
4. 有稳定主键的实体按主键增量合并。
5. 没有稳定主键的实体先建立映射或指纹，不要凭位置顺序覆盖。
6. 删除类变化优先标记为失效或缺失，不直接物理删除。
7. 用户手工补充的别名、说明、排序、标注、图片关联等 curated 字段不得被自动覆盖。
8. 每次发现新的逆向技巧、字段映射、跳过条件或性能优化，都应回写本文档或相关 Fanxiu 上下文文档。

## 推荐数据分层

凡修逆向数据建议至少分三层处理：

```text
raw_snapshot
  原始逆向输出、游戏配置导出、抓包样本、Unity 资源索引等，只读留档。

normalized_snapshot
  经过字段清洗、类型标准化、路径规范化、主键抽取后的中间结果。

curated_data
  CodeYun 图鉴实际展示或人工维护的数据，允许有补充说明、别名、排序和标注。
```

更新流程只应自动生成或刷新 `raw_snapshot`、`normalized_snapshot` 和差异记录；是否写入 `curated_data`，要按风险级别决定。

## 增量更新流程

标准流程：

```text
获取最新游戏数据
  -> 保存原始快照
  -> 规范化清洗
  -> 计算实体级 content_hash
  -> 与上一版 normalized_snapshot 比较
  -> 生成新增/修改/疑似删除/未变清单
  -> 自动应用低风险变化
  -> 高风险变化进入人工审查或报告
  -> 记录批次、校验结果和经验
```

每个更新批次建议记录：

```text
batch_id
game_version 或 source_version
source_path
source_hash
created_at
entity_types
added_count
modified_count
missing_count
unchanged_count
applied_status
notes
```

## Diff 规则

有稳定主键的实体，例如道具、技能、怪物、NPC、地图、活动、配置表行，应按主键比较：

```text
新增：新版本有，旧版本没有
修改：新旧都有，但规范化内容 hash 不一致
疑似删除：旧版本有，新版本没有
未变：新旧都有，hash 一致
```

字段级 diff 应尽量保留旧值和新值：

```json
{
  "entity_type": "item",
  "entity_id": "3020501",
  "change_type": "modified",
  "fields": {
    "name": ["旧名称", "新名称"],
    "effect_detail_preview": ["旧效果", "新效果"]
  }
}
```

没有稳定主键的资源，例如部分 Unity 资源、图片、音频、Prefab、Timeline、散落 Lua 片段，可优先使用组合指纹：

```text
canonical_path
asset_guid
bundle_name + asset_name
file_size + content_hash
type + normalized_name + content_hash
```

不要只依赖导出顺序、数组下标或临时文件名。

## 自动合并边界

可以自动应用的低风险变化：

- 新增实体，且不覆盖已有 curated 字段。
- 纯数值字段变化，例如等级、消耗、属性值、冷却时间。
- 新增搜索索引、预览文本、反向引用关系。
- 新增资源文件索引，且路径和 hash 都可确认。
- 旧实体在新版本缺失时，仅标记为 `missing_in_latest` 或 `deprecated_candidate`。

需要人工审查或至少生成报告的变化：

- 名称、品质、类型、分类、入口路径变化。
- 同一主键对应的核心语义大幅变化。
- 一条旧数据拆成多条，或多条合并成一条。
- 影响前端路由、菜单、图鉴 tab、搜索语义的变化。
- 会删除现有 curated 字段或用户标注的变化。
- 主键不稳定、疑似复用 ID、hash 变化但字段来源不明确。

## 性能策略

增量更新时优先跳过未变化输入：

- 对原始输入目录计算 manifest。
- 对每个源表或资源文件记录 `size/mtime/hash`。
- 对规范化后的实体记录 `content_hash`。
- 对耗时构建步骤记录依赖输入 hash。
- 只有依赖输入变化时才重新构建对应 catalog。

对于大型资源目录，优先按分区比较，例如：

```text
Item / Skill / Monster / Activity / Gongfa / Asset / Picture / Audio / Packet
```

不要因为一个小表变化就重建所有图鉴索引。

## 经验沉淀区

### 2026-05-30 初始约定

- 凡修逆向和图鉴数据要按版本快照和字段级 diff 处理。
- 默认禁止无理由全量覆盖业务数据。
- 删除类变化先标记，不物理删除。
- 人工维护字段和图鉴展示补充应与原始逆向层分离。
- 后续每次发现新的表关联、资源指纹、跳过策略、校验技巧，都应追加到本文档。

### 2026-05-30 首次按约定执行

- 先检查 `parsed_configs/*/rows.json` 与图鉴产物时间戳，再决定是否重建图鉴；本次 `Item/rows.json`、活动相关 rows 都早于现有图鉴产物，因此道具图鉴和活动图鉴不重建。
- 道具图鉴已有 `_is_default_catalog_stale` 机制，能按 schema 版本和依赖源文件 mtime 判断是否需要重建；执行增量更新时应优先调用该判断，不要直接跑 `build_fanxiu_item_catalog`。
- 活动图鉴已有“合并上一版缺失活动为 stale”的机制，本次人工按活动依赖表 mtime 判断未 stale；后续可把这个判断也沉淀成类似道具图鉴的统一 stale helper。
- 资源层可以轻量重跑 `build_fanxiu_resource_manifest_diff_report`，它只生成 APK 内置清单与下载资源清单的 diff 报告，不会覆盖图鉴业务数据。本次报告位置：`frxx_analysis_exports/apk_static_index/resource_manifest_diff_report.md`。
- 本次加载验证：道具 schema `47`，道具 `10030` 条，结构化效果详情 `8026` 条；活动 schema `5`，活动卡 `5914` 条，stale 活动 `0` 条。

### 2026-06-02 抓包运行态洞察

- 抓包服务架构约定见 `docs/凡修抓包服务架构约定.md`。凡修抓包相关功能必须按“抓包监控器 -> 抓包段存储 -> 解析队列 -> 业务增量写入器 -> 图鉴只读展示”设计；不要让图鉴页面触发抓包、解析或历史补扫。
- 抓包历史的业务层解码数据统一从 `fanxiu/tcp-flow` 读取；新增运行态洞察产物放在 `fanxiu/packet-insights/account_runtime_insights.json`，不要写进静态 `parsed_configs/*` 图鉴 catalog。
- 洞察层按 decoded 文件的 `path / mtime_ns / size` 计算 `source_signature`；签名和 schema 版本未变化时直接复用上次快照，新增或变化的 decoded 文件、或洞察字段结构升级时才重建运行态快照。
- 活动排行包 `SM_ActivityRankSync` 里的 `selfRankVO` 要随 `activity_rank_records.json` 一起持久化；它是当前账号个人排名、宗门、区服和分数的来源，不应只保留榜单前排。
- 账号相关运行态数据优先从服务端下发包抽取：`SM_Login` 提供账号/角色基础信息，`SM_Wallet` 提供钱包资源，`SM_AllBagSyncInfo` 提供背包物品格，`SM_SyncAllEquipment` 提供装备摘要，`SM_BlueStarSeaEnergyChange` 和 `SM_TakeMedicineSync` 提供玩法状态。
- decoded 包中部分大数组可能已经被解码层截断；洞察层应同时保留 `_count` 作为“声明数量”和实际解析条数作为“已解码数量”，图鉴展示时避免把截断样本误说成完整清单。
- 新包解析应该遵守“运行态快照独立于静态图鉴”的边界：静态活动、道具、功法等 catalog 继续由逆向配置表生成；抓包洞察只作为图鉴里的实时/历史观察层，用证据字段回链到 packet id、record id、pcap 名和 decoded 时间。
- 活动数据分三类处理：逆向真实活动、逆向模板活动、抓包活动。逆向真实活动通常有明确日期且时间提示置信度高，应保留在图鉴和日程里；逆向模板活动通常只有 `ARIT` 等相对时程、低置信度、无具体日期，只能作为模板/规则参考，不能混入“当前活动”“日程视图”或对象计数；抓包获得的 `SM_WorldLineActivitySync` 等服务端日程是真实运行清单，应与逆向真实活动合并展示，并用静态配置补名称、类型、奖励、条件等详情。
- 活动详情里的礼包、奖励等分支也要按当前活动实例筛选。遇到 `CrossGroupDay|...` 这类条件时，本服运行实例不应混入跨服分支；跨服运行实例应优先按抓包里的 `crossGroup` 选择匹配分支。前端可在展示层去重，但不要删除原始逆向行。
- 榜单奖励还要同时按 `ActivityIdOpenBefore/After` 和 `serverDay/worldLevel` 选择版本。`serverDay` 不能用抓包里的 `daoNian` 直接替代，应优先用服务端日程快照的 `openServerTime` 与当前活动 `startTime` 计算开服天数；例如 `2025-04-20 05:30:00` 开服、`2026-06-01 05:00:05` 开始的服内炼体约为第 407 天，应只命中 `serverDay=[31,9999]` 的 `OpenAfter` 奖励版本。

## 执行提示

接手凡修增量更新任务时，先读：

1. `docs/AI_CONTEXT.md`
2. `docs/FANXIU_REVERSE_CONTEXT.md`
3. `docs/凡修逆向增量更新约定.md`

然后再查找当前构建脚本、API、前端图鉴页面和最近一次生成产物。实施时优先做最小增量闭环：先选一个实体类型跑通快照、diff、应用、验证，再扩展到更多图鉴数据。
