# 星云表格插件与脚本分层设计

> Last Updated: 2026-04-29

本文档是阶段性设计备忘，不是最终实现规格。它记录当前关于“星云表格如何承载专用业务功能”的架构判断；后续在设计具体表格应用、插件能力或脚本能力时，如果发现这里的边界划分有偏差，应同步修订本文档。

## 1. 背景

星云表格的原始目标是把“功能”和“数据”分离：表格保存数据，系统提供通用编辑、展示和管理能力。

但实际业务里，有些 workbook 或 sheet 会天然带有很强的专用功能。例如报名表、考勤表、订单校对表、同步任务表等，它们不只是普通二维数据，还需要：

- 专用按钮、工具栏或侧边面板
- 专用导入、导出、清洗和校验
- 专用后端接口、任务和权限
- 专用统计、同步或批处理逻辑
- 未来可能还需要自定义函数、公式或轻量脚本

这类能力类似传统 Excel + VBA、金山在线表格 + JSA 的关系，但 CodeYun 的定制功能可能更接近系统级程序，而不仅是表格内脚本。

## 2. 当前判断

当前结论是：**允许先做插件层，而且这不是不工程化的妥协。**

真正需要避免的是把业务逻辑散落成：

```text
if sheet_id == 2:
    执行报名表特殊逻辑
```

这种写法会让功能和具体数据 ID 强耦合，后续复制表格、迁移数据、重命名业务或扩展第二张同类表都会变得困难。

更合理的连接方式是：

```text
workbook / sheet
-> app_key
-> config_json
-> CodeYun 中正式注册的插件功能
```

也就是说，表格数据只声明“我绑定了哪个表格应用”，具体功能仍然由 CodeYun 工程里的正式代码承载。

## 3. 分层模型

### 3.1 数据层

数据层负责 workbook、sheet、行列、单元格、字段配置和视图配置。

它应该回答的是：

- 这张表有哪些列？
- 有哪些行数据？
- 哪些列隐藏？
- 哪些字段是什么类型？
- 当前表格如何显示？

当前星云表格里的 `document_json`、`column_configs`、分页设置、隐藏列等都属于这一层。

数据层不应该直接承载复杂业务程序。

### 3.2 配置层

配置层负责声明式参数。它仍然可以作为数据存储，但它表达的是“怎么配置功能”，不是“功能代码本身”。

典型内容包括：

- 哪些列代表手机号、姓名、状态、金额
- 是否启用某个按钮或动作
- 导入导出模板如何映射字段
- 某个插件在这张表上的运行参数
- 某些规则链、校验项、默认筛选项

配置层适合数据化，因为它主要是参数，不是完整程序。

### 3.3 通用表格结构能力

有些能力虽然会先在某个业务表里出现，但本质不属于插件层，而属于通用表格结构能力。

典型例子是多级表头。它表达的是表格列结构：

```text
课程基本信息
  - 课程类型
  - 课程名称
  - 在线考勤表

时间节点
  - 课程开始日期
  - 课程结束日期
```

这不是“考勤汇总插件”的专有功能。更合理的归属是：

- `columns` 保存底层字段名
- `header_groups` 保存多级表头分组
- `column_configs` 保存字段显示、校验和表头样式
- 插件或模板可以生成这些配置，但不拥有多级表头能力本身

判断原则：

- 如果能力描述的是“表格怎么组织和显示”，优先做成通用表格能力
- 如果能力描述的是“这个业务要执行什么动作”，优先放到插件层
- 如果插件只是提供一套默认表头、默认字段和默认颜色，它只是生成配置，不应独占该能力

### 3.4 插件层

插件层指 CodeYun 工程里正式开发的系统级功能模块。它可以有前端页面、组件、工具栏按钮、后端接口、任务、权限和测试。

插件层适合承载：

- 业务含义明确的专用表格应用
- 需要后端接口或任务的能力
- 需要权限、审计、数据迁移的能力
- 需要长期维护和重构的能力

插件层不应该写死某个表格 ID。它应该通过稳定的 `app_key` 与配置层绑定。

示意模型：

```text
sheet_id = 2
app_key = "attendance_signup"
config_json = {
  "name_column": "姓名",
  "phone_column": "手机号",
  "status_column": "备注"
}
```

CodeYun 里注册 `attendance_signup` 后，前端和后端都围绕这个 `app_key` 找到对应扩展能力。

### 3.5 脚本层

脚本层是未来可能引入的可移植自定义能力，类似 VBA、JSA 或受限 JS。

它更适合承载：

- 自定义列计算
- 自定义函数
- 轻量批量清洗
- 公式中可引用的函数
- 简单自动化动作
- 对插件暴露能力的受限调用

脚本层不适合在一开始就替代插件层。否则 CodeYun 实际上需要先实现一套小型应用平台，包括脚本沙箱、权限模型、API 白名单、调试体验、版本管理、错误隔离和迁移机制。

## 4. 为什么先做插件层

### 4.1 系统级功能需要工程化代码

如果某个表格功能已经需要后端任务、权限、文件访问、外部接口或复杂 UI，它就不再是简单脚本问题，而是系统功能问题。

这类功能放在插件层更合适，因为它可以使用正常工程手段维护：

- Git 版本控制
- TypeScript / Python 类型约束
- 单元测试和接口测试
- 权限系统
- 错误处理
- 日志和任务状态
- 后续重构

### 4.2 脚本层成本高，不应过早成为基础设施

如果现在要求所有专用功能都用脚本层实现，就等于要求脚本层立即具备很强的平台能力。

需要提前解决的问题包括：

- 脚本能访问哪些 CodeYun API？
- 脚本能不能访问文件、网络、用户数据？
- 脚本如何鉴权？
- 脚本执行失败如何呈现？
- 脚本如何调试？
- 脚本如何版本化？
- 脚本如何随表格复制、导入、导出和迁移？
- 脚本如何避免破坏系统数据？

这些问题不是不能做，但不应该成为第一阶段的前置条件。

### 4.3 插件层和数据层仍然可以解耦

插件层不是把功能和数据重新耦合在一起。关键在于不要让插件直接依赖具体 ID，而是引入绑定关系。

推荐心智是：

```text
表格 = 数据容器
表格应用 = 系统级功能模块
绑定关系 = 某个 workbook/sheet 使用哪个表格应用
配置 = 这个应用在该表上的参数
脚本 = 后续用于增强应用或表格的轻量可编程能力
```

这样能同时避免两个极端：

- 极端一：所有特殊逻辑硬编码到具体 sheet ID 上
- 极端二：一开始就用脚本层重建整个应用平台

## 5. 推荐演进路径

### 第一阶段：插件层承载重业务

先允许某些 workbook 或 sheet 绑定 `app_key`，由 CodeYun 中的正式插件模块提供专用能力。

这一阶段重点是把绑定关系做清楚，而不是急着做脚本语言。

### 第二阶段：配置层抽出可变参数

当某个插件开始服务多张同类表时，把差异抽到配置层：

- 字段映射
- 功能开关
- 默认规则
- 模板选择
- 展示参数

这样可以避免为每张表复制一套插件代码。

### 第三阶段：脚本层补轻量自定义

当插件层和配置层仍然无法覆盖大量小变化时，再考虑脚本层。

脚本层先从低风险能力开始，例如：

- 单元格函数
- 列计算
- 批量文本处理
- 只读统计
- 调用少量白名单动作

不要一开始就开放完整系统能力。

### 第四阶段：成熟插件开放脚本扩展点

当某个插件已经稳定后，可以让它主动暴露有限扩展点给脚本层。

例如：

```text
attendance_signup 插件暴露：
- normalizePhone(value)
- buildRemark(row)
- validateSignupRow(row)
- exportPayload(rows)
```

脚本层调用这些受控接口，而不是直接访问系统内部对象。

## 6. 初步实现方向

后续如果进入实现，可以优先考虑以下结构。这里仅描述方向，不作为最终字段设计。

### 6.1 绑定模型

可以为 workbook/sheet 增加应用绑定关系：

```text
target_type: "workbook" | "sheet"
target_id: workbook_id 或 sheet_id
app_key: 稳定插件标识
config_json: 插件配置
enabled: 是否启用
created_at / updated_at
```

如果后续发现一个表需要多个插件，可以把绑定设计成一对多，并增加顺序、作用域或插槽信息。

### 6.2 前端注册

前端可以围绕 `app_key` 注册表格扩展能力：

```text
app_key -> {
  toolbarActions,
  sidePanels,
  contextMenuItems,
  validators,
  importExportActions
}
```

表格工作区只负责读取绑定关系并挂载扩展点，不直接知道每个业务插件的细节。

### 6.3 后端注册

后端可以围绕 `app_key` 注册服务能力：

```text
app_key -> {
  actions,
  tasks,
  validators,
  importers,
  exporters
}
```

权限仍然走 CodeYun 现有权限系统。插件可以有自己的 API scope 或动作权限。

### 6.4 脚本扩展点

脚本层后续可以作为插件能力的一种补充，而不是替代插件层。

推荐先让脚本运行在受限上下文中：

```text
输入：当前行、当前列、当前 sheet 的只读数据片段、插件暴露的白名单函数
输出：单元格值、校验结果、批处理结果或动作参数
```

不要让脚本直接获得数据库会话、文件系统、网络访问或任意后端内部对象。

## 7. 后续修订触发条件

本文档应在以下情况发生时修订：

- 设计第一个真实表格插件时，发现 `app_key + config_json` 不足以表达需求
- 某个插件需要同时绑定 workbook 和多个 sheet
- 表格复制、另存为模板、导入导出时需要决定插件绑定如何迁移
- 脚本层开始进入实际设计
- 公式、自定义函数、批处理动作之间出现边界冲突
- 权限、审计或多用户协作对绑定模型提出新要求

当前阶段最重要的结论是：

**先做插件层是合理的。插件层承载系统级功能，配置层承载参数，脚本层作为后续轻量可编程能力逐步引入。**
